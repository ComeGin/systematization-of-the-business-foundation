- 前提の作業: 動きの作り込み（`2026-10-19-aceternity-motion-design.md`。A／B／C の区分・アバター・ページの形のつながり）、JIS X 8341-3 の AA 改修（`docs/superpowers/plans/2026-10-18-jis-x-8341-3-accessibility.md`）

## 1. 目的

`HERO` 分類（トップのヒーロー・告知バナー・下層ページの導入ヒーロー）が、サイトの中で一番「受賞サイトの水準」に届いていない。
いまのトップのヒーローは、左に文字・右に 4:3 の写真・背景に光（Spotlight New と Background Beams）という、よくある SaaS の型である。

**訪問者がトップを開いて最初の 5 秒で、ComeGin の技術力を見て、「自社で使いたい」と感じて帰ること**がねらい（ユーザーの言葉）。
Favorite Website Awards を受賞できる水準を目標にし、インタラクションデザイナーの視点（触ったときの手応え・つながり・意味のある動き）で作る。

そのために、ComeGin の売り物である「再帰的に自己改善する事業経営基盤」**そのもの**を、机の上の小さな模型として見せる。
記事・問い合わせ・リードが流れ込み、エージェントが観測し、提案が生まれ、人が承認し、サイトに反映される。その循環が模型の中で実際に回っている様子を、Three.js の立体で描く。
模型の中には「このサイト自身」の小さな模型もあり、循環の最後に光の粒がそこへ届く。訪問者がいま見ているページが、この基盤で回っていることを一目で示す（★）。

参考にしたサイト（ユーザーが挙げた）:

| サイト | 効いている点 |
|---|---|
| [Interaction Library](https://library.jjangik.kr/) | 画面そのものが作品（ランプに照らされた本棚）。本を抜く、という触り方が 1 つに絞られている。**素材感と温度の直接の手本**（ユーザーが「木と紙」を選んだ） |
| [Nebulofi](https://nebulofi.vercel.app/) | 画面いっぱいの立体が主役で、文字は脇役。星を選ぶ、で操作が完結する |
| [anime.js](https://animejs.com/) | 自分のライブラリで自分のサイトを動かし、それが技術の証明になっている。**「自分の基盤で自分のサイトを回している」を見せる考え方の手本** |

## 2. ゴール・非ゴール・アンチゴール

### ゴール

- トップの 1-3 ヒーローが、ランプに照らされた「木と紙の模型」になる。模型の中で、光の粒が基盤の実際のデータの流れどおりに部品の間を受け渡される。
- 部品にカーソルを乗せると持ち上がり、押すと中の仕事が開く。「問い合わせ窓口」を押すと、他社の実績（掲載許可が取れたもの）が見える。
- サービス一覧・サービス詳細 4 ページの導入ヒーローが、同じ模型のうち、そのサービスに当たる部品へカメラが寄った**動く立体**になる。
- 会社概要・料金・ブログ一覧・お問い合わせ・送信完了の導入ヒーローが、同じ模型から撮った、そのページに当たる部品の**静止画**になる。
- どの端末・設定でも「同じ模型」に見え、読み込み・ページの移動につなぎ目が見えない（§9）。

### 非ゴール

- 1-3 以外のトップのセクション（1-4a 以降）を作り直すこと。
- 文言（タグライン・h1・本文・CTA のラベル）を変えること。文言の正本は `src/modules/site-content/` のまま。
- 規約・ポリシー（C の区分）を変えること。
- Lighthouse の performance 0.9 を守ること（ADR-29。動きを優先する。ただし §8 の予算は守る）。
- 実際の基盤の稼働データ（本番の件数など）をリアルタイムで模型に流すこと（★。§6.6）。

### アンチゴール（動いても失敗とみなすもの）

ユーザーが挙げた 2 つ:

1. **論理的に破綻している。**
   - 光の粒が、実際の基盤には無い経路を通る。部品の名前・役割が実際の仕組みと 1 対 1 で対応していない。
   - 循環の順番（観測 → 提案 → 承認 → 反映）が崩れる。とくに**承認を飛ばして反映される絵**は、この基盤の一番大事な約束（ADR-15・ADR-16。承認ゲート）に反する。
   - 架空の実績・架空の数値が出る（GL §8.4。1-8 の「架空の社名・人名・数値を足さない」と同じ約束）。
   - 代表のアバターが同じ画面に 2 人いる（模型の中と画面の端。§6.5）。
2. **シームレスでない。**
   - 読み込みの途中で、白い枠・構図のずれ・素材の切り替わりが見える。
   - トップからサービスへ移ったとき、模型がいったん消えて別の絵になる。
   - B のページの静止画が、トップの模型と別物に見える（光・角度・素材がそろっていない）。
   - 動きを減らす設定・スマートフォン・JS なし・WebGL なしのどれかで「壊れた」「別物」に見える。

これまでのアンチゴールも引き継ぐ:

- JIS X 8341-3 の AA 改修で通したもの（axe 違反 0、e2e、NVDA での確認）を壊すこと。
- h1・本文が、立体の読み込みを待たないと読めないこと。
- GA4・PostHog・Chatwoot・Cookie 同意の動作が変わること。
- B のページが、トップ・サービスと同じ華やかさになること。

## 4. 制約

- **文字は HTML。** タグライン・h1・本文・CTA は最初の HTML に入り、立体を待たずに読める（SEO 1.0、LCP、スクリーンリーダー）。立体は飾りの層と、触れる部品の層に分ける（§6.4）。
- **動きの規則（05-motion-spec.md §2）を守る。** 5 秒を超えて自動で動くもの（光の粒の流れ・ランプの揺らぎ）には一時停止ボタン（`MotionPauseFor`）。reduced-motion では静止画。JS なしでも静止画。
- **three は 1 チャンク。** 既存の `motion/lib/three.ts` の `loadThree()` を使い、地球儀・アバターと同じ three を共有する（05-motion-spec.md §4）。three は最初の描画の後に動的 import で読む。
- **区分（A／B／C）は変えない。** A＝トップ・サービス一覧／詳細、B＝ほかのページ、C＝規約・ポリシー。B に動く立体・光り物を入れない（アバターの例外は除く）。
- **誠実さ（GL §8.4）。** 架空の社名・人名・数値を出さない。実績は掲載許可が取れたものだけ（§7）。
- **リポジトリの規則。** git の状態を変える操作（commit など）はしない。デプロイはしない。ビルド・テストの実行とテストコードの追加は H-14 の範囲で許可済み。パッケージは pnpm。
- **モジュールごとにフォルダを作る**（ユーザーの条件）。§10。
- **このヒーローは「成果物（Astro）」の一部であり、クラウド（S3 ＋ CloudFront）から配る**（ユーザーの条件。再帰的自己改善のシステムはオンプレ、正本を持つシステムはクラウド）。模型の資産（glb・静止画）も `_astro/` の資産として同じ配信に乗せる。新しいサーバーやデータの置き場は作らない（★）。

## 5. 模型の構成

### 5.1 部品と実際の仕組みの対応

模型は「ComeGin の仕事場」である。土台の上に基盤の部品が並び、その周りに ComeGin の仕事（受託開発・コンサル・業務提携）の場所がある（★）。
**部品は実際の仕組みと 1 対 1 で対応させる**（アンチゴール 1）。名前は読者（IT 人材のいない中小企業の経営者）に向けて日常の言葉にし、押したときのパネルで実際の製品名を添える（★）。

| 部品（模型の中の物） | 実際の仕組み | 区分 | 冒頭に出るページ |
|---|---|---|---|
| 土台（模型全体が載る木の台） | 基盤一式（AWS のクラウドとオンプレ） | 基盤 | サービス：環境構築（A・動く） |
| 記事の棚 | Strapi（記事・キーワード・企画） | 基盤 | ブログ一覧（B・静止画） |
| 問い合わせ窓口 | 訪問者が入ってくる受付。チャット（Chatwoot）と、サイトのお問い合わせフォームの入口。**データの持ち主は Chatwoot だけ**（フォームの送信は窓口を通り抜けて名簿へ入る） | 基盤 | お問い合わせ（B・静止画） |
| 名簿 | Mautic（コンタクト・リード。フォームの送信先） | 基盤 | トップだけ |
| 配管 | n8n（仕組みの間の受け渡し） | 基盤 | トップだけ |
| 計器 | GA4・PostHog・Search Console（観測の元） | 基盤 | トップだけ |
| エージェントの詰所 | 監視アプリ・control-plane と 12 のエージェント（観測・起票） | 基盤 | トップだけ |
| 承認台と代表のアバター | **人の承認すべて**の象徴（★）。提案の承認〈GitHub の PR〉、記事の公開の判断〈Strapi〉、配信の承認、n8n のワークフローの有効化。パネルでこの 4 つを並べて示す | 基盤 | 会社概要（B・静止画） |
| 配信の口（出荷口） | ビルドと S3・CloudFront への配信（人の承認の後だけ。DD-05 §3・DD-06 §1.5）（★。レビューで「承認しただけでサイトに反映される絵になる」と指摘され、足した） | 基盤 | トップだけ |
| 小さなサイト | この公開サイト（Astro） | 基盤 | トップだけ |
| 工房（作業台と工具） | 受託開発 | 仕事 | サービス：受託開発（A・動く） |
| 設計の机（図面が広がる） | コンサル | 仕事 | サービス：コンサル（A・動く） |
| 渡り廊下（隣の建物とつなぐ） | 業務提携 | 仕事 | サービス：業務提携（A・動く） |
| 土台の値札（「1 人分」の札） | 料金 | — | 料金（B・静止画） |
| 窓口に光の粒が届いた瞬間 | 問い合わせの受付 | — | 送信完了（B・静止画） |
| 模型の全景を少し引いた位置 | — | — | サービス一覧（A・動く） |

### 5.2 光の粒の経路（データの流れ）

光の粒の経路は、`docs/DetailedDesign/` に書かれた実際の流れ（02 公開経路・03 運用経路・04 サーバー間・06 提案ループ）と**一致させる**。下はたたき台で、作り手は実装の前に各文書と照合し、食い違いがあれば文書の方を正とする（★）。

| 流れ | 経路（たたき台） | 照合する文書 |
|---|---|---|
| 問い合わせ（フォーム） | 訪問者 → 問い合わせ窓口（通り抜け）→ 名簿 → 配管（I-11） | 02 §5、04 |
| 問い合わせ（チャット） | 訪問者 → 問い合わせ窓口（ここに残る）→ エージェントの詰所（一次切り分け） | 02 §4、03 |
| 記事 | エージェントの詰所（下書き）→ 記事の棚 → 承認台（公開の判断・配信の承認）→ 配信の口 → 小さなサイト | 03 §4.1、05 §3 |
| 改善の循環 | 計器 → エージェントの詰所（観測）→ 提案 → 承認台（承認）→ 作用先（★下記） | 06 §1・§1.5 |

- 改善の作用先はサイトだけではない（DD-06 §1.5）。承認を通った金色の粒は、**サイトの改善なら配信の口 → 小さなサイト**、**Mautic・Chatwoot の改善なら名簿・窓口へ直接**戻る（★。どちらも描く。論理の正確さを優先する）。
- 「承認の後だけ作用する」ことが崩れなければ、粒の数や頻度は見た目で決めてよい。

- 粒の色で段階を区別する（★）: 流れ込む粒は白、提案になった粒は青（ブランドの青）、承認を通った粒は暖かい金色。**金色の粒だけが小さなサイトに届く**（承認を飛ばさないことが色で読める）。
- 承認台では、代表のアバターが粒を受け取って小さくうなずく（承認の身ぶり）。うなずいた後でだけ粒が金色になる（★）。
- 小さなサイトに金色の粒が届くと、小さなサイトの画面（このヒーローの縮小版）の一部が書き換わる（★）。書き換わりの中身は一般的な表現にとどめ、「何が改善されたか」を具体的に主張しない（架空の実績にしないため）。

### 5.3 素材と光

- 木の台（暖かい茶）、白い紙の部品（つや消し）、柔らかい影。ブランドの青は**光の粒と小さな印だけ**（H-11）。
- 部屋（背景）の暗さは navy.900（`--color-role-surface-hero`）に寄せ、ランプの光だけを暖かくする（★。試作は暗い茶だったが、ヒーローの下に続くサイトの紺とつなぐため。見比べて違和感があれば試作どおりの暗い茶に戻す）。
- 天井から吊ったランプが模型を照らす。ランプはわずかに揺らぐ（★）。
- 影・環境光の遮蔽（AO）は Blender で焼き込み、実行時のリアルタイムの影は使わない（★。§8 の負荷と、静止画との一致のため）。

## 6. トップのヒーロー（1-3）

### 6.1 構図

- Desktop: 画面いっぱい（ヒーローの区画の全面）が模型の部屋。文字（タグライン・h1・本文・CTA）は左に置き、模型は右から中央に置く（★。試作 B は文字が右だったが、日本語の読み始めと既存の Figma の配置〈左に文字〉に合わせる）。h1 の改行位置は仕様書のまま（BreakableHeading）。
- Mobile: 上に文字、その下に模型（4:3）。模型は Mobile でも**同じ動く立体**にし、負荷を下げる（§8）（★。アンチゴール 2「スマートフォンで別物に見える」を避けるため）。
- これまでの右の写真（`hero.photo`）はヒーローから外し、ページ内の別の場所へ移す（H-12）。移す先は作り手に任せるが、写真の意味（福祉・就労支援の現場）が伝わる文脈に置く（例: 1-4a の業務理念の近く）。会社概要・サービス詳細の写真も同じ。
- 背景の光（HeroBackdrop の Spotlight New・Background Beams・グリッド）・`MotionSymbol` も、トップのヒーローからは外す（★。模型が主役で、光が重なると模型のランプの光と論理が合わない）。
- 仕様書（01-content-spec.md §4.1 の 1-3「画像枠」、会社概要・サービス詳細の導入ヒーロー）と 05-motion-spec.md §8.2 を改める。なお、トップの画像枠の元の予定（2026-10-14 より前）は「ループの図」だった。模型はその予定に戻る形でもある。

### 6.2 触り方（インタラクション）

触り方は 1 つに絞る（参考サイトの共通点）: **部品に触れる → 持ち上がる → 押す → 開く**。

- カーソルを乗せる（キーボードではフォーカス）と、その部品がばねのような動きで少し持ち上がり、名前の札が出る（★）。
- 押すと、カメラがその部品へ寄り、部品の横に HTML のパネルが開く（§6.3）。Esc・閉じるボタン・部品の外を押すと、カメラが元の位置へ戻る。
- カーソルを動かすと視点がわずかに動く（視差）。ランプの光がカーソルの方へわずかに傾く（★）。
- 押せる部品は、トップでは基盤の部品（§5.1 の「基盤」の行）と工房・設計の机・渡り廊下。仕事の 3 つを押すと、パネルからそのサービスの詳細ページへ進める（★）。
- 画面の隅に「部品を押すと、中の仕事が開きます」の短い案内を出す（★）。

### 6.3 部品のパネル

- 中身は HTML（`site-content` の文言）。部品の名前、何をしているか（1〜2 文）、実際の製品名、関連するページへのリンク。
- 文言は新しく書く必要がある。`site-content` に置き、仕様書（01-content-spec.md）に追記する。書いた文言はユーザーの確認を通す（★。H-16「文言の既定値を持たない」に従い、部品は文言を持たない）。
- 「問い合わせ窓口」のパネルには「この窓口から始まった仕事」として実績を並べる（§7）。3 件とも**受託開発の実績**なので、「基盤を使っている会社」と読まれない言い方にする（★）。

### 6.4 アクセシビリティ

- 模型の canvas は `aria-hidden`。**押せる部品は、canvas の上に重ねた本物の HTML のボタン**（`<button>`）にする。ボタンの位置は毎フレーム、部品の画面上の位置に合わせる（★）。キーボードの Tab で部品を巡れ、フォーカスリングが見える（`data-surface="dark"` の白いリング）。
- パネルは非モーダルのダイアログ（開いたらパネルにフォーカス、閉じたら元のボタンへ戻す）（★）。
- reduced-motion・WebGL なし・一時停止のときも、ボタンとパネルは使える（静止画の上に同じ位置で重ねる）。
- 一時停止のボタンは、これまでどおりヒーローの右下・DOM の最後。

### 6.5 代表のアバター

- トップとサービスの模型では、代表のアバターが承認台に小さく立つ（H-5）。
- **同じ画面に 2 人いない**（アンチゴール 1）。模型が見えている間は、画面の端のアバター（05-motion-spec.md §10）を出さない。ヒーローが画面から外れたら、端のアバターが出る（H-13）。会社概要の静止画（承認台とアバターが写る）でも同じ。サービスのページで承認台が画面に入らないカメラ位置なら、模型にアバターは写らないので、端のアバターは通常どおり出してよい（★）。
- 端のアバターが出入りするときは、急に現れたり消えたりしない（シームレス）。既存のたたむ・開く動きを使う（★）。
- 模型の中のアバターは同じ `.vrm` を使い、縮小して置く。身ぶりは承認のうなずきと、待機の呼吸だけ（★）。

### 6.6 数字

- 「何周目」「最後の反映は 3 時間前」のような**稼働の数字は出さない**（★。試作 C にあった表現。実データに結びつけない数字は架空の数値になる）。
- 実データを出すなら、ビルドの時点で正本（Strapi など）から取った本物の値に限る。今回は扱わない（非ゴール）。

### 6.7 サービスのページ（A）の模型（★）

- サービス一覧・詳細 4 ページの模型は**眺める模型**にする。カメラは該当する部品に寄った位置で、視差（カーソルでわずかに動く）と、その部品のまわりの光の粒の流れだけ。部品のボタン・パネルは置かない。
  - 理由: サービスのページでは、そのサービスの説明はヒーローの下の本文が担う。パネルを重ねると同じ説明が 2 か所に出る。a11y の検証範囲と文言の確認の量も抑えられる。
- 動き続けるので、一時停止のボタンは置く（トップと同じ `MotionPauseFor`）。
- 島（island）はトップと共有し、触れる機能を props で切る（★）。

## 7. 実績のデータ

- 実績は `src/modules/site-content/` に 1 件ずつ置き、各件に**掲載許可の印**（例: `permission: 'granted' | 'pending'`）を持たせる（★）。`granted` のものだけを画面に出す。
- 同じデータを、ヒーローの「問い合わせ窓口」と 1-8 導入事例の**両方**が読む（★。二重に管理しない）。1-8 の仕様（ロゴ枠・お客さまの声・数値はすべて「準備中」）は、許可が取れた件から差し替えられる形にする。
- 許可が 1 件も無い間、窓口のパネルは正直に「掲載準備中」と書き、そのうえで「ComeGin はこの基盤で、自社のサイトを回しています」という自社の事実を見せる（★。文言はユーザーの確認を通す）。
- 掲載する項目は、会社名・内容（H-7 の表）・URL（ある場合）まで。ロゴ・お客さまの声・数値は、許可の範囲が分かってから決める（★）。

## 8. 性能の予算（★）

| 項目 | 予算 |
|---|---|
| 最初の描画 | 文字（HTML）と、模型の**静止画（ポスター）**だけ。ポスターは AVIF／WebP、`fetchpriority="high"`。three は読まない |
| three と模型の読み込み | 既存の `loadThree()`。ページの `load` の後の idle で読み始める |
| 模型の glb | 圧縮（meshopt または Draco、テクスチャは KTX2）で **1.5MB 以内**を目安 |
| 描画 | 影・AO は焼き込み。Desktop の描画解像度は最大 2 倍、Mobile は最大 1.5 倍。画面外・タブ非表示では rAF を止める（`run-when-visible.ts`） |
| 遅い端末 | 最初の数秒のフレーム時間を測り、遅ければ解像度を下げる。それでも遅ければポスターのまま止める（★） |
| Lighthouse | accessibility 1.0、SEO 1.0 を保つ。performance は ADR-29 のとおり warn |

## 9. シームレスの約束（★）

アンチゴール 2 に対する作り方の約束。

1. **ポスターと立体を同じ絵にする。** ポスターは、実行時と同じシーン・同じカメラ・同じ光で、Three.js 自身に描かせて書き出す（Blender の別のレンダラーで描かない。光の計算が違うとずれが見える）。立体の準備ができたら、最初のフレームをポスターと同じ構図で描いてから、ポスターを短いクロスフェードで消す。
2. **B のページの静止画も同じ方法で撮る。** 同じ模型・同じ光で、ページごとのカメラ位置から書き出す。
3. **ページの移動はカメラの移動として見せる。** トップ → サービス一覧 → サービス詳細は、カメラが模型の該当部品へ寄っていくように見せる（既存の View Transitions〈page-transition〉で、前のページの模型の最後のフレームと次のページのポスターをつなぐ）。
4. **どの状態でも同じ模型に見える。** reduced-motion・JS なし・WebGL なし・一時停止は、すべて同じポスター（動かないだけ）。
5. **読み込み中に白い枠を出さない。** ポスターの枠の大きさは CSS で先に確保する（CLS 0）。

## 10. モジュールの置き場（★）

ユーザーの条件「モジュールごとにフォルダを作成すること」に従い、新しいモジュールを 1 つ作る。

```
src/modules/diorama/
  index.ts              公開する部品（Astro コンポーネント・型）だけ
  client.ts             island の入口
  components/           DioramaHero.astro（トップ）、DioramaIntro.astro（サービスの導入）、DioramaStill.astro（B の静止画）
  islands/              DioramaIsland.tsx（React Three Fiber の描画と HTML のボタンの重ね合わせ）
  lib/                  parts.ts（§5.1 の対応表）、flows.ts（§5.2 の経路）、cameras.ts（ページごとのカメラ位置）、quality.ts（遅い端末の判定）
  assets/               diorama.glb、ポスター・静止画（ページごと）
  tools/                ポスター・静止画の書き出しスクリプト（§9 の 1・2）
```

- 文言は `site-content` に置く（部品は文言を持たない）。実績のデータも `site-content`（§7）。
- 既存の `PageIntro`（layout）・`motion`・`page-transition`・`avatar` とは、`index.ts` の公開部品を通してだけつなぐ。
- 模型の元データ（.blend）は `assets-original/diorama/` に置く（★。既存の `assets-original/avatar/` と同じ扱い）。

## 11. 告知バナー（1-1）

- 模型とは結びつけない（★）。文字と動きを磨くだけにとどめる（例: 「無料公開中」のバッジの小さな動き、矢印のホバーの手応え）。文言は変えない。

## 12. 作り手に任せること

- 模型の細部（部品の形・紙の折り目・木目・小物）、カメラの角度、光の粒の速さと数、ばねの強さ、パネルの見た目。試作 `material.html` の 1 と、Interaction Library の温度感を基準にする。
- Blender の中での作り方（モデリング・UV・焼き込みの手順）。ambientCG のどのテクスチャ（木・紙）を使うか。ambientCG は CC0 なのでクレジットは要らないが、使った素材の ID を `assets-original/diorama/README.md` に残す（★）。
- React Bits の部品を使うかどうか（ユーザーのフロントエンドの構成に含まれる。パネルの文字の出方などで、合うものがあれば使ってよい）。
- テストの組み方（H-14 で許可済み。これまでの単体・結合・E2E の書き方のメモに合わせる）。
