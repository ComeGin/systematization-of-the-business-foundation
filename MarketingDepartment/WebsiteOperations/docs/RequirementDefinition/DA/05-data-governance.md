# DA-05 データガバナンス

`CAP-15`（ガバナンス・アクセス管理）の対象のうち、データに関する部分を定義する。
とくに**エージェントがモデルにデータを渡す経路の安全装置**を明文化する（人間が見る画面と違い、エージェントは渡された値をそのまま別の場所へ書き出しうるため）。

### 1.2 個人に関わるデータを持つ SaaS は PostHog だけである

開発環境では、Strapi・Mautic・Chatwoot・Umami・n8n はすべて手元の Docker / PHP ビルトインサーバーで動く。**本番では、訪問者が直接触れる Mautic・Chatwoot・Umami を AWS の `ap-northeast-1` に置く**（AA-05 の ADR-12。DB は RDS、Chatwoot の添付ファイルは S3、Mautic の `media/` は EFS。TA-06）。**AWS は SaaS ではなく自分のアカウントの中で動かす基盤であり、`ap-northeast-1` から出ないため越境は生じない。** Strapi・n8n は本番でも自ホスト（オンプレミス）に残る。
**個人に関わるデータを持つ SaaS は PostHog だけである**（2026-09-18 までは「SaaS は PostHog だけ」だった。検索データの取得元として DataForSEO と GSC が加わった経緯は 1.2.1）。`backend/posthog-self-driving-report.md` に project 610214 の記載があり、インボックスの URL も `us.posthog.com` を指している（米国リージョン）。

したがって次の非対称が生じる。

- `E-09 Contact`（email を含む個人情報）は**自分の管理下（開発は自ホスト、本番は AWS の `ap-northeast-1`）に留まる**。
- `E-08 Person`（識別子付きの行動履歴）は**外部に出る**。
- セッションリプレイを有効にすると、**画面に映った内容そのもの**が外部に出る（現状は記録対象が無いため実害は発生していないが、ブラウザ側 SDK を入れた瞬間に発生する）。

このため以下を規則として定める。

- **PostHog の `distinct_id` に email をそのまま入れない**（`distinct_id` は外部に出る識別子であり、email を入れると個人情報そのものを越境させることになる）。
- セッションリプレイを有効にする場合は、入力欄のマスキング設定を先に入れる（フォームに入力された email がそのまま録画されるため）。
- `E-09` `E-10` の本文・email を PostHog のイベントプロパティに入れない。
- `backend/strapi-system/src/index.ts` が記事イベントに `$process_person_profile: false` を付けているのは、この方針と整合する（CMS の運用イベントで PostHog 側に person を作らない）。

### 1.2.1 OpenSEO が増やした外部送信

2026-09-18 に OpenSEO（セルフホスト）を採用したことで、**外部に出るデータの経路が 3 本増えた**（AA-05 の ADR-09）。

| 経路 | 出るもの | 個人情報 | 規則 |
|---|---|---|---|
| OpenSEO → DataForSEO | キーワード・ドメイン・地域コード | **含まない** | **会話本文・フォームの入力・コンタクトの属性をシードにしない。** Chatwoot の会話から記事化候補を拾う場合も（AA-03 の `agent/conversation-triage`）、キーワード調査に渡すのは要旨から作った検索語句であって、本文の一部ではない |
| Google Search Console → OpenSEO | 自サイトの検索実績 | 原則含まない | GSC 側で**件数の少ない検索クエリは匿名化されて返らない**。それでも検索クエリには利用者の入力がそのまま現れるため、**`E-13` の `evidence[].summary` に個々の検索クエリを転記しない**（件数と傾向だけを書く。`E-13` は GitHub に越境するため） |
| OpenSEO → OpenSEO 開発元の PostHog（米国） | 匿名テレメトリ（件数・無作為なインストール ID・失敗した設定チェックの名前と状態） | **含まない**（URL・キーワード・プロンプト・メール・IP 由来の位置情報を送らない。上流の `docs/SELF_HOSTING_DOCKER.md`） | **送信を許可する**（`R1` の 2026-09-18 の判断）。この基盤はこの送信に何も依存しない（TA-01 の経路 14） |

- **PostHog だけが SaaS である、という 1.2 の前提は崩れた。** ただし DataForSEO に送るのは個人情報を含まない問い合わせだけであり、**個人に関わるデータが越境する SaaS は依然として PostHog だけ**である。
- **OpenSEO の匿名テレメトリは送信を許可する**（`R1` の 2026-09-18 の判断）。送信先は OpenSEO 開発元の PostHog（米国）であり、上の表の 3 行目にあたる。**無作為なインストール ID は個人に結び付かず、利用者のメールや URL・キーワードも送らない**ため、個人に関わるデータが越境する SaaS が PostHog（こちらのプロジェクト）だけである点は変わらない。

### 1.3 通知に載せる範囲

顧客からの要求（フォーム送信・会話の開始）を運用者のメールアドレスへ通知する（BA-04、AA-02 の `I-21`）。**通知は `E-09` `E-10` の一部を AWS と各運用者のメールボックスへ複製することになる**ため、載せる範囲をここで固定する。

| 項目 | 載せるか | 理由 |
|---|---|---|
| 種別（`demo-requested` など） | **載せる** | 個人情報ではない |
| **会社名** | **載せる** | **法人情報であり個人情報ではない**（個人事業主の場合は氏名と一致しうるが、`E-09` の `company` として入力された値をそのまま扱う）。メールを見た時点で優先度を判断できるようにするため |
| Mautic の `contact_id` / Chatwoot の `display_id` | **載せる** | 識別子のみ。単体では個人を特定できない |
| 流入記事の URL・受付時刻 | **載せる** | 個人情報ではない |
| **email** | **載せない** | `E-09` の中核の個人情報。載せると各運用者のメールボックスが新たな保管先になり、転送で拡散する |
| **氏名** | **載せない** | 同上 |
| **問い合わせ本文・会話本文** | **載せない** | `E-10` は要配慮情報を含みうる（1.1） |

- **この規則は AA-03 の 3.4（`agent/conversation-triage` が会話本文を転記しない）と同じ形である。** 通知も `E-12` も「要旨と ID だけを残し、本文は元のシステムを見に行く」で統一する。
- **保管場所が 2 つ増える。** Amazon SNS（東京リージョン。メッセージは配信後に保持されない）と、**各運用者のメールボックス（保持期間をこちらから制御できない）**。後者のほうが影響が大きいため、載せる範囲を最小にすることが唯一の制御にあたる。
- **越境はしない。** SNS は東京リージョン（`ap-northeast-1`）を使う。PostHog（米国）と違い国外には出ない。

### 1.4 AWS に置いたことで増えた保管先（ADR-12）

2026-09-18 に Mautic・Chatwoot・Umami を本番では AWS に置くと決めた（AA-05 の ADR-12、TA-06）。**越境は増えない**（すべて `ap-northeast-1`）が、**同じ個人情報の置き場所が増える**。

| 保管先 | 入るもの | 個人情報 | 規則 |
|---|---|---|---|
| RDS の自動バックアップ（7 日。ポイントインタイムリカバリ） | `E-07` `E-09` `E-10` の DB 全体 | **含む** | **削除請求で DB から消しても、バックアップには保持期間が切れるまで残る。** 削除の完了を「保持期間の経過後」と説明する必要がある（5 節の削除請求の手順と一体で決める） |
| S3（Chatwoot の添付ファイル。バージョニング有効） | 訪問者が会話に添付したファイル | **含みうる**（要配慮情報を含みうる） | バージョニングにより、削除しても旧バージョンが残る。ライフサイクルルールで旧バージョンを消す期間を決める必要がある |
| EFS（Mautic の `media/`・設定）と AWS Backup | メール用の画像・アセット・設定 | 原則含まない | — |
| CloudWatch Logs（タスクのログ） | アプリケーションのログ | **混入しうる**（エラー内容に含まれる値） | `E-15` と同じ扱い。保持期間を無期限にしない |
| **Amazon SES** | **顧客向けメール**（Mautic の配信・フォームの自動返信、Chatwoot のメール） | **含む**（宛先の email・本文） | SES はメールを運ぶ手段であり、宛先への送信そのものが目的である。**送るかどうかは BA-05 の承認ゲート**を通る。社内向けの通知（1.3）は SES に載せない |

- **1.3 の「通知に email・氏名・本文を載せない」規則は変わらない。** SES（顧客向け）と SNS（社内向け）は用途を混ぜない（ADR-08・ADR-12）。
- **開発環境の値を本番に持ち込まない**のと同じく、**本番の DB のダンプを開発機に持ち込まない**（開発機が個人情報の新たな保管先になる）。検証に本番のデータが必要な場合の扱いは 5 節に上げる。

## 3. `sanitize()` の方針

`backend/chatwoot-mcp/src/services/results.ts` の `sanitize()` は、**上流 API のレスポンスをモデルに渡す前に必ず通す共通処理**である。
エージェントは受け取った値をそのまま別の場所へ書き出しうるため（提案の `evidence` に貼る、Chatwoot に返信する、など）、モデルに渡る前の一点で伏せるのが最も確実な防ぎ方になる。

### 3.1 実装されている挙動

- **秘匿情報らしいキーの値を `[redacted]` にする。** 判定は正規表現 `/secret|password|token|api_?key|hmac/i` によるキー名の部分一致（`api_key` と `apikey` の両方に当たる）。
- **例外リスト `NON_SECRET_KEYS` に載るキーは伏せない。** 現在は `website_token`（Web ウィジェットの埋め込み用トークン。公開ページに埋め込まれる値のため秘匿情報ではない）、`hmac_verified`、`hmac_mandatory` の 3 つ。
- **伏せ字にするのは、値が `null` でも空文字でも真偽値でもない場合に限る。** `token: null` や `hmac_mandatory: false` のような「設定されているか否か」の情報は、伏せずにそのまま返す（設定状態の把握はエージェントの判断に必要で、かつ秘匿性が無いため）。
- **`LONG_TEXT_LIMIT`（1,000 文字）を超える文字列を省略する。** 省略時は先頭 200 文字＋残り文字数と、`include_long_text=true` で全文を取れる旨の案内に置き換える。メール本文の HTML や長い会話メッセージが応答を埋め尽くすのを防ぐ。
- **オブジェクトと配列は再帰的に処理する。** ネストの深さに関わらず、どの階層にある秘匿キーも伏せられる。

### 3.2 `sanitize()` と併用される 2 つの上限

| 仕組み | 定数 | 値 | 役割 |
|---|---|---|---|
| `sanitize()` の長文省略 | `LONG_TEXT_LIMIT` | 1,000 文字 | 個々の文字列が長すぎるのを防ぐ |
| `truncate()` | `CHARACTER_LIMIT` | 25,000 文字 | 応答全体が大きすぎるのを防ぐ |
| `fitToLimit()` | `CHARACTER_LIMIT` | 同上 | 一覧の件数を半分ずつ減らして上限に収める |

- `fitToLimit()` で削られた分は「次のページ」では取得できない（ページ境界ではなく応答サイズで削るため）。`truncation_message` がその旨を伝える（DA-02 の 5.2 のデータ契約と対応）。

### 3.3 運用上の注意

- `jsonResult()` は内部で `sanitize()` を呼ぶが、**`formattedResult()` は呼ばない**（引数の `structured` が既に整形済みである前提のため）。新しいツールを追加するときは、`formattedResult()` に渡す前に呼び出し側で `sanitize()` を通す。
- `mautic-mcp` も同じ方針を取る（秘匿情報らしいキーを伏せ、1,000 文字超の文字列を省略する）。3 つ目の MCP サーバを作る場合もこの構造に合わせる。
- `sanitize()` は**秘匿情報の漏洩を防ぐ装置であって、個人情報を伏せる装置ではない**。email・氏名・会話本文はキー名が秘匿パターンに当たらないため、そのままモデルに渡る。個人情報の保護は `ACCESS_LEVEL` と取得範囲の制限（データ契約）で行う。

## 4. エージェントの読み書きの原則

### 4.1 最小権限

- **既定は参照のみ。** `CHATWOOT_ACCESS_LEVEL` / `MAUTIC_ACCESS_LEVEL` の既定値は `read_only`。書き込みが必要な用途に限って昇格させる。
- Mautic の API 認証情報は client_credentials でユーザーが紐づかないため、**権限は Mautic 側のロールで決まる**。参照専用のロールを割り当てる。
- Chatwoot の `api_access_token` は**ユーザーに紐づく**。操作履歴も権限もそのユーザーのものになるため、**専用のエージェントユーザーを作る**（AI 経由の返信を人手の返信と区別するため。加えて、そのユーザーの権限を絞ることでエージェントの権限を絞れる）。
- レポート・監査ログ・設定変更には管理者トークンが必要だが、**観測だけが目的なら管理者権限を与えない**（レポート API が使えない場合、エージェントはその項目をスキップする設計にする）。

### 4.2 `ACCESS_LEVEL` による制御

- **許可されないツールは「実行時に拒否する」のではなく「ツール一覧に登録しない」。** モデルからは存在しないように見えるため、そもそも呼ぼうとしない（拒否を返す設計だと、モデルが迂回路を探しはじめる）。
- 包含関係は `read_only` ⊂ `read_write` ⊂ `full`。`chatwoot-mcp` の検証ハーネス（`pnpm verify`）はこの包含関係を実際に検査している。
- `full` でのみ公開される操作（`chatwoot_delete_record` / `chatwoot_delete_contact` / `chatwoot_delete_message` / `chatwoot_merge_contacts`、`mautic_delete_record`）は不可逆。とくに `chatwoot_merge_contacts` は統合されたコンタクトを削除するため、取り消せない。
- 破壊的な操作には `destructiveHint: true` が付いており、MCP クライアント側で実行前の確認を求められる。**この確認をエージェントが自動で承認する運用にしない**（`CAP-06` の承認ゲートが形骸化する）。
- HTTP トランスポートの認証は固定 Bearer トークン（`MCP_AUTH_TOKEN`、32 文字以上）。比較は SHA-256 ダイジェストどうしの `timingSafeEqual`。stdio では不要。

### 4.3 監査ログ

| 記録する対象 | 記録先 | 状態 |
|---|---|---|
| Chatwoot 上の操作（誰が何を変えたか） | Chatwoot の監査ログ（`chatwoot_list_audit_logs`。Enterprise の `audit_logs` 機能が必要） | 未配線 |
| エージェントの実行（入力・結果・失敗） | `E-15 AgentRun`（n8n の実行履歴） | 未配線 |
| 改善提案の起票・承認・適用・差し戻し | `E-13` / `E-14`（Git の履歴と PR） | 未着手 |
| MCP サーバの動作ログ | stderr（`console.error`。stdout は MCP の通信専用のため使わない） | 実装済み |
| 環境変数の検証失敗 | stderr に**変数名と理由だけ**を出して `exit(1)`（値は出さない） | 実装済み |

- **`E-13` を経由しない変更を検出できることが、このガバナンスの要**。Chatwoot の監査ログと Git の履歴を突き合わせ、対応する `proposal_id` の無い変更を例外として扱う。
- 秘密値を含む環境変数ファイルは追跡しない。`.env.example` は必ず同時に更新する。
- `N8N_ENCRYPTION_KEY` と Chatwoot の `ACTIVE_RECORD_ENCRYPTION_*` を変更すると既存の暗号化データを復号できなくなる。鍵の変更は**データの喪失と同義**として扱い、`E-13` の `rollback.reversible: false` に相当する扱いにする。
- n8n の `sandbox-runner-1` は privileged な Docker-in-Docker（ホスト root 相当）のため、暗号化キーや DB パスワードを渡さない。この分離を崩さない。

## 5. 未決定事項

- PostHog のデータ保持期間（1.2 と 2 節で方針は書いたが、実際の設定は行っていない）。SaaS 側の設定であり、プランによって設定可能な範囲が異なる可能性がある。
- 個人情報の削除請求が来たときの手順。対象は `E-08` `E-09` `E-10` の 3 つだが、`E-08` は SaaS 側にあり、削除の反映が Mautic / Chatwoot と同時にならない。「どこまで削除したか」の記録をどこに残すかも未定（用語集に該当するエンティティが無いため、勝手に増やさずここに記録する）。
- 会話本文（`E-10`）をエージェントに読ませる範囲。`sanitize()` は個人情報を伏せないため、会話本文はそのままモデルに渡る。要配慮情報が含まれた場合の扱い（そもそも読ませないのか、読ませたうえで提案に転記しないのか）が未確定。
- **RDS のバックアップと S3 の旧バージョンに残る個人情報の扱い**（1.4）。削除請求で DB から消しても保持期間が切れるまで残る。保持期間（現在は暫定で 7 日）と、削除の完了をどう説明するかを削除請求の手順と一体で決める。判断者 `R1`。
- **本番のデータを開発・検証に使う必要が出た場合の扱い**（1.4）。匿名化してから持ち込むのか、持ち込まないのかが未定。判断者 `R1`。
- `E-13` を置く Git リモートリポジトリの所在。統制の記録が外部の SaaS（GitHub）に置かれることになり、`E-08` 以外にも越境が生じる。事業側の方針確認が必要。
- Chatwoot の監査ログは Enterprise の `audit_logs` 機能を必要とする。この機能が使えない場合、「`E-13` を経由しない変更の検出」という 4.3 の要が成立しない。代替手段（Chatwoot の webhook で変更を拾う）の検討が必要。
