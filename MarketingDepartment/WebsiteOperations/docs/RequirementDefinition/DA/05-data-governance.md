# DA-05 データガバナンス

`CAP-15`（ガバナンス・アクセス管理）の対象のうち、データに関する部分を定義する。
とくに**エージェントがモデルにデータを渡す経路の安全装置**を明文化する（人間が見る画面と違い、エージェントは渡された値をそのまま別の場所へ書き出しうるため）。

## 1. 個人情報の区分

### 1.1 エンティティ別の区分

### 1.2 個人に関わるデータを持つ SaaS は PostHog だけである

開発環境では、Strapi・Mautic・Chatwoot・Umami・n8n はすべて手元の Docker / PHP ビルトインサーバーで動く。**本番では、訪問者が直接触れる Mautic・Chatwoot・Umami を AWS の `ap-northeast-1` に置く**（AA-05 の ADR-12。DB は RDS、Chatwoot の添付ファイルは S3、Mautic の `media/` は EFS。TA-06）。**さらに ADR-16 で、正本のデータを持つ Strapi と n8n も AWS に置いた**（DB は RDS for PostgreSQL の共有インスタンス、Strapi のメディアは S3）。**AWS は SaaS ではなく自分のアカウントの中で動かす基盤であり、`ap-northeast-1` から出ないため越境は生じない。** Strapi の配置は、ADR-14 で AWS、同日の ADR-15 でオンプレだけ、同日の ADR-16 で再び AWS と変わった。オンプレに残るのは MCP サーバ・OpenSEO・監視アプリ・Lighthouse CI・ビルドと、全システムの開発環境である。**ただし ADR-18 で `E-15`（監視アプリの実行記録）の正本をオンプレに置いたため、本番の個人情報がオンプレに残りうる経路が 1 つできた**（1.5）。**同日の追加の決定で記録を要約と ID だけにし、この経路は塞ぐ前提になった**（要約の検査が漏れる余地は残る）。
**個人に関わるデータを持つ SaaS は PostHog だけである**（2026-09-18 までは「SaaS は PostHog だけ」だった。検索データの取得元として DataForSEO と GSC が加わった経緯は 1.2.1）。`backend/posthog-self-driving-report.md` に project 610214 の記載があり、インボックスの URL も `us.posthog.com` を指している（米国リージョン）。

したがって次の非対称が生じる。

- `E-09 Contact`（email を含む個人情報）は**自分の管理下（開発は自ホスト、本番は AWS の `ap-northeast-1`）に留まる**。
- `E-08 Person`（識別子付きの行動履歴）は**外部に出る**。
- セッションリプレイを有効にすると、**画面に映った内容そのもの**が外部に出る（現状は記録対象が無いため実害は発生していないが、ブラウザ側 SDK を入れた瞬間に発生する）。

このため以下を規則として定める。

- **PostHog の `distinct_id` に email をそのまま入れない**（`distinct_id` は外部に出る識別子であり、email を入れると個人情報そのものを越境させることになる）。
- セッションリプレイを有効にする場合は、入力欄のマスキング設定を先に入れる（フォームに入力された email がそのまま録画されるため）。
- `E-09` `E-10` の本文・email を PostHog のイベントプロパティに入れない。
- `backend/strapi-system/src/index.ts` が記事イベントに `$process_person_profile: false` を付けているのは、この方針と整合する（CMS の運用イベントで PostHog 側に person を作らない）。
- **PostHog のプロジェクトは開発と本番で分ける**（ADR-16）。開発環境の Strapi のイベントと例外は開発用のプロジェクトに送り、本番のデータに混ぜない。どちらのプロジェクトも米国リージョンにあるため、越境の範囲は変わらない。削除請求（2 節）の対象は本番用のプロジェクトの `E-08` である（開発環境には本番の個人情報を入れないため）。

### 1.2.1 OpenSEO が増やした外部送信

2026-09-18 に OpenSEO（セルフホスト）を採用したことで、**外部に出るデータの経路が 3 本増えた**（AA-05 の ADR-09）。

| 経路 | 出るもの | 個人情報 | 規則 |
|---|---|---|---|
| OpenSEO → DataForSEO | キーワード・ドメイン・地域コード | **含まない** | **会話本文・フォームの入力・コンタクトの属性をシードにしない。** Chatwoot の会話から記事化候補を拾う場合も（AA-03 の `agent/conversation-triage`）、キーワード調査に渡すのは要旨から作った検索語句であって、本文の一部ではない |
| Google Search Console → OpenSEO | 自サイトの検索実績 | 原則含まない | GSC 側で**件数の少ない検索クエリは匿名化されて返らない**。それでも検索クエリには利用者の入力がそのまま現れるため、**`E-13` の `evidence[].summary` に個々の検索クエリを転記しない**（件数と傾向だけを書く。`E-13` は GitHub に越境するため） |
| OpenSEO → OpenSEO 開発元の PostHog（米国） | 匿名テレメトリ（件数・無作為なインストール ID・失敗した設定チェックの名前と状態） | **含まない**（URL・キーワード・プロンプト・メール・IP 由来の位置情報を送らない。上流の `docs/SELF_HOSTING_DOCKER.md`） | **送信を許可する**（`R1` の 2026-09-18 の判断）。この基盤はこの送信に何も依存しない（TA-01 の経路 14） |

- **PostHog だけが SaaS である、という 1.2 の前提は崩れた。** ただし DataForSEO に送るのは個人情報を含まない問い合わせだけであり、**個人に関わるデータが越境する SaaS は依然として PostHog だけ**である。
- **OpenSEO の匿名テレメトリは送信を許可する**（`R1` の 2026-09-18 の判断）。送信先は OpenSEO 開発元の PostHog（米国）であり、上の表の 3 行目にあたる。**無作為なインストール ID は個人に結び付かず、利用者のメールや URL・キーワードも送らない**ため、個人に関わるデータが越境する SaaS が PostHog（こちらのプロジェクト）だけである点は変わらない。

### 1.3 通知に載せる範囲

顧客からの要求（フォーム送信・会話の開始）を運用者のメールアドレスへ通知する（BA-04、AA-02 の `I-21`）。**通知は `E-09` `E-10` の一部を AWS と各運用者のメールボックスへ複製することになる**ため、載せる範囲をここで固定する。

| 項目 | 載せるか | 理由 |
|---|---|---|
| 種別（`demo-requested` など） | **載せる** | 個人情報ではない |
| **会社名** | **載せる** | **法人情報であり個人情報ではない**（個人事業主の場合は氏名と一致しうるが、`E-09` の `company` として入力された値をそのまま扱う）。メールを見た時点で優先度を判断できるようにするため |
| Mautic の `contact_id` / Chatwoot の `display_id` | **載せる** | 識別子のみ。単体では個人を特定できない |
| 流入記事の URL・受付時刻 | **載せる** | 個人情報ではない |
| **email** | **載せない** | `E-09` の中核の個人情報。載せると各運用者のメールボックスが新たな保管先になり、転送で拡散する |
| **氏名** | **載せない** | 同上 |
| **問い合わせ本文・会話本文** | **載せない** | `E-10` は要配慮情報を含みうる（1.1） |

- **この規則は AA-03 の 3.4（`agent/conversation-triage` が会話本文を転記しない）と同じ形である。** 通知も `E-12` も「要旨と ID だけを残し、本文は元のシステムを見に行く」で統一する。
- **保管場所が 2 つ増える。** Amazon SNS（東京リージョン。メッセージは配信後に保持されない）と、**各運用者のメールボックス（保持期間をこちらから制御できない）**。後者のほうが影響が大きいため、載せる範囲を最小にすることが唯一の制御にあたる。
- **越境はしない。** SNS は東京リージョン（`ap-northeast-1`）を使う。PostHog（米国）と違い国外には出ない。

### 1.4 AWS に置いたことで増えた保管先（ADR-12・ADR-16）

2026-09-18 に Mautic・Chatwoot・Umami を本番では AWS に置くと決め（AA-05 の ADR-12、TA-06）、2026-09-19 に Strapi・n8n も加えた（ADR-16）。**越境は増えない**（すべて `ap-northeast-1`）が、**同じ個人情報の置き場所が増える**。

| 保管先 | 入るもの | 個人情報 | 規則 |
|---|---|---|---|
| RDS の自動バックアップ（7 日。ポイントインタイムリカバリ） | `E-07` `E-09` `E-10` の DB 全体 | **含む** | **削除請求で DB から消しても、バックアップには保持期間が切れるまで残る。** 削除の完了を「保持期間の経過後」と説明する必要がある（5 節の削除請求の手順と一体で決める） |
| S3（Chatwoot の添付ファイル。バージョニング有効） | 訪問者が会話に添付したファイル | **含みうる**（要配慮情報を含みうる） | バージョニングにより、削除しても旧バージョンが残る。ライフサイクルルールで旧バージョンを消す期間を決める必要がある |
| EFS（Mautic の `media/`・設定）と AWS Backup | メール用の画像・アセット・設定 | 原則含まない | — |
| **S3（Strapi のメディア。バージョニング有効。ADR-16）** | 記事の画像 | **含みうる**（取材記事の写真） | Chatwoot の添付ファイルと同じく、削除しても旧バージョンが残る。公開ページには `dist/` に取り込んだ複製が載る（ADR-11）ため、**差し替えには再ビルドと配信が要る** |
| **RDS の `n8n` データベース（実行履歴。ADR-16）** | Webhook で受けたペイロードと各ノードの入出力 | **含む**（`I-11` `I-12` で受けた `E-09` `E-10` の email・本文） | **`E-15` ではない**（エージェントの実行が残らない。ADR-18）。実行履歴は 90 日で消す（2 節）。**失敗した実行だけでなく成功した実行の入出力も残る**ため、保持の設定を n8n 側で明示する（5 節）。RDS の自動バックアップにも残る |
| CloudWatch Logs（タスクのログ） | アプリケーションのログ | **混入しうる**（エラー内容に含まれる値） | n8n の実行履歴と同じ扱い（当初は「`E-15` と同じ扱い」としていたが、ADR-18 で `E-15` は監視アプリの実行記録になった）。保持期間を無期限にしない |
| **Amazon SES** | **顧客向けメール**（Mautic の配信・フォームの自動返信、Chatwoot のメール） | **含む**（宛先の email・本文） | SES はメールを運ぶ手段であり、宛先への送信そのものが目的である。**送るかどうかは BA-05 の承認ゲート**を通る。社内向けの通知（1.3）は SES に載せない |

- **1.3 の「通知に email・氏名・本文を載せない」規則は変わらない。** SES（顧客向け）と SNS（社内向け）は用途を混ぜない（ADR-08・ADR-12）。
- **エージェントは本番の個人データに触れる**（ADR-15。同日の ADR-14 で書いた「開発環境に個人情報を持ち込まなければ、エージェントが個人情報に触れる経路は構造的に無くなる」は成り立たなくなった）。エージェントは MCP の本番用の登録で本番の Chatwoot・Mautic の `E-09` `E-10` を読み書きする（ADR-16 で本番の Strapi の `E-04` と n8n も加わった）。守りは `sanitize()`（モデルに返す前に秘密値と長文を伏せる）、`ACCESS_LEVEL`（本番は `read_write` まで。ADR-16 で確定）、エージェント定義の許可リストの 3 つである。**`strapi-prod` と `n8n-prod` は管理外の MCP であり、`sanitize()` が及ばない**（AA-05 の ADR-07）。開発環境の Strapi・Mautic・Chatwoot には引き続き本番の記事・コンタクト・会話を入れない。
- **本番の n8n は全システムの資格情報を持つ**（ADR-16）。資格情報は n8n の DB に `N8N_ENCRYPTION_KEY` で暗号化して置かれ、鍵は Secrets Manager にある（TA-06 の 7 節）。開発環境の資格情報を本番の n8n に持ち込まない。
- **開発環境の値を本番に持ち込まない**のと同じく、**本番の DB のダンプを開発機に持ち込まない**（開発機が個人情報の新たな保管先になる）。検証に本番のデータが必要な場合の扱いは 5 節に上げる。

### 1.5 監視アプリの実行記録（`E-15`）と個人情報（ADR-18。要約と ID だけを残す）

2026-09-19 に `R1` が、**`E-15 AgentRun` の正本を監視アプリ（ローカルの PC）の実行記録にする**と決めた（AA-05 の ADR-18、TA-07 の 3.6）。監視アプリはローカルに置いたまま、記録もローカルに保存する。ADR-18 の反映では「**越境は増えないが、本番の個人情報の置き場所が開発機に 1 つ増えうる**」とし、記録する範囲を未決定にしていた。**同日の追加の決定で、記録するのは要約と ID だけにした**（追加の決定 4）。あわせて**記録を S3 に写す**と決めた（追加の決定 5。写しは正本ではない）。

| 保管先 | 入るもの | 個人情報 | 規則 |
|---|---|---|---|
| **監視アプリのローカルの DB**（開発機。種類は未決定） | 1 回の起動（手動の指示・定期実行）ごとの実行記録。**要約・対象の ID（会話・コンタクト・記事など）・相関 ID（ULID）・成否・起動の種類**（ほかにエージェント名・開始日時など、個人に関わらない属性）。**ツールの呼び出しの結果は残さない** | **含まない前提**（人は ID で指し、要約にも個人情報を書かない。**要約の検査が漏れる余地は残る**） | 記録は監視アプリのサーバー側だけが書き、エージェントには書かせない（ADR-18）。**監視アプリが記録の前に、要約にメールアドレス・電話番号の形の文字列が無いかを検査する**（検査の方法は未決定。5 節）。保持期間は未決定（2 節） |
| **S3 の写し**（`ap-northeast-1`。写し専用のバケット。TA-06 の 4.7） | 上の記録の写し | 同上（**含まない前提**） | **追記だけを許し、削除と上書きを許さない。** 写しを書く資格情報は監視アプリのサーバー側だけに置く。越境しない（`ap-northeast-1`）。写す頻度と形式・保持期間は未決定 |

- **要約と ID だけにしたことで、1.4 の「本番の DB のダンプを開発機に持ち込まない」との緊張が解ける。** ADR-18 の反映では「ダンプは持ち込まなくても、エージェントが本番から読んだ値をツールの結果として記録すれば、同じ個人情報が断片的に開発機に溜まる」としていた。追加の決定で、1.3（通知）・AA-03 の 3.4（`conversation-triage`）の「要旨と ID だけを残し、本文は元のシステムを見に行く」と揃った。**誤った書き込みの調査では、ID から本番の管理画面で元のデータを引く**（調査に使える情報は減るが、元のデータは本番に残っている）。
- **人は ID で指す。** 顧客（コンタクト・会話の相手）を要約の中で指すときは、`E-09` の `id` や `E-10` の `display_id` を使い、氏名・メールアドレス・電話番号・会話本文の引用を書かない。**この規則はエージェント定義に置く**（AA-03）。要約はエージェントの出力であり、規則だけでは守りきれないため、監視アプリが記録の前に形で検査する。**形で検出できるのはメールアドレスと電話番号までで、氏名や本文の引用は検出できない**（検出の外に残る部分は規則に頼る）。
- **削除請求の対象から外れうる**（2 節）。ADR-18 の反映では「ツールの結果を残す場合、削除請求が来たら監視アプリの実行記録からも該当する値を消す必要がある」とし、`E-15` を削除請求の対象に加えていた。**追加の決定で記録に個人情報が入らない前提になったため、`E-15` は削除請求の対象から外れうる。** ただし要約の検査が漏れて個人情報が入った場合は、正本（ローカル）と S3 の写しの両方に残る。**S3 の写しは追記だけで削除を許さないため、写しから消すには人間（運用者）が別の権限で行うことになる**（手順は未決定。5 節）。
- **開発機のバックアップと S3 の写しに個人情報は入らない前提である**（TA-05 の 5 節）。ADR-18 の反映では「開発機の外に写す場合は、写し先も保管先として数える」としていた。写し先は S3（`ap-northeast-1`）に決まり、記録が要約と ID だけのため、個人情報の保管先として数えない（要約の検査が漏れた場合を除く）。
- **`sanitize()` は個人情報を伏せない**（3.3）。記録にツールの結果を残さないため、この性質は `E-15` には効かなくなった。要約の個人情報を防ぐのは、エージェント定義の規則と監視アプリの検査である。

## 3. `sanitize()` の方針

`backend/chatwoot-mcp/src/services/results.ts` の `sanitize()` は、**上流 API のレスポンスをモデルに渡す前に必ず通す共通処理**である。
エージェントは受け取った値をそのまま別の場所へ書き出しうるため（提案の `evidence` に貼る、Chatwoot に返信する、など）、モデルに渡る前の一点で伏せるのが最も確実な防ぎ方になる。

### 3.1 実装されている挙動

- **秘匿情報らしいキーの値を `[redacted]` にする。** 判定は正規表現 `/secret|password|token|api_?key|hmac/i` によるキー名の部分一致（`api_key` と `apikey` の両方に当たる）。
- **例外リスト `NON_SECRET_KEYS` に載るキーは伏せない。** 現在は `website_token`（Web ウィジェットの埋め込み用トークン。公開ページに埋め込まれる値のため秘匿情報ではない）、`hmac_verified`、`hmac_mandatory` の 3 つ。
- **伏せ字にするのは、値が `null` でも空文字でも真偽値でもない場合に限る。** `token: null` や `hmac_mandatory: false` のような「設定されているか否か」の情報は、伏せずにそのまま返す（設定状態の把握はエージェントの判断に必要で、かつ秘匿性が無いため）。
- **`LONG_TEXT_LIMIT`（1,000 文字）を超える文字列を省略する。** 省略時は先頭 200 文字＋残り文字数と、`include_long_text=true` で全文を取れる旨の案内に置き換える。メール本文の HTML や長い会話メッセージが応答を埋め尽くすのを防ぐ。
- **オブジェクトと配列は再帰的に処理する。** ネストの深さに関わらず、どの階層にある秘匿キーも伏せられる。

### 3.2 `sanitize()` と併用される 2 つの上限

| 仕組み | 定数 | 値 | 役割 |
|---|---|---|---|
| `sanitize()` の長文省略 | `LONG_TEXT_LIMIT` | 1,000 文字 | 個々の文字列が長すぎるのを防ぐ |
| `truncate()` | `CHARACTER_LIMIT` | 25,000 文字 | 応答全体が大きすぎるのを防ぐ |
| `fitToLimit()` | `CHARACTER_LIMIT` | 同上 | 一覧の件数を半分ずつ減らして上限に収める |

- `fitToLimit()` で削られた分は「次のページ」では取得できない（ページ境界ではなく応答サイズで削るため）。`truncation_message` がその旨を伝える（DA-02 の 5.2 のデータ契約と対応）。

### 3.3 運用上の注意

- `jsonResult()` は内部で `sanitize()` を呼ぶが、**`formattedResult()` は呼ばない**（引数の `structured` が既に整形済みである前提のため）。新しいツールを追加するときは、`formattedResult()` に渡す前に呼び出し側で `sanitize()` を通す。
- `mautic-mcp` も同じ方針を取る（秘匿情報らしいキーを伏せ、1,000 文字超の文字列を省略する）。3 つ目の MCP サーバを作る場合もこの構造に合わせる。
- `sanitize()` は**秘匿情報の漏洩を防ぐ装置であって、個人情報を伏せる装置ではない**。email・氏名・会話本文はキー名が秘匿パターンに当たらないため、そのままモデルに渡る。個人情報の保護は `ACCESS_LEVEL` と取得範囲の制限（データ契約）で行う。

## 4. エージェントの読み書きの原則

### 4.1 最小権限

- **既定は参照のみ。** `CHATWOOT_ACCESS_LEVEL` / `MAUTIC_ACCESS_LEVEL` の既定値は `read_only`。書き込みが必要な用途に限って昇格させる。
- Mautic の API 認証情報は client_credentials でユーザーが紐づかないため、**権限は Mautic 側のロールで決まる**。参照専用のロールを割り当てる。
- Chatwoot の `api_access_token` は**ユーザーに紐づく**。操作履歴も権限もそのユーザーのものになるため、**専用のエージェントユーザーを作る**（AI 経由の返信を人手の返信と区別するため。加えて、そのユーザーの権限を絞ることでエージェントの権限を絞れる）。
- レポート・監査ログ・設定変更には管理者トークンが必要だが、**観測だけが目的なら管理者権限を与えない**（レポート API が使えない場合、エージェントはその項目をスキップする設計にする）。

### 4.2 `ACCESS_LEVEL` による制御

- **許可されないツールは「実行時に拒否する」のではなく「ツール一覧に登録しない」。** モデルからは存在しないように見えるため、そもそも呼ぼうとしない（拒否を返す設計だと、モデルが迂回路を探しはじめる）。
- 包含関係は `read_only` ⊂ `read_write` ⊂ `full`。`chatwoot-mcp` の検証ハーネス（`pnpm verify`）はこの包含関係を実際に検査している。
- `full` でのみ公開される操作（`chatwoot_delete_record` / `chatwoot_delete_contact` / `chatwoot_delete_message` / `chatwoot_merge_contacts`、`mautic_delete_record`）は不可逆。とくに `chatwoot_merge_contacts` は統合されたコンタクトを削除するため、取り消せない。
- 破壊的な操作には `destructiveHint: true` が付いており、MCP クライアント側で実行前の確認を求められる。**この確認をエージェントが自動で承認する運用にしない**（`CAP-06` の承認ゲートが形骸化する）。
- HTTP トランスポートの認証は固定 Bearer トークン（`MCP_AUTH_TOKEN`、32 文字以上）。比較は SHA-256 ダイジェストどうしの `timingSafeEqual`。stdio では不要。

### 4.3 監査ログ

| 記録する対象 | 記録先 | 状態 |
|---|---|---|
| Chatwoot 上の操作（誰が何を変えたか） | **エージェントの送信は、エージェント専用ユーザーのメッセージ（`sender`）で追う**（ADR-17）。Chatwoot の監査ログ（`chatwoot_list_audit_logs`）は Enterprise の `audit_logs` 機能が必要なため、**頼らない**（ADR-16 では主な手段としていたが ADR-17 で改めた。使える環境では変更調査の補助に使える）。**会話の属性（担当者・ラベル・状態）の変更は、送信の記録からは追えない** | 未配線 |
| エージェントの実行（入力・結果・失敗） | `E-15 AgentRun`（**監視アプリの実行記録。ローカル**。ADR-18。当初は n8n の実行履歴とし、ADR-14・ADR-15 で監視アプリの実行記録を候補にし、ADR-17 で起動元が監視アプリに一本化された）。**監視アプリのサーバー側だけが書き、エージェントには書かせない**。ADR-18 の反映では入力・結果をどこまで残すかを未決定にしていたが、**追加の決定で要約と ID だけを残し、ツールの結果は残さないと決めた**（1.5）。**S3 に追記専用で写す**（TA-06 の 4.7） | 未着手 |
| エージェントによる本番への書き込み（誰が、何を、いつ） | エージェント専用ユーザーの送信の記録（`sender`。エージェント専用のアカウントの操作として残る）と `E-13` の `applied_at`・`change.diff_ref`（ADR-15）。**両者を突き合わせて、どの `E-13` にも対応しない送信を誤った書き込みの候補にする**（ADR-17、TA-07 の 6.2。監視アプリの定期実行の 1 つとして起動する。頻度は未決定）。Strapi への書き込みは下書きまでで（ADR-17）、公開は `R2` の管理画面での操作として Strapi に残る | 未着手 |
| 公開サイトへの配信の承認（誰が、いつ） | 未定（監視アプリの「承認して配信」の記録にするか。TA-07 の 9 節）。**`E-13` の `applied_at` は配信した人間が記録する**（ADR-16） | 未着手 |
| n8n のワークフローの本番での有効化（誰が、いつ） | n8n のワークフローの履歴と、`E-13` の `applied_at`（**有効にした人間が記録する**。ADR-16） | 未着手 |
| 改善提案の起票・承認・適用・差し戻し | `E-13` / `E-14`（Git の履歴と PR） | 未着手 |
| MCP サーバの動作ログ | stderr（`console.error`。stdout は MCP の通信専用のため使わない） | 実装済み |
| 環境変数の検証失敗 | stderr に**変数名と理由だけ**を出して `exit(1)`（値は出さない） | 実装済み |

- **`E-13` を経由しない変更を検出できることが、このガバナンスの要**。エージェント専用ユーザーの送信の記録と `E-13`（Git の履歴）を突き合わせ、対応する `proposal_id` の無い送信を例外として扱う（ADR-16 で監査ログとの突き合わせに決め、**ADR-17 で監査ログに頼らず送信の記録で行う形に改めた**。TA-07 の 6.2）。**検出できるのは送信だけ**であり、会話の属性の変更は検出の外に残る。**エージェント専用のアカウントで操作することが前提**であり、人間の管理者と同じトークンを使うと、操作の主体を区別できない。
- 秘密値を含む環境変数ファイルは追跡しない。`.env.example` は必ず同時に更新する。
- `N8N_ENCRYPTION_KEY` と Chatwoot の `ACTIVE_RECORD_ENCRYPTION_*` を変更すると既存の暗号化データを復号できなくなる。鍵の変更は**データの喪失と同義**として扱い、`E-13` の `rollback.reversible: false` に相当する扱いにする。
- n8n の `sandbox-runner-1` は privileged な Docker-in-Docker（ホスト root 相当）のため、暗号化キーや DB パスワードを渡さない。この分離を崩さない。**本番の n8n にはサンドボックスを置かない**（ADR-16。Fargate は privileged のコンテナを受け付けない）ため、この規則は開発環境に対するものになる。

## 5. 未決定事項

- PostHog のデータ保持期間（1.2 と 2 節で方針は書いたが、実際の設定は行っていない）。SaaS 側の設定であり、プランによって設定可能な範囲が異なる可能性がある。
- 個人情報の削除請求が来たときの手順。対象は `E-08` `E-09` `E-10` の 3 つ（ADR-18 の反映では `E-15` を加えて 4 つとしていたが、**追加の決定で `E-15` は要約と ID だけになり、対象から外れうる**。1.5）だが、`E-08` は SaaS 側にあり、削除の反映が Mautic / Chatwoot と同時にならない。「どこまで削除したか」の記録をどこに残すかも未定（用語集に該当するエンティティが無いため、勝手に増やさずここに記録する）。
- **`E-15` の要約に個人情報が入ってしまった場合の扱い**（ADR-18 の追加の決定で残った論点。1.5）。要約の検査が漏れると、正本（開発機）と S3 の写しの両方に残る。**S3 の写しは追記だけで削除と上書きを許さない**ため、消すには運用者が写し用とは別の権限で行う（Object Lock を使う場合は保持期間が切れるまで消せない。TA-06 の 11 節）。見つけたときに消すのか、ID で置き換えた版を追記するのかを決める。判断者 `R1`。
- **（2026-09-19 に ADR-15 で決着）エージェントが本番の会話・コンタクトに触れるか。** 触れる（本番用の MCP の登録）。これにより、下の「会話本文をエージェントに読ませる範囲」の論点が本番のデータについて生じる。判断者 `R1`。
- 会話本文（`E-10`）をエージェントに読ませる範囲。`sanitize()` は個人情報を伏せないため、会話本文はそのままモデルに渡る。要配慮情報が含まれた場合の扱い（そもそも読ませないのか、読ませたうえで提案に転記しないのか）が未確定。
- **RDS のバックアップと S3 の旧バージョンに残る個人情報の扱い**（1.4）。削除請求で DB から消しても保持期間が切れるまで残る。保持期間（現在は暫定で 7 日）と、削除の完了をどう説明するかを削除請求の手順と一体で決める。判断者 `R1`。
- **本番のデータを開発・検証に使う必要が出た場合の扱い**（1.4）。匿名化してから持ち込むのか、持ち込まないのかが未定。判断者 `R1`。
- `E-13` を置く Git リモートリポジトリの所在。統制の記録が外部の SaaS（GitHub）に置かれることになり、`E-08` 以外にも越境が生じる。事業側の方針確認が必要。
- **（2026-09-19 に ADR-17 で一部決着）Chatwoot の版と、誤った書き込みの突き合わせの頻度。** 検出の方式は ADR-16 で「監査ログと `E-13` を突き合わせる。Enterprise の `audit_logs` が使えなければ、エージェント専用のユーザーのメッセージ（`sender`）で代える」と決まり、Enterprise を使うかと頻度を未決定にしていた。**ADR-17 で、監査ログには頼らずエージェント専用ユーザーの送信の記録で行うと決めた**（Community 版で運用できるようにするため）。**残るのは突き合わせの頻度である。** 送信の記録は会話へのメッセージしか拾えず、ラベル・担当者・状態・コンタクトの属性の変更は拾えないため、「`E-13` を経由しない変更の検出」は部分的のままである（属性の変更の誤りは、各会話の履歴を人間が見て気づく）。Chatwoot の webhook で変更を拾う案は、webhook を止められる主体が変更を隠せるため監査ログの代わりにならない。判断者 `R1`。
- **突き合わせで会話本文に触れる範囲**（ADR-17 で生じた論点）。送信の記録は会話ごとのメッセージ履歴（`chatwoot_list_messages`）から取るため、突き合わせの処理はエージェント専用ユーザーの送信以外のメッセージ（顧客の本文）も読むことになる。エージェントに読ませる場合は、上の「会話本文をエージェントに読ませる範囲」と同じ論点になる。**送信者と送信日時・`display_id` だけを取り、本文はモデルに渡さない**処理（エージェントを使わない監視アプリの処理）にできるかを、取得手段（AA-02 の 5 節）と合わせて決める。判断者 `R1`。
- **（2026-09-19 に AA-05 の ADR-18 で一部決着）監視アプリの実行記録を `E-15` の正本にした場合の保管場所**（ADR-17 で生じた論点）。ADR-17 で起動元が監視アプリに一本化され、実行記録を `E-15` の正本にする条件が揃った。しかし監視アプリはローカル（開発機）にあり ADR-16 の基準（正本のデータを持つものはクラウド）に反し、実行記録にはエージェントが本番から読んだ `E-09` `E-10` が混入しうるため、本番の個人情報が開発機のディスクに残る、という論点だった。**ADR-18 で、実行記録をクラウドに送らず、`E-15` をローカルに置くことを ADR-16 の基準の例外として受け入れた**（1.5）。**保管場所は決着した。** 残った項目（記録する範囲・保持期間・開発機の外への写し）のうち、**記録する範囲と写しは同日の追加の決定で決着し、保持期間だけが残る**（下の項目）。
- **（2026-09-19 に AA-05 の ADR-18 の追加の決定で決着）`E-15` に記録する範囲**（ADR-18 で生じた論点。1.5）。ツールの呼び出しと結果をそのまま残すか、要約と ID だけにするか（入出力を残さず結果と失敗だけにする案を含む）を未決定にしていた。前者は誤った書き込みの調査に強いが、本番の個人情報がローカルに残り、削除請求の対象になる。後者は 1.3 と同じ「要旨と ID だけを残す」形に揃う。**要約と ID だけを残す**（要約・対象の ID・相関 ID・成否・起動の種類。ツールの結果は残さない）。**要約にも個人情報を書かない**（人は ID で指す規則をエージェント定義〈AA-03〉に置き、監視アプリが記録前にメールアドレス・電話番号の形を検査する）。
- **要約の個人情報の検査の方法**（ADR-18 の追加の決定で残った論点。1.5。TA-07 の 9 節）。メールアドレス・電話番号の形の検出の仕方（正規表現か、既存の検出の仕組みを使うか）と、検出したときに記録を拒むか伏せて記録するか。**氏名と本文の引用は形で検出できない**ため、検出の外に残る部分を規則だけに任せてよいかも合わせて決める。判断者 `R1`。
- **`E-15` の保持期間**（ADR-18 で生じた論点。2 節）。`E-13` は削除しないため、`E-15` を先に消すと `E-13` の `agent_run_id` の参照先が失われる。旧版は「記録する範囲を ID だけに絞るなら長く、ツールの結果を残すなら短く、の 2 段にする案もある」としていたが、**範囲が要約と ID だけに決まったため 2 段にする必要は無くなった**。**少なくとも改善の検証の期間（既定 30 日）と `rollback.deadline` を覆う**（ADR-18 の追加の決定）。**S3 の写しの保持期間も合わせて決める。** 判断者 `R1`。
- **（2026-09-19 に AA-05 の ADR-18 の追加の決定で決着）`E-15` を開発機の外に写すか**（ADR-18 で生じた論点。TA-05 の 5 節・8 節）。写す場合は写し先も個人情報の保管先になり、削除請求の対象と越境の有無が写し先に依存する、としていた。**S3（`ap-northeast-1`）に写す。** 記録が要約と ID だけのため、写し先は個人情報の保管先にならない前提で、越境もしない。写しは追記だけを許し、削除と上書きを許さない（TA-06 の 4.7）。残るのは写す頻度と形式である（TA-07 の 9 節）。
- **本番の n8n の実行履歴に残る個人情報の扱い**（1.4。ADR-16 で生じた論点。**ADR-18 で n8n の実行履歴は `E-15` ではなくなったが、個人情報が残る問題は変わらない**）。n8n は既定で実行の入出力を DB に保存し、Webhook で受けた `E-09` `E-10` の email・本文がそのまま残る。保持を 90 日（2 節）にするための n8n の設定（実行データの自動削除）と、成功した実行の入出力を保存しない設定にするか、削除請求（2 節）の対象に n8n の実行履歴を含めるかを決める。判断者 `R1`。
