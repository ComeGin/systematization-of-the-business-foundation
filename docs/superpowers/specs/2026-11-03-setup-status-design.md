# 監視アプリの「設定の状況」画面（本番の設定のずれと手順を 1 画面で見る）

- 日付: 2026-11-03
- 対象: `frontend/next-js`（監視アプリ）・`backend/control-plane`・`setup/`・`cloud/stacks/iam.yaml`・各モジュールの `setup/index.mjs`
- 状態: 設計（ユーザーとの対話で決めた内容。「〔判断: 設計者〕」と付けたものは設計者の判断で、ユーザーの決定ではない）

## 1. 何のためか

本番（クラウド・オンプレ・OpenSEO〈Search Console・GA4〉）を設定・運用する R1 が、次の 2 つで困っている（ユーザーの言葉）。

1. **今のシステムに設定の更新が必要なのかが分からない。**
   2026-11-03 の棚卸しで、PR #60 をマージした後に公開サイトの再配信と `n8n-prod` の再反映を忘れていたことが分かった。気づいたのは、人が `--check` と AWS の読み取りで棚卸しをしたからにすぎない。
2. **設定の手順書を `cloud`・`onprem`・`middleware`（と `setup`）の間で行き来しなければならない。**
   地図は `setup/00-setup-overview.md` の P1〜P15 だが、本文は `cloud/README.md`（約 1,600 行）・`onprem/README.md`・`middleware/…/README.md`・`setup/manual-steps.md` に分かれている。

実際の設定の作業で端末や AWS の画面と行き来するのは構わない（ユーザーの言葉）。**見る場所を 1 つにすること**が目的。

成功の姿: R1 が監視アプリを開くと、本番の設定の全体（P1〜P15）のどこに更新が必要かが分かる。そこを選ぶと、根拠と、正本の手順書の該当の節がその場で読める。更新が必要になったら、画面を開いていなくてもメールで知らされる。

## 2. 決めたこと（ユーザーの決定）

| 項目 | 決定 |
|---|---|
| 画面の形 | **B. 段階の地図＋詳細**。左に P1〜P15 の全体と状態、右に選んだ段階の手順・根拠・正本の本文（モックの A「やることの一覧」は採らなかった） |
| 状況のデータの取り方 | **監視アプリが自分で定期的に AWS（と本番の各製品）を読みに行く**。人が端末で `--check` を実行した結果を表示する形にはしない |
| AWS の主体 | 監視アプリの今の主体 `comegin-prod-control-plane`（写しの追記とハートビートの送信だけ）は**広げない**。**状況の確認専用の読み取りの主体を別に作る**。キーは監視アプリのサーバーだけが読み、エージェントには渡さない |
| 知らせ方 | 「更新が必要」「警告」を見つけたら**メールで知らせる** |
| GitHub の最新の取り方 | 監視アプリに **GitHub の読み取り専用のトークン**（fine-grained。対象はこのリポジトリだけ、権限は Contents と Pull requests の read だけ）を置き、**自分で main の最新を取る**。トークンは監視アプリのサーバーだけが読むファイルに置き、エージェントには渡さない。チェックアウトの中で fetch すると、`.git` を共有する作業ツリーの `origin/main` も新しくなる（許容） |
| 確認のコードと読むファイルの場所 | **コードは承認済みの main のチェックアウトから動かす**（ADR-18）。**追跡しない実行時のファイル**（`cloud/samconfig.toml`・`onprem/*/.env`・作業ツリーの `frontend/next-js/.env` など）と**突き合わせの基点だけは、明示した作業ツリーのパスから読む**（例 `CONTROL_WORKTREE`）。各モジュールの読み先をそれに合わせて直す |

## 3. やること・やらないこと

### やること（目標）

- 本番（`--target prod`）の設定の状況を、監視アプリが定期的に確かめて 1 画面に出す。
- 状況の確かめ方は**設定スクリプトの `check()` を再利用する**（同じ確認を二重に実装しない）。加えて、設定スクリプトが今は確かめていない**ずれ**（下の 5.3）を確かめる。
- 各手順に、正本の手順書の節の本文を、その場で読める形で付ける。
- 「更新が必要」「警告」が新しく出たらメールで知らせる。

### やらないこと（非目標）

- 画面から設定を**実行**すること（`apply`・デプロイ・AWS への書き込み・Secret の値の投入）。これまでどおり人が端末で行う（`00-setup-overview.md` の「人・端末」。Claude Code にも監視アプリにも行わせない）。
- 開発環境（`--target dev`）の状況。〔判断: 設計者〕開発の監視アプリでは、この機能は既定で無効にする（下の 7）。
- 手順書の編集。正本は今の Markdown のままで、画面は読むだけ。

### こうなったら失敗（反目標）

- 状況の確認の主体やキーが、エージェント（Agent SDK で起動する Claude Code）の環境や MCP の env に渡る。
- 画面・メール・保存した結果・ログに、秘密値（`prod.conf`・`prod.state.json` のトークンやパスワード、Secret の値）が出る。
- 状況の確認が**本番に書き込む**（状態ファイルの更新も含む。下の 5.1）。
- 「✓」と出ているのに実際は確かめていない（確かめられなかったものを ✓ にしない。〔未検査〕は〔未検査〕と出す）。
- メールが多すぎて読まれなくなる（同じ項目で何度も送る）。

## 4. 画面（`/setup-status`）

サイドナビに「設定の状況」を足す（`components/layout/routes.ts` に登録。既存の runs・jobs と同じ形。UI は Cloudscape）。

```
┌ 上: 最後に確かめた時刻・次の予定・「今すぐ確かめる」・全体の件数（● 更新が必要 n・! 警告 n・? 確かめられない n）
├ 左（段階の地図）            ├ 右（選んだ段階の詳細）
│ ✓ P1 env                    │ P12 ビルドと配信
│ ✓ P2 deploy                 │   根拠: 配信中のビルド 11-02 16:29／その後に main に入った公開サイトの変更 PR #60
│ …                           │   ● 承認済みの main でビルドし直す   [人・端末]
│ ● P12 ビルドと配信  ←選択   │      ▼ cloud/README.md 4.14 の本文（Markdown を描画）
│ ✓ P13 google                │   ✓ 配信用の主体 ComeginProdDeploy
│ ● P14 改善ループ            │   ◇ FAQ ボットの確認〔未検査〕
│ ! P15 仕上げ                │
│ ◇ 6 節 判断（R1）           │
```

- **状態の印は 5 種類**: ✓ 済み／● 更新が必要／! 警告／◇ 人が確かめる（〔未検査〕・〔申告〕・判断）／? 確かめられなかった（AWS に届かない・タイムアウト・資格情報が無いなど。理由を出す）。段階の印は、その中の項目で最も重いもの（● > ! > ? > ◇ > ✓）。
- 各項目に出すもの: 見出し・だれが（自動／人・端末／人・画面／判断。`00-setup-overview.md` の 0 節のラベル）・状態・**根拠**（何を見てそう判断したか。日時・コミット・件数など。秘密値は出さない）・止まる id（例 `next-js-prod:build`）・正本の節へのリンク。
- 正本の節は、行を開くとその場で本文を描画する（`00-setup-overview.md` の「— cloud 4.14」などの参照を、該当の見出しの節に解決する）。本文の中のほかの節への参照も、同じ画面の中で開けるとよい。〔判断: 設計者〕本文は**承認済みの main のチェックアウト**（`CONTROL_MAIN_CHECKOUT`）から読む（ADR-18。作業ツリーの未承認の手順書を見せない）。
- 選んだ段階は URL に持つ（`?step=P12`）。メールのリンクから直接開ける。
- 「今すぐ確かめる」は POST（既存の Route Handler と同じく、ログイン必須・`Origin` の確認）。確かめている間は二重に起動しない。

## 5. 状況の確かめ方

### 5.1 設定スクリプトの `check()` を監視アプリから呼ぶ

- 監視アプリ（control-plane）が、**承認済みの main のチェックアウトの** `setup/setup.mjs` と `setup/frontend.mjs` を `--target prod --check` で子プロセスとして実行し、結果を機械が読める形（新しいオプション。例 `--json`）で受け取る。対象の段階は `env`〜`operate` のすべて（`google`・`operate` を含む）。
- **前提として、`check()` が本当に読み取りだけであることを確かめて直す。** 2026-11-03 時点のコメントでは、`cloud` の段階 `apps` が DB 作成のタスクの成功を「確かめたら状態に残す」。`check` の途中で状態ファイル・環境変数ファイル・`prod.conf` に書くものが無いかを洗い出し、`--check` では書かないようにする（書く必要があるなら、状況の確認の結果としてだけ持つ）。
- **結果の形を構造化する。** 今の契約は `{ ok, notes: string[] }` で、警告は文の先頭の `! ` で表している。これに任意の `items` を足す（例: `{ key, step: "P12", level: "ok"|"action"|"warn"|"manual"|"unknown", title, evidence, stopId, docs: ["cloud/README.md#4.14"] }`）。`items` を持たないモジュールは、`ok` と `notes` を、モジュールと段階から決まる手順（下の 5.2 の対応表）に当てはめる（`! ` で始まる文は警告）。
- 子プロセスの出力は今も `mask()` で秘密値を伏せているが、監視アプリの側でも、保存・画面・メールに出す前にもう一度伏せる（下の 6）。
- `cloud/samconfig.toml` などの追跡しないファイルは、**承認済みの main のチェックアウトには無い**（2026-11-03 に確認）。ユーザーの決定（2 節）どおり、コードはチェックアウトから動かし、追跡しないファイルと突き合わせの基点は明示した作業ツリーのパスから読む。今の `check()` には、`ctx.W`・`ctx.REPO` がチェックアウトと同じだと止まるものがある（`next-js-prod` の「`CONTROL_MAIN_CHECKOUT` が作業ツリーと同じ場所」、`verdant-virgo` の同じ検査）。`ctx` に「作業ツリー」と「コードの場所」を分けて渡し、これらの検査と読み先を直す。人が作業ツリーで `--check` するときの動きは変えない。
- **初期設定用の値を消した後の扱い**〔判断: 設計者〕: `chatwoot-prod`・`n8n-prod` の `check()` は `prod.conf` の `CHATWOOT_ADMIN_TOKEN` を必須にしているが、P15 はこれを消すのを正しい運用としている。`mautic-prod`（2026-11-03 に直した）と同じく、**管理者のトークンが無いときは、そのトークンが要る項目を ◇（初期設定の値を消した後なので確かめない）として出し、ほかの項目は確かめ続ける**。● にはしない（P15 を済ませるとずっと ● になり、毎日のメールに出続けるため）。
- **製品の API を呼ぶ確認の間隔**〔判断: 設計者〕: `check()` の中には、確かめるたびに本番の製品に記録を残すものがある（例: `mcp-prod` が Mautic の `/oauth/v2/token` でトークンを取る。10 分ごとだと 1 日 288 件ほどトークンが Mautic の DB に積まれる）。こうした認証のついでの書き込みも反目標の「本番に書き込む」に準じて扱い、**製品の API を呼ぶ確認は 1 時間に 1 回まで**とする（「今すぐ確かめる」のときは呼ぶ）。AWS の読み取り・git・公開サイトの HTTPS・ローカルのファイルの確認は 10 分ごと。`check()` が製品の API を呼ぶ箇所は、6.1 の AWS の API と同じく全部洗い出して一覧にする。

### 5.2 手順の一覧（P1〜P15）と、確かめ方の対応

- `00-setup-overview.md` の 3 節（P1〜P15）・4 節（スクリプトが確かめる範囲）・5 節（申告制のフラグ）・6 節（判断）の項目を、構造化した一覧（以下「手順の一覧」）として持つ。各項目: 段階（P1〜P15・6 節）・見出し・だれが・種類（検査／警告／申告／未検査／判断）・止まる id・正本の節・確かめ方（モジュールと `items` の `key`、または 5.3 のずれの確認、または「無い」＝〔未検査〕）。
- **人が読む正本は `00-setup-overview.md` のまま。** 手順の一覧とずれないように、両方に同じ項目があることを機械で確かめる仕組みを用意する（〔判断: 設計者〕形は作る人に任せる。黙ってずれないことが条件）。
- 〔未検査〕・〔申告〕・判断の項目は常に ◇ で出す。ただし、確かめられるようになったもの（5.3）は確かめる。

### 5.3 設定スクリプトが今は確かめていない「ずれ」

ユーザーの困りごと 1 の中心。次の 4 つを「更新が必要」として確かめる。

| ずれ | 確かめ方（〔判断: 設計者〕の案） | 段階 |
|---|---|---|
| **公開サイトの再配信が必要**: 配信中のビルドより後に、`origin/main` に公開サイト（`frontend/verdant-virgo`）の変更が入った | ビルドのときに `dist` にビルドの情報（コミットとビルドの日時。秘密値なし）を焼き込み、公開サイトから HTTPS で読む（AWS の権限が要らない）。`origin/main` で、そのコミットより後に `frontend/verdant-virgo` を変えたコミットがあれば ●。根拠にコミットと PR を出す | P12・P13 |
| **チェックアウトが `origin/main` より遅れている**、または**チェックアウトを動かした後にビルドしていない**（監視アプリ・control-plane・本番の MCP の `dist`） | `next-js-prod` の `check` が既に見ている（`checkout`・`build`）。MCP の `dist` も同じ考え方で見る | P10・P14 |
| **本番の n8n のワークフローがリポジトリの JSON と違う**（PR で JSON を変えた後に `--only n8n-prod` を実行していない） | 本番の n8n の公開 API（キーは状態にある）でワークフローを読み、`origin/main` の `middleware/n8n/workflows/` と突き合わせる | P9・P14 |
| **公開済みの記事が増えたのに再配信していない**（記事はビルドのときに取り込む） | 〔判断: 設計者〕本番の Strapi（`127.0.0.1:1338`）の公開済み記事の最新の公開日時と、配信中のビルドの日時を比べる。対象に含めるかは作る人が決めてよい（含めないなら〔未検査〕として出す） | P12 |

**main の最新は監視アプリが自分で取る**（ユーザーの決定。2 節）。今の `next-js-prod` は fetch せず、人が fetch した `origin/main` と比べているだけなので、人が fetch しないと PR のマージに気づけない。これがユーザーの困りごと 1 の原因だった。
- 10 分ごとに、GitHub の読み取り専用のトークンで、チェックアウトの中で `git fetch origin main` する（チェックアウトの HEAD・作業ツリーのファイルは動かさない。`origin/main` の参照だけが新しくなる。`.git` を共有する作業ツリーの `origin/main` も新しくなるのは許容）。トークンは `git` の子プロセスにだけ渡し（コマンドラインや URL に埋め込まない。`ps` に出さない）、リモートの URL・`.git/config` に書き込まない。
- 根拠に出す PR 番号は、同じトークンで GitHub の API から引く（コミットに紐づく PR）。〔判断: 設計者〕取れなければコミットだけを出す。
- トークンの置き場（例 `~/.config/comegin/status-reader/github-token`、600）と、主体の確認（読めるリポジトリがこのリポジトリだけで、書けないこと）は、6.1 の AWS の主体と同じく `next-js-prod` が確かめる。I-13 の起票用の `GITHUB_TOKEN`（Issue を書ける）とは**別のトークン**にする。

### 5.4 いつ確かめるか

- 〔判断: 設計者〕**10 分ごと**と、「今すぐ確かめる」を押したとき、監視アプリの起動のとき。
  - **（2026-11-04 に改めた。ユーザーの決定）定期の確認は 1 時間ごと**（10 分は短すぎる）。製品の API の間隔（5.1）と同じになるので、製品の API の判定には 1 分のずれを許す（タイマーの揺れで 2 時間に 1 回にならないように。`backend/control-plane/src/status/service.ts` の `PRODUCT_API_DUE_SLACK_MS`）。`git fetch origin main` も 1 時間ごとになり、PR のマージに気づくのは最大 1 時間後（すぐ見たいときは「今すぐ確かめる」）。この節と 5.1・5.3 に残る「10 分ごと」は当初の判断の記録
- 〔判断: 設計者〕これは改善ループの処理ではなく監視なので、**0〜8 時（JST）の窓に縛らず一日中動かす**（`ops/README.md` の「時刻の決め方」は改善ループの定期実行の決まり）。定期実行の定義（`ops/schedules/*.yaml`）にも E-15 の実行記録にも入れない（1 日 144 回で一覧が埋まるため）。ハートビートと同じく、control-plane の中の仕組みとして動かす。
- 1 回の確認には上限の時間を設ける（例 5 分）。前の確認が終わっていなければ次は飛ばす。
- `CONTROL_SCHEDULER_ENABLED` とは別のスイッチにする（下の 7）。

## 6. 秘密値とデータの置き場

- 状況の確認の子プロセスは、`prod.conf`・`prod.state.json`（同じユーザー `kamegin` が読める）と、6.1 の主体のキー・5.3 の GitHub の読み取り専用のトークンを使う。**子プロセスの環境にだけ渡し**、監視アプリの `.env` やエージェントの環境には入れない。control-plane がエージェントを起動するときの環境に、このキーのファイルの場所や `AWS_*` が漏れないことを確かめる。
- 結果（項目ごとの状態・根拠・確かめた時刻）と、知らせた記録（6.2）は、`CONTROL_DATA_DIR` に置く（E-15 の `e15.sqlite` とは別。〔判断: 設計者〕SQLite でも JSON でもよい）。保存する前に、`prod.conf`・状態ファイルの秘密値の値をすべて伏せる（`setup/lib/core.mjs` の `mask()` と同じ考え方を監視アプリの側でも行う）。
- 履歴は、知らせるかどうかを決めるのに要る分だけ持つ（前回の状態と、項目ごとの最後に知らせた時刻）。

### 6.1 状況の確認専用の AWS の主体（ユーザーの決定）

- `cloud/stacks/iam.yaml` に、管理ポリシー `comegin-prod-status-reader`（仮の名前）を足す。中身は **5.1・5.3 の確認が使う読み取りの API だけ**（`check()` の本番の経路で `aws` を呼んでいる箇所を全部洗い出して決める。例: CloudFormation のスタックの読み取り、ECS のサービスの読み取り、ECR のイメージの一覧、Secrets Manager の `DescribeSecret`〈値の読み取り `GetSecretValue` は与えない〉、SES・SNS の購読・CloudWatch のアラームの読み取り、IAM のアクセスキーの一覧、DB 作成のタスクのログの読み取り）。
- **加えて `sns:Publish` を `comegin-ops-alert` の 1 トピックだけに与える**（メールの知らせ。6.2）。〔判断: 設計者〕知らせのために主体をもう 1 つ増やさない。
- 与えないもの: 書き込み全般・`secretsmanager:GetSecretValue`・購読やトピックの変更・アラームの変更・S3 のオブジェクトの読み取り（必要なら理由を書いて最小に）。
- 〔判断: 設計者〕`comegin-prod-control-plane` と同じ運用（`cloud/README.md` の 4.5.2）にそろえる: **管理ポリシーはスタックで作り、IAM ユーザー（例 `comegin-prod-status-reader`）は人が作ってそのポリシーだけを付け、キーも人が発行して**、監視アプリのサーバーだけが読むファイル（例 `~/.config/comegin/status-reader/aws-credentials`、600）に直接書く。
- 設定スクリプトの `next-js-prod`（段階 `operate`）が、このキーで `sts get-caller-identity` して主体を確かめる（`next-js-prod:principal` と同じ形の止まる id を足す）。段階 `operate` の `cloud` が見ている「有効なキーが 1 つだけ」の対象にもこのユーザーを足す。

### 6.2 メールでの知らせ（ユーザーの決定: メールで知らせる）

- 送り先は既存の SNS `comegin-ops-alert`（メールで購読済み。ハートビートのアラームと同じ受け口）。〔判断: 設計者〕
- 〔判断: 設計者〕送るとき:
  - 項目が **● 更新が必要** か **! 警告** に**新しくなった**とき（前回は違う状態だった）。同じ確認で複数あれば 1 通にまとめる。
  - ● か ! が残っているあいだ、**1 日 1 回、まとめのメール**（例 09:00 JST。残っている項目の一覧）。
  - **? 確かめられなかった**が 1 時間以上続いたとき（確認そのものが壊れていると、ずれがあっても黙ってしまうため）。
  - ✓ に戻ったときは送らない（翌日のまとめから消える）。◇ は送らない（常にあるため）。
- 件名は `[ComeGin 設定の状況]` で始め、本文には項目の見出し・段階・根拠・監視アプリのリンク（`<BETTER_AUTH_URL>/setup-status?step=P12`）を入れる。秘密値は入れない（5.1・6 の伏せ字を通す）。
- メールの送信に失敗しても、画面の表示と次の確認は止めない（サーバーのログに残し、画面にも「知らせを送れなかった」を出す）。
