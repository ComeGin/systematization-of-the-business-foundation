# AA-02 連携アーキテクチャ

AA（Application Architecture）層。ID は EA 共通用語集の定義をそのまま使う。

AA-01 で並べたアプリケーションの**間**を扱う。このファイルの目的は 2 つ。

- **いま何が繋がっていて、何が繋がっていないかを 1 枚の表で確定させる**（BA と DA が各所で「未配線」と書いてきた事実を、連携点の単位で棚卸しする）。
- **未配線・未着手の連携それぞれについて、どの手段で繋ぐかを決める**（3 節。これが次フェーズの着手リストになる）。

**状態が `実装済み` の連携は 4 本しかない。** 他はすべて `未配線` か `未着手` である。

## 1. 連携点カタログ

### 1.1 `実装済み` が 4 本しかないことの意味

I-01 から I-04 の 4 本以外はすべて未成立である。この 4 本の内訳は「Strapi から PostHog への一方向の通知 2 本」と「エージェントから 2 つの上流 API への呼び出し 2 本」であり、**訪問者に関わる連携が 1 本も無い**。

つまり現在の基盤は、**エージェントが操作できる道具は揃っているが、操作した結果が誰にも届かず、誰の反応も返ってこない**状態にある。AA-04 の再帰的自己改善ループが 1 周も回っていない直接の原因はここにある（入力となる I-05〜I-08 が 1 本も無い）。

### 1.2 冪等性を「要設計」とした 4 本

I-08 / I-11 / I-12 / I-18 の 4 本は、再実行で同じ操作が二重に起きる。とくに **I-08（フォーム送信）の二重実行は CVR を直接汚染する**（`E-09` が 2 件できると分子が 2 倍になる）。DA-02 が「CV の判定はクリックではなくフォーム送信完了」と定義した以上、送信完了の数え方が二重化すると KPI 全体が歪む。

対処の方針を 3 本に統一する。

- **email をキーにした統合を Mautic 側の既定にする**（同じ email の送信は既存コンタクトの更新になる。BA-04 の「作成または既存に統合」に対応）。
- **webhook の受け口（n8n）で重複排除する**。キーは `E-09` なら `contact_id` + イベント時刻、`E-10` なら `display_id` + メッセージ ID。
- **提案の起票（I-13）だけは冪等にする**。`proposal_id` が既に存在すれば起票しない（同じ観測から同じ提案が毎日起票され続けるのを防ぐ。AA-04 の暴走条件 2 への歯止め）。

### 1.3 露出経路の 2 分類（ngrok の常設トンネル）

**オンプレミス側への到達は ngrok の常設トンネルで行う**（`R1` の決定）。TA-01 が経路 4（公開サイトのブラウザからオンプレの観測系へ到達する手段）を未決定として残していたが、この決定がそれを解く。

前提として、オンプレのスタックはすべて `127.0.0.1` にバインドされている。したがって**クラウドに置かれた公開サイトのブラウザからは、Umami も Chatwoot も Mautic も到達できない**。この状態のままでは `CAP-10`（行動観測・効果測定）が成立せず、AA-04 のループに入力が発生しない。ngrok の常設トンネルはこの穴を塞ぐためのものであり、**「クラウドに展開するのは製品（Astro）のみ」という原則は保たれる**（新たに AWS へ展開するシステムは無い）。

固定ドメインの運用は既に始まっている（`frontend/verdant-virgo/astro.config.mjs` の `vite.server.allowedHosts` に `comegin-astro-dev.ngrok.app` がある）。新しい依存ではなく、既存の実践の延長として扱う。

露出する経路を 2 種類に分け、**同じトンネルに混ぜない**。

| 種別 | 誰が到達してよいか | 対象 | 該当する連携点 |
|---|---|---|---|
| **公開経路** | 無認証。全訪問者 | Umami のトラッカー配信とイベント受信、Chatwoot の Web ウィジェット、Mautic のフォーム受付とトラッキング、n8n の Webhook 受け口 | I-05 I-07 I-08 I-11 I-12 I-13 |
| **運用経路** | 運用者のみ。認証必須 | Strapi / Mautic / Chatwoot / Umami の各管理画面、n8n の UI、**エージェントが使う MCP サーバ** | I-03 I-04 I-16 I-17 |

**`I-21`（n8n → Amazon SNS）はこの 2 分類のどちらにも属さない。** 2 分類は「外から中への到達」を扱うものであり、`I-21` は**中から外への送信**にあたるため露出ではない（TA-01 の経路 10）。

分離する理由は 3 つ。

- **公開経路は当然に攻撃対象になる。** 管理画面が同じホスト名の下にあると、トラッカーの URL から管理画面の所在が推測できる。
- **エージェントの MCP は運用経路側である。** AA-03 の 2.3 で MCP を stdio 前提にしたため、**MCP は本来トンネルに載らない**（プロセス間通信でポートを使わない）。HTTP トランスポートで運用する場合のみ運用経路に現れ、そのときは固定 Bearer（`MCP_AUTH_TOKEN`）が唯一の防御になる。
- **BA-05 の `禁止` 分類（権限の付与・剥奪、アカウント操作）に到達できるのは運用経路だけ**である。公開経路からこの分類に届く導線を作らない。

**カタログの「発信元」列は、この 2 分類と対応している。** 発信元が `ブラウザ` の行（I-05〜I-08）は公開経路、発信元が `エージェント` の行（I-03 I-04 I-16 I-17）は運用経路。n8n が受ける Webhook（I-11 I-12）は発信元が上流システムだが、**到達のために公開経路を使う**（Mautic と Chatwoot はホスト内から n8n を叩けるので本来トンネルは不要だが、GitHub と GSC からの Webhook は公開経路を通る）。

### 1.4 ngrok を挟むことで新たに生じる制約

- **トンネルが落ちると観測が止まる。** ブラウザからの送信（I-05 I-06 I-07）は失敗しても黙って捨てる設計にしてあるため、**サイトは壊れないがデータだけが欠ける**。この欠測を「改善」と誤認しない歯止めが AA-04 の暴走条件 3 にあたる。トンネルの死活は `agent/ops-watcher` の監視対象に含める。
- **固定ドメインを使う**（無料の動的サブドメインだと、再起動のたびにトラッカーの URL が変わり、`Layout.astro` を書き換えることになる）。既に `comegin-astro-dev.ngrok.app` の実績がある。
- **URL を合わせる対象が複数ある。** `SITE_URL` / `N8N_WEBHOOK_URL` / `MCP_ALLOWED_HOSTS` / Vite の `allowedHosts`（`.claude/CLAUDE.md`）。1 つでもずれると連携が静かに失敗する。
- **PostHog だけはトンネルを通らない**（SaaS のためブラウザから直接到達する）。したがって **PostHog への送信だけはトンネルの死活に影響されない**。Umami と PostHog の数字が乖離する原因の 1 つになりうるので、乖離を調べるときは真っ先にトンネルの稼働時間を確認する。

## 2. 上流 API の落とし穴

エージェントが触る API の制約を、連携設計に効く形でまとめる。詳細は各 MCP の `README.md`（`backend/chatwoot-mcp/README.md`、`backend/mautic-mcp/README.md`）にある。

### 2.1 Chatwoot

| 落とし穴 | 連携設計への影響 |
|---|---|
| `Rack::Timeout` により 15 秒でリクエストを打ち切る | 期間の広いレポート・全文検索を 1 回で要求しない。観測の契約は月次より長い期間を 1 回で取らない（DA-02 の 5.2） |
| 起動直後の 1 回目が 500 になることがある | 3 秒待って 1 度だけ再試行する。再試行しても失敗したら `E-15 AgentRun` に `failure` として残し、その日の観測をスキップする |
| **ページ件数がサーバ側で固定**（会話 25 / コンタクト 15 / メッセージ 20 / 監査ログ 25） | クライアントから件数を増やせない。観測の契約には件数ではなく**ページ数の上限**を書く |
| 会話 ID は画面表示の `display_id`（内部 ID とは別） | 他システムに会話 ID を保存するときは必ず `display_id` を使う（後から人間が画面で照合できるようにするため） |
| チームを変更すると、そのチームに属さない担当者が自動的に外れる | `chatwoot_update_conversation` はチーム → 担当者の順に適用する。反映されなかった場合は警告が返るので、エージェントは警告を無視しない |
| 401 が「トークン不正」と「権限不足」の両方を意味する | 401 を一律に「認証の失敗」と解釈して再認証を試みない。権限不足の場合は再試行しても通らないため、その項目をスキップする設計にする |
| `api_access_token` が**ユーザーに紐づく** | 自動処理には専用のエージェントユーザーを作る。権限も操作履歴もそのユーザーのものになる（AA-03 の 2 節） |
| コンタクト一覧（検索なし）は email / 電話 / identifier のいずれかを持つものだけを返す | 「全コンタクト数」を一覧の件数から数えない |
| 会話一覧で `q`（本文検索）を指定すると `status` の絞り込みが無視される | 未解決の会話を本文検索で絞る、という組み合わせは成立しない |

### 2.2 Mautic

| 落とし穴 | 連携設計への影響 |
|---|---|
| **`PUT` は存在しない ID で新規作成してしまう** | **更新は `PATCH` 相当のみ。`mautic-mcp` は `PUT` を使うツールを 1 つも公開していない**（この制約に触れる経路をエージェントに与えない、という形で実装されている） |
| **`GET /api/smses/{id}/contact/{cid}/send` は GET でも SMS を送信する** | **`mautic-mcp` の対象外にしてある。** 参照系のつもりで呼んだ GET が外部に SMS を送るため、`sanitize()` でも `ACCESS_LEVEL` でも防げない（`read_only` でも参照系として登録されてしまえば呼べる）。**除外したこと自体が唯一の防御**であり、3 つ目の MCP サーバを作る場合も「GET だが副作用を持つ API」を同じ理由で除外する |
| 500 の主因は不正な `order_by` | 並び替えの指定はエージェントに自由入力させず、ツール側で許可値を限定する |
| 0 件のとき `[]` を返す（`null` ではない） | 空配列を「取得失敗」と誤認しない（失敗はエラーとして返る）。AA-04 の暴走条件 3 と対応する |
| OAuth2 client_credentials にはユーザーが紐づかない | 権限は Mautic 側のロールで決まる。参照専用のロールを割り当てる（DA-05 の 4.1） |
| メール送信・セグメント追加・キャンペーン追加などの操作系 API が対象外 | BA-05 が `承認` 分類にしているメール送信は、そもそも MCP ツールとして存在しない。**承認ゲート以前に手段が無い**状態になっている（AA-03 の 3 節で `agent/lead-ops` の権限を設計するときの前提） |

### 2.3 エージェントに触らせてはいけない API

上の 2 表のうち、**承認ゲートでは守れない 2 つ**を明示する。

- **Mautic の `PUT`。** 存在しない ID を渡すと更新のつもりで新規作成される。エージェントが ID を取り違えた場合、「更新が失敗した」ではなく「意図しないレコードが増えた」という形で失敗するため、失敗に気づけない。承認者が「このコンタクトを更新する」という提案を承認しても、実際に起きるのは別のことになりうる。**承認の対象と実行の結果が一致しない操作は、承認では守れない。**
- **Mautic の SMS 送信 API（GET）。** GET は参照であるという前提が破られており、`read_only` の `ACCESS_LEVEL` でも（ツールとして登録されていれば）呼べてしまう。BA-05 は「外部に露出する操作はすべて `承認`」としているが、この API は参照系の見た目をしているため分類の網から漏れる。

どちらも **MCP のツール一覧に載せない**ことで対処している。これは AA-03 の権限設計の原則（`ACCESS_LEVEL` は許可されないツールを登録しないことで実装する）と同じ形であり、**「危険な操作は分類するのではなく、到達できなくする」**という一貫した方針になっている。

## 3. 未配線・未着手の連携の実装方針

これが次フェーズの着手リストにあたる。手段は 5 択（Astro のインテグレーション / MCP ツールの直接呼び出し / n8n のワークフロー / Strapi のプラグイン・ライフサイクル / 手作業の設定）。

### 3.1 ブラウザ側トラッカー（I-05 I-06 I-07 I-08）

**手段: Astro のインテグレーション（`Layout.astro` へのスクリプト設置）＋ ngrok の公開経路。n8n も MCP も使わない。**

**4 本とも、到達先がオンプレか SaaS かで経路が分かれる。** Umami・Chatwoot・Mautic はオンプレにあるため **ngrok の固定ドメイン経由で到達する**（1.3）。PostHog だけが SaaS のためブラウザから直接到達する。したがって**トンネルが落ちると I-05 I-07 I-08 は止まり、I-06 だけが生き残る**。

| 連携 | 到達経路 | 実装方針 | 前提 |
|---|---|---|---|
| I-05 Umami | ngrok（公開経路） | `frontend/verdant-virgo/src/layouts/Layout.astro` に Umami のトラッキングスクリプトを直接置く。`src` とイベント送信先の両方を ngrok の固定ドメインにする。**同意の前でも送る**（cookie を置かず個人を識別しないため。DA-02 の 3 節） | Umami 側でサイトを登録し `websiteId` を得る ／ ngrok の常設トンネル |
| I-06 PostHog | **直接（SaaS）** | 同じ `Layout.astro` に `posthog-js` を置くが、**同意が取れるまで初期化しない**。`distinct_id` に email を入れない（DA-05 の 1.2）。セッションリプレイを有効にする場合は入力欄のマスキングを先に入れる | 同意取得 UI（DA-03 の未決定事項） |
| I-07 Chatwoot ウィジェット | ngrok（公開経路） | `website_token` を使った埋め込み。`sanitize()` の `NON_SECRET_KEYS` に `website_token` が入っているのは、この値が公開ページに埋め込まれる前提だから。ウィジェットのスクリプト配信元も ngrok の固定ドメインになる | Chatwoot 側で Web サイト受信箱を作成する ／ ngrok の常設トンネル |
| I-08 Mautic フォーム | ngrok（公開経路） | **Astro 側のフォームから Mautic の API を叩く**（BA-04 の未決定事項に対する AA の判断）。理由は 4 つ。(1) Mautic のフォーム埋め込みは外部スクリプトを読み込むため `CAP-09` の Lighthouse しきい値（SEO 1.0 / performance 0.9）に直接効く。(2) DA-03 が「hidden field に `distinct_id` と `umami_session_id` を載せる」ことを分母と分子を突合する唯一の接続点としており、自前のフォームのほうが制御できる。(3) 表示定義を Strapi 側の `E-06` に寄せる DA-01 の分割保持と整合する。(4) **ngrok を挟む構成では、埋め込みより自前のフォームのほうが失敗を扱いやすい**（トンネルが落ちたときに埋め込みは空白のまま黙って壊れるが、自前のフォームなら送信失敗を利用者に明示できる） | Mautic 側にフォームを作成し `mautic_form_id` を Strapi の `E-06` に記録する ／ ngrok の常設トンネル |

**`@astrojs/partytown` が導入済みで空回りしている**（DA-03 の 1.1）。トラッカーを載せる際に partytown 経由にするかは、Umami・PostHog それぞれの動作確認を経て決める（partytown は Web Worker にスクリプトを逃がすため、`document` に依存する処理が壊れることがある）。

### 3.2 Astro ← Strapi のデータ取得（I-09）

**手段: Astro のインテグレーション（ビルド時の fetch）。MCP は使わない。**

- Strapi の REST API をビルド時に呼び、`E-04` から記事ページを生成する。**MCP 経由にしない**（MCP はエージェントがモデル経由で使うための層であり、ビルドという決定論的な処理に挟むと `CHARACTER_LIMIT` による件数削減や `sanitize()` の省略が成果物に影響する）。
- `SITE_URL` 未設定のビルドは意図的に例外で停止する（`frontend/verdant-virgo/astro.config.mjs`）。この挙動は**変えない**（未設定だと sitemap と canonical に localhost が焼き込まれ、警告なく公開されるため）。
- Strapi が停止している状態でのビルドは**失敗させる**（記事 0 件のサイトが黙って公開されると、検索エンジンに空のサイトがインデックスされる）。

### 3.3 Webhook の受け口（I-11 I-12 I-18）

**手段: n8n のワークフロー。**

- Mautic・Chatwoot のどちらも webhook を送れるが、**受け口になるアプリケーションが n8n しか無い**（Astro は静的サイト、Strapi は自前の API を増やす必要がある）。
- **到達経路は 2 通りに分かれる。** Mautic と Chatwoot はホスト内にあるため n8n を直接叩ける（トンネル不要）。一方 **GitHub と Google Search Console からの webhook は ngrok の公開経路を通る**（`N8N_WEBHOOK_URL` を固定ドメインに合わせる）。n8n の UI 側は運用経路であり、**Webhook パスと UI を同じトンネルに混ぜない**（1.3）。
- n8n を経由させる理由は AA-05 の ADR-05 に書く。要点は「エージェントが直接ポーリングすると、実行のたびに取得範囲が変わって `E-12` が比較不能になる」こと。
- **n8n のワークフロー作成・変更は `承認` 分類**（BA-05）。ワークフロー自体が「承認なしで実行される操作の定義」になりうるため、エージェントが自分でワークフローを作って承認ゲートを迂回することを防ぐ。
- I-18（Mautic → PostHog の書き戻し）は**越境の可否が決まるまで実装しない**（DA-03 と DA-05 の未決定事項）。ワークフローを作れる状態にはしておくが、有効化しない。

### 3.4 提案の起票（I-13）と通知

**手段: エージェントがファイルを書き、n8n が搬送する。git 操作はエージェントが行わない。**

- エージェントは `docs/proposals/<proposal_id>.md` を**書くところまで**を担当する（AA-03 の 4 節。リポジトリのルールで状態変更系の git コマンドが使えないため）。
- コミットと PR 作成は人間、または明示的な指示を受けた場合に限る。n8n から GitHub API で起票する経路（I-13）を用意する場合も、**起票するのは提案であって承認ではない**（PR を作ることと PR を承認することは別の権限）。
- **通知は GitHub の PR の機能に任せる**（**`R1` の 2026-09-17 の決定**。DA-04 が未決定として残していた「通知先を Chatwoot にするか」を解決した）。`E-14 ApprovalRecord` の正本が PR のレビューである以上、**承認を求める通知も正本と同じ場所から出る**のが一貫する。Reviewer に `R2` を指定すれば、起票・レビュー依頼・マージ・クローズのいずれも GitHub の標準通知で届く。**通知のための連携点（旧 `I-14`）は設けない。**
- **Chatwoot を社内通知に使わない。** Chatwoot は「Web 接客 / チャット」であり（リポジトリルートの `README.md`）、顧客対応が用途である。改善提案の通知をここに置くと、`CAP-12` のレポート（未解決件数・応答時間）に内部の会話が混ざり、`E-10 Conversation` の正本も汚れる。加えて **`agent/conversation-triage` の取得範囲（直近の未解決の会話）が承認待ちの提案で埋まり、承認の滞留がそのまま顧客対応の見落としに変換される**（AA-03 の 3 節の取得範囲と衝突する）。
- **ただし `private` を固定する規則は残す。** `agent/conversation-triage` が会話の一次切り分けで書く社内メモ（`I-03`。**これは顧客対応の中の社内メモであり、用途として正しい**）では、**`private` を固定値 `true` とし、エージェントが指定できるパラメータにしない**。**`private=false` は顧客に即時送信される**ため、誤って顧客に送る事故が構造的に起きない形を維持する。

### 3.5 Google Search Console（I-15）

**手段: 手作業の設定 → その後 n8n のワークフロー。**

1. サイトの公開 URL を確定させる（`CAP-08` のホスティング先が未選定のため、ここで止まっている）。
2. Google Search Console にサイトを登録し、所有権を確認する（**人間の作業。エージェントは行えない**）。
3. Search Console API の認証情報を発行し、n8n の資格情報として登録する（秘密値のため環境変数ファイルの実体には置かず、n8n の資格情報ストアに入れる）。
4. 日次バッチで `E-12`（`source: gsc`）として取り込む。**ただし GSC のデータは 2〜3 日遅れて確定する**ため、他の観測と同じ日次サイクルに混ぜると「昨日のデータが無い」が常態化する（DA-04 の未決定事項）。取り込みは「3 日前までの確定データ」を対象にする。

**SEO が事業の目的でありながら、検索順位を測る手段が 1 つも無い。** この矛盾の扱いは AA-05 の ADR-06 で正面から記述する。

### 3.6 通知（I-21）

**手段: n8n のワークフローから Amazon SNS に発行する。本番は SNS、開発は MailHog。**

**`R1` の 2026-09-17 の決定。** 顧客からの要求（Mautic のフォーム送信・Chatwoot の会話開始）と、監視の検知を、**運用者のメールアドレスへ通知する**。

| 項目 | 値 |
|---|---|
| トピック | **2 本に分ける。** `comegin-lead-alert`（顧客からの要求）／ `comegin-ops-alert`（監視・障害） |
| リージョン | `ap-northeast-1`（東京）。**越境しない** |
| 宛先 | トピックごとの Email サブスクリプション（購読は**受信者の手作業**で確認する） |
| 開発環境 | MailHog（`backend/mautic-system` の 1025 / 8025）。SNS は使わない |
| 載せる範囲 | **種別・会社名・各システムの ID・流入記事・受付時刻のみ**。email・氏名・本文は載せない（DA-05 の 1.3） |
| 料金 | 月 1,000 通まで無料。超過分は $2.00/100,000 通。**CV が月 100 件規模なら $0** |

トピックを 2 本に分ける理由は 3 つ。

- **宛先を分けられる**（購読はトピック単位のため、1 本にまとめると宛先も 1 つになる）。
- **緊急度が違う。** リード通知は営業時間内に見れば足りるが、障害通知は即時性を要する。
- **無料枠の消費が読める。** 監視通知を「状態が変わったときだけ」に絞らないと、リード通知の枠まで食い潰す。

**エージェントは `I-21` を起動しない。** 通知の発行は n8n のワークフローが行い、その起動条件は n8n 側にある（`I-13` と同じ扱い。AA-03 の 5.2）。

**n8n に渡す IAM 権限は `sns:Publish` のみとし、対象トピックを限定する。** `sns:Subscribe` や `sns:SetTopicAttributes` を与えると、**n8n が通知先を自分で書き換えられる＝自分への通知を止められる**（AA-03 の「エージェントは自分の実行条件を変更できない」と同じ形の穴になる）。設計は TA-04。

### 3.7 デプロイ（I-20）

**手段: 未定（TA の判断事項）。**

- `CAP-08` のホスティング先が未選定のため設計できない。
- 決まっている制約は 2 つ。デプロイは `承認` 分類（BA-05）であり、リポジトリのルールとして明確な指示なくデプロイコマンドを実行しない（`.claude/rules/build-deploy.md`）。
- `.github/workflows/` は明確な指示がない限り作成しない（`.claude/rules/devops-testing.md`）ため、**CI によるデプロイの自動化は現時点で選択肢に入らない**。

## 4. 着手順の提案

3 節の方針を、依存の少ない順に並べる。BA-01 の「測定可能化の順序」と整合させている。

| 順 | 連携 | 依存 | これが通ると何ができるか |
|---|---|---|---|
| **0** | **ngrok の常設トンネル（公開経路）** | 固定ドメインの確保 | **1・4 の前提。これが無いとオンプレの観測系にブラウザから到達できない** |
| 1 | I-05（Umami トラッカー） | **0** | `SESSION-count` が測れる。CVR の分母が立つ |
| 2 | I-09（Astro ← Strapi） | Strapi に記事があること | 記事ページが公開でき、観測の対象が生まれる |
| 3 | I-10（Lighthouse CI の蓄積） | I-09 | `E-12` が継続的に溜まり、`CAP-09` の定点観測が成立する |
| 4 | I-08（CTA フォーム） | **0**、I-09、Mautic のフォーム作成 | `CV 数` と `CVR` が測れる。KPI ツリーの中段が埋まる |
| 5 | I-06（PostHog トラッカー） | 同意取得 UI（**0 には依存しない**。PostHog は SaaS のため直接到達する） | `CTR-cta`・ファネル・AB テストが測れる |
| 6 | I-15（GSC） | 公開 URL の確定 | `平均検索順位` が測れる。SEO の目的に対する測定が初めて成立する |
| 7 | I-11 I-12（webhook → n8n） | n8n のワークフロー作成（`承認` が必要）。外部からの受信は **0** | 観測の日次バッチと通知が自動化できる |
| 8 | I-13（提案の起票） | `docs/proposals/` の作成 | ループが 1 周する（AA-04 の 5 節） |
| **9** | **I-21（通知）** | 7（`I-11` `I-12` が n8n に届くこと）／ SNS のトピック作成と購読の確認（**人間の作業**） | **顧客からの要求に気づけるようになる。** BA-04 のトスアップ条件の「通知」が初めて成立する |

**手順 0（ngrok）が、観測系のほぼすべての前提になった。** オンプレのスタックが `127.0.0.1` バインドである以上、ブラウザ側の連携は 1 本残らずトンネルに依存する（例外は SaaS の PostHog だけ）。

**ただし 2 と 3 は 0 に依存しない。** Astro ← Strapi のビルド時取得も Lighthouse CI の計測も、同一ホスト内で完結する。**この性質が、AA-04 の最短経路（Lighthouse だけでループを 1 周させる）を成り立たせている。**

## 5. 未決定事項

- **同意取得（consent management）の実装手段。** I-06 の前提だが、DA-03 が未決定として残している。Astro のコンポーネントとして自作するか、外部のライブラリを使うかで `CAP-09` の Lighthouse スコアへの影響が変わる。
- **I-08 の二重送信対策の具体。** email をキーにした統合で吸収する方針は決めたが、同一 email から短時間に複数回送信された場合にポイントを何回加算するか（BA-04 のトスアップ条件は 1 回の送信につき加算する前提で書かれている）が決まっていない。実データが無いため妥当な窓幅を決められない。
- **ngrok の公開経路をドメインごとに分けるか、パスで分けるか。** 1.3 で「公開経路と運用経路を同じトンネルに混ぜない」と決めたが、固定ドメインを 2 本取るのか、1 本のドメインをパスで分けるのかは決めていない（後者だと、パスの推測で運用経路に到達できる余地が残る）。TA の公開面の設計に依存する。
- **ngrok のトンネルの死活監視と、落ちたときの扱い。** `agent/ops-watcher` の監視対象に含める方針は決めたが、落ちている間の観測欠損を `E-12` にどう記録するか（欠測として明示するのか、その日の観測自体を作らないのか）が未定。AA-04 の暴走条件 3 に直結する。
- **`SITE_URL` / `N8N_WEBHOOK_URL` / `MCP_ALLOWED_HOSTS` / Vite の `allowedHosts` を揃える手順。** 1 つでもずれると連携が静かに失敗する。ngrok の固定ドメインが確定した時点で、これらを 1 か所から生成する仕組みが要るかどうかを TA と決める。
- **I-16 I-17（管理外の MCP）を使い続けるか。** **AA-05 の ADR-07 に集約した**（リポジトリの `ACCESS_LEVEL` と `sanitize()` の保証が及ばない経路が存在する、というガバナンス上の穴）。`CAP-04` の実務がこの経路に依存しているため、エージェント設計（AA-03）では「書き込みを任せない」前提で組んでいる。前提が変われば AA-03 の権限表も変わる。
- **`E-15 AgentRun` の正本。** DA-01 が n8n の実行履歴を候補としつつ「n8n を経由しないエージェント実行が記録されない」ため不完全だと残している。AA-03 の編成では Claude Code から直接走るエージェントが大半のため、**このままだと `E-15` の大半が記録されない**。AA としても解決できず、TA の監視設計を待つ。
