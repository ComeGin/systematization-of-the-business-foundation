# AA-04 再帰的自己改善ループの制御仕様

AA（Application Architecture）層。ID は EA 共通用語集の定義をそのまま使う。

BA-01 は「この基盤が最適化する対象は、**観測してから改善が作用するまでの一巡に要する時間と人手**である」と定めた。その一巡が本ファイルの対象であり、`CAP-14`（改善提案の生成と承認）の実行仕様にあたる。

**先に結論を書く。このループは現在 1 周も回っていない**（5 節。観測側の入力が無く、`docs/proposals/` も承認機構も存在しない）。以下の 1〜4 節は To-Be の設計であり、5 節で最初の 1 周に必要な最小構成を示す。

## 1. ループの制御仕様

```mermaid
sequenceDiagram
    participant MON as 監視アプリ<br/>定期実行
    participant OBS as 観測基盤<br/>OpenSEO / Umami / PostHog / LHCI
    participant AG as 観測エージェント<br/>seo-auditor 他 3 本
    participant PW as agent/proposal-writer
    participant R2 as R2 SEO ディレクター<br/>人間ゲート
    participant ACT as 作用先<br/>本番
    MON->>AG: 日次で起動（取得範囲は定義に固定）
    AG->>OBS: 観測データを取得
    OBS-->>AG: 計測値と ref
    AG->>AG: E-12 を docs/audits/ に書く
    MON->>PW: 観測の完了後に起動
    PW->>AG: E-12 を読む
    PW->>PW: E-13 を docs/proposals/ に起票（draft）
    Note over PW,R2: エージェントはコミットも PR も作れない
    R2->>R2: コミットして PR を作る
    alt 承認
        R2->>R2: PR をレビュー承認（E-14）
        R2->>ACT: 本番に作用（applied_at を記録）
        ACT->>OBS: 変更が観測対象に反映される
    else 却下
        R2->>PW: rejected のまま残す
    end
    Note over OBS,ACT: judge_after まで待ってから検証
    AG->>OBS: 検証のため再計測
    AG->>PW: verification を書き戻す
```

**As-Is 注記。** この図で実際に流れているメッセージは **1 本もない**。監視アプリは雛形のみで定期実行の仕組みが無い（TA-07）。`AG->>OBS` の観測取得は、Lighthouse CI の結果がローカルのファイルに出ているだけで、それを `E-12` として読み取るエージェントが存在しない。GSC は OpenSEO への統合を決めたが未接続（ADR-06）、Umami と PostHog は訪問者のデータが 0 件。`docs/audits/` も `docs/proposals/` も未作成。`R2` の承認機構（PR レビュー）は仕組みとしては GitHub に既にあるが、レビュー対象となる PR が 1 件も存在しない。

図の中の 2 つの `Note` が、このループの設計上の要点にあたる。

- **「エージェントはコミットも PR も作れない」**（AA-03 の 5 節）。ループの中に必ず人間の手作業が 1 回入る。これは効率の問題ではなく、**閉路を切るための構造**である。
- **「`judge_after` まで待ってから検証」**（DA-04 の 4 節）。観測は日次、判定は 30 日後という非対称は意図的（早い判定が最も壊しやすい）。

**ループの起動元は監視アプリである**（`R1` の 2026-09-19 の決定。AA-05 の ADR-17、TA-07 の 3.5）。ADR-05 は日次のスケジュール起動を n8n に置いていたが、ADR-16 で n8n が AWS に移り、ローカルの Claude Code を起動できなくなった。**観測の日次バッチ・`I-13` の起票・公開された記事の確認・誤った書き込みの突き合わせは、監視アプリのスケジュールから起動する。** 取得の範囲はスケジュールの定義に固定し、エージェントに判断させない（ADR-05 の理由を監視アプリの側で守る）。**開発機が止まると、ループも止まる**（本番のサービスと n8n の決定論的な処理は止まらない）。止まったことはハートビートで知る（TA-07 の 8 節）。

**ループの観測元も作用先も本番である**（`R1` の 2026-09-19 の決定。AA-05 の ADR-15、TA-07。同日の ADR-14 の「作用先は開発環境」を置き換えた）。エージェントは監視アプリから起動され、MCP で本番の Strapi・Mautic・Chatwoot・Umami・n8n を読み書きする（本番は `read_write` まで。Strapi・n8n は ADR-16 で加わった）。記事は本番の Strapi（正本。ADR-16）に**下書きとして**書き、**公開は `R2` が本番の管理画面で行う**（ADR-17。`strapi-prod` のトークンに公開の権限が無い）。サイトはローカルのコードを更新して、本番の Strapi を読んでビルドし、**配信は人間が承認する**（ADR-15 の時点では記事の正本はオンプレの Strapi だった）。n8n のワークフローは `n8n-prod` で本番に置き、**有効化は人間が行う**。**`E-13` を `applied` にするのは本番に作用した時点**（Mautic・Chatwoot は MCP での書き込みの完了、Astro と Strapi の記事は承認後の配信の完了、n8n は有効化の完了）で、**`applied_at` は作用させた主体が記録する**（配信と有効化は実行した人間、MCP での書き込みは Claude Code。ADR-16、TA-07 の 6 節）。図の `R2->>ACT` は、この「人間の承認を経た作用」をまとめて描いている。記事の場合は、**`R2` が管理画面で公開 → 監視アプリの定期実行が公開を見つけて Claude Code がビルドと計測 → 人間が配信 → 配信した人間が `applied_at` を記録**、という 2 段階の人間の操作になる（ADR-17、TA-07 の 7 節）。

### 2.1 ステップ間で守る不変条件

- **`E-13` を経由しない変更を作らない。** 観測（`E-12`）から作用（`E-04` 他）に至る経路は `E-13` だけである（DA-01 の 6 節）。この型を通らない変更は例外として DA-05 の監査対象になる。
- **`evidence[]` が空の提案は承認しない**（DA-01 の 6.2）。根拠の無い提案は、承認者が妥当性を判断できない。
- **`E-12` は値を複製せず `ref` と `summary` だけを `E-13` に転記する**（DA-04 の 2 節）。元データが更新されたときに矛盾しないようにするため。
- **`E-05 Page` は直接書き換えられない。** 作用は必ず `E-04` かコードのどちらかを変えて再ビルドする経路を通る（DA-04 の 1.3）。適用手順には `SITE_URL` の設定を必ず含める。
- **ステップ 4 の `review` → `approved` の遷移だけは、エージェントが実行できない**（DA-01 の 6.3）。AA-03 の 5 節のとおり、これは権限設定ではなく実行手段の欠落として実装されている。

### 2.2 ステップ 5（作用）の自動化の範囲

DA-04 が未決定として残した「作用の自動適用をどこまで許すか」に、AA としての線を引く。基準は BA-05 の承認ゲートの 3 つの問い（外部に露出するか / 取り消せるか / エージェント自身の権限・実行条件を変えるか）。

| `change.kind` | 承認後の適用の主体 | 理由 |
|---|---|---|
| `content_rewrite` | エージェント（`agent/content-writer`）が下書きを更新し、**公開は `R2` が本番の管理画面で自ら行い（ADR-17）、配信も人間が行う** | 下書きの更新は取り消せる。公開は外部に露出する。**エージェントのトークンに公開の権限が無い**ため、公開の承認は仕組みで守られる |
| `cta_swap` | エージェントが `E-06` の表示定義を更新し、**ビルドとデプロイは `R1`** | 表示定義の変更は取り消せるが、公開には露出が伴う |
| `internal_link` | 同上 | 同上 |
| `technical_seo` | **マージまでは人間（`R1`）。マージ後の配信も人間が承認して行う**（ADR-15） | コード変更はエージェントがコミットできないためマージまでは人間。当初はマージ後のデプロイを自動化してよいとしていた（2.3） |
| `experiment_start` | **人間（`R3`）** | 実ユーザーに異なる体験を出す（BA-05 の `承認`） |
| `config_change` | **人間（`R1`）** | 設定変更は影響範囲が読みにくく、`禁止` 分類に隣接する（権限・実行条件に触れる可能性がある） |

**公開・実験開始の瞬間には必ず人間が居る。** エージェントが単独で完結できるのは「下書きと定義の更新」までである。**記事の公開については、ADR-17 でこれが約束ではなく仕組みになった**（`strapi-prod` のトークンに公開の権限が無く、公開の操作そのものを `R2` が行う）。

**ADR-16 により、上表の「エージェント」の書き込み先は、Strapi・Mautic・Chatwoot は本番（MCP の本番用の登録。Strapi は `strapi-prod` で、本番の Strapi が正本）、コードはローカルになる。** ADR-15 の時点では Strapi はオンプレ（正本）だった。ADR-14 で一度加えた「開発環境から本番の Strapi への反映」（`strapi transfer` など）は、ADR-15 で Strapi をオンプレだけに戻したことで不要になり、ADR-16 で本番に Strapi を戻した後も、記事を本番にだけ書くため不要のままである。公開サイトへの反映は、ADR-15・ADR-16 の時点では、この表の「公開は `R2`」を配信の承認として行うとしていた。**ADR-17 で「公開は `R2`」は 2 段階になった。** `R2` が本番の Strapi の管理画面で記事を公開し、監視アプリの定期実行がそれを見つけて Claude Code がビルドと計測を行い、人間が配信する（TA-07 の 7 節）。**設定の変更（`config_change`）は、開発用の登録で確かめてから `-prod` の登録で本番に適用する**（ADR-16 の「そろえ続ける」。TA-07 の 6.1）。

### 2.3 デプロイだけは承認ゲートがあっても自動化してよい（ADR-15 で変更）

**（2026-09-19 に ADR-15 で変更）配信は人間が承認して実行することになり、この節の「マージ後のデプロイは自動化してよい」は成り立たなくなった**（TA-03 の同じ整理も ADR-15 で改めた）。ADR-17 で記事の公開も `R2` の操作になり、記事では「公開」と「配信」の 2 回、人間が操作する。下の理由（2 度目の承認を求めると 1 度目の判断が雑になる）は懸念として残るため、マージや公開の承認と配信の承認を 1 回にまとめる方法は TA-03 の 7 節で決める。以下は当初の整理として残す。

BA-05 は「本番環境へのデプロイ」を `承認`（承認者 `R1`）に分類している。しかし **TA-03 の決定に従い、マージ後のデプロイは自動化してよい**。矛盾ではない。

理由は**承認の対象が「デプロイという操作」ではなく「デプロイされる内容 ＝ `main` の状態」だから**である。`main` へのマージ自体が `承認` 分類であり（`R1` が承認する）、その承認をもって「この内容を公開してよい」という判断は済んでいる。同じ内容に対して 2 度目の承認を求めると、**1 度目の判断まで雑になる**（「あとでデプロイのときにもう一度見るから」という逃げ道ができる）。

この整理は、BA-05 の分類基準の第 1 問（外部に露出するか）に照らしても一貫している。露出を決めているのはマージであって、デプロイはその決定を実行に移すだけの手続きである。

**ただし `LH-seo` のゲート（3.2）はデプロイの前後どちらにも効く。** マージが承認されていても、SEO スコアが 1.0 を割った状態のビルドは配信しない。

## 3. 安全装置

このループは自分自身を書き換える性質を持つため、安全装置は運用の約束ではなく**設計事項**として固定する。以下 7 項目は、効率化の名目で外さない。

### 3.1 1 サイクルあたりの変更上限

**同時に `applied` 状態にできる `E-13` は 3 件まで。同じ `target.identifier` に対しては 1 件まで。**

| 上限 | 値 | 理由 |
|---|---|---|
| 1 サイクル（月次）に適用してよい提案の数 | **3 件** | 4 件以上を同時に適用すると、次の観測で指標が動いたときにどの提案が効いたのかを分離できない（`expectation.metric` による判定が成立しない） |
| 同じ `target.identifier` に同時適用してよい数 | **1 件** | 同じページに 2 つの変更を入れると、効果の帰属が不可能になる |
| 1 日に起票してよい `E-13` の数 | **5 件** | 起票は `自律` だが、`R2` の承認待ち行列が伸びると承認が形式的な追認に退化する（BA-03 の「`R2` が承認できる量を超える生成は行わない」の定量化） |

上限に達した場合、`agent/proposal-writer` は起票を**止める**（キューに積まない）。積むと、承認が滞ったときに古い観測に基づく提案が後から適用される。

### 3.2 Lighthouse の SEO スコアが 1.0 を割ったら止める

**`LH-seo` が 1.0 未満になった時点で、ループの作用（ステップ 5）を全面的に停止する。**

- しきい値は `frontend/verdant-virgo/lighthouserc.cjs` に定義されており、`pnpm lh` は未達でコマンドが失敗する。**この失敗を無視して適用を続けない。**
- SEO が 1.0 の死守ラインであるのは、SEO 対策がこの計測の目的そのものだから（`.claude/CLAUDE.md`）。performance / accessibility / best-practices の 0.9 は目標値だが、SEO の 1.0 は**前提条件**である。
- 停止中にできるのは「`LH-seo` を 1.0 に戻す提案」だけ。それ以外の `change.kind` の適用を再開しない。
- 停止は `agent/seo-auditor` が検知し、`agent/proposal-writer` が起票を絞る。**検知するエージェントと止めるエージェントが同じにならないようにする**（自分で検知して自分で判断すると、検知の基準ごと緩められる余地が生まれる）。

### 3.3 ロールバック手順を必須項目にする

DA-01 の 6.2 は `rollback.procedure` / `rollback.reversible` / `rollback.deadline` を**必須**とし、`rollback.procedure` の欠落を「最も重い欠落」と書いている。AA としてこれを次の形で運用する。

- **`rollback.procedure` に具体を書く**（コマンド・PR 番号・版番号まで。「元に戻す」では不可）。
- **`rollback.reversible: false` の提案は `risk.level` を `high` として扱う**（DA-01 の 6.2）。不可逆な変更を通常の承認で通さない。
- **`verification.state` が `degraded` なら `rollback.procedure` を実行して `rolled_back` に落とす。** `no_change` の場合は戻さず、効果が無かったという事実を次の提案の `evidence` として残す。
- **`rollback.deadline` を過ぎた提案は、ロールバックできない前提で扱う。** 期日を過ぎた `applied` を放置しない（期日前に必ず検証する、が原則）。

#### 3.3.1 Git の外にある適用先は戻せない（この設計の最大の穴）

**`E-13` が Git にあることは、適用先も Git にあることを意味しない。** ADR-04 で「履歴・差し戻し・取り消しを Git が既に持っている」と書いたが、それが成立するのは**適用先が Git 管理下のファイルである場合に限る**。TA が指摘したとおり、次の 4 つは Git の外に実体があり、**PR を revert しても元に戻らない**（4 つ目の OpenSEO は 2026-09-18 に追加）。

| 適用先 | なぜ戻せないか | 優先度 |
|---|---|---|
| **n8n のワークフロー** | 実体は n8n の DB（本番は RDS。ADR-16）にあり、Git には存在しない。PR を revert しても稼働中のワークフローは動き続ける。**加えてワークフローは「承認なしで実行される操作の定義」であるため、戻せないことの影響が他の 2 つより大きい**（BA-05） | **最高** |
| Mautic のキャンペーン定義 | 実体は Mautic の MySQL にある。キャンペーンを開始すると、既に投入されたコンタクトは定義を戻しても元の状態に戻らない | 高 |
| PostHog の設定（feature flag・実験・保持期間） | 実体は SaaS 側にある。加えて**外部リージョンにあるため、こちらから状態を完全には把握できない** | 中 |
| **OpenSEO の設定（ランク追跡の対象とスケジュール）** | 実体は OpenSEO の DB にある。**設定を戻しても、その間に発生した DataForSEO の支出は戻らない** | 中 |

対処を 4 つ定める。

- **この 4 つを対象とする `E-13` は `rollback.reversible: false` を既定にする。** DA-01 の規定により、`false` の提案は `risk.level` が `high` として扱われる。**「Git にあるから戻せる」という思い込みで `true` を書かない。**
- **`rollback.procedure` に「Git の操作」を書かない。** 「PR #128 を revert する」では戻らない。**適用先の側で何をするかを具体的に書く**（「n8n のワークフロー `wf-daily-audit` を無効化し、バージョン履歴から版 3 に `restore` する」など）。n8n はワークフローのバージョン履歴を持つため、**適用前の版番号を `E-13` に記録しておく**ことを必須にする。
- **適用前の状態を `E-13` に添付する。** n8n はワークフローの JSON、Mautic はキャンペーンの定義、PostHog は flag の設定、OpenSEO はランク追跡の対象キーワードと頻度。**Git の外にあるものは、Git の中にコピーを取ってから触る**（これが唯一の「戻す手段」になる）。コピーは提案の一部であり、秘匿値を含む場合は含めない。
- **n8n のワークフローに対する `E-13` は、1 サイクルに 1 件までとする**（3.1 の上限より厳しい）。戻せない変更を同時に 2 つ入れない。
- **（ADR-16）本番の n8n への適用は 2 段に分ける。** エージェントは `n8n-prod` でワークフローを置く（作成と更新）までで、**有効化は人間（`R1`）が本番のエディターで行う**（BA-05 の `承認`）。置いただけのワークフローは動かないため、有効化の前に適用前の版番号と JSON を `E-13` に記録できる。

**この穴は ADR-04 の前提の限界にあたる。** Git を正本にしたことで得られたのは「提案と承認の履歴が残り、エージェントが書き換えられない」ことであって、「作用が必ず取り消せる」ことではない。**2 つを混同しない。**

### 3.4 承認を要する変更種別

BA-05 の承認ゲート一覧と**完全に一致させる**。ループの中で起きうる操作だけを抜き出した。

| 操作 | 分類 | 承認者 |
|---|---|---|
| 記事の下書き作成・更新（`publishedAt` を設定しない） | `自律` | — |
| 記事の公開・公開済み記事の更新 | `承認`（**実行は人間**。`R2` が本番の管理画面で自ら行う。ADR-17） | `R2` |
| 記事の削除・非公開化 | `承認`（**実行は人間**。ADR-17） | `R2` |
| 観測データの参照・集計・レポート生成 | `自律` | — |
| 改善提案（`E-13`）の生成 | `自律` | — |
| 改善提案の採用と適用 | `承認` | `R2` |
| AB テスト（`E-11`）の開始 | `承認` | `R3` |
| AB テストの停止 | `自律` | — |
| Chatwoot の社内メモの作成（`private=true`。社内メモ専用のツールか登録で行う。ADR-17） | `自律` | — |
| Chatwoot の顧客への返信（`private=false`） | `承認` | `R3` |
| Mautic のコンタクト作成・セグメント追加・スコア加算 | `自律` | — |
| Mautic からのメール送信・キャンペーン開始 | `承認` | `R3` |
| Mautic / Chatwoot のレコード削除 | `承認` | `R1` |
| Lighthouse CI の計測実行 | `自律` | — |
| コードの変更提案（ブランチ作成・PR の作成） | `自律` | — |
| コードの main へのマージ | `承認` | `R1` |
| 本番環境へのデプロイ | `承認` | `R1` |
| n8n ワークフローの新規作成・変更 | `承認` | `R1` |
| n8n のワークフローの本番での有効化 | `承認` | `R1` |
| OpenSEO の参照（費用の発生しないもの） | `自律` | — |
| OpenSEO の調査（1 回の見積もりが 2,000 クレジット以下） | `自律` | — |
| OpenSEO の調査（1 回の見積もりが 2,000 クレジット超） | `承認` | `R2` |
| ランク追跡の作成・対象キーワードの追加・スケジュールの設定 | `承認` | `R2` |
| ランク追跡のスケジュールの停止 | `自律` | — |
| OpenSEO のサイト監査（自サイト以外） | **`禁止`** | — |
| GSC / GA4 の OAuth 接続・切断 | **`禁止`** | — |
| DataForSEO の残高のチャージ・月次予算の変更 | **`禁止`** | — |
| 権限の付与・剥奪、`ACCESS_LEVEL` の変更、アカウント操作 | **`禁止`** | — |
| 認証情報・秘密値の閲覧 | **`禁止`** | — |
| 暗号化キーの変更（`N8N_ENCRYPTION_KEY`、`ACTIVE_RECORD_ENCRYPTION_*`） | **`禁止`** | — |

この表は BA-05 の再掲であり、**AA が追加・削除・分類変更をしたものは 1 件も無い**（OpenSEO の行は 2026-09-18 に、n8n の有効化の行は 2026-09-19 に ADR-16 で BA-05 へ追加したものの再掲。記事の公開・削除の「実行は人間」と社内メモの注記は、同日の ADR-17 で BA-05 に加えたものの再掲）。ループの実装がこの表から逸れていないかを、監査の際にこの 1 表で照合できるようにするために置いている。

なお `自律` の「コードの変更提案（ブランチ作成・PR の作成）」は、AA-03 の 5 節のとおり**エージェントには実行手段が無い**。分類上は `自律` だが、実行主体は人間になる（分類を緩める根拠には使わない）。

### 3.5 エージェントが自分の権限・実行条件を変更できないこと

BA-05 の `禁止` 分類を、ループの中で担保する。

| 対象 | 担保の仕組み | 種別 |
|---|---|---|
| MCP の `ACCESS_LEVEL` | 環境変数ファイルにあり、`PreToolUse` フックが読み書きをハード拒否する | 到達不能 |
| 上流 API のトークン | 同上 | 到達不能 |
| エージェントの指示・ルール（`.claude/` 配下） | ファイルは編集できるが、コミットできない（`.claude/rules/git.md`） | 到達不能に近い（人間のレビューを必ず経る） |
| n8n のワークフロー | 作成・変更が `承認` 分類。ワークフローは「承認なしで実行される操作の定義」になりうる | 承認 |
| 暗号化キー | `禁止`。変更はデータの喪失と同義として扱う（DA-05 の 4.3） | 承認でも通さない |
| **使える費用（DataForSEO の前払い残高・月次予算）** | チャージは DataForSEO のアカウント所有者（`R1`）だけが行える。エージェントにはアカウントも API の資格情報も渡さない（資格情報は OpenSEO の環境変数にあり、`PreToolUse` フックが読み書きを拒否する） | 到達不能 |
| OpenSEO のツールの許可リスト | エージェント定義（`.claude/agents/`）にあり、編集できてもコミットできない（AA-03 の 2.4・5.3） | 到達不能に近い |
| 安全装置の数値（3.1 の上限、3.2 のしきい値） | **`E-13` の `change.kind` が `config_change` に該当し、適用は `R1`** | 承認 |
| **定期実行の定義（起動の頻度・取得の範囲・使うエージェントとツール。ADR-17）** | **Git で持つ**（AA-05 の ADR-18 の追加の決定 3。TA-07 の 3.5）。**監視アプリは承認済みの `main` から作った別のチェックアウトで読む**。エージェントは作業ツリーで定義を書き換えて PR を作れるが、**PR が承認されて `main` に入るまで次の実行には効かない**。定義の変更は必ず PR を通す（`E-14` の承認と同じ経路。BA-05 の `承認`・`R1`）。ADR-18 の反映では「置き場所が未決定で、エージェントが編集できるファイルに置くと、監視アプリがそれを読む限りコミットを経ずに次の実行に効く」としていた | **承認**（`.claude/` 配下と同じく、人間のレビューを必ず経る。エージェントが `main` にマージできないことが前提。TA-04 の 9 節） |
| **エージェントの実行記録（`E-15` の正本。ADR-18）** | 監視アプリのローカルの DB にある。**書くのは監視アプリのサーバー側だけで、エージェントには書かせない**（TA-07 の 3.6）。ただしエージェントも同じ開発機で動き、ファイルを編集できるため、DB のファイルに直接届かないことの担保が要る。**記録は S3 に追記専用で写す**（ADR-18 の追加の決定 5。写しを書く資格情報は監視アプリのサーバー側だけに置き、削除の権限を持たせない）ため、ローカルの記録が書き換えられても、写した分は消せない | **到達不能にする**（ローカルの手段は未決定。6 節）。**S3 の写しは追記だけ**（TA-06 の 4.7） |

**「安全装置の数値」の行が重要である**（旧版ではこの行が表の最後だった）。安全装置そのものを緩める提案も `E-13` として起票できてしまう（起票は `自律`）。したがって「上限を 3 件から 10 件に上げる」という提案は、形式上は正当な提案として承認待ちに並ぶ。これを防ぐ手段は 2 つ。

- **`change.kind: config_change` の承認者を `R1` にする**（`R2` ではない）。提案を出す Capability（`CAP-14`、`R2`）と、安全装置を変える承認者（`R1`）を分離する。
- **安全装置に関わる値を変える提案は、`evidence[]` に「安全装置が実際に妨げになった事例」を含めることを必須にする。** 「速くしたい」だけの提案を通さない。

### 3.6 検知と判断を同じエージェントに持たせない

3.2 で述べた分離を一般化する。**観測エージェント（`E-12` を作る 4 本）と、提案エージェント（`E-13` を作る 1 本）を分けている**のは、この理由による。

観測と判断が同じ主体だと、「観測の閾値を自分の判断に都合よく調整する」経路が生まれる。分けておけば、`agent/proposal-writer` が読むのは `docs/audits/` に書かれた既成の `E-12` だけになり、観測そのものは書き換えられない。

### 3.7 提案の重複起票を検出する

`agent/proposal-writer` は起票の前に、**同じ `target.identifier` かつ同じ `change.kind` の `E-13` が既に存在しないか**を確認する。存在する場合は起票しない。

- `rejected` の提案も削除せず残すのは、この検出のため（DA-01 の 6.3）。一度却下された提案が翌日また起票されると、承認者が同じ判断を繰り返すことになる。
- `no_change` で終わった提案も残す（同じ施策を再び提案しないため）。

## 4. ループが暴走する条件と歯止め

暴走とは「ループが回り続けているのに、基盤が良くなっていない、または悪くなっている」状態を指す。検出できる形で列挙し、それぞれに歯止めを対応させる。

| # | 暴走の条件 | 何が起きるか | 歯止め |
|---|---|---|---|
| 1 | **指標の改善が偶然でも提案が採用され続ける** | 季節変動や外部要因による上振れを施策の効果と判定し、効かない施策が「成功事例」として蓄積される。次の提案がその事例を根拠にする | `expectation.judge_after`（既定 30 日）を短縮しない（3.3）／ **1 サイクル 3 件・同一対象 1 件の上限**で効果を分離可能に保つ（3.1）／ `verification` に `no_change` を正直に記録し、`improved` と同じ重みで次の `evidence` に使う |
| 2 | **提案が提案を生んで発散する** | 提案の適用が新しい観測を生み、それがまた提案を生む。起票数が承認能力を超え、承認が形式的な追認に退化する | **1 日 5 件の起票上限**（3.1）／ **重複起票の検出**（3.7）／ 起票できるエージェントを `agent/proposal-writer` 1 本に限定（AA-03 の 1.1）／ **上限に達したらキューに積まず止める** |
| 3 | **観測データの欠損を改善と誤認する** | トラッカーが止まった日を「CV が 0 になった」と読み、存在しない劣化に対する提案が出る。逆に、エラーが 0 件になったのを「直った」と読む | **空配列と取得失敗を区別する**（AA-03 の 3.2。Mautic は 0 件のとき `[]` を返す）／ `truncation_message` を見たら取り直す（AA-03 の 3.1）／ **再現できない観測を `evidence` に使わない**（DA-02 の 5.3）／ GSC の 2〜3 日の確定遅れを欠測と混同しない（AA-02 の I-15） |
| 4 | **エージェントが安全装置を緩める提案を出し続ける** | 上限・しきい値が少しずつ緩み、気づいたときには歯止めが無くなっている | `change.kind: config_change` の承認者を `R1` に分離（3.5）／ 安全装置に関わる提案は「実際に妨げになった事例」を `evidence` に必須（3.5） |
| 5 | **承認が追いつかず、古い観測に基づく提案が後から適用される** | 30 日前の観測を根拠にした提案が、状況が変わった後に適用される | 起票上限で待ち行列を作らない（3.1）／ `evidence` の `measured_at` が承認時点から一定期間を超えていたら**再観測してから適用する**（期間は運用開始後に決める。未決定事項） |
| 6 | **`LH-seo` の劣化を許容したまま改善を積む** | SEO の死守ラインを割った状態で他の指標を改善し続け、検索流入そのものを失う | **`LH-seo` が 1.0 未満なら作用を全面停止**（3.2）。停止中は SEO を戻す提案のみ |
| 7 | **エージェントが自分の実行履歴を書き換える** | `E-15 AgentRun` や `E-12` を改竄して、失敗を成功に見せる | `E-12` は追記せず新ファイルにする（AA-03 の 4.3）／ 観測エージェントと提案エージェントを分離（3.6）／ **`E-15` の正本を監視アプリの実行記録とし、監視アプリのサーバー側だけが書く**（エージェントには書かせない。ADR-18、TA-07 の 3.6。以前は正本が未確定なため、この歯止めが不完全だった）／ **ただし同じ開発機で動くエージェントが記録のファイルに届かないことの担保が未決定**（3.5 の表。6 節）／ **記録を S3 に追記専用で写す**（ADR-18 の追加の決定 5。写しは削除と上書きを許さないため、写した分は書き換えられない。写す頻度より新しい分は守られない） |
| 8 | **`E-13` を経由しない変更が混ざる** | 誰が何を変えたのか分からなくなり、効果の帰属が崩れる | **エージェント専用ユーザーの送信の記録（`sender`）と `E-13` を突き合わせ、対応する `proposal_id` の無い送信を誤った書き込みの候補として扱う**（ADR-17、TA-07 の 6.2、DA-05 の 4.3）。突き合わせは監視アプリの定期実行の 1 つとして起動する／ **Chatwoot の監査ログ（Enterprise の `audit_logs` 機能）には頼らない**（ADR-16 では監査ログを主な手段にしていたが、Community 版で運用できるよう ADR-17 で改めた）／ **拾えるのは送信だけで、会話の属性（担当者・ラベル・状態）の変更は拾えない**。突き合わせの頻度は未決定 |
| 9 | **戻せない適用先に変更を積み上げる** | n8n のワークフロー・Mautic のキャンペーン・PostHog の設定を「Git にあるから戻せる」と誤認して適用し、劣化したときに戻す手段が無い。とくに n8n では、**戻せないワークフローが承認ゲートを迂回する経路として残り続ける** | **3.3.1 の 4 対処**（`rollback.reversible: false` を既定にする／`rollback.procedure` に Git の操作を書かない／適用前の状態を Git にコピーしてから触る／n8n は 1 サイクル 1 件まで） |
| 10 | **観測経路が途切れた期間を指標の変化と誤認する** | 本番では、AWS の公開経路（ALB とその後ろの Umami・Chatwoot・Mautic。ADR-12）の障害で、セッション数と CV が 0 になる。これを「急激な悪化」と読んだ提案が出る。逆に復旧を「改善」と読む。**本番の n8n のタスクが止まると、計測は止まらず、止まるのは n8n への Webhook**（`I-11` `I-12`）で、Webhook を起点にした処理と通知が欠ける（ADR-16 の前は ngrok のトンネル断が同じ結果を生んでいた）。**ADR-17 で、開発機（監視アプリ）が止まると観測の日次バッチそのものが走らなくなった**。これは欠測ではなく未観測だが、再開後にまとめて観測した値を、止まっていた期間の変化と取り違えうる | `agent/ops-watcher` が ALB・ECS（本番の n8n を含む）の死活を監視対象に含める（AA-02 の 1.4）／ **観測経路が途切れていた期間を含む観測を `evidence` に使わない**／**PostHog だけは SaaS のため AWS 側の障害の影響を受けない**ので、Umami が 0 で PostHog が非 0 という組み合わせは欠測の徴候として扱う／ **開発機の停止はハートビートで知り**（TA-07 の 8 節）、止まっていた日の観測は取得の範囲が固定されているため後から実行して埋められる（埋めるかは処理ごとに決める。TA-07 の 3.5。6 節） |
| 11 | **調査が次の調査を呼び、費用を食い潰す** | OpenSEO の調査結果（競合・関連キーワード）が次の調査のシードになり、エージェントが DataForSEO の従量課金を積み上げる。**支出は取り消せない**。残高が尽きると、ランク追跡を含むすべての調査が同時に止まる | **費用の絶対上限を DataForSEO の前払い残高にする**（チャージは人間のみ。ADR-10）／ 月次予算 10 USD と 1 回 2,000 クレジットの上限（超えたら `R2` の承認）／ 費用を発生させうるエージェントを 2 本に限る（AA-03 の 2.4）／ **継続課金の設定（ランク追跡のスケジュール）はエージェントに許可しない** |

**歯止めが不完全な行が 2 つある**（#7 と #8。#7 は ADR-18 で `E-15` の正本と書き手が決まり、歯止めの形は定まったが、同じ開発機のエージェントが記録に届かないことの担保が残る。追加の決定で S3 に追記専用で写すことになり、写した分は守られるようになったが、写す頻度より新しい分と、書き換えられたことの検知は残る。#8 は ADR-16 で突き合わせの手段が決まり、ADR-17 で監査ログに頼らずエージェント専用ユーザーの送信の記録で行うと改めたが、送信以外の変更を拾えず、頻度も決まっていないため不完全のまま）。**#11 は前払い残高という到達不能性の歯止めを持つが、1 回あたりの上限は約束にとどまる**（ツールの引数で上限を指定できるのはランク追跡の実行だけ）。どちらも AA だけでは解けず、`E-15` の記録の守り（TA-07 の 3.6）と、送信以外の変更（会話の属性）を拾う手段に依存する。**不完全であることを隠さず、ループを本格稼働させる前に解く必要がある項目として記録する。**

**#11 は、エージェントの操作が初めて費用を発生させることから生じている。** BA-05 の分類基準の 2 問目（取り消せるか）で見れば、**支出は取り消せない操作**にあたる。

**#9 と #10 は、どちらも「観測や作用の経路が Git の外にある」ことから生じている。** `E-13` を Git に置いたことで統制の記録は守られたが、**記録が守られることと実体が守られることは別**である。

## 5. 現状とループを 1 周させる最短経路

### 5.1 現状（As-Is）

**このループは 1 周も回っていない。** 理由は 3 つで、いずれも欠落であって不具合ではない。

| 欠落 | 具体 |
|---|---|
| **入力が無い** | ブラウザ側のトラッカーが 1 つも設置されていない（`frontend/verdant-virgo/src/layouts/Layout.astro`）。`E-07` も `E-08` も 0 件。GSC は未着手。唯一 `E-12`（`source: lighthouse`）だけがローカルのファイルに出ているが、読み取るエージェントが無い |
| **トラッカーを置いても届かない** | Umami・Chatwoot・Mautic は開発機のローカルで `127.0.0.1` にバインドされており、公開サイトのブラウザから到達できない。**`R1` の 2026-09-18 の決定（ADR-12）により本番では AWS（ECS on Fargate ＋ ALB）に置くが、AWS 側はまだ 1 つも構築されていない**（TA-06。当初は ngrok の常設トンネルで解決する設計だった） |

加えて、**エージェントの定義ファイルが 1 つも存在しない**（`.claude/agents/` がリポジトリに無い）。AA-03 で設計した 12 本はすべて `未着手` である。

### 5.2 最短経路（ループを最初に 1 周させるための最小構成）

**全部を揃える必要は無い。** 1 周させることが目的なら、観測元は 1 つで足りる。**`Lighthouse CI` だけで 1 周できる**（既に動いており、ブラウザ側トラッカーにも Mautic にも GSC にも依存しないため）。

| 手順 | やること | 依存 | 対応する `E-ID` |
|---|---|---|---|
| 1 | `docs/audits/lighthouse/` と `docs/proposals/` を作る（空でよい） | 無し | `E-12` `E-13` の置き場 |
| 2 | `agent/seo-auditor` を定義する（`.lighthouse/` の JSON を読んで `E-12` を 1 件書くだけ） | 1 | `E-12` |
| 3 | `pnpm lh` を実行し、`E-12` を 1 件生成する | 2 | `E-12` |
| 4 | `agent/proposal-writer` を定義し、その `E-12` を根拠に `E-13` を 1 件起票する（`approval.state: draft`） | 3 | `E-13` |
| 5 | **人間が**コミットし、PR を作る | 4 | — |
| 6 | **`R2` が**PR をレビュー承認する（`E-14`） | 5 | `E-14` |
| 7 | 承認された変更を適用し、`E-13` に `applied_at` と `change.diff_ref` を書く | 6 | `E-13` |
| 8 | `pnpm lh` を再実行し、`E-13` の `verification` を埋める | 7 | `E-12` `E-13` |

**この経路は Umami・PostHog・Mautic・Chatwoot・GSC・n8n をいずれも必要としない。加えて AWS 側の構成（ALB・ECS）も ngrok のトンネルも、監視アプリの定期実行（ADR-17。`未着手`）も必要としない**（各手順は人間が起動する）。 ADR-15・ADR-16 の下でも成り立つ（ローカルのビルドと Lighthouse CI だけで閉じ、手順 7 の適用はコードの変更であり、本番への作用はマージと承認後の配信にあたる）。**ADR-16 で配信するビルドは本番の Strapi を読むことになったが、I-09 を配線する前のビルドは Strapi を読まず、配線した後も計測だけなら開発環境の Strapi を読むビルドで回せる**（AA-02 の 4 節）。 使うのは既に `実装済み` の Lighthouse CI と、既に存在する GitHub の PR レビューだけである。

**公開経路を必要としないことが、この経路を最短たらしめている最大の要因である。** 他のすべての観測元（Umami・Chatwoot・Mautic）は、公開サイトのブラウザから届くために AWS の公開経路（ALB とその後ろの ECS・RDS。ADR-12）が要る。Lighthouse CI だけが**同一ホスト内で完結する**ため、AWS 側の構築を待たずに 1 周できる。

### 5.3 最短経路を選ぶ理由

- **観測元を 1 つに絞ると、ループの形が検証できる。** 複数の観測元を同時に配線すると、1 周しなかったときに「どこで止まったのか」が分からない。
- **`E-12`（`source: lighthouse`）は既に出ている。** BA-01 の「測定可能化の順序」は Umami を 1 番目に置いているが、それは KPI を測るための順序であり、**ループを 1 周させるための順序ではない**。ループの検証だけなら、既にデータが出ている Lighthouse が最短になる。
- **`LH-seo` は死守ラインであり、最初に回すループの題材として妥当。** SEO スコアの劣化を検知して直す、という 1 周は、この基盤の目的そのものに直結する。
- **人間の手作業（手順 5・6）を最初から含める。** 後から人間ゲートを足すのではなく、最初の 1 周から入れておく（後付けにすると、動いている自動化に人間を割り込ませることになり、外す圧力が生じる）。

### 5.4 1 周したあとに足すもの

| 順 | 足すもの | これで何が変わるか |
|---|---|---|
| **0** | **AWS の Strapi・Umami・Chatwoot・Mautic・n8n と ALB（公開経路。TA-06）** | **本番のブラウザから観測系・接客系に到達できるようになる。以下の 1・2・3・5 と、エージェントの本番用の MCP の前提**（2026-09-18 に ngrok の常設トンネルから置き換えた。ADR-12。2026-09-19 に ADR-14 で Strapi を加え、同日の ADR-15 で外し、**ADR-16 で Strapi を戻して n8n を加えた**） |
| 1 | Umami のトラッカー（AA-02 の I-05） | `SESSION-count` が測れ、`agent/analytics-reporter` の入力ができる |
| 2 | Astro ← Strapi のデータ取得（I-09） | 観測対象のページが生まれる。`content_rewrite` の提案が意味を持つ |
| 3 | CTA フォーム（I-08） | `CVR-*` が測れ、`E-13` の `expectation.metric` に CVR 系を使えるようになる |
| 4 | GSC（I-15。**OpenSEO 経由**。ADR-06） | 検索順位が測れ、SEO の目的に対する測定が初めて成立する。**ドメインプロパティの登録と OAuth の接続は公開前に済ませてよい**（登録した日からしかデータが溜まらないため） |
| 5 | **監視アプリの定期実行**（観測の日次バッチと `I-13` の起票。ADR-17）と **n8n の Webhook の受け口**（I-11 I-12） | 観測と起票が自動化され、ループの所要時間が人間の手作業の頻度まで短縮される。**当初は「n8n の日次バッチ（I-11 I-12 I-13）」としていたが、ADR-17 で日次バッチの起動と `I-13` は監視アプリ（ローカル）に移った** |

**手順 0 を足した瞬間に、ループの入力が AWS の公開経路の死活に依存するようになる。** それまで（Lighthouse だけの段階）は観測が同一ホスト内で完結していて欠測が起きなかったが、0 以降は**ALB・ECS・RDS が止まった期間の観測が欠ける**。手順 5 以降は、**開発機（監視アプリ。ADR-17）と本番の n8n（ADR-16。それ以前の設計では ngrok のトンネル）の死活にも依存する**。開発機が止まると日次バッチと起票が止まり、n8n が止まると Webhook を起点にした処理と通知が止まる。暴走条件 #10 の歯止め（`agent/ops-watcher` による死活監視、欠測期間を `evidence` に使わない）を、手順 0 と**同時に**入れる。後から足さない。

**5 番目まで足して、初めて BA-01 が定義した「一巡に要する時間と人手」を測れるようになる。** それまでは 1 周ごとに人間が手で回すことになるが、**回る形であること自体が先で、速度は後**である。

## 6. 未決定事項

- **（2026-09-19 に ADR-15 で解決）本番の計測値を読む経路と、開発環境から本番への反映の食い違い。** 本番の値は MCP の本番用の登録で読み、Strapi はオンプレだけに戻したため反映の工程が無くなった。ADR-16 で本番に Strapi を戻した後も、記事は本番にだけ書くため反映の工程は無いままである。設定の食い違いは「そろえ続ける」（開発用の登録で確かめてから `-prod` で適用）で扱う（TA-07 の 6.1）。
- **（2026-09-19 に ADR-16 で解決）本番に作用した時点で `applied_at` を誰が記録するか。** **配信した人間が記録する。** n8n のワークフローの有効化も、有効にした人間が記録する。MCP での書き込みは Claude Code が完了と同時に記録する（TA-07 の 6 節・7 節）。**残るのは記録の漏れである。** 人間が記録を忘れると `approved` のまま残り、効果の検証が始まらない。監視アプリの「承認して配信」の操作に記録を含めるかは TA-07 の 9 節と一体で決める。
- **（2026-09-19 に AA-05 の ADR-18 で解決）`E-15 AgentRun` の正本が未確定のため、暴走条件 #7 の歯止めが不完全。** ADR-14・ADR-15 の時点では「エージェントの起動元が監視アプリに一本化されるなら」という条件付きで、ADR-17 で一本化された。AA-03 の編成では大半のエージェントが Claude Code から直接走り、n8n の実行履歴に記録されない。エージェントの実行そのものを追えないと、「どのエージェントの提案が採用されやすいか」という `E-13` の `created_by` の分析（DA-01 の 6.2）も成立しない、という論点だった。**ADR-18 で、監視アプリ（ローカル）の実行記録を正本にし、書くのは監視アプリのサーバー側だけと決めた**（TA-07 の 3.6）。
- **エージェントが `E-15` の記録に届かないことの担保**（暴走条件 #7。ADR-18 で生じた論点）。記録は監視アプリのローカルの DB にあり、エージェント（Claude Code）も同じ開発機で動いてファイルを編集できる。DB のファイルの置き場所と権限、`PreToolUse` フックの拒否の対象に含めるか（`.env` と同じ扱い）などで、エージェントから到達不能にする手段を決める。**ADR-18 の追加の決定で記録を S3 に追記専用で写すことになり**、写した分は書き換えられなくなった。ローカルの記録と S3 の写しを突き合わせれば書き換えに気づける（**本ファイルの判断**。突き合わせるかは未決定）。写す頻度（TA-07 の 9 節）がこの歯止めの隙間の長さを決める。判断者 `R1`。
- **暴走条件 #8 の歯止めが部分的にしか成立しない。** ADR-16 で「Chatwoot の監査ログと `E-13` を突き合わせる。使えなければエージェント専用のユーザーのメッセージ（`sender`）で代える」と決め、Chatwoot の版（Enterprise を使うか）を未決定にしていた。**ADR-17 で、監査ログ（Enterprise）には頼らず、エージェント専用ユーザーの送信の記録で行うと決めた**（Community 版で運用できるようにするため。TA-07 の 6.2）。これで版の論点は決着した。**残るのは突き合わせの頻度と、送信以外の変更（ラベル・担当者・状態・コンタクトの属性）を拾えないこと**である。属性の変更の誤りは、各会話の履歴を人間が見て気づくことになる。Chatwoot の webhook で変更を拾う案（DA-05）は、webhook は変更の通知であって監査ログの代わりにはならない（webhook を止められる主体が変更を隠せる）。加えて、送信を横断して取る手段が `chatwoot-mcp` に無い（AA-02 の 5 節）。判断者 `R1`。
- **（2026-09-19 に AA-05 の ADR-18 の追加の決定で解決）定期実行の定義をエージェントが書き換えられないことの担保**（3.5 の表。ADR-17 で生じた論点）。観測の取得範囲（ADR-05 の理由）と起動の頻度は、監視アプリのスケジュールの定義に固定する。この定義はエージェントの実行条件そのものであり、BA-05 の分類の 3 問目（エージェント自身の実行条件を変えるか）に当たる。**定義の置き場所（コードか、設定ファイルか、監視アプリの DB か）が決まっておらず、エージェントが編集できる場所に置くとコミットを経ずに次の実行に効く**。`.claude/` 配下と同じく Git の管理下に置き、監視アプリはコミット済みの版だけを読む、などの形を決める必要がある。**ADR-18 の決定の際に、AA-05・TA-07 の未決定事項として明記された**（対象は取得範囲・頻度・使うエージェントとツール。案は「Git で持ち、承認済みの `main` から作った別の場所で監視アプリが読む」）。**追加の決定で案のとおりに決まった。定義は Git で持ち、監視アプリは承認済みの `main` から作った別のチェックアウトで読む。定義の変更は必ず PR を通す**（3.5 の表）。残るのは、そのチェックアウトをいつ・誰が更新するか（TA-07 の 9 節）と、定期実行で起動された Claude Code が読むエージェント定義も `main` の版にするか（AA-03 の 8 節）である。判断者 `R1`。
- **開発機が止まっていた期間の観測を後から埋めるか**（暴走条件 #10。ADR-17）。観測の日次バッチは取得の範囲が固定されているため後から実行できるが、埋めるかは処理ごとに決めるとした（TA-07 の 3.5）。埋める場合に、後から実行した観測であることを `E-12` に残すかも合わせて決める。判断者 `R1` `R3`。
- **記事の公開と配信の間の時間差**（ADR-17）。`R2` が本番の管理画面で公開してから、監視アプリの定期実行が見つけてビルドと計測を行い、人間が配信するまでの間、本番の Strapi では公開済みでも公開サイトには出ていない。`applied_at` は配信の完了で記録するため効果の検証は狂わないが、公開の操作をきっかけに数える指標（`CONTENT-throughput`。DA-02）は配信より早く数える。公開の確認の頻度と合わせて決める。判断者 `R2` `R3`。
- **`evidence` の鮮度の上限が未定**（暴走条件 #5）。承認時点で観測から何日経っていたら再観測を求めるか、実データが無いため妥当な日数を決められない。
- **1 サイクル 3 件・1 日 5 件という上限に根拠が無い。** 「効果を分離できる件数」と「`R2` が承認できる件数」から決めた暫定値であり、実運用で検証するまで妥当性が分からない。BA-04 のポイント加算値（10 / 30 / 50）と同じ性質の暫定値として扱う。
- **`R2` が不在のときのループの停止条件。** BA-05 が代理承認を未決定としているため、`R2` が応答しない期間は承認待ちの `E-13` が溜まり続ける。起票上限（3.1）でキューは抑えられるが、**上限に達した時点でループが止まる**という挙動でよいのかは体制が固まってから決める。
- **戻せない適用先に対する `E-13` を、そもそも起票してよいか**（暴走条件 #9、3.3.1）。4 つの対処は「戻せないことを明示して慎重に扱う」というものだが、**n8n のワークフローに関しては「エージェント起票の提案の対象から外す」という選択肢もある**（人間が直接設計する）。ワークフローが承認ゲートを迂回する経路になりうる以上、慎重に扱うだけで足りるかは判断がついていない。ADR-16 で本番での有効化を人間の承認（`R1`）にしたため、エージェントが置いたワークフローが承認なしに動くことは無くなったが、有効化した後に戻せないことは変わらない。`R1` の決定を待つ。
- **観測経路（本番の ALB とその後ろの観測系、本番の n8n。ADR-16 の前は Webhook 用の ngrok のトンネル）が途切れていた期間の `E-12` の扱い**（暴走条件 #10、AA-02 の 5 節）。欠測として明示的に記録するのか、その日の観測自体を作らないのかが未定。前者だと `evidence` に欠測が混ざり、後者だと「観測が無い日」と「観測が 0 だった日」の区別が別途要る。
- **PostHog の Self-driving との二重ループ。** PostHog 側で Scout 2 本と Replay Vision スキャナ 2 本が独自に稼働している（実行予算 1 日 100 回）。本ループの安全装置はそちらに及ばない。両者が同じ対象に対して別々の改善を出した場合の調停手段が無い。
- **OpenSEO の順位計測（`source: serp`）を `expectation.metric` に使ってよいか。** DataForSEO の SERP は計測した時点の 1 回の検索結果であり、GSC の平均掲載順位（期間中の表示に基づく平均）とは定義が違う。同じ「順位」でも値が一致しないため、**判定には GSC の `GSC-position` を優先し、`SERP-position` は GSC に表示が無いキーワードに限る**案が有力だが、決めていない（DA-02 の 4.3）。判断者 `R3`。
- **Google のアルゴリズム更新を施策の効果と誤認しない手段。** GSC と SERP の数値は、こちらの施策と無関係な検索エンジン側の更新で大きく動く。暴走条件 #1（偶然の改善を効果と判定する）の外部要因が 1 つ増えた。更新の日付を観測の注記として残す仕組み（Umami の `get_annotations` のような）を用意するかどうかを決めていない。判断者 `R3`。
