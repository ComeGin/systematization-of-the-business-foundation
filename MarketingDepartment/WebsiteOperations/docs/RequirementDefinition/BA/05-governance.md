# 05. ガバナンス・セキュリティ運用

BA（Business Architecture）層。ロール ID・Capability ID は EA 共通用語集の定義をそのまま使う。この領域の主担当は `R1`（`CAP-15` ガバナンス・アクセス管理）。

## SSO とアクセス権限制御の方針

### 現状（As-Is）

**SSO は未導入である。** 対象システムはすべて個別にアカウントを持ち、認証情報も個別に管理されている。README に「シングルサインオン（SSO）やアクセス権限制御を徹底し」とあるのは To-Be の記述であり、現時点で実現している事実ではない。

| システム | 認証方式（As-Is） | 権限モデル | 状態 |
|---|---|---|---|
| Strapi | 管理画面の個別アカウント（メール＋パスワード） | Strapi のロール（Super Admin / Editor / Author）＋ API トークン | `未配線`（ロール設計をしていない。既定のまま） |
| Mautic | 個別アカウント。API は OAuth2 client_credentials | Mautic のロール（権限セット）。API クライアントの権限は紐づくユーザーに依存 | `未配線`（API クライアントは作成済みだが、専用ロールを切っていない） |
| Umami | 個別アカウント（ユーザー名＋パスワード） | 管理者／ユーザーの 2 段階。サイト単位の共有設定 | `未配線` |
| PostHog | 個別アカウント（プロジェクトトークンでイベント送信） | プロジェクト／組織のメンバーロール | `部分的`（Strapi からのイベント送信のみ配線済み。閲覧権限の設計は未着手） |
| Chatwoot | 個別アカウント（メール＋パスワード）。API は `api_access_token` ヘッダー | 管理者／エージェント。**トークンはユーザーに紐づき、権限も操作履歴もそのユーザーのもの** | `部分的`（`chatwoot-mcp` 用の専用エージェントユーザーを作る方針は README に記載済み） |
| n8n | オーナーアカウント。ホスト側は `127.0.0.1` にバインド | n8n のユーザー管理（Community 版は限定的） | `未配線`（外部公開時のトンネル経由のアクセス制御が未設計） |
| chatwoot-mcp / mautic-mcp | stdio は認証なし（プロセス起動権限がそのまま権限）。HTTP は固定 Bearer トークン（`MCP_AUTH_TOKEN`、32 文字以上、SHA-256 ダイジェストの `timingSafeEqual` で比較） | `ACCESS_LEVEL`（`read_only` ⊂ `read_write` ⊂ `full`）。**許可されないツールは登録しない**ため、モデルからは存在しないように見える | `実装済み`（この基盤で唯一、権限制御が実装レベルで完成している箇所） |
| GitHub（リポジトリ） | GitHub アカウント | リポジトリのコラボレータ権限、ブランチ保護 | `部分的`（Issue ブランチ ＋ PR 運用は決まっている。保護設定の有無は未確認） |
| Lighthouse CI | 認証なし（ローカル実行、結果は `./.lighthouse` に出力） | なし | `実装済み`（結果を外部公開しない方針は実装済み） |
| **OpenSEO**（セルフホスト） | **認証なし**（`AUTH_MODE=local_noauth`。単一のローカル管理者 `admin@localhost` として扱われる）。UI と MCP の両方が無認証 | **無し。** 到達できるプロセスはすべて管理者 | `実装済み`（`127.0.0.1:3001` にバインド。**ループバックに閉じていることが唯一の防御**。AA-05 の ADR-09） |
| DataForSEO | アカウント（メール＋パスワード）。API は Base64 の資格情報（`DATAFORSEO_API_KEY`） | アカウント単位。**前払い残高が支出の上限** | `実装済み`（OpenSEO に設定済み） |
| Google Cloud（GSC 用の OAuth クライアント） | Google アカウント。OAuth クライアント ID とシークレット | プロジェクトの IAM ／ GSC のプロパティ権限 | `未着手`（クライアント未発行） |

### To-Be の方針

- **SSO の導入は、システムの数ではなく「担当者の数が 2 名を超えた時点」を契機にする**（1 人が兼務している間は、SSO を入れても削減される作業がほぼ無く、導入と維持のコストだけが残るため）。それまでは後述の担当者変更チェックリストと、パスワードマネージャによる認証情報の集約で代替する。
- **SSO を入れる場合の対象は、人間がログインするシステムに限る**（Strapi / Mautic / Umami / PostHog / Chatwoot / n8n）。MCP サーバと Lighthouse CI は人間がログインしないため対象外。**OpenSEO も対象外**（ログインそのものが無い。守りはループバックで行う）。
- **エージェントの権限は SSO の外側で管理する。** エージェントが使うのは MCP の `ACCESS_LEVEL` と上流 API のトークンであり、人間の SSO セッションとは経路が別。この分離は維持する（エージェントの権限を人間のセッションに乗せると、人間のログイン状態がエージェントの実行可否を左右し、権限の境界が追えなくなるため）。
- **最小権限を既定にする。** MCP サーバの `ACCESS_LEVEL` は既定値の `read_only` から始め、必要が生じた Capability ごとに引き上げる。引き上げは `R1` の承認事項（後述の承認ゲート一覧）。

## 担当者変更時の手順

`R1` が実施し、完了を `R2` に報告する。各項目は完了を確認できる形で書く（「確認する」ではなく「〜になっていること」）。

### 参加時

- [ ] 割り当てるロール（`R1`〜`R4` のいずれか）を決め、RACI（03）に照らして必要な Capability を洗い出している
- [ ] 各システムのアカウントを作成し、**そのロールに必要な最小の権限のみ**を付与している
- [ ] Strapi のロールが Super Admin になっていない（`R4` 相当なら Author、`R2` 相当なら Editor）
- [ ] Chatwoot のロールが、レポート閲覧を必要としない場合はエージェントになっている（管理者にしない）
- [ ] 認証情報を本人以外が保持していない（初期パスワードは初回ログイン時に変更させる）
- [ ] GitHub リポジトリのコラボレータに追加し、直接 push ではなく PR 経由の運用であることを伝えている
- [ ] MCP サーバの認証情報（`MCP_AUTH_TOKEN`、上流 API のトークン）を渡していない（人間の作業に MCP のトークンは不要）
- [ ] OpenSEO を使う場合、**開発機のローカルで使うこと**を伝えている（無認証のため、トンネルや別端末から開かない。AA-05 の ADR-09）
- [ ] GSC を OpenSEO に接続する場合、**`comegin.com` の Google Workspace アカウントを使っている**（同意画面が「内部」のため、組織外のアカウントでは接続できない。TA-04 の 8.3）

### 離任時

- [ ] 各システムのアカウントを**無効化**している（削除ではなく無効化。削除すると操作履歴の帰属が失われるため）
- [ ] その人が発行した API トークンをすべて失効させている（Chatwoot の `api_access_token` は**ユーザーに紐づく**ため、アカウント無効化だけでは不十分な場合がある）
- [ ] Mautic の API クライアント（OAuth2）が離任者に紐づいていた場合、別のユーザーで再発行している
- [ ] GitHub のコラボレータから外している
- [ ] 共有していた認証情報（もしあれば）をすべてローテーションしている
- [ ] 離任者が担当していた Capability の `A` を、03 の RACI 表に従って別の人間に再割り当てしている（`A` が空席の Capability を作らない）
- [ ] **ローテーションしてはいけない値に手を付けていない**: `N8N_ENCRYPTION_KEY`、Chatwoot の `ACTIVE_RECORD_ENCRYPTION_*`（変更すると既存の暗号化データを復号できなくなる）
- [ ] 離任者の Google アカウントで OpenSEO の GSC 接続をしていた場合、**別の人のアカウントで接続し直している**（GSC の接続はアカウントに紐づく。離任者のアカウントを無効化すると GSC の取得が止まる）。`BETTER_AUTH_SECRET` は変えない（変えると保存済みのトークンを復号できない。TA-04 の 2 節）
- [ ] DataForSEO のアカウントを離任者が持っていた場合、所有者を移し、API の資格情報を再発行している

## 承認ゲートの一覧

エージェントが自律実行してよい操作と、人間の承認を要する操作の境界を定義する。**この表が再帰的自己改善の安全装置の土台**であり、エージェントが自分自身を改善する範囲を制限する唯一の明示的な境界である。

分類の定義。

- `自律` — エージェントが単独で実行してよい。事後に人間へ通知する。
- `承認` — 実行前に指定ロールの承認が必要。承認は `E-14` `ApprovalRecord` として記録する。
- `禁止` — エージェントは実行しない。人間が直接行う。

| 操作 | 分類 | 承認者 | 根拠 |
|---|---|---|---|
| 記事の下書き作成・更新（`publishedAt` を設定しない） | `自律` | — | 失敗しても公開されず、影響が閉じている |
| 記事の**公開**（`publishedAt` の設定）・公開済み記事の更新 | `承認` | `R2` | 04 の更新ワークフロー 3b。外部に露出する変更で、取り消しても検索エンジンには残る |
| 記事の削除・非公開化 | `承認` | `R2` | 既存の流入と被リンクを失う。取り消しが効かない |
| 観測データの参照・集計・レポート生成 | `自律` | — | 読み取りのみ。`sanitize()` で秘匿値は伏せられる |
| 改善提案（`E-13`）の**生成** | `自律` | — | 提案は提案にすぎず、実体に作用しない |
| 改善提案の**採用と適用** | `承認` | `R2` | `CAP-14` の中核。ここを自動化すると、提案の生成から適用までが閉路になり、外部からの是正が入らなくなる |
| AB テスト（`E-11`）の開始 | `承認` | `R3` | 実ユーザーに異なる体験を出す。同時実行数の管理が必要 |
| AB テストの停止 | `自律` | — | 停止は元の状態に戻す操作で、リスクが増えない方向 |
| Chatwoot の**社内メモ**の作成（`private=true`） | `自律` | — | 顧客には見えない |
| Chatwoot の**顧客への返信**（`private=false`） | `承認` | `R3` | 顧客に即時送信され、取り消せない |
| Mautic のコンタクト作成・セグメント追加・スコア加算 | `自律` | — | 04 のトスアップ条件に沿った機械的な処理。条件自体が承認済み |
| Mautic からの**メール送信**・キャンペーンの開始 | `承認` | `R3` | 外部に送信され、取り消せない |
| Mautic / Chatwoot のレコード削除（`full` 相当の操作） | `承認` | `R1` | 破壊的操作。MCP 側では `destructiveHint: true` が付与されている |
| Lighthouse CI の計測実行 | `自律` | — | 読み取りのみ |
| コードの変更提案（ブランチ作成・PR の作成） | `自律` | — | マージされるまで作用しない |
| コードの **main へのマージ** | `承認` | `R1` | 基盤そのものの変更。リポジトリの Git 運用（PR 経由）と整合する |
| 本番環境へのデプロイ | `承認` | `R1` | 外部に露出する。リポジトリのルール（明確な指示がない限りデプロイしない）と整合する |
| n8n ワークフローの新規作成・変更 | `承認` | `R1` | ワークフローは承認ゲートを迂回する経路になりうる（後述） |
| OpenSEO の参照（GSC の実績・URL 検査・保存済みの結果の読み取り） | `自律` | — | 読み取りのみ。**費用も発生しない**（GSC は自分の Google アカウントのデータ） |
| OpenSEO の調査（キーワード・SERP・競合・被リンク）。**1 回の見積もりが 2,000 クレジット以下** | `自律` | — | 外部に露出しない。**支出は取り消せないが**、1 回の額が小さく、月次予算（10 USD）と前払い残高の内側に収まる（AA-05 の ADR-10） |
| OpenSEO の調査。**1 回の見積もりが 2,000 クレジット超** | `承認` | `R2` | 取り消せない支出が 1 回で月次予算の 2 割を超える |
| OpenSEO の作業場への保存（キーワードの保存・タグ付け） | `自律` | — | 正本ではない（`E-01` の正本は Strapi）。取り消せる |
| **ランク追跡の作成・対象キーワードの追加・スケジュールの設定** | `承認` | `R2` | **継続課金を生む**。一度設定すると、以後の支出が承認なしに自動で続く（n8n のワークフローと同じく「承認なしで実行される操作の定義」になる） |
| ランク追跡のスケジュールの停止（手動に戻す） | `自律` | — | 支出を止める方向で、リスクが増えない |
| ランク追跡の対象キーワードの削除 | `承認` | `R2` | 順位の履歴の扱いを確認していない（取り消せない可能性がある） |
| OpenSEO のサイト監査（**自サイト**） | `自律`（**実行は人間**。AA-03 の 2.4） | — | 読み取りのみ。ただしツールの引数で監査先を縛れないため、エージェントには実行させない |
| OpenSEO のサイト監査（**自サイト以外**） | `禁止` | — | 第三者のサイトにクロールの負荷をかける。外部に露出する操作で、相手の承認が取れない |
| GSC / GA4 の OAuth 接続・切断、プロパティの選択 | `禁止` | — | 認証情報の発行にあたる。人間（`R1`）が行う |
| DataForSEO の残高のチャージ・月次予算の変更 | `禁止` | — | **エージェント自身の実行条件（使える費用）を変える操作**。3 問目の基準に当たる |
| 権限の付与・剥奪、`ACCESS_LEVEL` の変更、アカウントの作成・削除 | `禁止` | — | エージェントが自分の権限を拡張できてしまう。03 の RACI で `CAP-15` のエージェント列が `I` のみである理由 |
| 認証情報・秘密値の閲覧 | `禁止` | — | MCP の `sanitize()` と `PreToolUse` フックで機械的に遮断されている。手順としてではなく仕組みとして禁止する |
| 暗号化キーの変更（`N8N_ENCRYPTION_KEY`、`ACTIVE_RECORD_ENCRYPTION_*`） | `禁止` | — | 既存の暗号化データを復号できなくなる。人間が意図を持って行う場合のみ |

### 境界線の引き方（設計の要点）

分類は次の 3 つの問いで決めている。恣意的に個別判断しないための基準である。

1. **外部に露出するか。** 顧客・検索エンジン・受信者に届く操作はすべて `承認`。取り消しても届いた事実は消えないため。
2. **取り消せるか。** 元の状態に戻せる操作（下書き、AB テストの停止、PR の作成）は `自律`。戻せない操作（削除、送信、マージ）は `承認`。**支出も戻せない操作である**（2026-09-18 に OpenSEO の追加で明記）。ただし 1 回の額が小さく、上限（前払い残高と月次予算）が仕組みとして効いている範囲に限り `自律` とし、上限の内側で額の大きいものと、支出が自動で続く設定を `承認` にした。
3. **エージェント自身の権限や実行条件を変えるか。** 変える操作はすべて `禁止`。承認を挟んでも、承認を求める主体と承認の条件を書き換える主体が同じになりうるため、承認では守れない。

### 自動化が承認ゲートを迂回する経路に注意する

n8n のワークフロー作成を `承認` にしているのは、**ワークフロー自体が「承認なしで実行される操作の定義」になりうる**ため。エージェントが「記事を公開するワークフロー」を作って自律実行できてしまえば、公開の承認ゲートは事実上無効になる。同じ理由で、次の 2 つを原則とする。

- ワークフローが行う操作の分類は、**エージェントが直接行う場合と同じ分類を適用する**（実行手段を変えても承認要件は変わらない）。
- `sandbox-runner-1` は privileged な Docker-in-Docker でホスト root 相当のため、暗号化キーや DB パスワードを渡さない現在の分離を崩さない（この分離が崩れると、ワークフローから `禁止` 分類の操作に到達できる）。

## 未決定事項

- **`E-14` `ApprovalRecord` の記録場所と、承認の検証方法が未定。** 承認ゲートを「手順としての約束」から「状態としての前提」に変えるには、承認記録を機械が参照できる必要がある。DA の決定を待つ。
- **SSO の製品が未選定。** 導入契機を「担当者 2 名超」としたが、対象システム 6 つのうち Umami と n8n の Community 版は SSO 対応が限定的で、全システムを 1 つの IdP に寄せられない可能性がある。TA の調査事項。
- **承認の記録に非改竄性を持たせるか。** 現状は記録の存在だけを要件にしている。エージェントが承認記録自体を書き込める場合、承認の偽造が理論上可能になる。書き込み権限の分離が必要かどうかは、`E-14` の格納先が決まってから判断する。
- **`R2` が不在のときの承認の代理。** 公開承認が `R2` に一点集中しており、`R2` が動けない期間は `自律` 分類の操作しか進まない。代理承認者を置くか、期限付きで分類を緩めるかは体制が固まってから決める。
- **GitHub のブランチ保護設定の実態が未確認。** main への直接 push が技術的に防がれているかを確認していない（参照系の git コマンドでは設定を読めないため）。防がれていない場合、`承認` 分類の「main へのマージ」が手順上の約束にとどまる。
- **OpenSEO の承認ゲートの一部が約束にとどまる。** 「1 回 2,000 クレジット超は `承認`」は、ツールの引数で上限を指定できるランク追跡の実行を除き、エージェントの指示で守る約束である。到達不能性として効くのは前払い残高だけであり、**1 回あたりの上限を仕組みで守るには OpenSEO の MCP を包む自作サーバが要る**（AA-05 の ADR-10 の選択肢 2）。判断者 `R1`。
