# DD-01 フロー仕様の横断規約

詳細設計層。ID の採番の正本は層ごとのファイルにあり、索引は [`docs/README.md` の「ID の採番と正本」](../README.md) にある。

23 本の連携点に個別の仕様を書く前に、**全連携が共有する語彙と数値**をここで固定する。ここを飛ばして各フローを書くと、「失敗したら適切に再試行する」という同じ文が 20 回並び、20 通りの実装になる。

この文書で決めるのは 6 件（3 節から 8 節）。いずれも AA には無く、実装着手には不可欠だったものである。

## 1. この層が扱う範囲と扱わない範囲

| 扱う | 扱わない | 扱わない理由 |
|---|---|---|
| ペイロードの項目名・型・必須 | エンティティの意味と正本 | DA-01・DA-04 の担当 |
| 冪等キー・リトライ・タイムアウト | どのアプリが何を担うか | AA-01 の担当 |
| 失敗時の記録先と観測点 | 監視ツールの選定と配置 | TA-05 の担当 |
| 状態遷移の主体と実行手段 | 承認ゲートの分類そのもの | BA-05 の担当（この層は分類を**変えず**、実行手段の有無だけを記述する） |

## 3. 決定 1 相関 ID

### 3.1 何を解くか

AA-04 のループは観測（日次）から検証（30 日後）まで跨がる。その間に `E-12` が複数生成され、`E-13` に束ねられ、適用されて再計測される。**この一連を後から 1 本に繋ぐ識別子が、AA にも DA にも無い。**

`E-15 AgentRun` がその役を担うはずだったが、正本が未確定であり（DA-01・AA-03・AA-04 の未決定事項）、Claude Code から直接走るエージェントの実行は記録されない。**`E-15` の解決を待つと、それまでのあいだ 1 周を追跡できない。**（**2026-09-19 の ADR-18 で `E-15` の正本は監視アプリの実行記録に決まった。** 相関 ID はそのまま `E-15` を引くキーとして使い続ける。3.1）

**（2026-09-19）ADR-18 で `E-15` の正本は監視アプリ（ローカル）の実行記録に決まった**（AA-05 の ADR-18。TA-07 の 3.6）。1 回の起動（手動の指示・定期実行）を 1 件とし、相関 ID（ULID）で `E-13`・`E-14`・本番への書き込みと結ぶ。記録を書くのは監視アプリのサーバー側だけで、エージェントには書かせない。**この節の相関 ID は、`E-15` を引くキーとしてそのまま使い続ける**（3.2・3.4・3.7）。

### 3.2 決定

**新しいエンティティを作らず、各エージェント実行の開始時に ULID を 1 本発行し、その実行が生成するすべての成果物に埋め込む。**

| 項目 | 値 |
|---|---|
| 形式 | ULID（26 文字、Crockford Base32。例 `01JBQZ8F3K7XN2M5V9TWRC4HED`） |
| 発行の単位 | **エージェントの 1 実行につき 1 本**（1 エージェントが複数の `E-12` を書いても同じ ID）。**監視アプリの 1 回の起動が `E-15` の 1 件にあたり、相関 ID はその 1 件に 1 本である**（ADR-18。TA-07 の 3.6） |
| 発行主体 | **監視アプリのサーバー側が起動の直前に発行し、`E-15` に記録してからエージェントに渡す**（ADR-18 の後。この層の判断。3.2.1）。エージェントは渡された値を使い、自分では発行しない。**監視アプリを通らない実行**（1 周目の最短経路で人間が Claude Code を直接起動する場合。[06 の 5 節](06-proposal-loop-flows.md)）だけは、エージェントが実行の冒頭で自分で発行する（`E-15` には記録されない）。ADR-18 の前は、手動・定期を問わずエージェント自身が発行していた |
| 埋め込み先 | `E-12` の `fetch.correlation_id` ／ `E-13` の `agent_run_id`（3.4）／ stderr のログ行頭 ／ **`E-15`（監視アプリの実行記録）**（ADR-18） |

#### 3.2.1 発行主体を監視アプリに移す理由（ADR-18 の後）

- **エージェントが書き換えられない記録と、成果物に埋め込まれた値を突き合わせられる。** 監視アプリが発行して先に `E-15` に書けば、`E-12` `E-13` に埋め込まれた相関 ID が `E-15` に無い、または起動したエージェントと合わないことが、ずれとして見える（[07 の 7.1](07-failure-and-degradation.md)）。エージェント自身が発行していた間は、偽の値を書かれても気づく手段が無かった。
- **定期実行は 1 回の起動で 1 本のエージェントを動かす**（この層の判断）。日次バッチの観測系 4 本と `agent/proposal-writer` は別々の起動にし、`agent/proposal-writer` の起動は監視アプリが 4 本の終了を待ってから行う（[06 の 1.1](06-proposal-loop-flows.md)）。こうすると「エージェントの 1 実行につき 1 本」と「1 回の起動を 1 件」（TA-07 の 3.6）が一致し、DA-01 の `E-15` の属性 `agent_name` が 1 つに定まる。
- **手動の指示の 1 回で複数のエージェントが動く場合**は、同じ相関 ID を共有する（1 回の起動が 1 件であるため）。このとき `E-15` の `agent_name` が 1 つに定まらない（10 節）。

### 3.3 なぜ ULID か

**相関 ID だけは連番にできない。** `audit_id` と `proposal_id` が連番でよい理由（3.6）は、採番の範囲が `source` とディレクトリで分かれていることにある。一方で相関 ID は、**成果物を 1 つも書かないエージェントを含む全 12 本が、実行のたびに発行する**（`agent/knowledge-scout` も `agent/quality-checker` も発行する）。スコープする単位が無いため、連番にすると全エージェントを跨ぐ採番の調停役が要る。

| 候補 | 却下の理由 |
|---|---|
| 連番 | **スコープする単位が無い。** 全エージェントを跨ぐ調停役が要り、その調停役が単一障害点になる |
| UUIDv4 | 辞書順が時系列にならない。**stderr のログを ID で並べても実行順にならず**、複数エージェントのログが混ざったときに追えない |
| タイムスタンプのみ | 並列実行で同一ミリ秒の衝突が起きうる |
| **ULID** | 先頭 48 bit が UNIX ミリ秒のため**辞書順＝時系列**。残り 80 bit が乱数のため調停役なしで並列でも衝突しない。外部依存が小さい |

**ADR-18 で発行主体が監視アプリに寄っても ULID を保つ**（この層の判断）。監視アプリは調停役になりうるが、**監視アプリを通らない実行ではエージェントが自分で発行する**（3.2）ため、発行主体が 2 つ残る。2 つの主体が調停なしで衝突しない形は ULID のままである。既に `E-12` `E-13` に書いた値との互換も保てる。

### 3.4 `E-13` の `agent_run_id` を暫定で埋める

**相関 ID は `proposal_id` や `audit_id` を置き換えない。** それらの形式は DA-01 の 6 節が既に定めている。

| ID | 形式 | 定めた場所 | 採番の主体 |
|---|---|---|---|
| `proposal_id` | `PRP-<西暦>-<連番>` | DA-01 の 6.1 | `agent/proposal-writer`（**1 本だけ**） |
| `audit_id` | `AUD-<西暦>-<月日>-<source>-<連番>` | DA-01 の 6.1 | 観測エージェント（**`source` ごとに 1 本**） |
| `agent_run_id` | `RUN-<西暦>-<月日>-<連番>` | DA-01 の 6.1 | **監視アプリ**（ADR-18 で `E-15` の正本になった）。ADR-18 の前は `E-15` の正本が未確定のため、書ける主体が無かった。**`RUN-` 形式で採番するかは決まっていない**（下） |
| **`correlation_id`** | **ULID** | **この層** | **監視アプリが起動の直前に生成してエージェントに渡す**（ADR-18 の後。3.2）。監視アプリを通らない実行だけはエージェントが生成する |

**この層が解くのは 3 行目である。** DA-01 は `agent_run_id` を**必須**としながら、`E-15 AgentRun` の正本が未確定のため**値を書ける主体が存在しない**（DA-01・AA-03・AA-04 の未決定事項）。必須項目が空のまま起票されると、DA-01 の 6.2 の「無い場合に壊れること」（提案の生成過程を追えない）がそのまま起きる。（**ADR-18 で書く主体は監視アプリに決まった。** 以下の暫定の扱いは、ADR-18 の前の経緯として残す）

**決定: `E-15` の正本が決まるまで、`agent_run_id` に相関 ID（ULID）を入れる。**

**（2026-09-19）ADR-18 で `E-15` の正本は監視アプリの実行記録に決まり、実行記録は相関 ID で `E-13` と結ぶことになった**（TA-07 の 3.6）。したがって**`agent_run_id` に入れた ULID は、そのまま `E-15` の 1 件を引く参照として働く。** 暫定策は「空欄を埋めるだけ」から「正本への参照」に変わった。

```yaml
agent_run_id: 01JBQZ8F3K7XN2M5V9TWRC4HED   # 監視アプリが渡した correlation_id。E-15（監視アプリの実行記録）を引くキー
```

- **ULID を `agent_run_id` の正式な形式にするのが、この層の推奨である**（この層の判断）。`E-15` の側が ULID で引ける以上、`RUN-` 形式を別に採番すると 2 つの ID の対応を持つことになり、移行（3.7）も要る。ただし DA-01 の 6.1 が定めた形式を変えるのは型の変更であり、この層では決めない（10 節。判断者 `R3`）。
- **形式が `RUN-...` と違うことが、暫定であることの目印になる**（DA-01 が `RUN-` 形式を保つ場合）。後から `RUN-` で始まらない値を探せば、移行対象を機械的に列挙できる。
- 1 つの `E-13` が複数のエージェント実行の観測を根拠にする場合、**`agent_run_id` には起票した実行（`agent/proposal-writer` の実行）の ULID を入れる**。観測側の実行は `evidence[].audit_id` から辿る（各 `E-12` の `fetch.correlation_id` から観測側の `E-15` も引ける）。
- **`agent_run_id` を書くのは起票するエージェント（`agent/proposal-writer`）であり、監視アプリではない**（`E-13` はエージェントの成果物）。エージェントが渡された値と違う値を書くことは防げないが、`E-15` と突き合わせれば見つかる（[07 の 7.1](07-failure-and-degradation.md)）。

### 3.5 ファイル名は DA-01 の ID 体系に従う

```
docs/audits/<source>/<audit_id>.md     例 docs/audits/lighthouse/AUD-2026-0915-lighthouse-0031.md
docs/proposals/<proposal_id>.md        例 docs/proposals/PRP-2026-0042.md
docs/knowledge/<YYYY-MM-DD>-<slug>.md  知見メモ（対応する E-ID が無いため ID 体系の外）
```

**ULID をファイル名に使わない。** DA-01 の 6.1 が `docs/proposals/<proposal_id>.md` と明記しているため、ここを変えると型定義の書き換えになる。

### 3.6 連番が並列実行で衝突しない理由

連番は一般に採番の調停役を要するが、**この基盤の編成では調停役が不要である**。既存の 2 つの規約がそれを保証している。

| 規約 | 効き方 |
|---|---|
| **`audit_id` が `source` と日付でスコープされる**（DA-01 の 6.1） | 採番の範囲が `source` ごとに分かれる |
| **1 エージェント 1 ディレクトリ**（AA-03 の 4.3） | 各 `source` のディレクトリに書くエージェントが 1 本に固定される |

したがって AA-03 の 4.1 が観測系 4 本を並列実行しても、**4 本は互いに異なる `source` のディレクトリに書く**ため連番が衝突しない。

`proposal_id` はさらに単純で、**起票できるエージェントが `agent/proposal-writer` の 1 本に限定されており**（AA-03 の 1.1）、その 1 本は観測系 4 本の完了を待ってから走る（AA-04 の 4.1）。並列採番が起きる構造になっていない。

**採番の直前に既存のファイルを一覧して最大の連番を取る**、という実装でよい。ロックは要らない。

### 3.7 `E-15` の正本が決まったときの移行

**既存のファイル名は変えない。** `agent_run_id` の値だけを `RUN-...` 形式に置き換え、ULID との対応表を `E-15` 側に持たせる。

ファイル名を変えると Git の履歴上で別ファイルになり、`E-13` の `evidence[]` が指す参照が切れる。

**（2026-09-19）ADR-18 で `E-15` の正本が決まり、対応表の置き場は `E-15` そのもの（監視アプリの実行記録）になった。** 監視アプリの実行記録は 1 件ごとに相関 ID を持つため、`RUN-` 形式の ID を足す場合も、同じ 1 件の中に 2 つの ID が並ぶだけで、別の表は要らない。**ULID を正式な形式にすれば（3.4 の推奨）、この移行そのものが要らなくなる。** どちらにするかは DA の判断（10 節）。

- **監視アプリを通らずに走った実行**（3.2。1 周目の最短経路）の ULID は `E-15` に無い。これらの `E-13` は `agent_run_id` から `E-15` を引けないことを前提に扱う（監視アプリを作る前の実行であり、[06 の 5 節](06-proposal-loop-flows.md)の手順で人間が起動した記録が別に残る）。

## 4. 決定 2 失敗分類の語彙

### 4.1 何を解くか

AA-03 の 3.2 は「**空配列を失敗と誤認しない、失敗を 0 と誤認しない**」を要求し、AA-04 の暴走条件 #3 はこの誤認を暴走条件に数えている。しかし「区別する」としか書かれておらず、**区別した結果をどこに何という名前で書くか**が決まっていない。

### 4.2 決定

**すべての取得結果を次の 9 値のいずれかに分類し、`E-12` の `fetch.outcome` に必ず記録する。**

| 値 | 意味 | 成功か | `evidence` に使えるか |
|---|---|---|---|
| `ok` | 取得でき、1 件以上あった | 成功 | 使える |
| `empty_but_ok` | 取得できたが 0 件だった | **成功** | **使える**（0 件であることが事実） |
| `timeout` | こちらから打ち切った | 失敗 | 使えない |
| `unreachable` | 接続できなかった（DNS・TCP・トンネル断） | 失敗 | 使えない |
| `auth_failed` | 認証情報が通らなかった（401 で、権限不足と区別できた場合） | 失敗 | 使えない |
| `permission_denied` | 認証は通ったが権限が無い（403、または Chatwoot の判別不能な 401） | 失敗 | 使えない |
| `rate_limited` | 上流に絞られた（429） | 失敗 | 使えない |
| `truncated` | 応答が `CHARACTER_LIMIT` で削られた（`truncation_message` が付いた） | **部分的成功** | **使えない**（AA-03 の 3.1） |
| `invalid_response` | 応答は返ったが解釈できない（想定外の形・Mautic の `order_by` 起因の 500） | 失敗 | 使えない |

### 4.3 `E-12` に記録する `fetch` ブロック

新しいエンティティを作らず、`E-12 AuditResult` の frontmatter に次のブロックを足す。

```yaml
fetch:
  outcome: ok            # 4.2 の 9 値のいずれか
  attempts: 2            # 実際に試行した回数（初回を含む）
  correlation_id: 01JBQZ8F3K7XN2M5V9TWRC4HED
  measured_at: 2026-09-17T06:00:00+09:00   # 取得を完了した時刻（JST・ISO 8601）
  range:
    from: 2026-08-13
    to: 2026-09-16       # 取得対象の期間。期間を持たない観測では省略
  note: ''               # outcome が ok 以外のときだけ、機械が読まない補足を書く
```

- **`measured_at` は「取得を完了した時刻」であって「データが表す時刻」ではない。** GSC のように確定が 2〜3 日遅れる観測は、`range.to` が `measured_at` の 3 日前になる（AA-02 の I-15）。この 2 つを混同すると暴走条件 #3 を踏む。
- **`outcome` が `ok` か `empty_but_ok` 以外の `E-12` は `E-13` の `evidence[]` に使えない。** これは `agent/proposal-writer` の起票前チェックとして実装する（[06 の 1 節](06-proposal-loop-flows.md)）。
- **`empty_but_ok` を成功に数えるのがこの分類の要点である。** Mautic は 0 件のとき `[]` を返す（AA-02 の 2.2）。「CV が 0 件だった」と「Mautic に到達できなかった」を同じ `失敗` に丸めると、存在しない劣化に対する提案が生まれる。

### 4.4 分類の判定順

上流の応答を分類するときは、**上から順に当てはめる**（下ほど広い分類のため、順序を変えると `invalid_response` にすべてが吸い込まれる）。

1. 接続自体が確立しなかった → `unreachable`
2. こちらのタイムアウトで切った → `timeout`
3. HTTP 429 → `rate_limited`
4. HTTP 403 → `permission_denied`
5. HTTP 401 → 上流ごとに判定（5.3）
6. 応答に `truncation_message` がある → `truncated`
7. 応答を解釈できない、または上流固有の既知の 5xx → `invalid_response`
8. 解釈でき、件数が 0 → `empty_but_ok`
9. それ以外 → `ok`

## 5. 決定 3 リトライ方針

### 5.1 何を解くか

AA-02 には「1 回だけ再試行」「3 秒待って 1 度だけ」「401 で 1 回だけ再取得」が**別々の場所に別々の文で**書かれている。連携が 20 本あるので、このまま実装すると 20 通りの再試行が生まれる。

### 5.2 決定（分類ごとの既定）

**再試行の可否は 4.2 の分類から決まる。** 連携ごとに上書きしてよいのは「回数」だけで、**「しない」を「する」に変えてはいけない**。

| 分類 | 再試行 | 回数 | 間隔 | 理由 |
|---|---|---|---|---|
| `unreachable` | する | 2 | 3 秒 → 9 秒 | ALB の後ろの ECS タスクの入れ替え時の瞬断を吸収する（当初は ngrok の瞬断も想定していたが、ADR-16 で本番の経路から ngrok は消えた）。3 倍刻みにするのは、合計 12 秒が Chatwoot のタイムアウト（12 秒）と同じ桁に収まるため |
| `timeout` | する | 1 | 3 秒 | 上流が一時的に重いだけの可能性がある。2 回以上は待ち時間が観測サイクルを圧迫する |
| `rate_limited` | する | 1 | `Retry-After` の値。無ければ 60 秒 | 上流が指定した値に従う。独自の値を使うと絞りがさらに強まる |
| `auth_failed` | **上流ごと**（5.3） | ≤ 1 | 即時 | トークンの期限切れなら再取得で通るが、権限不足なら何度やっても通らない |
| `truncated` | する（**条件を狭めて**） | 1 | 即時 | 同じ条件で再送しても同じ結果になる。期間か件数を半分にして取り直す（AA-03 の 3.1） |
| `permission_denied` | **しない** | 0 | — | 再試行しても通らない。その項目をスキップして観測を続ける（AA-02 の 2.1） |
| `invalid_response` | **しない** | 0 | — | 原因はこちらの入力にあることが多い（Mautic の 500 の主因は不正な `order_by`。AA-02 の 2.2） |
| `empty_but_ok` | しない | — | — | 成功しているため |

**費用が発生する連携（`I-22` の調査系・`I-23`）は、すべての分類で回数を 0 に上書きする**（2026-09-18 に追加）。再試行は「同じ要求をもう一度送る」ことであり、送るたびに課金される経路では、一時的な失敗を吸収する効果より二重課金の害が大きい。これは「しない」への上書きであり、上の規則（「しない」を「する」に変えてはいけない）と矛盾しない。

**再試行の総予算は 1 連携あたり 30 秒。** 上の回数と間隔を積み上げても超えないが、連携ごとに回数を上書きするときはこの予算を超えないことを確認する。

**（2026-10-04 追記）`rate_limited` の待ちと総予算の関係。** `Retry-After` が無いときの既定 60 秒は、それだけで総予算 30 秒を超える（「積み上げても超えない」は `rate_limited` については誤りだった）。**総予算を優先する**: 待ちが残りの予算に収まるときだけ 1 回再試行し、収まらなければ待たずに `rate_limited` で失敗として記録する（次の定期実行に任せる）。上流が指定した値より短く待って送り直すことはしない（絞りを強めないという表の理由と両立する）。control-plane の実装で判明。

### 5.3 `auth_failed` の上流ごとの扱い

**401 の意味が上流によって違う。** ここが最も事故の起きやすい箇所なので、上流ごとに明示する。

| 上流 | 401 の意味 | 再試行 | 根拠 |
|---|---|---|---|
| **Mautic** | OAuth2 のアクセストークンの期限切れ | **する（1 回）。** トークンを再取得してから 1 度だけ | ユーザーが紐づかない client_credentials のため、401 は期限切れ以外の意味を持ちにくい。`mautic-mcp` に実装済み |
| **Chatwoot** | **「トークン不正」と「権限不足」の両方** | **しない。** `permission_denied` として扱い、その項目をスキップする | AA-02 の 2.1。区別できない以上、通らない側に倒す |
| GitHub | トークンの失効・スコープ不足 | しない | 起票の失敗は `E-15` に残して翌日再試行する（AA-02 の I-13）。**記録するのは起票の処理を動かす監視アプリ自身である**（ADR-18。[06 の 2 節](06-proposal-loop-flows.md)） |
| Google Search Console（**OpenSEO 経由**） | OAuth の未接続・失効・取り消し。OpenSEO は HTTP の 401 ではなく **`not_connected` という応答**で返す | **しない。`auth_failed` に分類する** | 人間が OpenSEO の画面で接続し直す（TA-04 の 8.3）。同意画面は「内部」のため 7 日の失効は起きないが、接続したアカウントの無効化や同意の取り消しで起きる |
| DataForSEO（**OpenSEO 経由**） | 残高不足 | **しない。`permission_denied` に分類する** | 再試行しても通らず、**再試行は課金を伴いうる**。残高の補充は人間（`R1`） |

**Chatwoot の 401 を「認証の失敗」と解釈して再認証を試みない。** トークンはユーザーに紐づいており（AA-02 の 2.1）、権限不足の場合に再認証しても同じトークンが返るだけである。

### 5.4 Chatwoot 起動直後の 500

AA-02 の 2.1 が挙げる例外。**分類としては `invalid_response`（再試行しない）に当たるが、この 1 ケースだけ例外的に再試行する。**

- 条件: Chatwoot への**最初のリクエスト**が 500 を返した場合のみ
- 3 秒待って 1 度だけ再試行する
- 再試行しても失敗したら `E-15 AgentRun` に `failure` として残し、**その日の観測をスキップする**（部分的な観測を `E-12` にしない）。**`E-15` に書くのは監視アプリであり、エージェントではない**（ADR-18）。エージェントは失敗を実行の結果として返し、監視アプリがそれを `E-15` の `outcome` に記録する

**2 回目以降のリクエストの 500 には適用しない**（それは本物の異常であり、再試行で隠すべきではない）。

## 6. 決定 4 冪等キー

### 6.1 何を解くか

AA-02 の 1.2 は `I-08` `I-11` `I-12` `I-18` の 4 本を「要設計」とし、方針を 3 つ示したが**キーの構成・保存先・保持期間を決めていない**。とくに `I-08`（フォーム送信）の二重実行は CVR の分子を直接汚染する。

### 6.2 決定

| 連携 | 冪等キー | 保存先 | 保持期間 | 重複時の挙動 |
|---|---|---|---|---|
| `I-08` フォーム送信 | `mautic_form_id` + `lower(email)` + `送信日（JST の日付）` | **3 層で守る**（6.3） | 24 時間（暫定） | 2 件目以降は `E-09` を更新するが、**CV としては数えない** |
| `I-11` Mautic → n8n | `contact_id` + **イベント種別** + `webhook の timestamp`（秒精度）（**2026-10-04 にイベント種別を追加**。Mautic はフォーム送信 1 回で `lead_post_save`・`points_change`・`list_change`・`form_on_submit` を同じ秒に出すため、種別を含めないと後着の `form_on_submit`〈無料相談の通知〉が先着の別イベントの重複として捨てられる。実装で判明） | n8n の Data Table `dedup_mautic` | 7 日 | 何もせず 200 を返す（上流に再送させない） |
| `I-12` Chatwoot → n8n | `display_id` + `message_id` | n8n の Data Table `dedup_chatwoot` | 7 日 | 同上 |
| `I-13` ローカル → GitHub（ADR-17。ADR-05 では n8n → GitHub） | `proposal_id`（`PRP-<西暦>-<連番>`。DA-01 の 6.1） | GitHub 側のファイルの存在そのもの | 無期限 | 起票しない（AA-02 の 1.2、AA-04 の 3.7）。**起票の主体が n8n から監視アプリの定期実行に移っても、キーと保存先は変わらない**（保存先が GitHub 側にあるため） |
| `I-18` Mautic → PostHog | **定義しない** | — | — | **前提待ち。** 越境の可否が決まるまでキーの形も決めない（email のハッシュも個人データとして越境しうるため、キー設計自体が越境の判断に依存する） |

### 6.3 `I-08` を 3 層で守る理由

静的サイトのフォームは**サーバ側の受け口がこちらに無い**（Astro のビルド成果物であり、`I-08` はブラウザから Mautic を直接叩く）。したがって「1 か所で弾く」ができず、3 層に分ける。

| 層 | 何をするか | 何を防ぐか | 防げないもの |
|---|---|---|---|
| **1 ブラウザ** | 送信ボタンを押した時点で無効化し、`sessionStorage` に送信済みを記録する | 二重クリックと、同一タブでの再送信 | 別タブ・リロード後・別端末 |
| **2 Mautic** | email をキーにした統合を既定にする（同じ email の送信は既存コンタクトの更新になる） | `E-09` が 2 件できること | **送信イベントは 2 件記録される**（CV の分子は依然 2 になる） |
| **3 集計時** | `CV 数` を**フォーム送信の件数ではなく、`mautic_form_id` + `lower(email)` + 日付で畳んだ件数**として数える | CVR の分子の汚染 | — |

**第 3 層が本命である。** 1 と 2 は「起きにくくする」だけで、二重送信を 0 にはできない。**`CV 数` の数え方の側で畳むことが、唯一の確実な対処**にあたる。

- この畳み方は `agent/analytics-reporter` の集計仕様として [03 の 3 節](03-operation-path-flows.md) に書く。
- **24 時間という窓幅は暫定値。** BA-04 のトスアップ条件が「1 回の送信につき加算する」前提で書かれているため、同一日の複数送信を 1 回に畳むのが最も整合するという理由で選んだ。実データが無いため妥当性は検証していない（未決定事項）。
- **DA-02 の「CV の判定はフォーム送信完了」という定義は変えていない。** 変えたのは判定ではなく**数え方**であり、同じ完了イベントを何件と数えるかの規則をここで与えた。

## 7. 決定 5 タイムアウト

### 7.1 決定の原則

**上流に固定の打ち切りがある場合は、必ずその内側で自分から切る。**

上流に切られると HTTP 500 として返り、`invalid_response`（再試行しない）に分類されてしまう。自分で切れば `timeout`（1 回再試行する）に分類でき、**一時的な遅延と本物の異常を区別できる**。

### 7.2 値

| 連携 | タイムアウト | 根拠 |
|---|---|---|
| `I-03` Chatwoot（MCP 経由） | **12 秒** | `Rack::Timeout` の 15 秒より内側。3 秒の余裕は、ネットワークの往復に充てる（本番ではオンプレの MCP サーバから AWS の ALB への往復。ADR-12） |
| `I-04` Mautic（MCP 経由） | 30 秒 | 上流に固定の打ち切りが無い。`mautic_query_stats` の重い集計を通すために長めに取る |
| `I-16` Strapi（`strapi-mcp` / `strapi-prod` 経由） | 20 秒 | 管理外の MCP のため上流の挙動を保証できない。既定より短くして、止まったときに早く気づく（本番の `strapi-prod` は ALB 越しのリモート接続になる。ADR-16） |
| `I-17` GA4（OpenSEO の MCP 経由。**2026-10-06 ADR-25: 旧版は Umami の MCP で 20 秒**） | 30 秒 | OpenSEO の参照系と同じ（[03 の 5 節・6 節](03-operation-path-flows.md)）。管理外の MCP で、その先の GA4 の Data API の応答も待つ |
| `I-01` `I-02` Strapi → PostHog | **5 秒**（`flush()` を待つ上限） | 記事の保存とリクエストの応答を止めないため。超過したら送信を諦める（送信失敗が保存を止めない、という既存の設計） |
| `I-05` `I-06` `I-07` ブラウザ → 各所 | **設定しない**（非同期で投げっぱなし） | サイトの表示を止めないため。失敗は黙って捨てる（AA-02 の I-05） |
| **`I-25` ブラウザ → Cal.com**（2026-10-01 に追加）〔2026-10-06 ADR-24: SaaS の Cal.com に直接届く〕 | **設定しない**（埋め込み側の既定に従う） | **`I-07` と同じ扱い。** 埋め込みの読み込みであり、こちらからタイムアウトを与えられない。**失敗したら代替の案内（メールで日程を調整する）を出す**ところが `I-07` と違う（DD-02 の 7.3） |
| **ブラウザ → 同意の受け口**（同日に追加。I-ID を持たない） | **設定しない**（非同期で投げっぱなし） | **同意の判定は Cookie で行う**ため、サーバ側の記録が遅れても訪問者の体験は変わらない（DD-02 の 8.3）。失敗は黙って捨てる |
| `I-08` ブラウザ → Mautic | **10 秒** | **これだけは応答を待つ。** 送信失敗を利用者に明示する必要がある（AA-02 の 3.1） |
| `I-09` Astro ← Strapi（ビルド時） | 1 リクエスト 20 秒 / ビルド全体 5 分 | 全体上限を置くのは、Strapi が応答しないときにビルドが無限に待たないため。**ADR-16 で読み先が本番の Strapi（ALB 越し）になったが、値は変えない**（ローカルから AWS への往復が加わる分は 1 リクエストの 20 秒に収まる想定。実測していない） |
| `I-13` ローカル → GitHub（ADR-17） | 30 秒 | 起票の主体が n8n から監視アプリの定期実行に移っても値は変えない |
| `I-15` Search Console（`I-22` の参照系で読む） | 30 秒 | OpenSEO が GSC を呼んで返すまでを含む。当初の 60 秒（API 直接）から、`I-22` の参照系に揃えた |
| `I-22` OpenSEO（調査系） | **90 秒** | DataForSEO の集計を待つ。**調査系は `timeout` でも再試行しない**（再試行が 2 回目の課金になる。[03 の 6 節](03-operation-path-flows.md)） |
| `I-21` Amazon SNS | **10 秒** | 通知のためにワークフローを長く止めない。**失敗しても顧客対応もループも止めない**ため、短く切って諦める |
| `I-27` points-api → unMineable（2026-10-03 に追加） | **30 秒** | 日次のバッチで、利用者の待ちが無い。応答の遅い外部の SaaS |
| `I-28` points-api → thirdweb（同上） | **30 秒**（送信の受付まで。チェーンでの確定は日次の突き合わせで確かめる） | 確定を待つとタイムアウトが長くなりすぎる |

### 7.3 ブラウザ側だけ扱いが違う理由

`I-05` `I-06` `I-07` `I-25` と同意の受け口は**タイムアウトを設定しない**が、`I-08` だけは 10 秒で切る。

- 前者は**観測と接客の付帯機能**であり、失敗してもサイトの価値は損なわれない。利用者に見せる意味も無い。
- `I-08` は**利用者の意思表示そのもの**である。送られていないのに送られたと思わせるのは、観測の欠損より重い（AA-02 の I-08「送信失敗は利用者に明示する（黙って失敗させない）」）。
- **`I-25`（2026-10-01 に追加）は中間にある。** 利用者の意思表示（面談の予約）を扱うが、**予約の確定は Cal.com の中で起きる**ため、こちらでタイムアウトを測る対象が無い（埋め込みが描画に失敗したかどうかしか分からない）。**代わりに、失敗したときの代替の案内を必ず出す**という形で「黙って失敗させない」を守る（DD-02 の 7.3）。
- **同意の受け口（同日に追加）は `I-05` 側である。** 利用者の操作が起点だが、**操作の結果（同意の成立）は Cookie で完結している**ため、サーバ側の記録の失敗は観測の欠損に近い（DD-02 の 8.3）。

## 8. 決定 6 `E-13` の状態遷移

### 8.1 何を解くか

AA-04 の 2.1 は「`review` → `approved` の遷移だけはエージェントが実行できない」と書いている。しかし**他の遷移について同じ検査がされていない**。遷移が 8 つあるうち 1 つだけを検査しても、他の 7 つに抜け道があれば意味が無い。

### 8.2 決定（状態遷移表）

**すべての遷移について、実行主体・実行手段・エージェントの到達可能性を書く。**

| # | 遷移 | 実行主体 | 実行手段 | エージェントの到達可能性 | 根拠 |
|---|---|---|---|---|---|
| T1 | （無）→ `draft` | `agent/proposal-writer` | `docs/proposals/<id>.md` を新規作成 | **到達可** | BA-05 `自律`（提案は実体に作用しない） |
| T2 | `draft` → `review` | **人間** | コミットしてブランチを作り、PR を作る | **到達不能** | `.claude/rules/git.md`（状態変更系の git コマンドが使えない） |
| T3 | `review` → `approved` | **`R2`** | PR のレビュー承認（`E-14`） | **到達不能** | T2 が到達不能なため、レビュー対象を作ることすらできない |
| T4 | `review` → `rejected` | **`R2`** | PR のクローズ、または変更要求 | **到達不能** | 同上 |
| T5 | `approved` → `applied` | `change.kind` ごとに異なる（8.3） | 適用操作 + `applied_at` と `change.diff_ref` の記録（**記録するのは本番に作用させた主体**。8.3。ADR-16） | **一部到達可** | AA-04 の 2.2 |
| T6 | `applied` → `verified` | 再計測はエージェント、**判定は `R3`** | `verification.state` を `improved` / `no_change` / `degraded` のいずれかで書き戻す | **到達可**（ファイル編集まで。正本への反映は T2 と同じくコミットが要る） | AA-04 の 2 節ステップ 6 |
| T7 | `applied` → `rolled_back` | **`R1`** または **`R2`** | `rollback.procedure` を実行 | **到達不能** | AA-04 の 3.3.1（適用先が Git の外にあるものを含むため） |
| T8 | `rejected` → （終端） | — | **削除しない** | — | AA-04 の 3.7（重複起票の検出に使う） |

- **T2 を `I-13` で自動化する場合も、エージェントは到達不能のままにする。** ADR-17 で `I-13` の主体が n8n から監視アプリの定期実行（ローカル）に移った。**この層では、起票を行うのはエージェントではなく監視アプリの決定論的な処理とし、GitHub のトークンを Claude Code の実行環境に置かない**と決めた（[06 の 2.4](06-proposal-loop-flows.md)。配信用の IAM を渡さないのと同じ形。TA-07 の 7 節）。エージェントにトークンを渡すと、T2 の行が `到達可` に変わる。

### 8.3 T5 の内訳

AA-04 の 2.2 の表を、到達可能性の観点から読み直す。

| `change.kind` | 適用の主体 | エージェントが到達できる範囲 |
|---|---|---|
| `content_rewrite` | エージェントが下書きを更新、**公開は `R2`**（本番の Strapi の管理画面で行う。ADR-17） | **下書きの更新まで到達可。** `publishedAt` の設定に到達できない（`agent/content-writer` に権限を与えない。AA-03 の 2.1。**本番では `strapi-prod` の Admin トークンに公開・非公開化の権限を与えない**。ADR-17） |
| `cta_swap` | エージェントが `E-06` の表示定義を更新、**ビルドとデプロイは `R1`** | 表示定義の更新まで到達可 |
| `internal_link` | 同上 | 同上 |
| `technical_seo` | **マージまで人間（`R1`）。** マージ後のデプロイは自動化してよい | **到達不能**（コードの変更はできるがコミットできない） |
| `accessibility`（2026-10-18 に追加。ADR-27） | `technical_seo` と同じ。加えて公開の前に人がスクリーンリーダーで確かめる（BA-04 の 3b） | **到達不能**（`technical_seo` と同じ） |
| `experiment_start` | **人間（`R3`）** | **到達不能** |
| `config_change` | **人間（`R1`）** | **到達不能**（加えて秘密値と `ACCESS_LEVEL` は `PreToolUse` フックがハード拒否する） |

**エージェントが単独で完結できる遷移は T1 と、T5 のうち 3 種の「定義の更新」だけである。**

**`applied_at` を記録する主体は、本番に作用させた主体に合わせる**（`R1` の 2026-09-19 の決定。AA-05 の ADR-16、TA-07 の 6 節）。

| 作用の手段 | `applied_at` を記録する主体 | 記録の時点 |
|---|---|---|
| MCP の本番用の登録での書き込み（Mautic・Chatwoot） | **エージェント（Claude Code）** | 書き込みの完了と同時 |
| 公開サイトの配信（`s3 sync` と CloudFront の無効化）。**本番の Strapi（`strapi-prod`）への記事の書き込みもこの行に従う**（ADR-17 の後は、エージェントの下書き → `R2` の公開 → ビルドと計測 → 配信の順。[05 の 3.2](05-build-and-delivery-flows.md)） | **配信した人間** | 配信の完了（**Strapi での公開の時点ではない**） |
| n8n のワークフローの有効化（`n8n-prod` で置いたもの） | **有効にした人間** | 有効化の完了 |

- **人間が記録する 2 つは、作用の操作と記録の操作が別になる。** 書き忘れると `approved` のまま残り、検証（T6）が始まらない（[06 の 1.5](06-proposal-loop-flows.md)）。
- **Strapi への書き込みを配信の行に入れたのはこの層の判断である。** 本番の Strapi に書いても、訪問者に届くのは配信の後である（ADR-11。公開ページは Strapi を実行時に参照しない）。検証は公開サイトの観測で行うため、書き込みの時点で `applied` にすると効果の無い期間を数えることになる。**（2026-09-19 解決）TA-07 の 6 節・BA-05・AA-04・DA-01 もこの判断に合わせた。**

### 8.4 禁止する遷移

**表に無い遷移は起こしてはならない。** とくに次の 3 つは、起きた場合に承認機構が破れている徴候として扱う。

| 禁止する遷移 | なぜ禁止か | 検出の手段 |
|---|---|---|
| `draft` → `applied`（`review` と `approved` を飛ばす） | 承認を経ずに作用した。承認機構が機能していない | `E-13` に `approval.state: approved` の記録と対応する PR 番号が無いのに `applied_at` がある |
| `applied` → `draft`（同じ提案の再利用） | 適用済みの提案を書き換えると、`verification` の対象が変わる。効果の帰属が崩れる | `applied_at` を持つファイルへの変更が Git の差分に現れる |
| `verified` → `applied`（再適用） | 同じ施策を 2 回適用すると、1 サイクル 3 件・同一対象 1 件の上限（AA-04 の 3.1）を回避できる | 同じ `proposal_id` に `applied_at` が 2 つ現れる |

検出の具体は [07 の 4 節](07-failure-and-degradation.md) に書く。

### 8.5 この表の使い方

**エージェントを追加するとき、この表で 1 行ずつ「そのエージェントが到達できるか」を確認する。** `到達不能` の行が 1 つでも `到達可` に変わったら、BA-03 の「Accountable をエージェントに置かない」が破れている。

確認は権限設定の読み合わせではなく、**そのエージェントのツール一覧に実行手段が現れないことの確認**で行う（AA-03 の 6 節・ADR-03「分類するのではなく到達できなくする」）。

## 9. ログと観測点

### 9.1 出力先

- **stdout は MCP の通信専用。** ログは必ず `console.error`（stderr）へ（`.claude/CLAUDE.md` の不変条件）。この規約は詳細設計のすべての実装に及ぶ。
- **ログ行の先頭に相関 ID を置く。** 形式は `<ULID> <レベル> <連携点 ID> <本文>`（例: `01JBQZ8F3K7XN2M5V9TWRC4HED WARN I-03 outcome=permission_denied attempts=1`）。
- **秘匿値をログに書かない。** MCP の `sanitize()` はモデルに返す値にしか効かず、ログには効かない。
- **stderr のログ行は `E-15` に取り込まない**（ADR-18 の追加の決定 4 を受けたこの層の判断）。`E-15` に残すのは要約・対象の ID・相関 ID・成否・起動の種類だけである（TA-07 の 3.6）。ログ行はこの列挙に無く、`sanitize()` も通らない（上流のエラー文に顧客の値が混ざりうる）。**失敗の分類は `E-12` の `fetch.outcome` に残る**（4.3）ため、`E-15` には実行の成否と要約があれば足りる。ログ行の相関 ID は、stderr の側から `E-15` の 1 件を引くために使う。

### 9.2 各連携が必ず持つ観測点

| 観測点の種類 | 何を見るか |
|---|---|
| 成功したこと | 成果物が生まれたか（`E-12` のファイル、Mautic の `E-09`、PostHog のイベント） |
| 失敗したこと | stderr のログに `outcome` が `ok` / `empty_but_ok` 以外の行が出たか |
| 沈黙したこと | **成果物も失敗ログも無い**状態。最も気づきにくいので、日次バッチの完了そのものを記録する（[07 の 3 節](07-failure-and-degradation.md)）。**ADR-17 で日次バッチの起動元が監視アプリになったため、起動した事実と見送った事実は監視アプリの側にも残る**（TA-07 の 3.5）。**ADR-18 でその記録が `E-15` の正本になった**（TA-07 の 3.6） |

**3 つ目が最も重要である。** 失敗は気づけるが、**そもそも動かなかったことには気づけない**。これが観測経路の断（暴走条件 #10。本番では ALB の後ろの障害と、本番の n8n のタスクの停止。ADR-16 の前は Webhook 用の ngrok のトンネル断も含んでいた）と欠測（#3）の検出が難しい理由にあたる。

- **`I-08` の重複排除の窓幅 24 時間に根拠が無い。** BA-04 のトスアップ条件との整合から選んだ暫定値であり、実データが取れるまで妥当性は分からない（AA-04 の 3.1 の上限値と同じ性質）。

- **（2026-09-19 解決）本番の Strapi への書き込みを `applied` とする時点**（8.3）。上位層（TA-07 の 6 節・BA-05・AA-04・DA-01）を「配信の完了」に合わせた。

- **手動の指示の 1 回で複数のエージェントが動いた場合の `E-15` の単位**（3.2.1。ADR-18 で新たに生じた）。TA-07 の 3.6 は「1 回の起動を 1 件」とし、DA-01 は `E-15` の属性に `agent_name`（1 つ）を置く。定期実行は 1 回の起動で 1 本のエージェントを動かすことで両者を一致させた（この層の判断）が、手動の指示では 1 件に複数のエージェントが入りうる。`agent_name` を複数持てるようにするか、手動の指示もエージェントごとに起動を分けるかを決めていない。判断者 `R1`。

- **ログの保持期間と保存先。** 9 節で stderr への出力を決めたが、**stderr がどこに残るか**は実行基盤に依存する（Claude Code から直接走る場合はセッションのログ、n8n から走る場合は実行履歴）。これは `E-15` の正本の問題と同じ根を持つ（TA-05 の監視設計待ち）。**ADR-17 でエージェントの起動元は監視アプリに一本化され、n8n からエージェントが走る経路は無くなった。** 置き場の候補は監視アプリの実行記録の 1 つに絞られたが、保持期間はまだ決めていない（判断者 `R1`）。**（2026-09-19 に ADR-18 で置き場は決着）監視アプリの実行記録が `E-15` の正本になった**（TA-07 の 3.6）。残るのは上位層の 3 つの未決定と同じもので、**実行記録に何を残すか**（ツールの結果を残すか、要約と ID だけか。stderr のログ行をどこまで取り込むか。本番の個人情報がローカルに残りうる）、**保持期間**、**開発機の外に写すか**である（TA-07 の 9 節。DA-05）。**ログ行を取り込むなら、9.1 の「秘匿値をログに書かない」に加えて個人情報も書かない形にする必要がある**（ログは `sanitize()` を通らない）。あわせて、**MCP サーバの stderr が Claude Agent SDK 経由で監視アプリに届くか**を実装時に確かめる（届かなければ、MCP サーバ側のログは `E-15` に入らない。TA-07 の 9 節の「Claude Agent SDK の仕様の確認」と同じ根）。**（2026-09-19 に ADR-18 の追加の決定で 2 つが決着）`E-15` には要約と ID だけを残し（決定 4）、S3 に追記専用で写す（決定 5）。** これを受けて、この層では **stderr のログ行を `E-15` に取り込まない**と決めた（9.1）。上の「個人情報も書かない形にする」「MCP サーバの stderr が届くか」は `E-15` の論点ではなくなった。**残るのは 2 つで、`E-15` の保持期間**（上位層の未決定。少なくとも検証の期間〈既定 30 日〉と `rollback.deadline` を覆う。TA-07 の 9 節）と、**`E-15` と切り離した stderr そのものの保存先と保持期間**である（監視アプリのプロセスのログか、Claude Code のセッションのログか。stderr は 9.2 の「失敗したこと」の観測点であり、`sanitize()` を通らないため、保存するなら `E-15` と違って開発機の外に写さず、短く持つのがこの層の見立て）。判断者 `R1`。
