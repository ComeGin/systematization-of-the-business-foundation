## 1. 秘匿値の管理方針

> **（2026-10-06）ADR-24: Cal.com は SaaS（cal.com）になった。** **Cal.com の鍵（セッションの秘密鍵・連携の暗号化の鍵）と、Cal.com 用の Google の OAuth クライアントシークレットを、ComeGin の Secrets Manager に置く必要はなくなった**（SaaS の側が持つ。TA-06 の 7 節の該当行は ADR-19 の記述）。**代わりに、Cal.com のアカウント（管理者のログイン・MFA・Google Calendar の接続・Webhook を使う場合の署名鍵）を人間（`R1` `R3`）が管理する**（認証情報は ComeGin の環境変数ファイルに置かない。無料プランでの管理者の数と MFA の可否は未確認）。**Cal.com は管理画面の関門（`admin-auth`）の保護対象から外れる**（管理画面は SaaS 側のログイン）。**公開サイトの CSP を設ける場合は、完了画面だけ Cal.com の配信元を許可する**（DD-02 の 7 節。許可するドメインは実測で確定する）。

> **（2026-10-06）ADR-25〈AA-05〉: Umami を廃止し、アクセス解析は GA4（SaaS）にした。** **Umami の秘密値（`APP_SECRET`・DB のパスワード・エージェント用の API キー）は、本番・開発とも置き場ごと無くなった**（Secrets Manager の `umami` の値・RDS の `umami` のユーザー・`~/.config/comegin/mcp/umami-dev.env`。開発機に残る `~/.config/comegin/setup/dev.state.json` の `UMAMI_*` と `umami-dev.env` はユーザーが片付ける）。**GA4 の測定 ID（`G-…`。`PUBLIC_GA4_MEASUREMENT_ID`・setup の `GA4_MEASUREMENT_ID`）とプロパティ ID（数字。`GA4_PROPERTY_ID`）は秘密値ではない**（測定 ID は公開サイトの HTML に出る）。**新しい秘密値は OpenSEO の GA4 の OAuth トークン**で、GSC と同じ OAuth クライアント・同じ置き場（OpenSEO の DB。8 節）になる。**公開サイトの CSP を設ける場合は GA4 のホストを許可する**（7 節の末尾）。

### 生成の仕組み（As-Is）

一部の Docker スタックには `dev/init-env.sh` が置かれており、これが環境変数ファイルを用意する。**5 スタックのうち 2 つにしか無い。**

| スタック | スクリプト | 状態 |
|---|---|---|
| n8n | `middleware/n8n/dev/init-env.sh` | `実装済み` |
| Chatwoot | `backend/chatwoot-system/dev/init-env.sh` | `実装済み` |
| Mautic | **無し**（`backend/mautic-system/docker/compose.yaml` が `${MYSQL_ROOT_PASSWORD:?...}` の形で必須化し、値は人間が手で置く） | `部分的` |
| Umami | **無し**（値が compose に直書きされており、置き場そのものが無い）。2026-10-06 に `middleware/umami/dev/init-env.sh` を足した（3 節）が、**同日の ADR-25 で Umami ごと廃止した** | **廃止**（ADR-25） |
| **OpenSEO** | **無し**（上流の手順どおり `.env.example` を複製して環境変数ファイルを作り、値を人間が置く。上流の compose が `env_file` でこのファイルを必須にし、起動時の preflight が値の欠落を検査する） | `部分的`（8 節） |

Mautic と Umami に生成の仕組みが無いことの意味は同じではない。Mautic は compose が `${MYSQL_ROOT_PASSWORD:?...}` の形で値の欠落を起動時に失敗させるため、**未設定のまま動いてしまうことは起きない**（値の生成を人間がやるだけ）。Umami は値が直書きされているため、**プレースホルダのまま正常に起動する**。危険なのは後者である（3 節）。（以上の Umami の記述は旧版。**ADR-25 で Umami を廃止した**）

スクリプトが守っている性質は 3 つある。

- **テンプレートから作る。** 追跡対象の `.env.example` を雛形として、追跡対象外の環境変数ファイルを作る。したがって新しい変数を足したときは `.env.example` を必ず同時に更新する（更新を忘れると、次に環境を作り直した人の手元でだけ変数が欠ける）。
- **冪等である。** 書き換えるのは「未定義・空・`.env.example` の初期値のままの項目」だけで、何度実行しても既存の値は変わらない。値を作り直したいときは**該当行を空にしてから再実行する**（スクリプトに「上書きする」オプションを持たせていないのは、取り返しのつかない上書きを手順の中に用意しないため。3 節の `N8N_ENCRYPTION_KEY` のような値が誤って再生成される事故を、機能として存在させないことで防いでいる）。
- **生成した値を画面に出さない。** 実行ログにもターミナルの履歴にも秘密値が残らない。

### 取り扱いの規則

| 規則 | 内容 | 根拠 |
|---|---|---|
| 実体を追跡しない | 秘密値を含む環境変数ファイルは各プロジェクトの `.gitignore` で除外する | リポジトリに入った秘密値は履歴から消せない |
| `.env.example` は必ず同時に更新する | キー名とコメントだけを置き、値は初期値かプレースホルダにする | 上記のとおり |
| エージェントは秘密値を読まない | `PreToolUse` フック（`~/.claude/hooks/protect-secrets.sh`）が該当パスをハード拒否する | BA-05 は「認証情報・秘密値の閲覧」を `禁止` に分類し、「手順としてではなく仕組みとして禁止する」と明記している |
| モデルへ返す前に伏せる | MCP サーバの `sanitize()` が `secret` / `token` / `password` / `api_key` / `hmac` を含むキーを `[redacted]` にする | 5 節 |
| 再帰検索は `rg` を使う | `rg` は `.gitignore` を尊重するため、除外済みの環境変数ファイルを自動的に読み飛ばす | フックはコマンド文字列に現れたパスしか見ないため、ディレクトリを再帰的に辿る経路は自衛が要る |

### AWS の認証情報（Amazon SNS）

ADR-08 により、n8n から Amazon SNS へ通知を発行する（TA-01 の経路 10）。**このための認証情報を最小権限で発行する。**

> **（2026-10-06）ADR-21 で、主体が再び変わった。次の表を優先し、その下の ADR-16 の表と文は旧版として残す。** 本番の n8n はオンプレに戻ったため、ECS のタスクロールは使えない。SNS への発行もハートビートの送信も、**IAM ユーザーのアクセスキー**で行う。実装は `cloud/stacks/iam.yaml`。
>
> | 項目 | オンプレの n8n（本番）→ SNS・CloudWatch | 監視アプリ（オンプレ）→ CloudWatch・S3 |
> |---|---|---|
> | 主体 | **IAM ユーザー `comegin-<env>-onprem-n8n-sns`**（管理ポリシー `comegin-<env>-onprem-n8n-sns`。**名前は変えない**。変えると作り直しになる） | 監視アプリ用の管理ポリシー `comegin-<env>-control-plane`（`ControlPlanePolicy`） |
> | 権限 | **`sns:Publish`**（`comegin-ops-alert`・`comegin-lead-alert` の 2 トピックに限定）＋ **`cloudwatch:PutMetricData`（条件キー `cloudwatch:namespace` = `ComeGin/OnpremN8n`。n8n のスケジュール実行のハートビートを送る）** | `s3:PutObject`（`E-15` の写しへの追記）＋ `cloudwatch:PutMetricData`（名前空間 `ComeGin/Onprem`。監視アプリのハートビート） |
> | 与えない権限 | `sns:Subscribe` / `sns:Unsubscribe` / `sns:SetTopicAttributes` / `sns:DeleteTopic`、`cloudwatch:PutMetricAlarm` / `DisableAlarmActions` / `DeleteAlarms`（自分への監視を止められない）、**監視アプリの名前空間 `ComeGin/Onprem` への送信**（n8n が監視アプリの生存を偽れない） | `s3:DeleteObject` ほか、アラームを変える権限、`sns:*` |
> | 置き場 | **本番の n8n の資格情報ストア**（種類は **AWS**。`AWS SNS 発行（アクセスキー）`。RDS の `n8n` に暗号化されて保存される。**`onprem/n8n/.env` には置かない**。人が IAM のコンソールでキーを発行して入れる。Assume Role と「システム資格情報」は使わない）。**SNS 用のノードとハートビートの HTTP Request ノード（`PutMetricData` の署名）が同じ資格情報を使う** | 監視アプリのサーバー側の環境変数だけ（Claude Code の実行環境に渡さない） |
> | 鍵の更新 | アクセスキーの定期交換の手順を決める（未決定事項。DD-04 の 8.7 と同じ） | 同左 |
>
> **ハートビートの送り手は 2 本で決着した**（TA-05 の項目 3・16・17）。**`ComeGin/Onprem`（改善ループの生存）の送り手は監視アプリ**（TA-07 の 8 節の「送り手を移すか」は、移したものとして決着）、**`ComeGin/OnpremN8n`・メトリクス `ScheduleHeartbeat`（本番の n8n のスケジュール実行の生存）の送り手は本番の n8n**。名前空間を分けるのは、**片方がもう片方の生存を偽れないようにするため**である。アラームは `cloud/stacks/observability.yaml` の 2 つ（通知先は ops のトピック。有効・無効のスイッチ `HeartbeatAlarmActionsEnabled` は共有）。**漏れたときにできること**: n8n の IAM ユーザーのキーが漏れても、できるのは「2 トピックへの発行（通知の偽装・無料枠の消費）」と「n8n のハートビートの偽装」であり、通知先は変えられず、監視アプリの生存は偽れない。

**ADR-16 で主体が 2 つに分かれた。** 旧版では、オンプレの n8n が 1 つの IAM ユーザーで SNS への発行とハートビートの送信の両方を行う前提だった。ADR-16 で本番の n8n が AWS に移り、ハートビートは開発環境の n8n が送る（暫定。TA-07 の 8 節）ため、次のように分ける（**本ファイルの判断**。TA-06 の 7 節の「n8n から SNS への発行はタスクロール」に合わせた）。

| 項目 | 本番の n8n（AWS）→ SNS | 開発環境の n8n（オンプレ）→ CloudWatch |
|---|---|---|
| 主体 | **タスクロール**（IAM ロール。アクセスキーを発行しない。TA-06 の 7 節） | **ハートビート専用の IAM ユーザー**（既存の `comegin-iam` を使い回さない） |
| 権限 | **`sns:Publish`** （リソースを `comegin-lead-alert` と `comegin-ops-alert` の 2 トピックに限定する） | **`cloudwatch:PutMetricData`**（条件キー `cloudwatch:namespace` で名前空間 `ComeGin/Onprem` に限定する。オンプレの生存信号〈ハートビート〉を送るため。TA-05 の 4 節） |
| 与えない権限 | **`sns:Subscribe` / `sns:Unsubscribe` / `sns:SetTopicAttributes` / `sns:DeleteTopic`** | **`sns:*` のすべて**（開発環境の通知は MailHog に送る。ADR-08）と、アラームを変える・止める権限 |
| 置き場 | —（タスクロールは資格情報を置く場所を持たない） | **開発環境の n8n の資格情報ストア**（環境変数ファイルの実体には置かない） |
| 鍵の更新 | 不要（一時認証情報が自動で更新される） | アクセスキーの定期交換の手順を決める（未決定事項） |

**ADR-16 でアクセスキーの管理対象が減った。** SNS に発行できる長期のアクセスキーは無くなり、残るのは名前空間を限定した `cloudwatch:PutMetricData` だけのキーである。漏れても、できるのはハートビートを偽って送ることだけになる（オンプレの全滅を隠せるが、通知先を変えることはできない）。

**ADR-17 で、ハートビートの送り手を監視アプリにすることを検討する**（未決定。TA-07 の 8 節・9 節）。エージェントの定期実行の起動元が監視アプリになり、監視アプリが生きていることこそ知りたい状態になったためである。移す場合は、上の表の「開発環境の n8n（オンプレ）→ CloudWatch」の主体が監視アプリに替わり、**ハートビート専用の IAM ユーザーのアクセスキーは監視アプリのサーバー側の環境変数に置く。Claude Code の実行環境には渡さない**（監視アプリが Claude Code を起動するときに環境変数を引き継がせない。TA-07 の 3.4 の Anthropic の API キーと同じく、サーバー側にだけ置く）。権限（`cloudwatch:PutMetricData` を名前空間 `ComeGin/Onprem` に限定）は変えない（**本ファイルの判断**）。

**本番の n8n のスケジュール実行を監視するためにハートビートを送らせる場合**（TA-05 の 4 節の項目 3。案）は、本番のタスクロールに `cloudwatch:PutMetricData` を**別の名前空間に限定して**足す。オンプレの名前空間（`ComeGin/Onprem`）とは分け、本番の n8n がオンプレの生存を偽れないようにする。

**`cloudwatch:PutMetricData` を足しても、この境界は崩れない。** 与えるのは生存信号を「送る」権限だけで、アラームを作る・変える・止める権限（`cloudwatch:PutMetricAlarm` / `cloudwatch:DisableAlarmActions` / `cloudwatch:DeleteAlarms`）は与えない。n8n が生存信号を送れなくなれば、アラームは欠損を違反として扱って通知する（止める側の権限が無いので、自分への監視を止められない）。

**`sns:Subscribe` と `sns:SetTopicAttributes` を与えないことが、この設計の要点にあたる。** 与えると **n8n が通知先を自分で書き換えられる＝自分への通知を止められる**。これは AA-03 の 6 節が「エージェントは自分の権限・実行条件を変更できない」として到達不能性で担保した構造と同じ形であり、**通知の側にも同じ境界を置く**。

- **トピックの作成と購読の設定は人間（`R1`）が行う。** n8n（本番のタスクロール・開発環境の IAM ユーザーのどちらにも）にもエージェントにも権限を与えない。
- **トピックポリシーで `sns:Unsubscribe` を制限する。** SNS の通知メールには購読解除リンクが付いており、**転送を受けた人でも解除できてしまう**（解除されると通知が静かに止まる。TA-05 の 4 節）。（**2026-10-04 追記**: 実装中に、SNS の公式ドキュメントでは、メールの解除リンクからの解除を止めるのはトピックポリシーではなく、購読の確認時に `ConfirmSubscription` へ `AuthenticateOnUnsubscribe=true` を付けることだと分かった。トピックポリシーの Deny は補助として残し、確認は `aws sns confirm-subscription --authenticate-on-unsubscribe true` で行う。手順は `cloud/README.md`。コンソールで確認 URL を貼り付ける方法でこのフラグが付くかは未確認）
- **購読の確認は受信者の手作業である**（自動化できない）。担当者変更の手順（BA-05）に購読の追加と削除を含める。

### AWS 上の秘密値（ADR-12・ADR-15・ADR-16）

AA-05 の ADR-12 で、Mautic・Chatwoot・Umami の本番を AWS（ECS on Fargate）に置くことになった（**Umami は 2026-10-06 の ADR-25 で廃止。下の表から Umami の値を外した**）。ADR-14 で加えた Strapi は ADR-15 で取り消し（Strapi はオンプレだけ）、**ADR-16 で Strapi と n8n の本番を AWS に置いた**。**本番の秘密値は環境変数ファイルではなく AWS Secrets Manager に置き、タスク定義の `secrets` で注入する。** 詳細は TA-06 の 7 節。

| 秘密値 | 本番の置き場 | 開発環境の置き場 |
|---|---|---|
| RDS のマスターパスワード | Secrets Manager（**RDS に管理させる**。タスクには渡さず、アプリ用のユーザーを別に作る） | —（Docker の `POSTGRES_PASSWORD` / `MYSQL_ROOT_PASSWORD`） |
| アプリ用の DB パスワード・ElastiCache の AUTH トークン（**Strapi と n8n の DB ユーザーを含む**。ADR-16） | Secrets Manager | 各スタックの環境変数ファイル（Strapi は SQLite のためパスワードが無い） |
| **SES の SMTP 認証情報**（Mautic 用と Chatwoot 用で別々に発行） | Secrets Manager | —（MailHog。認証なし） |

## 2. 変更してはいけない鍵

**この表の鍵を変更すると、既存の暗号化データを復号できなくなる。** 変更は BA-05 で `禁止` に分類されており、エージェントは行わない。人間が意図を持って行う場合のみ、データの移行手順と一体で実施する。

| 鍵 | 所在 | 変更したときに起きること | 分類 |
|---|---|---|---|
| `N8N_ENCRYPTION_KEY` | n8n の環境変数（**本番は Secrets Manager**。ADR-16。TA-06 の 7 節） | 保存済みクレデンシャルを復号できなくなる。ワークフローの形は残るが、接続先に繋がらない。**ADR-16 の後、本番の n8n は全システムの資格情報を持つため、失うと本番の自動化がすべて止まり、資格情報を全部登録し直すことになる** | `禁止` |
| `ACTIVE_RECORD_ENCRYPTION_PRIMARY_KEY` | Chatwoot の環境変数 | 暗号化済みの属性を復号できなくなる | `禁止` |
| `ACTIVE_RECORD_ENCRYPTION_DETERMINISTIC_KEY` | Chatwoot の環境変数 | 決定的暗号化された値での検索と復号ができなくなる | `禁止` |

| **`BETTER_AUTH_SECRET`**（`admin-auth`） | **`admin-auth` の Secrets Manager**（本番。TA-06 の 7 節） | **発行済みのセッションとトークンが無効になる。** 管理者は全員ログインし直しになる（ALB のセッションが残っている間は管理画面を使い続けられる）。保存しているのは許可リストとログインの記録だけで、失われる業務データは無い | 変更は `R1` の判断（`SECRET_KEY_BASE` と同じ扱い） |

**本番の Chatwoot・n8n の鍵は Secrets Manager に置く**（1 節）。所在が変わっても、変更したときに起きることは表のとおりで変わらない。

**本番の Strapi の鍵（`APP_KEYS`・`ADMIN_JWT_SECRET`・`API_TOKEN_SALT` など。ADR-16）も Secrets Manager に置く。** 表には載せていない。変更したときに起きることは、`ADMIN_JWT_SECRET` は管理画面のセッションの失効、`API_TOKEN_SALT` は発行済みの API トークン（ビルド用の読み取り専用のトークンを含む）の照合の失敗と想定しているが、**Strapi 5 の実装で確かめていない**（9 節）。確かめるまでは `SECRET_KEY_BASE` と同じく「変更は `R1` の判断」として扱う。

### `POSTGRES_PASSWORD` は性質が違う

`POSTGRES_PASSWORD` は**変更してもデータを失わないが、変更しても反映されない**。PostgreSQL / MySQL の公式イメージはデータディレクトリが空のときにだけ初期化処理を走らせるため、環境変数を書き換えても既存のボリュームには効かない（`backend/chatwoot-system/docker-compose.yaml` に「パスワードはボリューム初期化時にだけ反映される。後から変える場合はボリュームの作り直しが必要」とコメントがある）。

結果として、値を変えたつもりでアプリケーション側だけが新しいパスワードを使い、DB は古いパスワードのままで**接続できなくなる**という失敗の仕方をする。ローテーションが必要な場合は DB 側で `ALTER USER` を実行し、環境変数はそれに合わせる。**本番の RDS ではこの性質は無い**（ボリュームの初期化という概念が無く、マスターパスワードは RDS が管理する。アプリ用ユーザーのパスワードは DB 側と Secrets Manager を同時に変える）。

この区別は BA-05 の離任時チェックリスト（「共有していた認証情報をすべてローテーションしている」）を実行するときに効いてくる。**ローテーションしてよい値・してはいけない値・してもボリュームを作り直さないと効かない値**の 3 種があり、一律に扱うと壊す。

`middleware/umami-master/docker-compose.yml` には次の 4 点の問題がある。**本タスクの修正スコープ外**だが、事実として記録し、対処方針と方針上の衝突を明示する。

**ADR-12 の後、この 4 点は開発環境だけの課題になった。** 本番の Umami は ECS on Fargate で動き、この compose を使わない。本番では private サブネットに置いて ALB だけをインターネットに面させ（課題 1 が構成上起きない）、`APP_SECRET` などの値は Secrets Manager から注入し（課題 2・3）、DB は RDS のアプリ用ユーザーで接続する（課題 4）。設計は TA-06 の 5.6・7 節。**開発環境では 4 点とも残る。**

| # | 課題 | 現状 | 影響 |
|---|---|---|---|
| 1 | 全インターフェース公開 | `"3000:3000"` と書かれており、`127.0.0.1` にバインドしていない | 同一ネットワーク上の他の端末から管理画面に到達できる。n8n・Chatwoot・Mautic はすべて明示的にループバックへバインドしているため、**Umami だけが例外** |
| 2 | `APP_SECRET` がプレースホルダ | `replace-me-with-a-random-string` のまま | セッション・トークンの署名鍵が公開されている既知の文字列である。到達できれば偽造が成立しうる |
| 3 | 二要素認証の鍵がプレースホルダ | `TWO_FACTOR_ENCRYPTION_KEY` が `replace-me-with-a-64-character-hex-string` のまま | 二要素認証を有効にしても、その秘密が既知の鍵で暗号化される。**「2FA を入れたから安全」という判断が成立しない** |
| 4 | DB 認証が `umami` / `umami` | `POSTGRES_PASSWORD: umami`、`DATABASE_URL` も同じ値を直書き | 課題 1 と組み合わさると影響が広がる（ただし DB 自体はホストへ公開していない） |

さらに、これら 4 点に共通する根の問題がある。

- **compose に秘密値を直書きしており、環境変数の間接参照すら使っていない。** 他のスタックは `${APP_SECRET:?...}` のような参照を書き、値を追跡対象外のファイルに置いている。Umami はこの形になっていないため、**`dev/init-env.sh` による生成機構を適用する余地が構造的に存在しない**（生成した値を書き込む先が無い。書き込むなら compose 本体を書き換えることになり、それは追跡対象のファイルに秘密値を入れることを意味する）。

### 課題 1〜4 が同時に存在する理由

4 点はいずれも上流の compose をそのまま取り込んだ結果であり、個別の判断ミスではない。`middleware/umami-master` は上流のファイルを無改変で取り込んだ（2026-09-18 に v3.4.0 の 2,026 ファイルへ取り込み直した）ディレクトリであり、その中の `docker-compose.yml` は**上流が「まず動かしてみる」ために提供しているサンプル**である。サンプルにプレースホルダが入っているのは上流の問題ではなく、それを運用に使っていることが問題にあたる。

### 対処方針

| 課題 | 対処 | 状態 |
|---|---|---|
| 1 | `127.0.0.1:3000:3000` にバインドし直す | **対処済み**（2026-10-06。`middleware/umami/compose.yml`。`ss -ltn` で `127.0.0.1:3000` だけを確認） |
| 2 | `APP_SECRET` を生成し、追跡対象外のファイルから参照する | **対処済み**（`${APP_SECRET:?...}` で `.env`〈追跡対象外〉を参照。未設定なら compose が失敗する） |
| 3 | `TWO_FACTOR_ENCRYPTION_KEY` を生成する（`openssl rand -hex 32`。上流のコメントに生成方法が書かれている） | **対処済み**（64 桁の hex を生成。同上） |
| 4 | `POSTGRES_PASSWORD` を生成する。**ボリュームの初期化前に行う**（2 節のとおり、後から変えても反映されない） | **対処済み**（32 文字の英数字を生成。新しいボリューム `umami_db-data` の初期化前に行った。`dev/init-env.sh` は、`POSTGRES_PASSWORD` を新しく書いたときに同名のボリュームが既にあれば警告する） |
| 共通 | `dev/init-env.sh` 相当を追加し、上記 3 つの値を冪等に生成させる | **対処済み**（`middleware/umami/dev/init-env.sh`。未定義・空・例の初期値のままの項目だけ書き換える。2 回目の実行で全部「維持」になることを確認。値は表示しない） |

**確認していない点**: 新しい DB に対する setup の `apply` の通し実行（管理者の設定し直し〜API キー〜MCP の確認）は、Wave 4 でユーザーが行う（実行する前の `check` では「API キーが無効」と報告される状態）。**OpenSEO は今回この表の対象ではないが、イメージが `latest` のまま・匿名のテレメトリが有効のままである**（9 節の未決定事項）。

### 上流を無改変に保つ方針とセキュリティ要件の衝突

**この 2 つは両立しない。** 対処方針を実行するには `middleware/umami-master/docker-compose.yml` を書き換えるか、その compose を使わないかのどちらかしかない。

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A | 上流の `docker-compose.yml` を直接書き換える | 変更が最小 | 上流を無改変に保つ方針を破る。上流を更新するたびに衝突する。**8,500 ファイルの取り込み全体について「どこを改変したか」を追う必要が生じる**（1 か所でも改変すると、無改変という前提そのものが失われる） |
| B | `docker-compose.override.yml` を足す | 上流ファイルを 1 バイトも変えない。Compose が自動で読む | **`ports` は既定でリストが連結されるため、単純な override では `"3000:3000"` を取り消せない。** Compose の `!override` タグ（Compose v2.24 以降）でリストごと置き換える必要がある。本セッションでは実際に適用して確認していない |
| C | Umami を他のスタックと同じ形にする（`middleware/umami` に自作の compose と `dev/init-env.sh` を置き、上流の compose を使わない） | 上流ディレクトリに一切触れない。`backend/chatwoot-system` や `middleware/n8n` と同じ「公式イメージを動かすための compose と環境変数テンプレートだけを自作する」形に揃う。リポジトリの命名規則とも整合する | 上流の compose 更新に自動では追随しない（ただし Umami の compose は 2 サービスと 1 ボリュームだけで、追随の負担は小さい） |

**推奨は C（2026-10-06 に採用した。`middleware/umami`）。** 上流の取り込みを「読むための資料」として無改変に保ったまま、運用する実体は自作側に置くという分離になり、リポジトリ全体の構成（自作 8,500 対 160 の区別）と矛盾しない。B は上流ファイルを変えない点で魅力的だが、`ports` の連結という一点で目的（課題 1 の解消）を達成できない可能性があり、その確認ができていない状態で採用できない。

**旧版では「ngrok による露出が決まったことで、課題 1 の重みが増した」と書いていた。** Umami を開発機からトンネルで公開する前提では、`0.0.0.0` のままだとトンネルにいくら認証をかけても同一ネットワークから素通りで管理画面に到達できたためである。**ADR-12 で本番の Umami は AWS に移り、開発機の Umami をトンネルで公開する経路は無くなった**（TA-01 の 7 節）。課題 1 の影響は「同一ネットワーク上の他の端末から開発環境の管理画面に到達できる」ことに戻った。

なお **Umami は現在どの構成要素とも配線されていない**。この対処は「今すぐ壊れているものを直す」作業ではない。**`CAP-10` の前提条件は、本番については TA-06 の構成（Secrets Manager の値と RDS のユーザーを、トラッカーを設置する前に用意すること）に移った。** 開発環境の課題 4 は、開発用のデータが入り始める前に直すほうが安い（後から直すとボリュームの作り直しが要る）。

## 4. n8n の sandbox 分離

`middleware/n8n/compose.yml` では、`sandbox-api` と `sandbox-runner-1` にだけ環境変数ファイルを渡していない。必要な変数を `environment:` に個別に列挙している。

| サービス | 環境変数ファイル | 渡している値 | 理由 |
|---|---|---|---|
| `n8n` | 渡す | 全体 ＋ DB 接続 | 本体はすべてを必要とする |
| `sandbox-api` | **渡さない** | サンドボックスの API キー・登録トークン・mTLS の証明書パスのみ | 暗号化キー・DB パスワード・モデル API キーを渡さない（公式のセキュリティチェックリストに準拠） |
| `sandbox-runner-1` | **渡さない** | 同上 | **`privileged: true` の Docker-in-Docker であり、公式も「ホストの root 相当」と警告している** |
| `runners` | 渡さない | 共有シークレットとタイムゾーンのみ | Code ノードのユーザーコードを実行する |
| `searxng` | 渡さない | `SEARXNG_SECRET` のみ | 内部からのみ利用する |

**この分離を崩さない。** 制約として明記する。

理由は 2 段ある。

1. **直接の理由**: `sandbox-runner-1` はホストの root 相当の権限を持つ。ここに `N8N_ENCRYPTION_KEY` や DB パスワードが渡っていれば、サンドボックス内で実行される任意のコードからそれらが読める。サンドボックスは本来「信頼できないコードを隔離して動かす」ためのものなので、そこに最高権限の秘密値を置くのは目的と正反対にあたる。
2. **ガバナンス上の理由**: BA-05 が明示しているとおり、この分離が崩れると**ワークフローから `禁止` 分類の操作に到達できる**。承認ゲートの一覧は「エージェントが何をしてよいか」を定義しているが、その定義が有効なのは、定義の外側に回り込む経路が無い場合に限る。sandbox の分離はその回り込みを塞ぐ構造の一部である。

**本番の n8n にはサンドボックスを置かない**（AA-05 の ADR-16。TA-06 の 3.1）。`sandbox-runner-1` は privileged な Docker-in-Docker であり、Fargate は privileged のコンテナを受け付けない。本番のタスクは本体（`n8n`）と `runners` だけで、**上の表のうちサンドボックスの 2 行は開発環境だけの事実になる**。本番でもこの分離の考え方は保つ。

- **`runners` に渡すのは `N8N_RUNNERS_AUTH_TOKEN` とタイムゾーンだけにする**（本番はタスク定義の `secrets` でサイドカーに注入する。TA-06 の 7 節）。`N8N_ENCRYPTION_KEY` と DB のパスワードは本体のコンテナにだけ渡す。**同じタスクのサイドカーでもコンテナごとに渡す値を分けられる**ため、「同じタスクだから同じ値」にしない。
- **本番のワークフローがサンドボックスを必要とした時点で、n8n を EC2 起動タイプの ECS に移す**（ADR-16）。そのときは、この節の分離（`sandbox-api` / `sandbox-runner-1` に暗号化キーや DB パスワードを渡さない）を本番にもそのまま持ち込む。
- **本番の n8n のタスクは、共有の RDS for PostgreSQL に届く**（`n8n` データベースを使うため。TA-06 の 4.3）。ワークフローの Code ノードから、同じインスタンスの他のデータベース（`chatwoot` / `strapi` / `admin_auth`。**`umami` は ADR-25 で削除**）に接続を試みることはネットワーク上はできる。**守りはデータベースごとのユーザーの分離だけ**であり、n8n のユーザーに他のデータベースへの権限を与えない。

関連する運用上の制約。

- `n8nio/n8n` と `n8nio/runners` のバージョンは必ず一致させる（`N8N_VERSION`）。ずれると task runner の認証・プロトコルが噛み合わない。本番でも同じ（TA-06 の 3.2）。
- `sandbox-certs` が作る mTLS 証明書は自動更新されない。期限が切れたら `sandbox-tls` ボリュームを作り直す。
- `sandbox-api` の 8080 / 9090、`sandbox-runner-1` のポートは**ホストに公開しない**。compose にその旨のコメントがある。

## 5. MCP サーバの権限設計

`backend/chatwoot-mcp` と `backend/mautic-mcp` は意図的に同じ構造を取っている。**これがエージェント層の権限の土台であり、AA が設計するエージェントの権限はこの上に載る。** ADR-15（2026-09-19。ADR-14 の「接続先は開発環境だけ」を改めた）で、**同じ MCP サーバを開発用と本番用に 2 回登録し、本番用は `ACCESS_LEVEL` を `read_write` までにする**（TA-07 の 3.3。ADR-15 では暫定、ADR-16 で確定）。`ACCESS_LEVEL` が絞るのは「どのツールを使えるか」、登録（接続先と資格情報）が絞るのは「どの環境に届くか」であり、2 つは別の層で効く。エージェントは監視アプリ（TA-07）から Claude Agent SDK 経由で起動される。

**ADR-16 で、リポジトリ管理外の本番用の登録が 2 つ加わった。** `strapi-prod`（Strapi の組み込みの `/mcp`）と `n8n-prod`（n8n の `/mcp-server/http`。暫定）である。どちらも製品の組み込みの MCP で、本節の不変条件（`ACCESS_LEVEL` の「登録しない」・`sanitize()`・`CHARACTER_LIMIT`）は及ばない。**絞る手段は製品側のトークンの権限と、エージェント定義のツールの許可リストだけになる**（下の「上流 API への認証の違い」）。

### 守っている不変条件

| 不変条件 | 実装 | なぜそうするか |
|---|---|---|
| **`ACCESS_LEVEL` は「許可されないツールを登録しない」ことで実装する** | `read_only` ⊂ `read_write` ⊂ `full`。`register*Tools(server, ctx, accessLevel?)` が登録するツールを絞る | 実行時に拒否する方式だと、モデルからは「存在するが拒否される機能」に見える。モデルは拒否されると迂回路を探す。**登録しなければモデルからは存在しないため、迂回の動機自体が生じない**。`chatwoot-mcp` の verify はこの包含関係を検査している |
| HTTP トランスポートの認証は固定 Bearer | `MCP_AUTH_TOKEN`（32 文字以上）。比較は SHA-256 ダイジェスト同士の `timingSafeEqual` | ダイジェスト同士を比較するのは長さの違いで早期に失敗しないようにするため。`timingSafeEqual` はタイミング差から値を推測されないようにするため |
| stdio では認証しない | `TRANSPORT=stdio` のとき `MCP_AUTH_TOKEN` は不要（`config.ts` の `refine`） | プロセスを起動できる権限がそのまま権限になる。別途トークンを置いても保護の層が増えない |
| **stdout は MCP の通信専用** | ログは必ず `console.error`（stderr）へ | stdout に 1 行でも余計な出力が混ざると、MCP のフレーミングが壊れてクライアントとの接続が切れる |
| 設定の失敗は「変数名と理由だけ」を出す | `src/config.ts` が zod で検証し、失敗時に値を出さずに `exit(1)` | エラーメッセージ経由で秘密値が漏れる経路を塞ぐ |
| **モデルに返す前に必ず `sanitize()` を通す** | `secret` / `token` / `password` / `api_key` / `hmac` を含むキーは `[redacted]`。`LONG_TEXT_LIMIT` 超の文字列は `include_long_text=true` がない限り省略。例外は `NON_SECRET_KEYS`（`website_token` など公開前提の値） | BA-05 の「認証情報・秘密値の閲覧」`禁止` を、手順ではなく仕組みで実現している箇所 |
| 応答サイズは `CHARACTER_LIMIT` に収める | 一覧系は `fitToLimit()` で件数を半分ずつ減らし、`truncation_message` を添える | 上流のページサイズが固定のため、こちら側で件数を制御するしかない |
| 更新は `PATCH` 相当のみ | Mautic の `PUT` は使わない | `PUT` は存在しない ID を渡すと新規作成してしまう（更新のつもりが作成になる事故を、手段を持たないことで防ぐ） |
| 破壊的操作には `destructiveHint: true` | `src/tools/annotations.ts` の `READ_ONLY` / `CREATE` / `DESTRUCTIVE` | クライアント側の確認に委ねる。BA-05 の「レコード削除は `R1` の承認」と対応する |

### 上流 API への認証の違い

| 製品 | 方式 | 帰結 |
|---|---|---|
| Chatwoot | `api_access_token` ヘッダー | **トークンはユーザーに紐づく。** 権限も操作履歴もそのユーザーのものになる。したがって MCP 用の専用エージェントユーザーを作り、その権限を絞ることが、そのまま MCP の権限設計になる |
| Mautic | OAuth2 client_credentials | トークンをプロセス内でキャッシュし、期限 60 秒前に更新。401 では 1 回だけ再取得する。API クライアントの権限は紐づくユーザーに依存する |
| ~~Umami（Umami MCP。管理外）~~ **2026-10-06 ADR-25 で廃止**（`umami`・`umami-prod` の登録を外した） | （旧）API キー（Bearer） | 旧版: キーはユーザーに紐づき、閲覧専用のユーザーで発行することが MCP の権限設計だった |
| **GA4（OpenSEO の MCP 経由。管理外。2026-10-06 に追加。ADR-25）** | **OpenSEO が持つ Google の OAuth トークン**（スコープ `analytics.readonly`。8 節）。OpenSEO の MCP 自体は無認証（`local_noauth`。`127.0.0.1` に閉じることが守り） | **GA4 への書き込みの経路は無い**（スコープが参照のみ）。エージェントが使える GA4 のツールは **analytics-reporter の許可リストの 5 本**（`get_google_analytics_traffic_acquisition`・`page_performance`・`organic_landing_pages`・`organic_overview`・`measurement_health`）だけで、他のエージェントには持たせない（AA-03 の 2.4）。**ただし OpenSEO の MCP は 1 つの登録（`openseo`）で費用の出るツールも公開するため、守りはエージェント定義の許可リスト（使えるが使わせない）になる**（ADR-10 と同じ） |
| **Strapi（Strapi の組み込みの MCP。管理外。ADR-16）** | **Admin トークン**（Strapi の管理画面で発行） | **MCP のツールはトークンに与えた権限の範囲に絞られる**（AA-05 の ADR-16）。本番のトークンには削除の権限を与えない（`read_write` 相当）。これが `strapi-prod` にとっての `ACCESS_LEVEL` の代わりになる（ADR-07 の「`strapi-mcp` には `ACCESS_LEVEL` 相当の境界が無い」は、本番ではトークンの権限で埋まる）。ADR-16 の反映では公開（publish）の権限を与えるかを未決定にしていた。**ADR-17 で、公開・非公開化・削除の権限を与えず、下書きまで（作成・読み取り・更新）に絞ると決めた**（公開は `R2` が管理画面で行う。ADR-03 の「許可されないものは登録しない」と同じ考え方で、承認を仕組みで守る）。**Strapi 5 の Admin トークンで公開だけを外せるかは未確認**（9 節） |
| **ビルド（Strapi の Content API。ADR-16）** | **API トークン（読み取り専用）** | MCP ではなく、ローカルの `astro build` が使う。書き込みの権限を持たないため、漏れても読めるのは Content API に公開した範囲だけ（下書きを含めるかは Strapi 側の設定による） |
| **n8n（n8n のインスタンスの MCP。管理外。ADR-16。暫定）** | **n8n の MCP のアクセストークン** | **トークンでツールの範囲を絞れるかを確認していない。** `n8n-prod` を「ワークフローの作成と更新まで。有効化と実行は許さない」（TA-07 の 3.3）に絞る手段が、エージェント定義のツールの許可リストしか無い場合、**ADR-03 の「登録しない」より弱い守り（使えるが使わせない）になる**（9 節） |

### AA への引き渡し

**エージェントの権限設計は、この土台の上でのみ成立する。** AA が守るべき対応関係を明示する。

| BA-05 の分類 | 対応する `ACCESS_LEVEL` | AA が設計すること |
|---|---|---|
| `自律`（読み取り） | `read_only` | 観測・分析・提案生成を行うエージェントは `read_only` で起動する |
| `自律`（作成系。下書き・社内メモ・コンタクト作成） | `read_write` | 作成してよい対象に限って `read_write` を与える |
| `承認`（公開・送信・削除） | `read_write` または `full` ＋ **人間の承認** | `ACCESS_LEVEL` を上げることは承認の代わりにならない。ツールが登録されていることと、使ってよいことは別である |
| `禁止`（権限の変更・秘密値の閲覧） | どの `ACCESS_LEVEL` でも到達しない | MCP に該当するツールが存在しない。AA はこの前提に依存してよい（**ただしリポジトリ管理外の MCP は例外**。`strapi-mcp` / `strapi-prod` / Umami MCP〈**ADR-25 で廃止**〉は AA-05 の ADR-07、OpenSEO は ADR-10〈**ADR-25 で GA4 の読み取りも OpenSEO の MCP になった**〉、**`n8n-prod` は ADR-16**。とくに n8n の MCP はワークフローを作れるため、**ワークフローを介して n8n に保存した全資格情報を使う操作に到達しうる**。有効化を人間に残すことがこの経路の守りになる） |

- **本番用の登録は `read_write` を上限にする**（ADR-15 で暫定、ADR-16 で確定）。上の表の `full` は開発環境だけで使う。本番のレコード削除・統合は、人間が本番の管理画面で行う。`strapi-prod` は Admin トークンの権限で、`n8n-prod` はツールの許可リストで同じ範囲に絞る。
- **`read_write` には Chatwoot の顧客へのメッセージ送信が含まれ、ADR-16 で本番でも許すと決めた**（`chatwoot-prod` から送信系のツールを外さない）。送信の分類は BA-05 のとおり `承認`（`R3`）であり、`ACCESS_LEVEL` を上げることが承認の代わりにならないのは上の表のとおり。ADR-16 の反映では「誤った送信は Chatwoot の監査ログ（Enterprise の `audit_logs`。Community 版ではエージェント専用ユーザーの `sender`）と `E-13` の突き合わせで見つける」としていた。**ADR-17 で監査ログには頼らず、エージェント専用ユーザーの送信の記録（`sender`）と `E-13` を、監視アプリの定期実行で突き合わせることにした**（TA-07 の 6.2）。**拾えるのは送信だけで、会話の属性（担当者・ラベル・状態）の変更は拾えない。**
- **社内メモと顧客への送信を分ける**（ADR-17）。`read_write` は上の表の「作成系（社内メモ）」と「送信（`承認`）」を同じ段で登録する。しかも `chatwoot_send_message` は両方を 1 つのツールで兼ね、`private` の既定値が `false`（顧客に送信）であるため、**社内メモのつもりの呼び出しで `private` を付け忘れると、取り消せない送信が起きる。** **社内メモ専用のツールを `chatwoot-mcp` に足すか、社内メモ用の登録を分けて**、社内メモだけを使うエージェントの許可リストに `chatwoot_send_message` を載せない。どちらにするかは未決定（TA-07 の 9 節）。ツールを足す場合、`ACCESS_LEVEL` のどの段に登録するか（社内メモだけを登録する段を設けるか）も合わせて決める（**本ファイルが見つけた論点**。ADR-03 の「登録しない」で分けるなら段が要り、許可リストで分けるなら「使えるが使わせない」の弱い守りになる）。
- **最小権限を既定にする。** BA-05 のとおり `read_only` から始め、必要が生じた Capability ごとに引き上げる。引き上げは `R1` の承認事項。
- **`ACCESS_LEVEL` の引き上げをエージェント自身にさせない。** BA-05 で `禁止` に分類されている。エージェントが自分の権限を変えられると、承認を求める主体と承認の条件を決める主体が同じになり、承認では守れなくなる。
- **エージェントの権限は人間の SSO の外側で管理する。** 6 節。

## 6. SSO の技術的実現方式

### 現状

**SSO は未導入である。** 対象システムはすべて個別のアカウントを持ち、認証情報も個別に管理されている（BA-05 の As-Is 表）。README の「シングルサインオン（SSO）やアクセス権限制御を徹底し」は To-Be の記述である。

BA-05 は導入契機を「担当者の数が 2 名を超えた時点」とし、対象を「人間がログインするシステム」に限っている。本節はその方針を受けて、技術的に実現できるかを検討する。

### 各システムの SSO 対応可否

### この表から導かれる結論

**全システムを 1 つの IdP に寄せることはできない。**
BA-05 は「Umami と n8n の Community 版は SSO 対応が限定的」と書いているが、実際にはそれより範囲が広く、**Strapi・Chatwoot・n8n が上位エディション、Umami が非対応、PostHog と GitHub が有料プラン**という状況にある（**2026-10-06 ADR-25: Umami は廃止し、後継の GA4 は Google Workspace のアカウントでログインする**）。対象 6 システムのうち、追加費用なしで SSO に寄せられるものはおそらく 1 つも無い。

**だから代替策を採る。** SSO は将来の目標として残し、当面のガバナンスは次の 3 点で成立させる（決定事項）。

| # | 代替策 | 実現手段 | 状態 |
|---|---|---|---|
| 1 | **アクセス経路を絞る** | **本番の Strapi・Mautic・Chatwoot・n8n の管理画面（Umami は ADR-25 で廃止）は、ALB の OIDC 認証（IdP は自作の `admin-auth`〈Better Auth〉、ログインは Google Workspace）。機械向けの API は製品側の認証 ＋ WAF のレート制限。訪問者向けのパスは認証・認可をせず WAF のレート制限だけ**（TA-06 の 5.2・5.2.1）。**ローカルに残るもの（OpenSEO・監視アプリ・全システムの開発環境）はループバックバインド**のまま（7 節）。Strapi と n8n は ADR-15 まではループバックの側にあったが、ADR-16 で本番を AWS に置き ALB の側に移った | `未着手` |
| 2 | **パスワード管理** | パスワードマネージャによる認証情報の集約 ＋ 各システムの二要素認証 | `未着手` |

#### 代替策 1 の実現手段が変わった（重要）

本ファイルの初版では、代替策 1 を「ほぼ全システムが `127.0.0.1` にバインドされているため、開発機に入れる人だけがログイン画面に到達できる。開発機の OS ログインが事実上の第 1 関門になっている」という形で書いていた。

**TA-01 で ngrok の常設トンネルによる露出が決定したため、この前提は崩れる。** 管理画面をトンネル越しに開いた時点で、開発機の OS ログインは関門ではなくなる（トンネルの URL を知っていれば、誰の開発機にも入らずにログイン画面へ到達できる）。

したがって代替策 1 の実現手段は、**ループバックバインドから ngrok 側の認証（OAuth / Basic 認証 / IP 制限など）へ移る**。移行にあたっての約束を 3 つ置く。

- **認証は ngrok の手前でかける。** 各製品のログイン画面を第 1 関門にしない（製品ごとに強度がばらつき、Umami〈ADR-25 で廃止〉のように二要素認証が実質機能しない製品もあるため。3 節の課題 3）。
- **管理画面のトンネルを、認証を設定する前に開かない。** 開けた瞬間から探索の対象になる。順序として「認証の設定 → トンネルの公開」を守る。
- **無認証で開く経路（訪問者向け）と要認証の経路（運用者向け）を混在させない。** 7 節で分離する。

#### 代替策 1 の実現手段が再び変わった（ADR-12）

**2026-09-18 の ADR-12 で、管理画面を ngrok で露出する前提そのものが無くなった。** 本番の Mautic・Chatwoot・Umami（ADR-25 で廃止）は AWS に移り、管理画面は ALB の後ろに置かれる。オンプレに残る n8n・Strapi・OpenSEO には運用者向けのトンネルを張らない（TA-01 の 7 節。ngrok に残るのは n8n の Webhook と Astro dev サーバーだけ）。

**2026-09-19 の ADR-16 で、Strapi と n8n の本番も AWS に移った。** 本番の Strapi の `/admin` と n8n のエディターは、Mautic・Chatwoot・Umami と同じく ALB の関門の内側に置く。**管理画面がインターネットに面する数は 3 つから 5 つに増えた**（AA-05 の ADR-16 の欠点として受け入れた）。（**2026-10-06: ADR-21 で Strapi・n8n はオンプレの `127.0.0.1` に、ADR-25 で Umami は廃止になり、ALB の関門の内側の管理画面は Mautic・Chatwoot の 2 つ〈と `admin-auth`〉になった**）ローカルに残るのは OpenSEO・監視アプリ・全システムの開発環境だけで、ngrok に残るのは Astro dev サーバーだけである（TA-01 の 7 節）。

| 対象 | 関門 | 根拠 |
|---|---|---|
| Mautic・Chatwoot・**Strapi（`/admin`）・n8n（エディター）**の管理画面（**Umami は ADR-25 で廃止**）（本番。**オンプレの PC のブラウザから開く**。ADR-14。Strapi と n8n は ADR-16） | **ALB の `authenticate-oidc`。IdP は自作の `admin-auth`（Better Auth の OAuth 2.1 Provider ＋ JWT プラグイン。`auth.comegin.com`）**（`R1` の 2026-09-18 の決定。AA-05 の ADR-13）。`admin-auth` は Google Workspace の OIDC でログインさせ（OAuth クライアントは「内部」）、**ID トークンの `hd` クレームが `comegin.com` であることをサーバー側で検査し、管理者の許可リストに載っている email だけを通す。** MFA は **Google Workspace の 2 段階認証を組織で必須にする**。ALB のセッションは 12 時間（43,200 秒） | TA-06 の 5.2.1。**製品の SSO ではなく、製品の手前にかける関門である**（本節の「SSO を導入しない」判断とは別の層）。各製品のログインはこれまでどおり各製品のアカウントで行う。Workspace のアカウントと許可リストの追加・削除は BA-05 の担当者変更チェックリストに含める |
| 同上の API（ローカルの Claude Code の MCP〈本番用の登録〉とビルドから。ADR-15・ADR-16。**監視アプリの定期実行が公開を確かめる読み取りも含む**。ADR-17。**n8n からの API は ADR-16 で VPC の中に移り、ALB を通らない**） | **ALB では認証をかけない。** 製品側の認証（Chatwoot の `api_access_token`、Mautic の OAuth2 client_credentials、Strapi の Admin トークンと読み取り専用の API トークン、n8n の MCP のアクセストークン）＋ **WAF のレート制限**。通すのは Chatwoot の `/api/v1/accounts/*`・`/api/v2/accounts/*`、Mautic の `/api/*`・`/oauth/v2/token`、（Umami の `/mcp` は ADR-25 で廃止）**Strapi の `/mcp` と `/api/*`（Content API）、n8n の `/mcp-server/http`**（ADR-16）だけ | ブラウザでのログインができないため。オンプレの送信元 IP は固定ではなく、IP での許可は採らない（`R1` の 2026-09-18 の判断）。**Mautic の API の Basic 認証（`api_enable_basic_auth`）は無効のまま**にする（有効にすると、パスワードでログインする口が管理者の認証の外に出る） |
| OpenSEO と、全システムの開発環境（**Strapi・n8n の開発環境を含む**）の管理画面（オンプレ） | **ループバックバインド**（開発機の OS ログインが第 1 関門） | 初版の形に戻る。トンネルを張らない限り、開発機に入れる人だけが到達できる。ADR-15 までは n8n・Strapi の本番もここにあったが、ADR-16 で AWS に移った |
| **監視アプリ（Next.js。オンプレ。3200）** | **ループバックバインド ＋ Better Auth のログイン**（TA-07 の 3.4） | **エージェントを動かせる入口**であり、到達できる人は開発環境と本番の Strapi・Mautic・Chatwoot・n8n に対して MCP の書き込み権限の範囲で何でもできる（ADR-15・ADR-16。Umami は ADR-25 で廃止。GA4 は OpenSEO 経由の読み取りだけ）。**ADR-17 でエージェントの定期実行の起動元にもなった**（スケジュールの定義を書き換えられる人は、定期実行の取得の範囲と作用を変えられる）。トンネルを張らない（OpenSEO と同じ扱い） |
| Astro dev サーバー（オンプレ） | ngrok（現状は `allowedHosts` の Host 照合のみ） | TA-01 の経路 6。9 節の未決定事項 |

**訪問者向けの経路（ウィジェット・フォーム・トラッカー・メールの計測。TA-06 の 5.3）は、認証も認可もしない。WAF のレート制限だけをかける**（`R1` の 2026-09-18 の決定）。訪問者にログインを求めることはできないため、1 つの送信元から短時間に大量のリクエストが来ることだけを防ぐ。

**`admin-auth` はベンダーを増やさない。** Google Workspace は GSC の OAuth で既に使っており（8 節）、Better Auth はライブラリ、`admin-auth` は自作のサービスである。**管理画面への通信は `admin-auth` を通らない**（ログインのときだけ関わり、その後は ALB のセッション Cookie で判定される）。`admin-auth` が止まると新しいログインだけができなくなり、既存のセッションと訪問者向けの機能は影響を受けない。**Google Workspace の在籍（認証）と、管理画面に入ってよいこと（認可）を分ける**のが、Google を ALB の IdP に直接使わず Better Auth を挟む理由である（ADR-13）。

**旧版の 3 つの約束は ALB にそのまま引き継ぐ。** 認証は製品の手前（ALB）でかける／**ALB のリスナールールを設定する前にターゲットを登録しない**（開けた瞬間から探索の対象になる）／無認証の経路と要認証の経路を許可リストで分ける。

その他の約束。

- **「SSO が入らないから権限管理をしない」という帰結にはしない。** BA-05 の担当者変更チェックリストは SSO の有無に関わらず実行できる形で書かれている（最小権限の付与、離任時の無効化とトークン失効）。SSO は権限管理の手段の 1 つであって、前提ではない。**代替策 3 がそのまま機能する。**
- **（2026-10-06 に解消。ADR-25 で Umami を廃止）開発環境では、代替策 1 は Umami の課題 1 を直すまで成立しない。** 開発機の Umami は `0.0.0.0` にバインドされており、同一ネットワークから到達できる。本番の Umami は private サブネットにあり、この問題は起きない（3 節）。
- **エージェントの権限は代替策の外側に置く。** BA-05 のとおり、エージェントが使うのは MCP の `ACCESS_LEVEL` と上流 API のトークンであり、人間のセッションとは経路が別である。この分離は維持する（エージェントの権限を人間のセッションに乗せると、人間のログイン状態がエージェントの実行可否を左右し、権限の境界が追えなくなる）。SSO を将来導入しても、この分離は変えない。

## 7. 経路の分離（本番は ALB、オンプレに残る経路は ngrok）

**旧版の前提は「TA-01 の決定により、オンプレ側は ngrok の常設トンネルで露出する」だった。** 2026-09-18 の ADR-12 で、訪問者向けの経路（Umami・Chatwoot・Mautic）と、その管理画面は AWS の ALB に移った（**Umami は 2026-10-06 の ADR-25 で廃止。後継の GA4 はブラウザから Google に直接届き、ALB を通らない**）。**本番では、下の分離設計を ngrok ではなく ALB のリスナールールと WAF で実現する**（TA-06 の 5 節）。ADR-12 の後に ngrok に残ったのは n8n の Webhook 受け口（TA-01 の経路 5）と Astro dev サーバー（経路 6）だった。**ADR-16 で n8n が AWS に移り、Webhook は VPC の中で届くようになったため、ngrok に残るのは Astro dev サーバーだけである。**

**要件が正反対の 2 種類の経路を同じ入口で扱うという構造は、ALB でも変わらない。**

| 種別 | 到達してよい主体 | 認証 | 認証を誤ると何が起きるか |
|---|---|---|---|
| 訪問者向け | 公開サイトの全訪問者 | **無し**（認可もしない。本番は WAF のレート制限だけ） | 認証をかけると訪問者が到達できず、`CAP-10`（行動観測）と `CAP-12`（Web 接客）が成立しない |
| 運用者向け | `R1`〜`R4` のみ | **必須** | 認証が無いと管理画面が誰でも開ける。（旧版: Umami は `APP_SECRET` がプレースホルダのため、到達できた時点で偽造が成立しえた。ADR-25 で廃止） |

**この 2 つを同じ規則で扱わない。** 混ぜると、無認証にすれば管理画面が開き、認証をかければトラッカーが止まるという二択になる。旧版ではトンネルを分けることで、本番では ALB のリスナールールをパス単位で分けることで解く。**ALB にはもう 1 種類、ローカルからの API 呼び出し（Claude Code の MCP とビルド。ADR-15・ADR-16）が入ってくる**（ブラウザでのログインができないため、API のパスだけを ALB の認証なしで通し、製品側の認証と WAF のレート制限で守る。TA-06 の 5.2）。ADR-15 までは n8n（オンプレ）からの API 呼び出しもここに含んでいたが、ADR-16 で n8n は AWS に移り、VPC の中から呼ぶ。

### 分離できない製品がある（正直に記す）

**Chatwoot は、ウィジェットと管理画面を同一オリジンで配信する**（旧版は「Umami と Chatwoot は、トラッカー／ウィジェットと…」。Umami は ADR-25 で廃止）。したがってホスト（サブドメイン）を分けるだけでは分離できず、**パス単位の制御が必須**になる。本番ではこの制御を ALB のリスナールールで行う（TA-06 の 5.2・5.3）。Chatwoot の `/cable`（WebSocket）はウィジェットと管理画面が共用するため、無認証で通して製品側の認証に任せる。

これは次の 2 点で設計上の負担になる。

- **パスの一覧が製品のバージョンに依存する。** Chatwoot のウィジェットのパス（旧版では Umami のトラッカーのパスやイベント受信のエンドポイントも。ADR-25 で廃止）は、製品の更新で変わりうる。変わったことに気づく手段は「計測が止まる」か「管理画面が開いてしまう」のどちらかであり、**後者は気づきにくい**（許可リスト方式にして、列挙したパス以外は認証必須にすれば、失敗は必ず前者の側に倒れる）。
- **許可リストは列挙で作る。** 「管理画面のパスを塞ぐ」ではなく「トラッカーのパスだけを無認証で通し、それ以外はすべて認証必須」とする（拒否リスト方式だと、列挙し漏れたパスが無認証で開く。許可リスト方式なら、列挙し漏れたパスは認証必須になって単に不便なだけで済む）。

Mautic・n8n・Strapi は管理画面のパスがまとまっている（`/s/`、UI 全体、`/admin`）ため、分離は比較的容易である。

### 到達しない経路は開けない

**外部から到達する必要が無い経路はトンネルを張らない**（本番では ALB に出さない）。ADR-15 まではエンドポイント 11（Strapi のコンテンツ API）がその例だった（ADR-14 で機械向けに開ける形にしたが、ADR-15 で Strapi がオンプレだけに戻り、開けなかった）。**ADR-16 でビルドがローカルから本番の Strapi を読むことになり、エンドポイント 11 は外から到達する必要がある経路に変わった。** 代わりに、**エンドポイント 9（n8n の Webhook 受け口）が「開けない」例になる**。送信元の Chatwoot・Mautic・Strapi が同じ VPC にいるため、ALB に出す理由が無い。「将来使うかもしれない」という理由で開けない（開いた経路は 1 本ずつ守る対象になり、守る対象が増えるほど守りが薄くなる）。

### 公開サイトの CSP（2026-10-06 に追加。ADR-25）

**公開サイト（`comegin.com`）に CSP を設ける場合、GA4 のために次のホストを許可する。** 広告の機能を使わない GA4 の値で、Google の CSP ガイド（https://developers.google.com/tag-platform/security/guides/csp の「Google Analytics」の、広告の機能を使わない場合の表）で確かめた。**`stats.comegin.com`（旧 Umami）は外す。**

| ディレクティブ | 許可するホスト（GA4 の分） |
|---|---|
| `script-src`（`script-src-elem`） | `https://www.googletagmanager.com` |
| `img-src` | `https://www.googletagmanager.com` `https://*.google-analytics.com` |
| `connect-src` | `https://www.googletagmanager.com` `https://*.google-analytics.com` `https://*.google.com` |

- **上の表の値で確定した**（2026-10-06。Google のガイドの「広告の機能を使わない GA4」の値。**`*.analytics.google.com` と `*.googletagmanager.com` のワイルドカードは使わない**）。実装の後は Tag Assistant の CSP の検査（同じガイドの「Troubleshoot with Tag Assistant」）で、ブロックされた配信元が無いことを確かめる。
- **`cloud/` に CSP は無い。** CloudFront に付けている AWS 管理の応答ヘッダーポリシー（`Managed-SecurityHeadersPolicy`）は CSP を含まない（`cloud/stacks/cdn.yaml` のコメント、https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/using-managed-response-headers-policies.html）。**CSP は公開サイトの実装のときに足す**（付け方は CloudFront の応答ヘッダーポリシーか Astro かを実装のときに選ぶ。`cloud/README.md` の 5 節）。
- **gtag.js を初期化するインラインスクリプトは nonce かハッシュで許す**（同じガイド。`'unsafe-inline'` は使わない）。静的配信では nonce を毎回作れないため、ハッシュになる見込み（DD-02 の 2.5）。
- Cal.com の埋め込み（ADR-24）・PostHog・Chatwoot の許可は各設計に従う（1 節の冒頭の注記）。

同じ理由で、PostgreSQL / MySQL / Redis・n8n の `sandbox-api` / `sandbox-runner-1` / `runners` / `searxng`・MCP サーバの HTTP ポート・**OpenSEO（`3001`）**は、いずれもトンネルを張らない。**本番の RDS・ElastiCache・EFS も同じ扱いで、private サブネットに置き、Fargate のタスクのセキュリティグループからだけ受ける**（TA-06 の 5.6）。本番の n8n の `runners` は同じタスクのサイドカーで、外に出さない（本番にサンドボックスは無い。4 節）。運用者が DB に入る必要があるときは踏み台を置かず、ECS Exec か Session Manager のポートフォワードを使う。

## 8. OpenSEO と GSC の OAuth

AA-05 の ADR-09 で採用したセルフホストの OpenSEO（`middleware/open-seo-main`）について、秘匿値と到達範囲の規則を定める。

### 8.1 秘匿値

| キー | 用途 | 置き場 | 変更したときに起きること |
|---|---|---|---|
| `DATAFORSEO_API_KEY` | DataForSEO の資格情報（メールと API パスワードの Base64） | `middleware/open-seo-main` の環境変数ファイル（追跡対象外） | ローテーションしてよい。**支出の上限は資格情報ではなく前払い残高で縛る**（AA-05 の ADR-10） |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | GSC の OAuth クライアント（**2026-10-06 ADR-25: GA4 も同じクライアントを使う**） | 同上 | 変えると GSC と GA4 の再接続が要る |
| `BETTER_AUTH_SECRET` | 保存した OAuth トークン（GSC・GA4）の暗号化 | 同上 | **2 節の表のとおり。変えると GSC と GA4 の再接続が要る** |
| `OPENROUTER_API_KEY` | SAM（アプリ内エージェント） | **置かない**（ADR-09） | — |

- **環境変数ファイルは Git の追跡対象外である**（2026-09-18 に、ファイルが存在するのに `git status` が clean であることで確認。値は読んでいない）。どの `.gitignore` で除外されているかは確認していない。
- **`init-env.sh` を足さない。** `middleware/open-seo-main` は上流の取り込みであり、Umami（ADR-25 で廃止）と同じく**スクリプトを足すと上流無改変の前提が崩れる**（3 節）。`BETTER_AUTH_SECRET` は `openssl rand -base64 32` で人間が生成する（上流の手順どおり）。
- **`OPENSEO_TELEMETRY_DISABLED` は置かない**（匿名テレメトリの送信を許可する。`R1` の 2026-09-18 の判断。ADR-09・TA-01 の経路 14）。

### 8.2 到達範囲

- **UI と MCP は無認証である**（`AUTH_MODE=local_noauth`。compose が固定している）。到達できるプロセスはすべてローカルの管理者として扱われ、**DataForSEO の費用を発生させる操作もできる**。
- **`127.0.0.1:3001` に閉じる。トンネルを張らない**（7 節のエンドポイント 13）。上流の compose は既にループバックにバインドしている。
- **`ALLOWED_HOST` を設定しない。** これはリバースプロキシやトンネルのホスト名を許可する設定であり、設定すること自体が「外から開く」準備になる。
- **MCP の Origin 検査は OpenSEO の既定に任せる。** セルフホスト版は要求の Host から許可リストを作らず、localhost 系の Origin だけを通す（DNS リバインディングで外部のページから叩かれる経路を塞ぐ実装。`src/server/mcp/transport.ts`）。

### 8.3 GSC の OAuth 同意画面

**同意画面の公開状態で、接続が 7 日で切れるかどうかが決まる。**

| 設定 | リフレッシュトークン | 評価 |
|---|---|---|
| 外部（External）・テスト中（Testing） | **7 日で失効する**（Google の公式ドキュメントで確認済み。対象外になるのは `openid` やメール・プロフィールだけを求める場合で、Search Console のスコープは該当しない） | 使わない。週に 1 度、誰も気づかないまま GSC の取得が止まる |
| **内部（Internal）** | 7 日の失効の対象外（Google Workspace の組織内に限られる） | **採用する。** `comegin.com` は Google Workspace である（`R1` の 2026-09-18 の確認） |
| 外部・本番（In production） | 長期（取り消されるか 6 か月使われないと失効） | 内部を選べない場合の代替。スコープの審査の要否を確認する |

- **スコープは `webmasters.readonly`（参照のみ）である**（OpenSEO のコードで確認）。OpenSEO から Search Console の設定を変える経路は無い。
- **リダイレクト URI は `http://localhost:3001/api/gsc/oauth/callback`** とする。運用者のブラウザがローカルの OpenSEO に戻るだけで、トンネルを必要としない。
- **接続した Google アカウントが離任すると取得が止まる**（BA-05 の離任時チェックリスト）。
- **「内部」は組織内の利用者に限る設定である。** 接続できるのは `comegin.com` の Workspace アカウントだけであり、**そのアカウントが Search Console のプロパティにアクセスできる必要がある**（ドメインプロパティを登録したアカウント、または権限を付与されたアカウント）。

### 8.4 GA4 の OAuth（2026-10-06 に追加。ADR-25）

出典は `middleware/open-seo-main/docs/SELF_HOSTING_GOOGLE_ANALYTICS.md` と、スコープの定義 `middleware/open-seo-main/src/shared/ga4.ts`。

- **OAuth クライアントは GSC と共用する**（8.1 の `GOOGLE_CLIENT_ID`・`GOOGLE_CLIENT_SECRET`。同意画面は 8.3 の「内部」のまま）。**同意は GSC とは別に取る**（GA4 の接続で改めて許可する）。

- **n8n のエディターに入れる管理者を絞るか**（1 節）。`admin-auth` の許可リストは管理画面ごとに分かれていない（ALB の 1 つの関門）。n8n のエディターは全資格情報に届くため、許可リストを管理画面ごとに分けるか（Better Auth の側でホスト名ごとに許可を持つか）を決める。判断者 `R1`。
- **エージェントから監視アプリの実行記録（`E-15`）に届かないことの担保**（1 節。ADR-18）。記録は監視アプリのローカルの DB にあり、エージェント（Claude Code）も同じ開発機で動いてファイルを編集できる。DB のファイルを置く場所とファイルの権限（監視アプリのプロセスだけが読み書きできる形にするか）、`PreToolUse` フックの拒否の対象に記録の置き場所を加えるか（環境変数ファイルと同じ扱い）を決める。AA-04 の暴走条件 #7 の歯止めがこれに依存する。**ADR-18 の追加の決定で、記録を S3 に追記専用で写すことになった**ため、ローカルの記録が書き換えられても写した分は消せない（写す頻度より新しい分と、書き換えられたことの検知は残る）。判断者 `R1`。
- **監視アプリのサーバー側の環境変数が Claude Code に引き継がれないことの確認**（1 節。ADR-17・ADR-18）。監視アプリが本番を読むための資格情報・ハートビート専用の IAM ユーザー・**実行記録の写しを書く資格情報**がすべてこの前提に依存する。上の「監視アプリが本番を読むための資格情報の置き場」と一体で確かめる。判断者 `R1`。
- **Strapi の鍵を変更したときに起きることを確かめていない**（2 節）。`API_TOKEN_SALT`・`ADMIN_JWT_SECRET`・`ENCRYPTION_KEY` を変えたとき、発行済みの Admin トークンと API トークンが使えなくなるか、データが失われるかを Strapi 5 の実装で確かめ、2 節の表に載せるかを決める。
- **監視アプリに「承認して配信」の操作を置く場合の、配信用 IAM の置き場**（TA-07 の 7 節・9 節）。Claude Code の実行環境と分けることが条件になる。判断者 `R1`。
- **`MCP_AUTH_TOKEN` のローテーション手順が未定。** 2 節の分類でいえば「ローテーションしてよい値」だが、HTTP トランスポートで運用を始めた場合、トークンを変えるとクライアント側の設定も同時に変える必要がある。現状は stdio 運用のため顕在化していない。
- **（2026-09-18 に解決）`comegin.com` が Google Workspace のドメインか。** Workspace であり、同意画面を「内部」にする（8.3）。
- **（2026-10-03 に追加）thirdweb の Vault の管理者の鍵の保管方法。** AWS に置かないと決めたが、`R1` の手元のどこに置くか（紛失すると POL を送れなくなる）。
