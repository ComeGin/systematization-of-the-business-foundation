## 1. 現状の監視手段

| 手段 | 監視対象 | 検知できること | 通知先 | 状態 |
|---|---|---|---|---|
| Docker の healthcheck | 各スタックのコンテナ | プロセスが応答しないこと | **無し**（`docker compose ps` を人が見るまで誰も知らない） | `実装済み` |
| `restart: always` / `unless-stopped` | 同上 | — | — | `実装済み`（検知ではなく回復の手段） |
| `depends_on` ＋ `condition: service_healthy` | 起動順序 | 依存先が healthy になる前に起動すること | — | `実装済み` |
| PostHog の Error Tracking | Strapi の例外 | 未処理の例外（`ApplicationError` と 4xx の `HttpError` は除く） | PostHog の inbox（**開発と本番でプロジェクトを分ける**。ADR-16） | `実装済み`（開発環境の Strapi のみ） |
| PostHog の Scout | プロジェクト横断 | 設定・計装の不備、横断的な相関 | PostHog の Self-driving inbox | `未配線`（入力となるデータがほぼ無い） |
| PostHog の Replay Vision スキャナ | セッションリプレイ | 記事の公開・編集操作中の可視の破綻と苛立ち | 同上 | `未配線`（ブラウザ SDK 未設置のため記録が 0） |
| Lighthouse CI | 公開物の品質 | 4 カテゴリのしきい値割れ | ビルドの成否 | `実装済み`（ローカル実行のみ） |
| `chatwoot-mcp` の検証ハーネス | Chatwoot API との疎通 | ツールの動作不良、`ACCESS_LEVEL` の包含関係の破れ | 実行者の画面 | `実装済み`（手動実行） |

**横断的な監視基盤は無い。**
どのスタックが落ちているかを 1 か所で見る仕組みも、落ちたことを人間に知らせる経路も存在しない。healthcheck は「コンテナが自分の状態を報告する」ところまでで止まっており、その報告を集める先が無い。

これは `CAP-13` の成熟度が BA-02 で `部分的` とされている理由そのものである（「Strapi の例外は PostHog に送られる。それ以外のシステムの監視・通知経路は無い」）。

**ADR-12（AA-05）で、本番の監視対象が 2 つの場所に分かれた。** Mautic・Chatwoot・Umami（**2026-10-06 ADR-25 で廃止。後継の GA4 は SaaS で、監視の対象は「計測が入っているか」だけになる。4 節の項目 21**）の本番は AWS（ECS on Fargate ＋ RDS・ElastiCache・S3・EFS。TA-06）で動き、全システムの開発環境・Strapi（記事の正本。ADR-15）と管制（監視アプリ・n8n・OpenSEO・MCP サーバ）はオンプレに残った。**ADR-16 で Strapi と n8n の本番も AWS に移り、本番の監視対象はすべて AWS にある。** オンプレに残るのは全システムの開発環境と道具（監視アプリ・Claude Code・MCP サーバ・OpenSEO・Lighthouse CI・ビルド）で、**オンプレの監視は「開発と更新の作業が止まっていないか」を見るものになった。** **ADR-17 でエージェントの定期実行の起動元が監視アプリ（オンプレ）になったため、「改善ループが止まっていないか」もオンプレの監視で見る**（4 節の項目 16・17・19）。 **この表と 2 節の healthcheck は、開発環境とオンプレに残るシステムについての事実である。** 本番の 5 システム（Strapi・Mautic・Chatwoot・Umami・n8n）には ALB のターゲットのヘルスチェック・ECS のサービスの状態・CloudWatch のメトリクスが使えるが、いずれも `未着手`（4 節の項目 12〜15）。

**監視の表示先は監視アプリ（Next.js。オンプレ。TA-07）にまとめる**（ADR-14）。管理者はオンプレの画面だけを操作するため、4 節の各項目の状態（開発環境のヘルスチェックと、本番の CloudWatch のアラームの状態）を監視アプリの 1 画面で見る。**通知（SNS）と表示（監視アプリ）は役割が違う。** 監視アプリはオンプレにあるため、オンプレが落ちれば表示も止まる。止まったことを知らせるのは、オンプレの外にある CloudWatch → SNS の経路（項目 16）である。

## 2. healthcheck の一覧

各 compose に定義されている healthcheck。**これが現在唯一の機械的な死活監視である。** Chatwoot・Mautic・**n8n（ADR-16）**の行（**Umami の 2 行は 2026-10-06 の ADR-25 で外した**）は開発環境の定義であり、本番（AWS）では ECS のコンテナのヘルスチェックと ALB のターゲットのヘルスチェックで置き換える（TA-06）。本番の n8n にはサンドボックスが無いため、`sandbox-api` の行は開発環境にだけある。

| スタック | サービス | 判定方法 | 間隔 / リトライ | 定義箇所 |
|---|---|---|---|---|
| Chatwoot | `postgres` | `pg_isready -U $POSTGRES_USER -d $POSTGRES_DB` | 10s / 10 回（`start_period: 30s`） | `backend/chatwoot-system/docker-compose.yaml` |
| Chatwoot | `redis` | `redis-cli ping` の結果に `PONG` が含まれるか | 10s / 5 回 | 同上 |
| Chatwoot | `mailhog` | `wget` で `/api/v2/messages?limit=1` を叩く | 10s / 5 回 | 同上（イメージに healthcheck が無いため自作） |
| Chatwoot | `rails` / `sidekiq` | **無し** | — | 同上 |
| n8n | `postgres` | `pg_isready` | 5s / 10 回 | `middleware/n8n/compose.yml` |
| n8n | `n8n` | `wget -qO- http://localhost:5678/healthz` | 10s / 10 回（`start_period: 60s`） | 同上 |
| n8n | `sandbox-api` | `wget -qO- http://localhost:8080/healthz` | 5s / 5 回（`start_period: 10s`） | 同上 |
| n8n | `runners` / `sandbox-runner-1` / `searxng` | **無し** | — | 同上 |
| Mautic | `mysql` | `mysqladmin ping -h 127.0.0.1 --silent` | 10s / 10 回（`start_period: 30s`） | `backend/mautic-system/docker/compose.yaml` |
| Mautic | `mailhog` | `wget` で `/api/v2/messages?limit=1` | 10s / 5 回 | 同上（自作） |

| **OpenSEO** | `open-seo` | `node` で `/api/health` を叩く（設定と DB の状態を返す） | 30s / 3 回（`start_period: 300s`。初回起動時のビルドを待つ） | **イメージ側**（`middleware/open-seo-main/Dockerfile.selfhost`。compose には書かれていない） |

### ここから分かる穴

- **アプリケーション本体に healthcheck が無いスタックがある。** Chatwoot の `rails` と `sidekiq` には定義が無い。DB と Redis が healthy でも Rails が応答しない状態は検知されない（`chatwoot-mcp` 経由の呼び出しが失敗して初めて分かる）。**本番では `chatwoot-web` は ALB のターゲットのヘルスチェックで見えるようになるが、`chatwoot-worker`（Sidekiq）は ALB の後ろに無いため、本番でも同じ穴が残る**（`mautic-cron` も同じ）。
- **Mautic の Web は Docker の外にある。** PHP ビルトインサーバーはホストのプロセスとして動くため、compose の healthcheck の対象外である。止まっていても `docker compose ps` には現れない。
- **healthcheck は再起動を引き起こさない。** Compose の healthcheck は状態を報告するだけで、unhealthy になっても再起動しない（`restart: always` が効くのはプロセスが終了した場合）。**応答しないまま生き続けるコンテナ**が最も検知されにくい。
- **n8n の `runners` に healthcheck が無い。** Code ノードの実行が落ちても n8n 本体は healthy のままであり、ワークフローが個別に失敗する形でしか現れない。**本番でも `runners` はサイドカーで ALB の後ろに無いため、同じ穴が残る**（ADR-16）。

## 3. PostHog Self-driving の位置づけ

`backend/posthog-self-driving-report.md` に設定内容が記録されている。

| 要素 | 内容 | 状態 |
|---|---|---|
| Scout（有効 2 本） | `signals-scout-general`（横断的な相関）、`signals-scout-health-checks`（計装の不備） | `未配線`（入力がほぼ無い） |
| Scout（無効 25 本） | 対応する製品面の使用が確認できないため | — |
| Replay Vision スキャナ（2 本） | `CMS article publishing breakage`（記事の管理・公開中の可視の破綻。`/admin/content-manager` を対象、サンプリング 0.5）、`CMS editor frustration`（`$rageclick` 全体、サンプリング 1.0） | `未配線`（ブラウザ SDK 未設置のため対象セッションが 0） |
| シグナルソース | `health_checks`、`error_tracking` の 3 種、`conversations` の `ticket` | `部分的`（`error_tracking` のみ入力がある） |
| 実行予算 | **Scout は 1 日 100 回** | — |

- **Scout とスキャナは「エージェントによる監視」であり、この基盤の `CAP-13` を内製化する手段の 1 つにあたる。** 人間が閾値を決めて張るアラートではなく、観測面を巡回して異常を見つける形をとる。
- **ただし現在は入力が無く、実質的に何も見ていない。** Session Replay は有効だがブラウザ SDK が無いため記録が 0 件、Support は有効だが受信チャネルが無いためチケットが 0 件である。「有効だが不活性（enabled but inert）」という状態が複数ある。
- **実行予算 1 日 100 回は、監視の頻度を設計する際の制約になる。** Scout を増やすほど 1 本あたりの巡回頻度が下がる。有効にするのは入力が実際に存在する面だけにする（現在 25 本を無効にしているのはこの判断の実例）。
- **PostHog の監視対象は PostHog に届いているデータに限られる。** Docker コンテナが落ちたことも、n8n のスケジュールが止まったことも PostHog には届かない。**Self-driving は横断的な監視基盤の代わりにならない**（4 節）。

**ADR-25 でアクセス解析の正本を GA4 にした。PostHog の用途は次の 4 つに絞る。** **PostHog のページビュー・セッションの数字は報告に使わない**（流入・ページ・参照元の数字は GA4 が正本。指標が重なるときは GA4 を優先する）。

|---|---|---|

| 記事のイベント | Strapi の `article_created`・`article_published`・`article_updated`・`article_deleted`（`CONTENT-throughput`） | `agent/analytics-reporter` |

## 4. 横断的な監視基盤が無いことの扱い

現在、次の 3 つは誰も検知しない。

| 検知されない事象 | 影響 | 現在気づく手段 |
|---|---|---|
| コンテナが unhealthy のまま応答しない | `chatwoot-mcp` / `mautic-mcp` の呼び出しが失敗する | エージェントが失敗して初めて分かる |
| Mautic の PHP ビルトインサーバーが止まる | Mautic の API が使えない | 同上 |
| **n8n のスケジュール実行が止まる**（**ADR-17 の後は、監視アプリの定期実行が止まることを含む**） | 日次の観測収集、週次・月次の定例がすべて止まる | **無し**（TA-03 の 3.3 で指摘した「静かに止まる」失敗） |

3 つ目が最も重い。**ADR-17 で定期実行は 2 系統に分かれた。** エージェントを使う定期処理（観測の日次バッチ・`I-13` の起票・公開された記事の確認・誤った書き込みの突き合わせ・月次分析など）は監視アプリ（ローカル）が起動し、エージェントを使わない決定論的な定期処理は本番の n8n（AWS）が行う（TA-03 の 3.3）。**改善ループを回しているのは前者**であり、開発機か監視アプリが止まると、訪問者にも本番の n8n にも影響が出ないまま改善ループだけが止まる。**再帰的自己改善のループは、止まったことが観測されないと止まったまま再開しない。** 観測系が止まれば `E-13` は生成されず、`E-13` が無ければ改善は起きず、改善が起きないことは誰にも異常として見えない（提案が来ないことと、提案すべきことが無いことが区別できない）。

### 内製化の方針

`CAP-13` の内製化の方針は BA-02 で「監視と一次対応を n8n のワークフローに寄せ、検知を `E-13` に変換して `CAP-14` に流す。エージェントは検知と提案までを担い、復旧操作は承認ゲートの対象とする」と定められている。これを TA として具体化する。

|---|---|---|---|---|
| 1 | 各スタックのコンテナの状態（**ADR-16 の後は開発環境だけ**） | 開発環境の n8n から `docker compose ps` 相当を取得、または各サービスの healthcheck 用エンドポイントを叩く | **旧版は Amazon SNS の `comegin-ops-alert` へ発行**（ADR-08）。**ADR-16 で対象が開発環境だけになったため、監視アプリの表示にとどめるか SNS に出すかは未決定**（8 節） | `未着手` |
| 2 | Mautic の Web の死活 | `http://127.0.0.1:8000/` への疎通（**開発環境**。本番は項目 12） | 同上 | `未着手` |

項目 9〜11 は OpenSEO の採用（AA-05 の ADR-09）で新たに必要になった。

- **項目 10 は「落ちた」ではなく「切れた」を見る。** OpenSEO が動いていても、GSC の OAuth が失効すると GSC の取得だけが `not_connected` を返して止まる。同意画面を「内部」にした（TA-04 の 8.3）ため 7 日ごとの失効は起きないが、**接続した Workspace アカウントの無効化（離任）や同意の取り消し**で起きる。GSC が SEO の目的に対する唯一の測定である以上（ADR-06）、**最も静かに、最も重いものが止まる**経路にあたる。
- **項目 11 は、セルフホストでは OpenSEO が支出を計量しない**ことから必要になる（`whoami` の残高が `null`）。支出を知る手段は DataForSEO 側にしか無い。残高が尽きると調査もランク追跡も同時に止まり（DD-07 の 6 節）、**止まったことはエージェントの調査が失敗して初めて分かる**。

項目 6 と 7 は、当初 TA-01 の経路 4・7 が ngrok の常設トンネルに決まったことで必要になった。**ADR-12 で経路 4・7 は AWS の ALB に移ったが、2 つの項目の性質は変わらない**ため、対象を ALB に置き換えて残す。

- **経路 4 が止まっても訪問者には見えにくい。** トラッカーが読み込めないだけならページは表示され、観測データが入ってこなくなるだけである（**ADR-25 でトラッカー〈Umami〉は経路 4 から外れた。GA4 の欠測は項目 21 で見る**）。ただし ADR-12 の後、経路 4 にはチャットとフォームも含まれ、**止まると問い合わせを受け付けられなくなる**。
- **項目 7 は「落ちたこと」より「認証が外れたこと」を見る。** 落ちれば運用者が困って気づくが、認証だけが外れた状態は誰も困らないまま管理画面が公開される（TA-04 の 7 節の分離が破れた状態にあたる）。ALB のリスナールールの優先度を 1 つ誤るだけで起きる。したがって監視は疎通ではなく**認証が効いていることを確認する**形にする（`200` が返ることを異常として扱う）。
- **項目 6 と 7 の実行場所の問題は小さくなった。** 旧設計では、オンプレから自分のトンネルを叩くとローカルに到達して成功する場合があった。本番の ALB は外部にあるため、オンプレから叩いても外部からの到達を確認できる。AWS 内から確認する手段（Route 53 のヘルスチェックや CloudWatch Synthetics）もある（8 節）。

**トンネル断の影響範囲は、ADR-12 で n8n の Webhook だけに縮み、ADR-16 で本番から無くなった。** ADR-12〜ADR-15 では、ngrok を通る公開の経路は TA-01 の経路 5 だけだった。ADR-16 で n8n が AWS に移り、経路 5 は VPC の中で完結する。ngrok に残るのは Astro dev サーバーの共有だけで、落ちても本番には影響しない。**ただし Webhook が静かに止まりうる点は変わらない**（本番の n8n が止まっている間、Mautic・Chatwoot の側では送信の失敗しか残らず、n8n には何も届かない。項目 12・15）。

**項目 12〜14 は n8n を経由せず、CloudWatch アラームから SNS に直接発行する。** 旧版の理由は「AWS 側の監視を n8n（オンプレ）に集めると、開発機が止まったときに AWS 側の監視も止まる」だった。**ADR-16 で n8n も AWS に移ったが、n8n 自身が監視対象（項目 12）であるため、理由は変わらない。** **監視対象と通知経路を分ける**という ADR-08 の要請を、AWS 側では CloudWatch と SNS だけで満たせる。

**項目 3 は n8n 自身では実装できない。** n8n が止まっているかどうかを n8n のワークフローで監視すると、n8n が止まったときに監視も止まる。**旧版は項目 16 のハートビートでこれを解いた。** n8n は生存信号を「送る」だけで、止まったかどうかの判定は n8n の外の CloudWatch が行う。**欠損データを違反として扱う**ことが要点で、これによって「信号が来ない」ことそのものが異常になる（何も起きていないことと、止まっていることを区別できる）。**ADR-16 で、スケジュール実行をする n8n（本番。AWS）とハートビートを送る n8n（開発環境。オンプレ）が分かれた**ため、同じ仕組みを本番の n8n にも置く（項目 3 の案）。**ADR-17 で、エージェントを使う定期処理の起動元が監視アプリ（オンプレ）に移った。** 監視アプリの定期実行については、「スケジュール実行をする主体がハートビートを送る」という旧版の形に戻せる（送り手を監視アプリにする。TA-07 の 9 節）。

**項目 16 は 3 つの止まり方をまとめて検知する。** 開発機そのものの停止、開発環境の n8n の停止（またはスケジュール実行の停止）、開発機の回線断のどれでも信号が届かなくなる。**どれが原因かは区別できない**が、どれもオンプレ全体を調べる契機としては同じである。**ADR-16 の後、オンプレの全滅で止まるのは開発環境・ビルドと配信・エージェントの作業・OpenSEO だけで、本番のサービス・記事の正本・自動化は止まらない。** **ADR-17 の後、止まる「エージェントの作業」にはエージェントの定期実行が含まれる**（改善ループが止まる）。**今の送り手（開発環境の n8n）では、監視アプリだけが止まった状態を検知できない**（開発環境の n8n が信号を送り続けるため）。送り手を監視アプリに移せば、「監視アプリの停止（またはスケジュールの停止）」が 4 つ目の止まり方として同じ信号で検知できる。代わりに、開発環境の n8n の停止は検知されなくなるが、開発環境の n8n は ADR-17 の後は本番にも改善ループにも関わらないため、失うものは小さい（**本ファイルの判断**）。

- **15 分（3 期間）待つのは、1 回の送信の失敗で通知しないためである。** 開発機の一時的なスリープや回線の瞬断で通知が出続けると、通知が読まれなくなる。
- **開発環境の n8n に与えるのは `cloudwatch:PutMetricData` だけである**（名前空間 `ComeGin/Onprem` に限定。TA-04 の 1 節）。アラームを変える・止める権限を与えないため、n8n が自分への監視を止めることはできない。**送り手を監視アプリに移す場合も同じ権限だけを与え、その資格情報を Claude Code の実行環境に渡さない**（エージェントが自分への監視を止めたり偽ったりできないようにする。TA-04 の 1 節）。
- **開発機を意図的に止めるとき（休日など）は、止める前にアラームのアクションを無効にする**（`R1` の 2026-09-18 の決定。ADR-16 の後も手順は変えない。無効にするのはオンプレのハートビートのアラームだけで、本番の n8n のアラーム〈項目 3 の案〉は止めない）。アラームの操作は人間だけが行う（n8n には `cloudwatch:PutMetricData` しか与えない。TA-04 の 1 節）。**ADR-17 の後は、止めている間は監視アプリの定期実行（観測の日次バッチなど）も止まる。** 再開後に止まっていた間の分を取り戻すかは定期処理ごとに決める（TA-07 の 3.5）。**（2026-10-06。ADR-21）無効にするアラームは 2 つになった: `comegin-<env>-onprem-heartbeat`（監視アプリ）と `comegin-<env>-onprem-n8n-schedule-heartbeat`（オンプレの n8n。本番の n8n もオンプレなので、開発機と一緒に止まる）。上の「本番の n8n のアラームは止めない」は ADR-16 の記述で、ADR-21 の後は止める。** `aws cloudwatch disable-alarm-actions --alarm-names comegin-prod-onprem-heartbeat comegin-prod-onprem-n8n-schedule-heartbeat`（`cloud/README.md` の 4.15）。**止める間は Webhook（`I-11` `I-12`）も届かず、顧客の要求の通知が出ない**（DD-07 の 2.5）ため、止める時間を運用者に知らせる。手順は次のとおり。

| # | いつ | 操作 |
|---|---|---|
| 1 | 止める前 | ハートビートのアラームのアクションを無効にする（`DisableAlarmActions`） |
| 2 | 同時に | **再開予定の時刻に、アクションを有効に戻す 1 回限りのスケジュールを作る**（EventBridge Scheduler から `EnableAlarmActions` を呼ぶ） |
| 3 | 再開後 | ハートビートが届き、アラームの状態が `OK` に戻ったことを確かめる（送り手を監視アプリに移した場合は、監視アプリを起動しないと `OK` に戻らない） |

- **有効に戻し忘れると、オンプレの全滅が知らされない状態が続く**（無効になったアラームは、無効になっていること自体を通知しない）。手順 2 で戻す操作を先に予約しておくのはこのためである。**予定の時刻に開発機がまだ止まっていれば、その時点で通知が出る**。これは正しい動作である（予定どおりに再開できていないことを知らせている）。
- 再開が早まった場合は、手順 3 の後に手で有効に戻し、予約したスケジュールを消す。

- **復旧操作は自動化しない。** BA-05 に明示の分類は無いが、コンテナの再起動は「元の状態に戻す操作」に見えて、実際には原因を消してしまう（落ちた理由が分からなくなる）。検知と提案までをエージェントが担い、再起動は人間が行う。
- **通知先は Amazon SNS のトピック `comegin-ops-alert` に決定した**（`R1` の 2026-09-17 の決定。ADR-08）。**決め手は「監視対象が通知経路を兼ねてはならない」という要請である。** 当初案の Chatwoot は監視対象そのものであり、**Chatwoot が落ちると「落ちた」という通知も届かない**。SNS はオンプレの外にあるため、オンプレが全滅しても通知が届く。**全滅を検知する主体は項目 16 の CloudWatch アラーム**であり、検知から通知までの経路にオンプレの構成要素が 1 つも入らない。
- **GitHub の PR は代替にならない。** 改善提案の通知は同日に GitHub へ一本化したが（AA-02 の 3.4）、「コンテナが落ちた」は提案ではなく即時性のある警報であり、`E-13` の起票と承認を経る形に合わない。**上の表の項目 4（しきい値割れ）だけは例外で、`E-13` の起票で足りる。**
- **リード通知とはトピックを分ける**（`comegin-lead-alert` / `comegin-ops-alert`）。購読はトピック単位のため、分けないと宛先を分けられない。緊急度も違う。
- **通知は「状態が変わったときだけ」発行する。** SNS の無料枠は月 1,000 通であり、監視を 5 分間隔で回して毎回通知すると 1 日で枠を超える。**`ok → ng` と `ng → ok` の遷移のときだけ**発行し、`ng` が続いている間は発行しない。
- **項目 8（購読状態の監視）が新たに要る。** SNS の通知メールには購読解除リンクが付いており、**転送を受けた人でも解除できる**。解除されると**通知が静かに止まる**（誰も困らないまま監視が無効になる。項目 7 の「認証だけが外れた状態」と同じ性質の失敗にあたる）。対処は 3 つ。
  - トピックポリシーで **`sns:Unsubscribe` を制限する**（TA-04 の 1 節）。
  - 購読の確認は**メールのリンクを踏まず、AWS コンソールで確認 URL を貼り付けて行う**（解除リンクを含むメールを残さない）。（**2026-10-04 追記**: 実装中に、SNS の公式ドキュメントでは、メールの解除リンクからの解除を止めるのはトピックポリシーではなく、購読の確認時に `ConfirmSubscription` へ `AuthenticateOnUnsubscribe=true` を付けることだと分かった。トピックポリシーの Deny は補助として残し、確認は `aws sns confirm-subscription --authenticate-on-unsubscribe true` で行う。手順は `cloud/README.md`。コンソールで確認 URL を貼り付ける方法でこのフラグが付くかは未確認）
  - **`Confirmed` の購読数を監視する**（項目 8）。**この監視の結果だけは SNS では知らせられない**（通知経路そのものが壊れている場合があるため）。項目 3 と同じく **n8n の外**に置き、別の手段で知らせる必要がある（8 節）。
- **`comegin-ops-alert` に個人情報を載せない。** 監視の通知はシステムの状態を伝えるものであり、顧客のデータを含める理由が無い（DA-05 の 1.3 はリード通知の規則だが、監視通知にはさらに強く「一切載せない」を適用する）。

### 収益化の監視（2026-10-03 に追加。ADR-20）

`points-api` が検知し、Amazon SNS（`comegin-ops-alert`）へ通知する。

**訪問者が生んだデータと記事の正本の復旧が、運用担当者の手作業に依存しなくなった。** 下の「バックアップ方針」で未決定だった実行主体と保管先の問題は、本番の 5 システム（Strapi・Mautic・Chatwoot・Umami・n8n）について RDS・S3・AWS Backup で解ける（ADR-12・ADR-16。**Umami は ADR-25 で廃止。GA4 のデータは Google の側にあり、こちらで復旧できない〈PostHog と同じ扱い。下の表〉**）。**ADR-15 の時点では「Strapi は記事の正本であり、開発機の故障で失われうる」としていたが、ADR-16 でこの問題は解消した。** オンプレに残るのは OpenSEO と監視アプリの実行記録（**`E-15` の正本。ADR-18**。TA-07 の 3.6）で、これらについてはバックアップの問題が残る（8 節）。ADR-17 でエージェントの起動元が監視アプリに一本化され（手動の指示と定期実行）、監視アプリの実行記録を `E-15` の正本にする条件が揃った。その時点では「正本にすると決めた場合、開発機にしか無い正本になり、ADR-16 の『正本はクラウド』の基準と食い違う」としていた。**ADR-18 で、監視アプリの実行記録を正本とし、ローカルに置くことを ADR-16 の基準の唯一の例外として受け入れた。** したがって**監視アプリの実行記録は開発機にしか無い正本**であり、バックアップの優先度は OpenSEO と同じか、それ以上になる（下の「開発機のバックアップの意味」。8 節）。**ADR-18 の追加の決定で、この記録を S3 に追記専用で写すと決めた**（上の表。写しは正本ではない）。これで `E-15` については開発機の外のバックアップの保管先が決まり、残るのは OpenSEO である。

**ADR-17 の後、本番の n8n の実行履歴は `E-15` `AgentRun` の正本の候補から外れ、ADR-18 で `E-15` ではないことが確定した。** エージェントは n8n から起動されなくなり、n8n の実行履歴に残るのはエージェントを使わない決定論的な処理だけになった（TA-03 の 3.3）。上の表の n8n の行は ADR-18 に合わせて改めた。開発環境のデータ（Strapi・n8n を含む）は失っても作り直せるため、バックアップの優先度は低い。**開発機のバックアップは、本番の復旧には関わらない**（TA-06 の 4.5）。

**開発機のバックアップの意味（ADR-18）。** ADR-16 で「開発機のバックアップは本番の復旧に関わらない」としたことで、開発機のバックアップの重みは下がっていた。**ADR-18 で `E-15` の正本が開発機に置かれ、開発機のバックアップが再び意味を持つ。** 本番の復旧に関わらないことは変わらない（訪問者へのサービスにも影響しない）。守る対象は**調査と検証の根拠**である。

| 失うもの | 何が困るか |
|---|---|
| 監視アプリの実行記録（`E-15`） | **本番への誤った書き込みを調べる根拠**（どの起動の、どのエージェントが、何をしたか。TA-07 の 6.2）と、**改善の検証の根拠**（`E-13` の `agent_run_id` の参照先。`E-13` は Git にあり削除しないため、参照だけが残って参照先が無い状態になる） |
| OpenSEO の順位の履歴 | 取り直せない（上の表） |

- **同じ機内に置くバックアップはディスク障害に対して無力である。** ADR-18 の反映では開発機の外に写すかを未決定とし、「写す先をクラウドにすると ADR-18 の『ローカルに置く』とどう整合させるか」を論点に残していた。**ADR-18 の追加の決定 5 で、S3 に写すと決めた。正本はローカルのまま、写しだけをクラウドに置く**（写しは正本ではなく、開発機を失ったときの復旧に使う。TA-06 の 4.7）。
- **写しは追記だけを許し、削除と上書きを許さない。** 写しを書く資格情報は監視アプリのサーバー側だけに置き、削除の権限を持たせない（TA-04 の 1 節）。エージェントがローカルの記録に届いてしまっても、写した分は消せない。
- **写しに本番の個人情報は入らない前提である**（DA-05 の 1.5）。ADR-18 の反映では「記録する範囲が決まらないと、写し先の守りの水準と削除請求の手順が決まらない」としていたが、**追加の決定 4 で記録を要約と ID だけにした**ため、写し先は個人情報の保管先にならない（要約の検査が漏れる余地は残る。TA-07 の 3.6）。
- **写す頻度と形式、保持期間は未決定**（8 節）。頻度が開発機を失ったときに失われる範囲を決める。

**Strapi の記事は、RDS と S3 の 2 か所にまたがる**（本文は RDS の `strapi` データベース、画像はメディアのバケット）。RDS はポイントインタイムリカバリで任意の時点に戻せるが、S3 はバージョニングでオブジェクトごとに戻す。**RDS だけを過去の時点に戻すと、その後にアップロードした画像への参照が消え、逆にその時点に存在した画像が S3 で消されていれば参照が壊れる。** 復旧の手順でこの 2 つを揃える方法は 8 節の未決定事項とする。

| n8n のクレデンシャル | `db-data`（**本番は RDS の `n8n` データベース**） ＋ **`N8N_ENCRYPTION_KEY`**（**本番は Secrets Manager**） | 鍵が無ければ暗号文は無意味。ワークフローの形は残るが接続先に繋がらない。**ADR-16 の後、本番の n8n は全システムの資格情報を持つため、本番の自動化がすべて止まる** |

### バックアップ方針

| 対象 | 方法 | 頻度 | 保管場所 |
|---|---|---|---|
| Docker ボリューム | 各 DB の論理ダンプ（`pg_dump` / `mysqldump`）を取る。**ボリュームのファイルコピーではなく論理ダンプにする**（稼働中のデータディレクトリをコピーすると不整合なコピーになる） | 日次 | オンプレの別の場所 ＋ 外部 |
| 添付ファイル（`storage_data`） | ファイル単位のコピー | 日次 | 同上 |
| **Strapi（`backend/strapi-system` の SQLite と `public/uploads`）** | SQLite の整合したコピー ＋ `public/uploads` のファイル単位のコピー。**ADR-15 では記事の正本の守りだったが、ADR-16 で正本が本番の Strapi（RDS と S3）に移り、開発用のデータの守りになった**（優先度は他の開発環境のデータと同じ） | 日次（**ADR-16 の後は頻度を下げてよい**。8 節） | オンプレの別の場所 ＋ 外部 |
| OpenSEO（`open_seo_data`） | SQLite の整合したコピー（コンテナを止めて複製するか、SQLite のバックアップ機能を使う。**稼働中のファイルをそのまま複製しない**） | 週次（順位計測の頻度に合わせる） | 同上 |
| **監視アプリの実行記録（`E-15` の正本。ADR-18）** | **S3 に写す**（ADR-18 の追加の決定。形式は未決定。DB の整合したコピーか、1 件ごとの追記か。TA-07 の 3.6） | 未決定（日次が目安。定期実行が日次のため） | **S3 の写し専用のバケット**（`ap-northeast-1`。追記だけ。削除と上書きを許さない。TA-06 の 4.7）。記録は要約と ID だけのため、写し先は個人情報の保管先にならない前提（DA-05 の 1.5）。ADR-18 の反映では「開発機の外に写すか」を未決定にしていた |
| 暗号化キー（環境変数ファイル） | **ボリュームのバックアップとは別の場所に保管する** | 変更時（通常は変更しない） | パスワードマネージャなど |
| n8n のワークフロー（JSON） | Git（TA-03 の 6 節） | 日次 | リポジトリ |
| `sandbox-tls` | **取らない** | — | — |
| `redis_data` | **取らない**（キューであり、失っても再実行で回復する） | — | — |

**鍵とデータを同じ場所に保管しない。** 両方が同じバックアップに入っていると、そのバックアップが漏れた時点で復号も同時に可能になる（バックアップを取ることが、平文でデータを置くことと同じ意味になってしまう）。

**本番ではこの原則が弱くなる。** RDS のスナップショットと Secrets Manager の鍵は、**同じ AWS アカウントの中にある**。サービスは別だが、アカウントの管理者権限が漏れれば両方に届く。**ADR-16 で n8n の資格情報の暗号文（RDS）と `N8N_ENCRYPTION_KEY`（Secrets Manager）もこの形になり、アカウントの管理者権限が漏れると、全システムの資格情報を復号できる状態になる。**IAM で読み取れる主体を分けることが当面の手段であり、アカウントを分けるかどうかは TA-02 の 9 節の未決定事項と一体で決める（8 節）。

### 復旧の順序

1. 環境変数ファイルを復元する（`dev/init-env.sh` は**実行しない**。実行すると空の項目に新しい鍵が生成され、暗号化データが復号できなくなる）
2. ボリュームを作り、論理ダンプをリストアする
3. Chatwoot は `docker compose run --rm rails bundle exec rails db:chatwoot_prepare` を実行する（entrypoint がマイグレーションしないため、初回とイメージ更新後は必須）
4. n8n のワークフローを、Git のエクスポートから必要に応じてインポートする（自動化しない。TA-03 の 6 節）
5. 疎通を確認する（2 節の healthcheck と `chatwoot-mcp` の `pnpm verify`）

**本番（AWS）の復旧は手順が違う。** RDS はポイントインタイムリカバリで**新しいインスタンスとして**復元されるため、エンドポイントが変わる（Secrets Manager の接続先を更新し、ECS サービスを再デプロイする）。**PostgreSQL の共有インスタンスを戻すと、Chatwoot・Umami・`admin-auth`・Strapi・n8n の 5 つのデータベースが同じ時点に戻る**（**ADR-25 で Umami を外した**）（データベース単位では戻せない。1 つだけ戻したいときは、新しいインスタンスから該当のデータベースを論理ダンプで移す）。**Secrets Manager の鍵は作り直さない**（手順 1 と同じ理由。`N8N_ENCRYPTION_KEY` を含む）。DB の移行は 1 回だけのタスクで実行する（TA-06 の 3.3）。疎通の確認は 4 節の項目 6・7 と同じく、訪問者向けのパスが認証なしで通り、管理画面が `admin-auth`（`auth.comegin.com`）の認可エンドポイントに転送されることを見る。

**手順 1 で `dev/init-env.sh` を実行しないことが最も重要である。** このスクリプトは冪等で「空の項目だけを埋める」ため、環境変数ファイルを復元せずに実行すると、新しい鍵が生成された状態で完全に正常に見える環境ができあがる。そして既存のデータだけが復号できない。**失敗が失敗に見えない**という点で、この経路が最も危険にあたる。

### 再帰的自己改善にとって何が欠落しているか

管理外のものは 3 つに分けられる。

1. **管理外で正しいもの** — コンテンツ本体（`E-04`）、クレデンシャル、計測結果（`E-12`）。それぞれ別の正本を持つか、意図的に追跡しない理由がある。
2. **管理外だと履歴が欠落するもの** — n8n のワークフローと実行履歴、Chatwoot の Webhook 設定、Mautic のキャンペーン定義、**OpenSEO のランク追跡の設定**（旧版の「Umami のサイト設定」は ADR-25 で外した）。
3. **管理外であることに気づきにくいもの** — PostHog の設定、**GA4 のプロパティの設定**（ADR-25）。外部にあるため、リポジトリを見ても存在自体が分からない。

**2 と 3 が、この基盤が自己改善型であることの妨げになる。**
DA-01 は `E-13` の要件を「履歴が残る」「差し戻せる」「取り消せる」の 3 つと定義し、Git がそれを満たすことを理由に正本を Git に置いた。しかし**提案が Git にあっても、提案の適用先が Git の外にあれば、取り消せるのは提案文だけで実体は取り消せない**。

したがって `E-13` の型には「適用先が管理下にあるかどうか」が反映されるべきである。現状、適用先ごとに次のように分かれる。

| 提案の適用先 | 取り消せるか | 手段 |
|---|---|---|
| Astro のコード | 取り消せる | `git revert` |
| `docs/` の文書 | 取り消せる | 同上 |
| Strapi の記事 | 部分的に取り消せる | draft / publish の状態を戻す。ただし公開済みの記事は検索エンジンに残る。**Strapi のコンテンツタイプ（スキーマ）はコードにあるため `git revert` と再デプロイで戻せる**（ADR-16。ただし項目の削除のように、本番のデータが失われる変更は戻らない） |
| **n8n のワークフロー** | **取り消せない** | エクスポート方針（TA-03 の 6 節）を実装すれば取り消せるようになる |
| **Mautic のキャンペーン定義** | **取り消せない** | 手段が無い |
| **PostHog の設定** | **取り消せない** | 手段が無い |
| **OpenSEO のランク追跡の設定** | **設定は戻せるが、支出は戻らない** | 画面で戻す。適用前の対象キーワードと頻度を `E-13` に写しておく（AA-04 の 3.3.1） |

この表の下 3 行が、`CAP-14` のループを閉じるうえで残っている穴にあたる。優先度は n8n が最も高い（改善提案の適用先として最も頻繁に使われることが想定されるため）。

### 課題: 見直す前提の数値が、見直した履歴の残らない場所にある

上の表の「Mautic のキャンペーン定義」には、具体的な食い違いがある。

BA-04 は MA へのトスアップ条件として、**ポイントの加算値（ホワイトペーパー DL `+10` / 無料トライアル申込 `+30` / デモ予約 `+50`）と MQL のしきい値（累計 `50`）**を定めている。そしてこれらについて次のように明記している。

> ポイントの加算値（10 / 30 / 50）と MQL のしきい値（50）は暫定値。実データが取れるまで妥当性を検証できない。運用開始後に `CAP-14` の対象として見直す前提で置く。

**見直す前提で置かれた数値が、見直した履歴の残らない場所（Mautic の `mysql-data`）に置かれることになっている。** これは単なる管理漏れではなく、BA-04 の意図と TA の構成管理が噛み合っていない箇所にあたる。

具体的に何が困るか。

- `10` を `15` に変えたとき、**いつ・誰が・なぜ変えたかが残らない。** 次にその数値を見た人には、それが初期値なのか調整後の値なのかが区別できない。
- `E-13` の `verification`（既定で 30 日後に効果を判定する）が、**比較対象となる変更前の値を参照できない。**
- 同じ理由で、変更を取り消せない（元の値が記録されていないため、戻すべき値が分からない）。
- Lighthouse CI のしきい値（`frontend/verdant-virgo/lighthouserc.cjs`）が Git 管理下のコードに置かれ、変更が PR の差分として見えるようになっているのと**対照的**である。判断基準を外に出さないという方針（BA-02 の「外部サービスの成果物ではなく判断基準を内製する」）が、Mautic 側では実現していない。

選択肢は 2 つある（**推奨は出さない。DA と AA の判断に依存するため**）。

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A | **n8n と同様のエクスポート方針を採る。** Mautic の API 経由でキャンペーン・セグメント・フォームの定義を定期的に書き出し、Git に入れる（`mautic-mcp` に参照系のツールが既にある） | 定義の全体が履歴に残る。n8n のエクスポート（TA-03 の 6 節）と同じ仕組みを流用でき、運用の型が 1 つで済む | 書き出す対象が広く、差分が安定しない可能性がある（n8n と同じく、実行のたびに変わるフィールドの除去が要る）。**Mautic の定義を Git から戻す手段は無い**ため、履歴としてしか使えない |
| B | **しきい値だけを Git 管理の設定ファイルに逃がす。** ポイント加算値と MQL しきい値を Git 上の設定として持ち、Mautic 側へは n8n から反映する（Mautic のキャンペーン定義は「設定を読んで動く」形にする） | 変更が PR の差分として見える。Lighthouse CI のしきい値と同じ扱いに揃う。対象が数値 4 つだけなので差分が安定する | 数値の正本が Mautic ではなく Git になるため、**Mautic の管理画面で直接変更できてしまう経路を塞ぐ必要がある**（塞がないと正本が 2 つになり、どちらが効いているか分からなくなる）。反映の仕組み（n8n のワークフロー）を作る必要がある |

どちらを採るにせよ、**この数値が `E-13` の適用対象になる**ことは BA-04 が既に決めている。適用対象が管理外にあるという状態を放置すると、`CAP-14` が「提案はできるが、適用した結果を検証できない」という形で不完全なまま回ることになる。

## 7. Lighthouse CI の運用

`frontend/verdant-virgo/lighthouserc.cjs` の設定と、その運用上の意味。

| 設定 | 値 | 理由 |
|---|---|---|
| `numberOfRuns` | `3` | 単発の計測は数値がブレるため、3 回走らせて中央値を採用する |
| `startServerCommand` | `astro preview --port 4322` | **4322 に固定する。** 4321 だと Astro が dev サーバーとの衝突を避けて別ポートへ退避し、LHCI が dev サーバーを誤計測する |
| `chromeFlags` | `--headless=new` | GUI の無い環境では X サーバーが不在で、付けないと Chrome が即死する |
| `upload.target` | `filesystem` | **既定の `temporary-public-storage` はレポートを外部に公開するため使わない** |
| `outputDir` | `./.lighthouse` | 出力先。`.gitignore` で除外済み |
| `categories:performance` | `error`, `minScore: 0.9` | 本番ビルドの実測ベースラインが 0.98〜1.00 のため余裕がある |
| `categories:accessibility` | `error`, `minScore: 0.9` | 同上 |
| `categories:best-practices` | `error`, `minScore: 0.9` | 同上 |
| **`categories:seo`** | **`error`, `minScore: 1`** | **SEO 対策がこの計測の目的なので満点を死守ラインとする** |

ファイル拡張子が `.cjs` なのは `package.json` が `"type": "module"` であり、LHCI が `require()` で読み込むため。

### 運用上の約束

- **SEO 1.0 は緩めない。** 緩めるべき理由が生じた場合、それはしきい値の問題ではなく、Lighthouse の SEO 監査項目のどれが満たせなくなったかの問題である。しきい値の変更は `E-13` として起票し、`R2` の承認を経る（しきい値をコードで管理しているのは、この変更を PR の差分として見えるようにするためである）。
- **結果を外部に公開しない。** `upload.target` を `temporary-public-storage` に戻さない。公開サイトの構造と計測結果が第三者から読める状態を作らない。
- **3 回計測の中央値であることを忘れない。** 計測が 1 回で終わらないため、CI に載せると相応の時間がかかる。頻度を上げるより、ビルドごと ＋ 週次の定点という 2 段構えにする（TA-03 の 3.3）。
- **合成計測と実測を混同しない。** DA-04 は Core Web Vitals の実測を Umami（`get_performance`）、合成計測を Lighthouse CI と役割分担している（**2026-10-06 ADR-25: 実測は PostHog の `$web_vitals`〈p75〉に変わった。3 節。実測は同意した訪問者だけの標本であり、Lighthouse CI は同意の前の状態〈GA4・PostHog のタグが無い状態〉を測る**）。Lighthouse のスコアが良いことと、実ユーザーの体験が良いことは別である。

- **（2026-10-06 に送り手は決着）ハートビートの送り手。** 監視アプリに移した（builtin `heartbeat`）。オンプレの n8n は別の名前空間で送る（項目 3）ため、「開発環境の n8n の停止とオンプレの全滅を区別できない」（DD-07 の 8 節）は、**監視アプリの停止（`ComeGin/Onprem`）と n8n の停止（`ComeGin/OnpremN8n`）を別のアラームで見分けられる**形で解けた。**残る論点**: 重大度（`comegin-ops-alert` の即時の通知のままか）、「改善ループが何日止まってよいか」（TA-01 の 9 節）、開発機の夜間・休日の停止の扱い（DD-07 の 8 節。ADR-21 で顧客の要求の通知にも効くようになった）。以下は ADR-17 の時点の記述。
- **ハートビートの送り手と重大度**（4 節の項目 16・17。ADR-17）。開発環境の n8n が送るのを続けるか、監視アプリ（ADR-17 で定期実行の起動元になった）に移すか。移すと、監視アプリだけが止まった状態も検知でき、項目 17 を兼ねられる（本ファイルは移すほうが目的に合うと考える。4 節）。移す場合の資格情報の置き場は TA-04 の 1 節・9 節。重大度（ADR-16 で下げる検討をし、ADR-17 で「改善ループの停止」として重みが戻った）と、「改善ループが何日止まってよいか」（TA-01 の 9 節）も合わせて決める。TA-07 の 9 節と同じ項目。判断者 `R1`。
- **監視アプリの定期実行の失敗と、誤った書き込みの候補を通知するか**（4 節の項目 19・20。ADR-17）。監視アプリの表示だけでは、画面を開かない日が続くと気づかない。`comegin-ops-alert` に出すなら監視アプリに `sns:Publish` が要り、TA-04 の 1 節の「SNS に発行できる長期のアクセスキーを無くした」判断と食い違う。代わりに、失敗が続いたら監視アプリがハートビートを止める（項目 16 に畳み込む）形も考えられるが、「止まっている」と「動いているが失敗している」が区別できなくなる。**誤った書き込みの候補を通知する場合も、メッセージの本文や顧客の名前を載せない**（件数と会話の ID だけにする。4 節の「`comegin-ops-alert` に個人情報を載せない」）。判断者 `R1`。
- **（2026-10-06 に ADR-21 で更新）Webhook の受け口の死活の検知手段が無い。** 経路は VPC の中ではなく WireGuard 越しのオンプレのプロキシ（`10.99.0.2:5680`）になった。**プロキシだけの停止・ワークフローの未公開・送信元の制限の誤り（本番の Webhook がすべて 404 になる）・WireGuard の断（n8n が RDS に届かないまま動き続ける場合）は、項目 3 のハートビートでも分からない**（ハートビートの送信先の CloudWatch はトンネルを通らない）。WireGuard の EC2 の停止は ops に通知されるが、トンネルそのものの監視はまだ（cloud/README の 5 節）。候補は DD-07 の 8 節（EC2 からの疎通の定期確認・製品側の送信失敗のログ・監視アプリの定期実行による突き合わせ）。**決めていない。** 判断者 `R1`。以下は ADR-16 の時点の記述。
- **VPC の中の Webhook の取りこぼしの検知手段**（4 節の項目 15。ADR-16）。n8n のタスクの停止は項目 12 で分かるが、送信先の URL の誤り・内部の名前の解決の失敗・製品側の Webhook の無効化は分からない。本番の n8n の実行履歴に Webhook 起点の実行が一定期間無いことを見るか、Chatwoot・Mautic の送信失敗のログを CloudWatch Logs のメトリクスフィルタで拾うか。問い合わせが少ない時期は「一定期間無い」が正常と区別できない点も考慮する。判断者 `R1`。
- **（2026-10-06 に ADR-21 で更新）Strapi と n8n の ECS のアラームは要らなくなった**（オンプレに移った）。**n8n は項目 3、Strapi の死活（オンプレのハートビート）は未設計**（cloud/README の 5 節）。**n8n の実行履歴の保持期間は 90 日に決めた**（項目 13）。共有の RDS のしきい値の見直し（`strapi`・`n8n` が載る）は残る。以下は ADR-16 の時点の記述。
- **Strapi と n8n の CloudWatch アラームの追加**（4 節の項目 12・13。ADR-16）。ECS のサービス 2 つ分（タスク数・ALB のターゲット・5xx）と、共有の RDS に `strapi` と `n8n` が載ることによるストレージ・接続数のしきい値の見直し。**n8n の実行履歴の保持期間**（n8n の設定で古い実行を削除するか）もストレージの見積もりに効くため合わせて決める。項目 12〜14 のしきい値と一体で決める。
- **開発環境の監視の通知先**（4 節の項目 1・2。ADR-16）。旧版では、オンプレのコンテナの停止を SNS の `comegin-ops-alert` に出す前提だった。ADR-16 で対象は開発環境だけになり、本番の障害と同じトピックに出すと通知の重みが揃わなくなる。監視アプリの表示にとどめるか、SNS に出すか（その場合は開発環境の n8n に `sns:Publish` が要り、TA-04 の 1 節の判断と食い違う）を決める。判断者 `R1`。
- **Strapi の記事を復旧するときの RDS と S3 の揃え方**（5 節。ADR-16）。本文（RDS）と画像（S3）は戻し方が違い、同じ時点に揃える手順が無い。S3 のバージョニングで「その時点のバージョン」に戻す手順を作るか、画像を消さない運用（削除は論理削除にとどめる）で済ませるかを決める。判断者 `R1`。
- **監視アプリが本番の CloudWatch のアラームの状態を読む手段が未定**（1 節）。読み取り専用の IAM（`cloudwatch:DescribeAlarms`）をオンプレに置くことになる。ADR-15 で本番の資格情報はローカルの PC に置かれることになったため（TA-04 の 1 節）、同じ守り（専用の主体・Git で追跡しない・Claude Code の実行環境に渡すか）で置けるかを決める。判断者 `R1`。
- **`RPO` / `RTO` の合意が無い。** どれだけのデータ損失を許容するか、どれだけの時間で復旧すべきかが決まっていないため、日次という頻度も根拠のない暫定値にとどまる。
- **Mautic の設定ファイルをバックアップ対象に含めるかが未確定。** TA-04 の未決定事項と同じ。本セッションでは内容を確認していない。
- **PostHog のデータの復旧手段が無いことをどう扱うかが未定。** `E-08` `Person` と `E-11` `Experiment` の正本が外部にあり、オンプレのバックアップでは復旧できない。定期的にエクスポートして手元に持つか、SaaS 側の保証に委ねるかを決めていない。
- **Chatwoot の `rails` / `sidekiq` に healthcheck を足すかが未確定。** 2 節で穴として指摘したが、追加すると `backend/chatwoot-system/docker-compose.yaml` を変更することになる。この compose は自作（公式イメージを動かすための設定のみ）であるため上流との衝突は起きないが、変更の是非を `R1` が判断していない。
- **DataForSEO の支出を取得する手段が未定**（4 節の項目 11）。セルフホストの OpenSEO は支出を計量しない。DataForSEO のダッシュボードを人間が月次で見るか、DataForSEO の API で残高を取るか（その場合は資格情報を OpenSEO 以外の場所にも置くことになる）を決めていない。判断者 `R1`。
- **OpenSEO のバックアップの具体的な手順が未検証**（5 節）。D1 のローカル実装（wrangler の状態ディレクトリ内の SQLite）をどの単位で複製すれば整合するかを、実際に復元して確かめていない。
- **（2026-10-06）OpenSEO のイメージの固定と匿名テレメトリの停止は、ユーザーの判断を待っている**（`setup` の `apply` には入れていない。TA-04 の 9 節）。
- **OpenSEO の上流の更新をどう取り込むか。** compose は `ghcr.io/every-app/open-seo:latest` を使っており、`docker compose pull` のたびに版が変わる。**MCP のツール定義が黙って変わる**（ADR-10 の許可リストがツール名に依存している）ため、`OPEN_SEO_IMAGE` で版を固定するかどうかを決めていない。判断者 `R1`。
- **（2026-10-03 に追加）収益化の監視が `points-api` 自身の停止を拾えない。** `points-api` が止まると上の 4 つの通知も止まる。ハートビート（4 節）の対象に加えるかを決める。
