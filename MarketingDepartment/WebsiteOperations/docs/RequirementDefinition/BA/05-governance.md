# 05. ガバナンス・セキュリティ運用

BA（Business Architecture）層。ロール ID（正本は BA-03）・Capability ID（BA-02）はそれぞれの正本の定義をそのまま使う（索引は [`docs/README.md` の「ID の採番と正本」](../../README.md)）。この領域の主担当は `R1`（`CAP-15` ガバナンス・アクセス管理）。

## SSO とアクセス権限制御の方針

### 現状（As-Is）

**SSO は未導入である。** 対象システムはすべて個別にアカウントを持ち、認証情報も個別に管理されている。README に「シングルサインオン（SSO）やアクセス権限制御を徹底し」とあるのは To-Be の記述であり、現時点で実現している事実ではない。

### To-Be の方針

- **SSO の導入は、システムの数ではなく「担当者の数が 2 名を超えた時点」を契機にする**（1 人が兼務している間は、SSO を入れても削減される作業がほぼ無く、導入と維持のコストだけが残るため）。それまでは後述の担当者変更チェックリストと、パスワードマネージャによる認証情報の集約で代替する。
- **SSO を入れる場合の対象は、人間がログインするシステムに限る**（Strapi / Mautic / Umami / PostHog / Chatwoot / n8n）。MCP サーバと Lighthouse CI は人間がログインしないため対象外。**OpenSEO も対象外**（ログインそのものが無い。守りはループバックで行う）。
- **エージェントの権限は SSO の外側で管理する。** エージェントが使うのは MCP の `ACCESS_LEVEL` と上流 API のトークンであり、人間の SSO セッションとは経路が別。この分離は維持する（エージェントの権限を人間のセッションに乗せると、人間のログイン状態がエージェントの実行可否を左右し、権限の境界が追えなくなるため）。
- **エージェントは開発環境と本番の Strapi・Mautic・Chatwoot・Umami・n8n を MCP で操作する**（`R1` の 2026-09-19 の決定。AA-05 の ADR-15 で Mautic・Chatwoot・Umami、ADR-16 で Strapi・n8n。同日の ADR-14 の「開発環境だけ」を置き換えた）。管理者は監視アプリからエージェントに指示し、エージェントを使う定期処理も監視アプリが起動する（ADR-17）。本番の登録は `ACCESS_LEVEL=read_write` を上限にし（ADR-16 で確定。Strapi は Admin トークンの権限で下書きまでに絞る。ADR-17）、トークンはエージェント専用のアカウントで発行する。**本番の記事の公開（ADR-17）、公開サイトへの配信、n8n のワークフローの本番での有効化は人間が行う。**
- **最小権限を既定にする。** MCP サーバの `ACCESS_LEVEL` は既定値の `read_only` から始め、必要が生じた Capability ごとに引き上げる。引き上げは `R1` の承認事項（後述の承認ゲート一覧）。

## 担当者変更時の手順

`R1` が実施し、完了を `R2` に報告する。各項目は完了を確認できる形で書く（「確認する」ではなく「〜になっていること」）。

### 参加時

- [ ] 割り当てるロール（`R1`〜`R4` のいずれか）を決め、RACI（03）に照らして必要な Capability を洗い出している
- [ ] 各システムのアカウントを作成し、**そのロールに必要な最小の権限のみ**を付与している
- [ ] 本番の Strapi・Mautic・Chatwoot・Umami・n8n の管理画面を使う場合、**`comegin.com` の Google Workspace アカウントを発行し、2 段階認証を登録させている**（Workspace の組織で 2 段階認証を必須にしておく）。そのうえで **`admin-auth` の管理者の許可リストに email を追加している**（`R1` が行う。Workspace のアカウントを持つだけでは管理画面に入れない。`admin-auth` は製品の手前の関門であり、各製品のアカウントとは別に要る。TA-04 の 6 節・TA-06 の 5.2.1・AA-05 の ADR-13）
- [ ] Strapi のロールが Super Admin になっていない（`R4` 相当なら Author、`R2` 相当なら Editor）
- [ ] Chatwoot のロールが、レポート閲覧を必要としない場合はエージェントになっている（管理者にしない）
- [ ] 認証情報を本人以外が保持していない（初期パスワードは初回ログイン時に変更させる）
- [ ] GitHub リポジトリのコラボレータに追加し、直接 push ではなく PR 経由の運用であることを伝えている
- [ ] MCP サーバの認証情報（`MCP_AUTH_TOKEN`、上流 API のトークン）を渡していない（人間の作業に MCP のトークンは不要）
- [ ] OpenSEO を使う場合、**開発機のローカルで使うこと**を伝えている（無認証のため、トンネルや別端末から開かない。AA-05 の ADR-09）
- [ ] GSC を OpenSEO に接続する場合、**`comegin.com` の Google Workspace アカウントを使っている**（同意画面が「内部」のため、組織外のアカウントでは接続できない。TA-04 の 8.3）

### 離任時

- [ ] 各システムのアカウントを**無効化**している（削除ではなく無効化。削除すると操作履歴の帰属が失われるため）
- [ ] **`admin-auth` の管理者の許可リストから email を削除し、Google Workspace のアカウントを停止している**（どちらか一方でも新しいログインは止まるが、両方を行う。削除・停止しても、ALB の既存のセッションがすぐには切れない可能性がある〈最長で ALB のセッションの期限の 12 時間。実地では未確認〉。確実に止めるため、各製品のアカウントの無効化を先に済ませる）
- [ ] その人が発行した API トークンをすべて失効させている（Chatwoot の `api_access_token` は**ユーザーに紐づく**ため、アカウント無効化だけでは不十分な場合がある）
- [ ] Mautic の API クライアント（OAuth2）が離任者に紐づいていた場合、別のユーザーで再発行している
- [ ] GitHub のコラボレータから外している
- [ ] 共有していた認証情報（もしあれば）をすべてローテーションしている
- [ ] 離任者が担当していた Capability の `A` を、03 の RACI 表に従って別の人間に再割り当てしている（`A` が空席の Capability を作らない）
- [ ] **ローテーションしてはいけない値に手を付けていない**: `N8N_ENCRYPTION_KEY`、Chatwoot の `ACTIVE_RECORD_ENCRYPTION_*`（変更すると既存の暗号化データを復号できなくなる）
- [ ] 離任者の Google アカウントで OpenSEO の GSC 接続をしていた場合、**別の人のアカウントで接続し直している**（GSC の接続はアカウントに紐づく。離任者のアカウントを無効化すると GSC の取得が止まる）。`BETTER_AUTH_SECRET` は変えない（変えると保存済みのトークンを復号できない。TA-04 の 2 節）
- [ ] DataForSEO のアカウントを離任者が持っていた場合、所有者を移し、API の資格情報を再発行している
- [ ] **本番の n8n に、離任者のアカウントで発行したトークンを資格情報として登録していた場合、エージェント専用・システム用のアカウントで発行し直して登録し直している**（n8n は本番の Chatwoot・Mautic などの資格情報を自分の DB に持つ。ADR-16、TA-06 の 7 節。`N8N_ENCRYPTION_KEY` は変えない）

## 承認ゲートの一覧

エージェントが自律実行してよい操作と、人間の承認を要する操作の境界を定義する。**この表が再帰的自己改善の安全装置の土台**であり、エージェントが自分自身を改善する範囲を制限する唯一の明示的な境界である。

分類の定義。

- `自律` — エージェントが単独で実行してよい。事後に人間へ通知する。
- `承認` — 実行前に指定ロールの承認が必要。承認は `E-14` `ApprovalRecord` として記録する。
- `禁止` — エージェントは実行しない。人間が直接行う。

| 操作 | 分類 | 承認者 | 根拠 |
|---|---|---|---|
| 記事の下書き作成・更新（`publishedAt` を設定しない） | `自律` | — | 失敗しても公開されず、影響が閉じている |
| 記事の**公開**（`publishedAt` の設定）・公開済み記事の更新 | `承認`（**実行は人間**。`R2` が本番の Strapi の管理画面で自ら行う。ADR-17） | `R2` | 04 の更新ワークフロー 3b。外部に露出する変更で、取り消しても検索エンジンには残る。**ADR-17 で `strapi-prod` の Admin トークンに公開の権限を与えないことにし、承認を約束ではなく仕組みで守る**（エージェントは下書きまで。公開済み記事の更新も、エージェントが書いた下書きを `R2` が公開して反映する） |
| 記事の削除・非公開化 | `承認`（**実行は人間**。ADR-17） | `R2` | 既存の流入と被リンクを失う。取り消しが効かない。`strapi-prod` のトークンに削除（ADR-16）と非公開化（ADR-17）の権限を与えない |
| 観測データの参照・集計・レポート生成 | `自律` | — | 読み取りのみ。`sanitize()` で秘匿値は伏せられる |
| 改善提案（`E-13`）の**生成** | `自律` | — | 提案は提案にすぎず、実体に作用しない |
| 改善提案の**採用と適用** | `承認` | `R2` | `CAP-14` の中核。ここを自動化すると、提案の生成から適用までが閉路になり、外部からの是正が入らなくなる |
| AB テスト（`E-11`）の開始 | `承認` | `R3` | 実ユーザーに異なる体験を出す。同時実行数の管理が必要 |
| AB テストの停止 | `自律` | — | 停止は元の状態に戻す操作で、リスクが増えない方向 |
| Chatwoot の**社内メモ**の作成（`private=true`） | `自律` | — | 顧客には見えない。**社内メモ専用のツールか社内メモ用の登録で行い、社内メモだけを使うエージェントには `chatwoot_send_message` を見せない**（ADR-17。このツールは社内メモと送信を兼ね、`private` の既定値が `false` のため、付け忘れ 1 つで顧客に届く） |
| Chatwoot の**顧客への返信**（`private=false`） | `承認` | `R3` | 顧客に即時送信され、取り消せない |
| Mautic のコンタクト作成・セグメント追加・スコア加算 | `自律` | — | 04 のトスアップ条件に沿った機械的な処理。条件自体が承認済み |
| Mautic からの**メール送信**・キャンペーンの開始 | `承認` | `R3` | 外部に送信され、取り消せない |
| Mautic / Chatwoot のレコード削除（`full` 相当の操作） | `承認` | `R1` | 破壊的操作。MCP 側では `destructiveHint: true` が付与されている |
| Lighthouse CI の計測実行 | `自律` | — | 読み取りのみ |
| コードの変更提案（ブランチ作成・PR の作成） | `自律` | — | マージされるまで作用しない |
| コードの **main へのマージ** | `承認` | `R1` | 基盤そのものの変更。リポジトリの Git 運用（PR 経由）と整合する |
| 本番環境へのデプロイ | `承認` | `R1` | 外部に露出する。リポジトリのルール（明確な指示がない限りデプロイしない）と整合する |
| **公開サイトへの配信**（Astro のビルド成果物を S3 に同期。TA-07 の 7 節） | `承認`（**実行は人間**） | `R2` | ADR-15 で、Claude Code はビルド（ADR-16 で本番の Strapi を読む）と計測までを行い、配信は人間が承認して実行する。配信用の IAM はエージェントに渡さない。**記事の場合は、`R2` が管理画面で公開したものを監視アプリの定期実行が見つけてビルドと計測を起こし、その後に人間が配信する**（ADR-17。公開と配信の 2 段階。同じ人が続けて行うかは運用で決める）。**Astro の変更の `E-13` の `applied` への遷移はこの配信をもって行い、`applied_at` は配信した人間が記録する**（ADR-16。AA-04 の 2 節） |
| **エージェントによる本番の Strapi・Mautic・Chatwoot への MCP での書き込み**（TA-07 の 6 節） | 操作の種類に応じて上の表の分類に従う（メール送信・キャンペーンの開始・顧客への返信は `承認`、下書き・社内メモ・ラベルは `自律` など）。**記事の公開はここに含まれない**（ADR-17。`strapi-prod` は下書きまでで、公開は `R2` が管理画面で行う） | 操作に応じた承認者（メール・キャンペーン・顧客への返信は `R3`、設定は `R1`） | ADR-15 で本番の Mautic・Chatwoot、ADR-16 で本番の Strapi（ADR-17 で下書きまで）への書き込みが可能になった。**`承認` の操作は承認を得てから実行し、書き込みの完了をもって `E-13` を `applied` にする**（`applied_at` は Claude Code が書き込みの完了と同時に記録する。ADR-16）。**Strapi の記事は例外で、公開サイトへの配信の完了をもって `applied` にし、配信した人間が記録する**（訪問者に届くのは配信の後のため。TA-07 の 6 節）。**顧客へのメッセージ送信（Chatwoot）も許す**（ADR-16。`chatwoot-prod` から送信系のツールを外さない。分類は上の「顧客への返信」のとおり `承認`・`R3`。ADR-15 の時点では未決定だった） |

### 境界線の引き方（設計の要点）

分類は次の 3 つの問いで決めている。恣意的に個別判断しないための基準である。

1. **外部に露出するか。** 顧客・検索エンジン・受信者に届く操作はすべて `承認`。取り消しても届いた事実は消えないため。
2. **取り消せるか。** 元の状態に戻せる操作（下書き、AB テストの停止、PR の作成）は `自律`。戻せない操作（削除、送信、マージ）は `承認`。**支出も戻せない操作である**（2026-09-18 に OpenSEO の追加で明記）。ただし 1 回の額が小さく、上限（前払い残高と月次予算）が仕組みとして効いている範囲に限り `自律` とし、上限の内側で額の大きいものと、支出が自動で続く設定を `承認` にした。
3. **エージェント自身の権限や実行条件を変えるか。** 変える操作はすべて `禁止`。承認を挟んでも、承認を求める主体と承認の条件を書き換える主体が同じになりうるため、承認では守れない。**例外は定期実行の定義の変更**（ADR-18 の追加の決定）で、承認の仕組み（PR のレビューとマージ、監視アプリが承認済みの `main` だけを読むこと）がエージェントの届かない場所にあるため、`承認` で守る。この例外は「エージェントが `main` にマージできない」ことに依存する（未決定事項の「GitHub のブランチ保護設定の実態が未確認」）。

### 本番への書き込みと分類（ADR-15・ADR-16・ADR-17・ADR-18）

**上の表の分類は、本番に対する操作を基準にしている。** ADR-15 でエージェントは本番の Mautic・Chatwoot に、ADR-16 で本番の Strapi と n8n にも MCP で書き込むため、表の分類がそのままエージェントの操作に効く。

- **`承認` の操作は、承認を得てから本番に書き込む。** 同日の ADR-14 では「本番に届くのは人間の反映だけ」を最後の砦にしていたが、ADR-15 で本番への書き込み手段がエージェントに渡ったため、**承認ゲートと `ACCESS_LEVEL`（本番は `read_write` まで。ADR-16 で確定）とエージェント定義の許可リストが砦になる**。Strapi は `ACCESS_LEVEL` を持たないため、Admin トークンの権限が同じ役割を果たす（ADR-16 で削除を外し、**ADR-17 で公開・非公開化も外して下書きまでにした**）。
- **本番の記事の公開、公開サイトへの配信、n8n のワークフローの本番での有効化は、実行手段の点でも人間に残す**（`strapi-prod` に公開の権限を与えない。ADR-17。**本番の n8n に登録する Strapi の資格情報にも公開・非公開化・削除の権限を与えない**。ADR-18。配信用の IAM をエージェントに渡さない。`n8n-prod` に有効化を許さない。ADR-16）。**記事の公開は、承認者（`R2`）が自分で行う操作になった**（承認と実行が同じ人間に揃い、「承認を得たはずの公開」と「実際の公開」の食い違いが起きない）。
- **取り消せない送信を、引数の付け忘れ 1 つで起こせる形にしない**（ADR-17）。Chatwoot の社内メモ（`自律`）と顧客への返信（`承認`・`R3`）は、今の `chatwoot_send_message` では同じツールの `private` の値でしか分かれず、既定値は `false`（顧客に送信）である。社内メモ専用のツールか登録を分け、社内メモだけを使うエージェントには送信のツールを見せない（方法は未決定。TA-07 の 9 節）。
- **本番への誤った書き込みは、エージェント専用ユーザーの送信の記録（`sender`）と `E-13` の突き合わせで見つける**（ADR-17、TA-07 の 6.2）。**ADR-16 では Chatwoot の監査ログ（Enterprise の `audit_logs` 機能）を主な手段とし、使えなければ `sender` で代える形にしていたが、ADR-17 で Community 版で運用できるよう監査ログに頼らないことにした。** 拾えるのは送信だけで、会話の属性（担当者・ラベル・状態）の変更は拾えない。突き合わせは監視アプリの定期実行の 1 つとして起動する（頻度は未決定）。**エージェント専用のアカウントでトークンを発行することが、この突き合わせの前提になる。**
- **開発環境と本番の設定はそろえ続ける**（ADR-16、TA-07 の 6.1）。エージェントは設定の変更を開発用の登録で確かめてから `-prod` の登録で本番に適用する。承認は本番への適用に対して求める。

### 自動化が承認ゲートを迂回する経路に注意する

n8n のワークフロー作成を `承認` にしているのは、**ワークフロー自体が「承認なしで実行される操作の定義」になりうる**ため。エージェントが「記事を公開するワークフロー」を作って自律実行できてしまえば、公開の承認ゲートは事実上無効になる。同じ理由で、次の 2 つを原則とする。

- ワークフローが行う操作の分類は、**エージェントが直接行う場合と同じ分類を適用する**（実行手段を変えても承認要件は変わらない）。**ADR-17 でエージェントのトークンから記事の公開の権限を外した後も、本番の n8n に公開の権限を持つ Strapi の資格情報を登録すれば、ワークフロー経由で同じ穴が開く**（ADR-17 の時点では未決定事項だった）。**ADR-18 で、本番の n8n に登録する Strapi の資格情報にも公開・非公開化・削除の権限を与えない（下書きまで）と決めた。** 今の設計で本番の n8n が Strapi に書く処理は無いため、**必要になるまで登録しない**。n8n のワークフローはエージェントが `n8n-prod` で作れるため、n8n の資格情報もエージェントのトークンと同じ範囲に絞らないと、記事の公開を人間だけが行う形がこの経路で崩れる。
- `sandbox-runner-1` は privileged な Docker-in-Docker でホスト root 相当のため、暗号化キーや DB パスワードを渡さない現在の分離を崩さない（この分離が崩れると、ワークフローから `禁止` 分類の操作に到達できる）。**本番の n8n にはサンドボックスを置かない**（ADR-16。Fargate は privileged のコンテナを受け付けない）ため、この分離は開発環境で守るものになる。

## 未決定事項

- **`E-14` `ApprovalRecord` の記録場所と、承認の検証方法が未定。** 承認ゲートを「手順としての約束」から「状態としての前提」に変えるには、承認記録を機械が参照できる必要がある。DA の決定を待つ。
- **SSO の製品が未選定。** 導入契機を「担当者 2 名超」としたが、対象システム 6 つのうち Umami と n8n の Community 版は SSO 対応が限定的で、全システムを 1 つの IdP に寄せられない可能性がある。TA の調査事項。
- **承認の記録に非改竄性を持たせるか。** 現状は記録の存在だけを要件にしている。エージェントが承認記録自体を書き込める場合、承認の偽造が理論上可能になる。書き込み権限の分離が必要かどうかは、`E-14` の格納先が決まってから判断する。
- **`R2` が不在のときの承認の代理。** 公開承認が `R2` に一点集中しており、`R2` が動けない期間は `自律` 分類の操作しか進まない。代理承認者を置くか、期限付きで分類を緩めるかは体制が固まってから決める。**ADR-17 で記事の公開は `R2` が本番の管理画面で自ら行う操作になり、承認だけでなく操作も `R2` に集中した。** 代理を置く場合は、本番の Strapi の管理画面で公開できるアカウントと `admin-auth` の許可リストにも代理を加える必要がある。
- **GitHub のブランチ保護設定の実態が未確認。** main への直接 push が技術的に防がれているかを確認していない（参照系の git コマンドでは設定を読めないため）。防がれていない場合、`承認` 分類の「main へのマージ」が手順上の約束にとどまる。
- **（2026-09-19 に ADR-15 で解決）開発環境から本番への反映の手段。** Strapi はオンプレだけに戻り、Mautic・Chatwoot はエージェントが MCP で本番に書き込むため、反映の工程は無くなった。ADR-16 で本番に Strapi を戻した後も、記事は本番にだけ書くため反映の工程は無いままである。設定と構造は「そろえ続ける」で扱う（TA-07 の 6.1）。
- **本番への作用（MCP での書き込み・承認後の配信・n8n の有効化）を `E-14` の承認とどう結び付けて記録するか**（ADR-15、TA-07 の 9 節）。`applied_at` を誰が記録するかは ADR-16 で決まった（下の表）が、`applied_at` と `E-14` を結ぶ方法は決まっていない。判断者 `R1`。
- **Strapi 5 の Admin トークンで「公開だけを外す」権限の設定ができるか**（実装時の確認。TA-07 の 9 節）。方針は ADR-17 で決着した（下の表）が、Strapi 5 の管理画面の権限の粒度で公開を作成・更新から分けられるかは確かめていない。分けられない場合は、エージェントが公開できてしまう状態で運用するか、自作の MCP に切り替えるかを決め直す（AA-05 の ADR-07）。判断者 `R1` `R2`。
- **（2026-09-19 に ADR-18 の追加の決定で決着）定期実行の定義の変更の分類**（ADR-17 で生じた論点）。監視アプリのスケジュールの定義（取得範囲・頻度・使うエージェントとツール）はエージェントの実行条件であり、上の分類基準の 3 問目に照らせばエージェントには `禁止`（人間が行う）になる、としていた。定義の置き場所（エージェントが編集できない場所か）も決まっていなかった（AA-04 の 3.5・6 節）。**ADR-18 の追加の決定で、定義を Git で持ち、監視アプリは承認済みの `main` のチェックアウトで読むと決まった。変更は必ず PR を通す。** これを受けて承認ゲートの一覧に `承認`（承認者 `R1`）として載せた（**承認者を `R1` にしたのは本ファイルの判断**。`main` へのマージの承認者に合わせた）。残るのは、監視アプリが読む `main` のチェックアウトをいつ・誰が更新するか（TA-07 の 9 節）と、エージェントが `main` にマージできないことの担保（GitHub のブランチ保護と資格情報。上の「GitHub のブランチ保護設定の実態が未確認」・TA-04 の 9 節）である。判断者 `R1`。
- **記事の公開と配信を同じ人が続けて行うか**（ADR-17、TA-07 の 7 節）。公開（`R2`）と配信（承認者 `R2`、実行は人間）は別の操作になった。同じ人が続けて行えば手間は減るが、配信の前の計測結果（Lighthouse）を見る機会が形式化しうる。運用で決める。判断者 `R2`。
- **OpenSEO の承認ゲートの一部が約束にとどまる。** 「1 回 2,000 クレジット超は `承認`」は、ツールの引数で上限を指定できるランク追跡の実行を除き、エージェントの指示で守る約束である。到達不能性として効くのは前払い残高だけであり、**1 回あたりの上限を仕組みで守るには OpenSEO の MCP を包む自作サーバが要る**（AA-05 の ADR-10 の選択肢 2）。判断者 `R1`。

| Chatwoot の社内メモのつもりの呼び出しが顧客に届きうる（`chatwoot_send_message` の `private` の既定値が `false`） | **社内メモ用のツールか登録を分け**、社内メモだけを使うエージェントに送信のツールを見せない（どちらにするかは未決定。実装はまだ） |

### 2026-09-19 に ADR-18 で決着したこと

| 旧未決定事項 | 決着 |
|---|---|
| 本番の n8n に登録する Strapi の資格情報の権限（ADR-17 で生じた論点。エージェントのトークン〈`strapi-prod`〉から公開の権限を外しても、n8n に公開の権限を持つトークンを登録すると、ワークフロー経由で公開できる） | **公開・非公開化・削除の権限を与えない**（`strapi-prod` と同じく下書きまで）。**必要になるまで登録しない**（今の設計で本番の n8n が Strapi に書く処理は無い）。これで「記事の公開は人間だけ」がどの経路でも崩れない（「自動化が承認ゲートを迂回する経路に注意する」） |
| 定期実行の定義の変更の分類と置き場所（ADR-17 で生じた論点） | **定義は Git で持ち、変更は必ず PR を通す**（追加の決定 3）。監視アプリは承認済みの `main` から作った別のチェックアウトで読むため、エージェントが作業ツリーで書き換えても、承認されて `main` に入るまで次の実行に効かない。承認ゲートの一覧では `承認`（`R1`） |
| エージェントの実行記録（`E-15`）を人間が消す場面（削除請求） | **記録を要約と ID だけにした**（追加の決定 4。人は ID で指し、要約にも個人情報を書かない）ため、削除請求の対象から外れうる（DA-05 の 1.5。要約の検査が漏れる余地は残る）。**S3 の写しは追記だけで、削除と上書きを許さない**（追加の決定 5） |
