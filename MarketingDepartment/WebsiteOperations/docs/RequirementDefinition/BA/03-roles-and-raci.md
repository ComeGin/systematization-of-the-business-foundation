## 役割定義の正規化

### README に 2 系統の定義が重複している事実

ルート `README.md` の「スキーム（運用体制と業務フロー）」節には、役割の定義が**2 箇所に分かれて重複して書かれている**。

- 系統 A（「役割の明確化」の行）— Web マスター（全体の構築・管理）／コンテンツディレクター（SEO・記事作成）／データアナリスト（CVR 改善）の 3 つ。
- 系統 B（「役割分担の明確化」の行）— SEO ディレクター（全体戦略・キーワード選定・カスタマージャーニー設計・KPI 管理）／コンテンツエディター・ライター（記事構成案・取材・執筆・校正）／エンジニア・Web デザイナー（テクニカル SEO・表示速度改善・CTA デザインの実装）の 3 つ。

両者は別々の役割集合ではなく、**同じ体制を粒度違いで 2 回書いたもの**である。系統 A の 3 役割のうち 2 つが系統 B の 3 役割と責務範囲で重なり、残りが片方にしか現れない。この重複を放置すると、RACI の行と列がどちらの系統を指すのか決まらず、承認の所在が曖昧になる。

## エージェントの位置づけ

エージェントは**ロールではなく実行手段**として扱う。RACI 表では「エージェント」という独立した列を設けるが、これは `R1`〜`R4` と並ぶ 5 つ目のロールではなく、いずれかのロールが自分の Responsible を委任した先である。

### Accountable をエージェントに置かない理由

RACI 表の Accountable（説明責任）は、**すべての Capability について人間のロールに置く**。エージェントには一切置かない。理由は 3 つ。

- **説明責任は事後に問える相手にしか置けない。** エージェントは実行のたびにインスタンスが変わり、判断の根拠を後から一貫して説明できる主体ではない（`E-15` `AgentRun` は実行履歴であって責任の帰属先ではない）。
- **再帰的自己改善で最も危険なのは承認の自動化である。** Accountable をエージェントに移すと、エージェントが生成した提案をエージェントが承認する閉路ができ、外部からの是正が入らないまま基盤が自分を書き換え続ける。人間の Accountable は、このループを必ず一度切るための設計上の楔である。
- **権限の出所が人間にしかない。** エージェントが使う認証情報（MCP の `ACCESS_LEVEL`、上流 API のトークン）はすべて人間が発行したものであり、エージェントの権限は委任された権限にすぎない。委任元を超える責任を委任先に置くことはできない。

したがって RACI 表のエージェント列に現れるのは `R`（実行）、`C`（助言・下案の提示）、`I`（通知のみ）の 3 種だけで、`A` は現れない。

### `R4` のエージェント委任と `R2` の承認責任

`R4`（コンテンツエディター／ライター）は、下の定義のとおり**原則としてエージェントに委任する**。すなわち `CAP-04`（コンテンツ制作）の実務は `strapi-mcp` 経由でエージェントが行い、人間の `R4` は取材素材の提供と、エージェントが扱えない一次情報の確認に限定する。

ただし委任されるのは Responsible だけで、Accountable は `R2` が持ち続ける。具体的には次の形を取る。

- エージェントが記事を作成しても、`publishedAt` を設定する操作（＝公開）は `R2` の承認を経る（04 の更新ワークフロー、05 の承認ゲート一覧を参照）。**本番では公開の操作そのものを `R2` が本番の Strapi の管理画面で行う**（AA-05 の ADR-17。エージェントのトークンに公開の権限を与えないため、エージェントは下書きまでしか書けない）。
- エージェントの生成物に誤りがあった場合の説明責任は `R2` にある。`R4` を「エージェントがやったこと」として免責の口実に使わない。
- `R2` が承認できる量を超える生成は行わない（承認が追いつかない量を生成すると、承認が形式的な追認に退化し、`CAP-06` が無効化されるため）。

- `A/R` は同一ロールが説明責任と実行の両方を持つことを表す。

|---|---|---|---|---|---|
| `CAP-01` 事業戦略・KPI 管理 | I | **A/R** | C | I | R（データ集計と草案の提示） |

### 表の読み方と設計上の要点

- **`A` は 18 行すべてで `R1`〜`R3` のいずれかにある。** `R4` には `A` が 1 つも無い（`R4` はエージェント委任が前提で、承認責任は `R2` が持つため）。エージェント列にも `A` は無い。
- **`CAP-06` と `CAP-14` だけ、エージェントの `R` と人間の `A` が意図的に分離されている。** どちらも「承認」を含む Capability であり、実行（チェック・提案生成）は自動化してよいが、可否の決定は人間に残す。
- **`CAP-15` はエージェント列が `I` のみ。** 権限の付与・剥奪をエージェントが実行できると、エージェントが自分の権限を拡張できてしまう（`ACCESS_LEVEL` を上げる操作自体がエージェントの手の届く範囲に入るため）。この 1 行だけは自動化の対象外として固定する。
- **`CAP-07`（公開）は `R1` が `A`、`R2` が `C`** という配置になっている。これは公開という技術操作の責任は `R1`、公開してよいかという内容判断は `R2`、という分担を表す（技術的に公開できることと、公開してよいことを混同しないため）。**（2026-09-19 に AA-05 の ADR-17 で変更）** エージェントのトークンから記事の公開の権限を外し、本番の Strapi での公開の操作は `R2` が自ら行うことになったため、`R2` の列に `R` を加え、エージェントの `R` を「承認後の公開操作」から「公開された記事のビルドと計測」に改めた。`A` は `R1` のまま（配信〈S3 への同期〉を含む技術操作の説明責任は変わらない）。

## 未決定事項

- **`R1`〜`R4` が実在の何人に割り当てられるかが未定。** 現状は実質 1 人がすべてのロールを兼務している可能性が高い。兼務の場合、`CAP-06` のダブルチェックと `CAP-14` の承認が同一人物の自己承認になるため、承認ゲートの実効性が落ちる。兼務時の代替手段（一定時間を空けてからの再確認、チェックリストの機械的検証など）は 05 の承認ゲート設計に依存するため、ここでは決めない。
- **エージェントを `R5` としてロール表に加えるかどうか。** 本ファイルは `R1`〜`R4` だけを定義し、RACI では**列**としてのみエージェントを扱っている。**人間のロールと同じ系統の ID をエージェントに与えると、RACI の Accountable（全 18 Capability で人間にある）がエージェントに付きうる形になる**ため、安易に足さない。足す必要が生じたときは、本ファイルで採番し、承認責任の所在を同時に決める。判断者 `R1`。
- **`E-15` `AgentRun` をどこまで RACI の証跡として使うか。** 「誰が実行したか」の記録としてエージェントの実行履歴を残す方針は妥当だが、格納先が未定だった（DA-01 で「エージェントの実行履歴」とだけ定義されていた）。**格納先は 2026-09-19 に AA-05 の ADR-18 で決まった**（監視アプリ〈ローカル〉の実行記録。1 回の起動を 1 件とし、相関 ID で `E-13`・`E-14`・本番への書き込みと結ぶ。記録は監視アプリのサーバー側だけが書く。TA-07 の 3.6）。残るのは、証跡として使える範囲である。**記録の単位は起動であって人間ではない**ため、手動の指示を出した人間（ロール）を記録に含めるかと、保持期間（DA-05 の 2 節。証跡として使うなら短くできない）を合わせて決める。**記録する範囲は同日の ADR-18 の追加の決定で決まった**（要約・対象の ID・相関 ID・成否・起動の種類だけ。ツールの結果は残さない。要約にも個人情報を書かない。DA-05 の 1.5）。指示を出した人間を記録する場合も、ロール（`R1`〜`R4`）か管理者の ID で指し、氏名やメールアドレスを書かない形になる（**本ファイルの判断**。人は ID で指す規則に合わせる）。判断者 `R1`。
