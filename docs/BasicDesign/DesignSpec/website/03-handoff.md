### 2.1 既定値の 2 つの性質（H-16 の補足）

**「依存している instance がある」だけでは、良い既定値と悪い既定値を区別できない。** 2026-10-01 の Figma では両方が混在していた。

| | セクション固有の既定値（**危険**） | 最も多く使う正しい値（**残してよい**） |
|---|---|---|
| 例 | `CTABanner.Title`「まずは、いまの課題をお聞かせください」 | `ServiceCard.Product 2`「受託開発：要件定義〜運用保守」 |
| 依存している instance | 0〜5 件 | 28 件 |
| その依存は正しいか | **たまたま正しい、または誤り** | **すべて正しい** |
| 新しく置いたとき | **必ず誤る**（別のセクションに別のセクションの見出しが出る） | **多くの場合正しい** |
| 判定 | `【要記入】…` にする | そのまま |

**判定の基準**: その文字列が、**その部品をその用途で置くすべての場所**で正しいなら既定値にしてよい。**1 つのセクションでだけ**正しいなら既定値にしてはいけない。

「すべての場所で正しいか」だけだと、メール欄のヘルパー文（`FormField.Helper`「ご連絡はこのメールアドレスにお送りします。」依存 29 件）まで危険側に落ちてしまう。これは**メール欄すべてで正しい**ので残す。

**2026-10-01 の実績**: TEXT 型の既定値 53 件のうち、**17 件を `【要記入】…` に変え、15 件は「最も多く使う正しい値」として判断して残した**（依存あり 11 ＋ 用途単位で正しい 4）。残りは元から中立な既定値。残した 15 件の一覧は `02-component-map.md` §7.4。

**分類は既定値の文面で決めず、instance の実値を突き合わせて決める。** `SourceDownloadBlock` の `Title` / `Body` は「この部品専用だからどこでも正しい」と判断して残す側に分類していたが、**実値を見るとページごとに文言が違っていた**（トップと Services / Pricing で別の文章）。**部品の用途が 1 つでも、文言が 1 つとは限らない。**

**この誤りを見つけたのは目視ではなく、単位スペースの検査だった。** 既定値の「23,000 **空き** 円」が引っかかったので実値を見にいき、分類の誤りと **4 件目の「消えた文言」**（既定値が Services / Pricing 版のさらに古い文章だった）が同時に判明した。**表記の機械的な検査が、人の分類の誤りを検出する**経路がある。

**既定値を一括で書き換えるコストは高い。** 1 件ごとに「明示値 → 既定値変更 → 直後に実測 → 必要なら入れ直し」の 4 段階が要り（§10 の「値が既定値と同一だと上書きが登録されたか確認できない」）、そのすべてで `applyMixed()` による和欧の当て直しが発生する。**危険なものだけを選んで直す**のが正しい。

### 3.1 `role/text-link` と `role/text-brand` の境目

| 使う色 | 対象 | 下線 |
|---|---|---|
| `role/text-link` #0579CE（4.53:1） | **押せる文字だけ** | **必須** |
| `role/text-brand` #045D9D（6.87:1） | リンクではない青の強調（トップのタグライン 5 件） | **付けない** |
| `role/text-link-hover` #045D9D | リンクのホバー | — |

`role/text-brand` と `role/text-link-hover` は**値が同じ #045D9D だが別トークン**。役割が違うものを 1 つのトークンで表すと、「リンクのホバーだけ濃くしたい」となったときにタグラインまで動く。

**トークンの値を変えたとき、一緒に動いたものが本当に同じ役割かを見る。** これは役割の対応が崩れていることを見つける検査になる。2026-10-01 に `role/surface-brand` を blue.500 → blue.600 にしたとき、**ボタンの地（面の用途）と一緒に、テキストリンクの矢印アイコンまで動いた**。矢印はリンクの一部として読まれる要素なので `role/text-link` が正しく、**値が同じだったために同じトークンを当てていた**ことが露出した（9 件を修正）。**肉眼では区別できない差でも、トークンを動かすと現れる。**

なお `role/surface-brand` に残した 46 件は正しい用途（**42 件がボタンの地**、**4 件が `SourceDownloadBlock` の見出しに付く単独の強調アイコン**）。**リンクの中の矢印だけが誤りだった。**

**検査に例外を作らず、色の意味を分けて検査を単純に保つ。** 「`role/text-link` なのに下線が無い TEXT」は**例外なしで 0 件でなければならない**。タグラインを除外条件に入れる案もあったが、`role/text-brand` に移せば除外しなくても引っかからなくなる（例外を書くと、その例外の妥当性を誰も再検証しなくなる）。

## 4. レイアウトの寸法

| 項目 | Desktop | Mobile |
|---|---|---|
| フレーム幅 | 1440px | 390px |
| コンテンツ幅 | 1152px（左右余白 144） | 358px（左右余白 16） |
| **ヘッダーの高さ** | **56px**（ロゴ**シンボル単体 35.79 × 32** ＋ 上下余白 12 × 2。8pt グリッドに乗る） | 同 |
| セクションの上下余白 | 96px（ヒーロー上は 128） | 64px |
| 記事本文の幅 | 720px | 358px |
| フォームの中身の最大幅 | 640px | 全幅 |

**ヘッダーのロゴはシンボル単体 35.79 × 32px。ほかの場所（フッターなど）は横組み 160px のまま。**

**シンボルは正方形ではない。** SVG マスターは 264.847 × 236.774 で**縦横比 1.1186 : 1**。ガイドライン §9.5 が指定しているのは**高さ 32px だけ**なので、**幅は比率どおりの 35.79px** にする。32×32 にすると §4.6-1（縦横比を変える）の違反になる。

**下端は 1px 罫線（`role/border`）。** ロゴの 12px 下にあり、X ＝ 8px のゾーン外なので §4.6-8 を満たす。**`strokesIncludedInLayout` を `false` にすること** — `true` だと罫線の 1px が高さに足されて 57px になり、8pt グリッドから外れる。

**シンボルの色はフルカラー版。** 白背景なので §4.5 のとおり。32px は単色ネイビーに切り替える 24px の下限を超えている。

ガイドライン §4.4 は「**画面での最小サイズの下限を割る場合は、その組みを使わずシンボル単体に切り替える**」と定めている。**ヘッダーはまさにその場面。** §9.5 の「ヘッダーのロゴは高さ 32px」は、**シンボル単体を前提にした寸法**として読む。

| | 横組み 160×49.16px | **シンボル 32×32px** |
|---|---|---|
| アイソレーション X | 49.16 × 0.336 ＝ **16.52px** | 32 × **0.25** ＝ **8px** |
| ヘッダー上下余白 12px で足りるか | **足りない**（4.52px 不足） | **足りる** |
| Mobile の左 16px で足りるか | **足りない**（0.52px 不足） | **足りる** |
| 下端の 1px 罫線 | **ゾーン内（§4.6-8 違反）** | **ゾーン外。罫線を残せる** |
| ヘッダーの高さ | 74.16px | **56px**（8pt グリッドに乗る） |

**横組みは「幅 160px 以上 ＋ 上下左右に 16.52px 以上」を要求するので、高さの限られた面には構造的に収まらない。** フッターは高さに余裕があるので横組みで問題ない。

**当初は横組み 160px を選んでいた（2026-10-01 に撤回。`design-system` が提案し lead が承認した判断）。** 「§9.5 の 32px と §4.4 の最小幅 160px が矛盾している」と読んだためだが、**矛盾ではなく §4.4 の「シンボルに切り替える」を読み落としていた**。誤りに気づけなかった原因は、**最小サイズだけを見てアイソレーションを計算しなかったこと**。判断者は lead。

**寸法の判断をするときは §4.3（アイソレーション）・§4.4（最小サイズと切り替え）・§4.5（背景別の選び方）をセットで確かめる。** 最小サイズだけを見ると、アイソレーションが入らない寸法を選んでしまう。

**ガイドラインへの指摘として立てていた「§9.5 の 32px は §4.4 の最小幅を割る」は撤回した。** ガイドラインは正しく、こちらの読み落としだった。**指摘を立てたまま GL を直すと、正しい規定を壊していた。**

**寸法の正本は `tokens.json` で、PDF 本文はこれと食い違っている箇所がある。** ガイドライン §10.3-5（JSON が正）により JSON 側が正。**PDF を見て作業すると誤った寸法を使う**（`01-content-spec.md` §11.6 の R-3・R-4）。2026-10-01 に全項目を突き合わせた結果が下の 3 件。

| 項目 | `tokens.json`（正） | PDF 本文（誤） |
|---|---|---|
| ロゴ最小サイズ・**画面**（縦組み / 横組み / シンボル） | **112 / 160 / 24px**、下限 **96 / 136 / 16** | 96 / 144 / 20、下限 80 / 120 / 14 |
| ロゴ最小サイズ・**印刷** | **20mm / 32mm / 8mm** | 18mm / 28mm / 6mm |
| 影のベース色 | **`rgba(10, 59, 122, …)`** | `rgba(0, 53, 119, …)` |

**シンボル 32px は `tokens.json` のシンボル最小 24px（絶対下限 16px）を満たす。**

**一致していたもの**: アイソレーション（高さに対する比。横組み 0.336・縦組み 0.165・**シンボル 0.25**）、タイプスケール（サイズ 9 段・行送り・字間・ウェイト）、8pt グリッド、角丸。

**`tokens.json` に対応項目が無いもの**（PDF でしか裏が取れない。JSON の最上位キーは `color` / `typography` / `space` / `radius` / `shadow` / `logo` の 6 つだけで、版面や画像の寸法は入っていない）: OGP 1200×630、SNS 1200×675、スライド 16:9、名刺 91×55mm、A4 版面、罫線 0.5pt。**これらを「`tokens.json` に裏がある」と書かないこと。**

## 10. Figma を機械で操作するときの落とし穴

同じ検査を再現するスクリプトが `qa-audit.js` にある（読み取り専用。先頭の `PAGE_ID` を書き換えて `use_figma` に貼る）。下の落とし穴は、このスクリプトを書く過程で実際に踏んだもの。

**この節の落とし穴は、ほぼ 2 つの形に収まる。守るのは次の 2 文。**

> 1. **検査・走査の結果を報告するときは、母数と「数え方の条件」を添える。** 何件中の何件か、どこを見てどこを見ていないか。**0 件は「本当に 0 件」と「網が届いていない」を区別できない。**
> 2. **一括置換をしたら、置換後に「逆向きの条件」で走査する。** 直したものを数えるのではなく、**直しすぎたもの**を探す。
> 3. **当たった 1 件ずつが本当に該当するかを、現物で確かめてから直す。** 語が一致しただけでは該当しない。

**3 つは別の失敗を塞いでいる。どれか 1 つでは足りない。**

| # | 失敗の形 | なぜほかで防げないか |
|---|---|---|
| 1 | **網が狭すぎて見落とした** | — |
| 2 | **網が広すぎて壊した** | **1 では防げない。** 母数は添えてあり、件数も正しかった（「136 か所を密着表記にした」は事実で、置換の 1 件 1 件も正しく見えた） |
| 3 | **網は正しいが、判定の基準が間違っている** | **1 でも 2 でも防げない。** 範囲も件数も正しく、当たった語も実在する。**間違っているのは「当たった ＝ 直すべき」という判定のほう** |

3 の実例: 部品ページで旧表記を語で検索したら **25 件当たって本物は 3 件**。**機械的に直せば 4 件を壊していた**（`role/focus-ring` は blue.500 を指し続けており、`role/text-accent-subtle` も現行）。

**規則 1 は「母数」だけでは足りない。** 2026-10-01 に**母数の食い違いが 4 回**起きた（ページ直下のノードをスキップ／kit 変数を 0 件と誤報／「20 か所」がバインド数とノード数の混同／同じ 14 Contact を 1,336 と 1,209 で数えた）。**いずれも数え方の定義を書かずに数字だけ並べたことが原因。** 添えるべきは次の 4 つ。

| 項目 | 例 |
|---|---|
| **起点の選び方** | ページ直下の全ノードか、`findAll` を持つものだけか |
| **単位** | ノード数か、バインド数か、塗りのセグメント数か、プロパティ数か |
| **`visible=false` を含むか** | 含めると数が増える |
| **何を母数の分母にしたか** | 全 TEXT か、中身のある TEXT か、TEXT プロパティか |

**数字より条件のほうが突き合わせに必要。** 条件が書いてあれば、数が違っても**なぜ違うかが説明できる**。条件が無いと、同じ対象を数えたのか別の対象を数えたのかが分からない。

2026-10-01 に 13 件の誤報告があり、**10 件は「網の外にあるものを『無い』と報告した」**（規則 1 で防げる）、**1 件は「網が広すぎて壊した」**（規則 1 では防げない。母数を添えた報告が正しく、置換もすべて正しそうに見えたため。規則 2 で防ぐ）、**2 件は「結論の根拠を確かめずに出した」**（表の行数をプロパティ数として報告／部品の用途の単一性から文言の単一性を推論）。

**規則で塞げないものもある。** 2026-10-01 には、**単位スペースの検査が既定値の分類の誤りを拾い**、**和欧間の点検が一括置換の壊れを拾った**。どちらも狙って見つけたものではない。**検査を増やすこと自体に、別の誤りを見つける効果がある。**

**走査は `setCurrentPageAsync` で。`page.loadAsync()` では中身が全部読めない。** これが最も重大な落とし穴で、**検査結果を静かに無意味にする**。

同じ `10 Top` を 3 通りで数えた実測値（2026-10-01）。

| 方法 | ノード | 文字 |
|---|---|---|
| `loadAsync()` ＋ `findAll(述語)` | — | リンク **0 件**（誤り） |
| `loadAsync()` ＋ `findAll(() => true)` | **421**（誤り） | **50**（誤り） |
| **`setCurrentPageAsync()` ＋ `findAll(() => true)`** | **2,467**（正） | **803**（正） |

**ノードで約 6 倍、文字で約 16 倍の取りこぼし。** さらに悪いことに、**同じコードでも実行ごとに結果が変わる**（19:03 の走査では正しい件数、19:17 では桁が落ちた）。一度正しい数が出ても、次の実行で静かに壊れる。

- **`use_figma` の呼び出しを対象ページごとに分け、各回の冒頭で `setCurrentPageAsync` を 1 回だけ呼ぶ。** `setCurrentPageAsync` は 1 回の呼び出しで 1 度しか呼べないため、7 ページなら 7 回に分けることになる。**1 回で全ページを回そうとすると、必然的に `loadAsync` に頼ることになり、この取りこぼしが起きる**
- 正しい母数の目安（2026-10-01 / builder の 7 ページ）: 10 Top 2,467 / 803、11 Services 1,360 / 382、12 Pricing 833 / 243、13 About 514 / 142、14 Contact 2,201 / 565、15 Blog 1,087 / 344、16 System 1,521 / 533。**計 9,983 ノード / 3,012 文字**（Mobile の文字 1,420）
- **母数が上の桁より小さければ、検査が成立していない。** 「0 件」は取りこぼしと区別できないので、母数のない報告は受け取らない

**色の検査は 3 本必要。それぞれ拾える対象が違う。**

| 検査 | 拾えるもの | 素通りするもの |
|---|---|---|
| **C1 パレット外の色** | ブランドのパレットに無い色 | パレット内の色なら、バインドされていてもいなくても通る |
| **C2 未バインドの塗り・線** | バインドされていない生の塗り（**非表示のものを含む**） | バインドされていれば、参照先がライブラリでも通る |
| **C3 ライブラリ（kit）の変数への参照** <br>`getVariableByIdAsync(id).remote === true` の件数で数える | kit の変数を指したままの塗り | **削除済みのローカル変数への参照**（`remote` が false なので） |
| **C4 削除済み変数へのぶら下がり** <br>**ローカル一覧（`getLocalVariablesAsync()`）にも無く、`remote` でもない変数への参照** | 削除したのに参照が残っている変数（**値が描画され続ける**） | — |

**C4 が無いと、削除した変数の色が画面に出続けているのに 4 本すべてを通り抜ける。** Figma は**削除済み変数を、参照が残っているかぎり `getVariableByIdAsync()` で名前も値も返し続ける**。2026-10-01 には、削除済みの `accent/*` の緑 #007A55 が **11 Services 8 か所・16 System 20 か所で実際に描画されていた**（スクリーンショットで確認）。C1 でだけ拾えた。

**パレットの定義も明示する。** 「**ローカル変数のうち COLOR 型の解決値の集合**」を正とし、**描画される実際の色と突き合わせる**（変数名ではなく解決値で比べる）。**件数は走査のたびに数える。** 変数は作業中に増える（2026-10-01 には 88 → 89 → 92 件と 2 回増えた）ので、**件数を検査スクリプトに書き写すと古くなる**。

**混植テキストの `node.fills` は `figma.mixed` になる。** `Array.isArray(node.fills)` で絞ると**弾かれて母数から落ちる**ので、**`getStyledTextSegments(['fills'])` を併用する**。`role/text-link` ＋ 下線のリンクはまさに和欧混植の形なので、**最も落ちやすい対象が最も重要な検査対象**になる（2026-10-01 に 15 Blog 344 件・16 System 605 件が該当）。**走査範囲を広げても直らない** — 落ちる理由が走査の届く範囲ではなく**型チェックの副作用**だから。

**色以外の `boundVariables` も検査する。** 2026-10-01 には、builder が置いた自作フレームの**余白・間隔・角丸が kit 変数のまま 517 件**残っていた（10 Top 307・11 Services 152・12 Pricing 58）。「自作フレームはブランドトークンにバインドし直す」を**色しかやっていなかった**。対象は `paddingLeft` / `paddingTop` / `itemSpacing` / `topLeftRadius` などの寸法系。**kit instance のルートと内側は許容**（§8）。値が 1:1 なら見た目は変わらないので、**高さの実測で差 0 を確かめる**。

**名前ではなく、所属・出自で判定する。** 2026-10-01 に**同じ形の失敗が 3 回**出た。

| # | 何を名前で判定したか | 出た誤り |
|---|---|---|
| 1 | 変数名が `shadcn` で始まるか | **`alpha/*` 系 62 件を落とした**（うち 10 件は透明度 0.0001 のほぼ透明な塗り） |
| 2 | 変数のコレクション名が `ComeGin` で始まるか | **削除済みの `accent/*` を自作扱い**にした（ローカル変数なので `remote` でも拾えない）。緑が 22 ノードで描画され続けた |
| 3 | instance の名前に `" - Nova"` が含まれるか | **改名すると自作扱い**になる。10 Top で 155 件、03 Components で 162 件を誤って「自作」と数えていた |

正しい判定は、変数なら **`getLocalVariablesAsync()` の ID 集合に在るか**、instance なら **`mainComponent.remote`**、文章中のトークン名なら **その名前の変数が現存するかを問い合わせる**。**名前は変わる。出自は変わらない。**

**とくに #4 が示すのは、トークンの差し替えが「全体一律ではなく役割ごと」だということ。** `role/surface-brand` は blue.500 → blue.600 に動いたが、`role/focus-ring` は blue.500 のまま（UI 部品の境界に必要な 3:1 を満たすため）。**「この色はもう使わない」という言い方が成立しない**ので、語で検索して一括で直してはいけない。

**変数名ではなく、所属するコレクションで判定する。** `getVariableCollectionByIdAsync(v.variableCollectionId).name` がブランドのコレクションでなければライブラリの変数、と数えるのが確実。名前で絞ると、命名規則から外れたもの（`alpha/*` など）を落とす。

**変数名で絞らない。** 2026-10-01 の移行では「名前が `shadcn` で始まる」で数えたため、**`alpha/*` 系の 62 件を落とした**。うち 10 件は**透明度 0.0001 のほぼ透明な塗り**（副ボタンの地）で、**透明度を移さずに付け替えると真っ白のベタになる**ところだった。付け替えるときは解決値の `a` を paint の `opacity` に移す。

**付け替えの対応表は 1 つに決めて共有する。** 同じ移行を複数人で行うと、同じ変数が別のトークンに寄せられる。2026-10-01 には `secondary foreground` を片方が `text-body`（#1A1A1A）、正本は `text-heading`（navy.700 #003577）としており、**見た目に出る差**になった。対応表は `02-component-map.md` §9.1。

**検査は「3 本を、母数を添えて、全ページに」。**

- **`node.findAll(...)` は子孫だけを返し、`node` 自身は入らない。** 必ず `[n, ...n.findAll(() => true)]` の形で自分自身を足す。2026-10-01 には**ヘッダーの罫線がルートに付いていたため「罫線 0 件」と出て、罫線が消えたと誤認しかけた**。
  **この取りこぼしは「無いものを有る」ではなく「有るものを無い」と読む向きに出る。** ほかの記録（網の外にあるものを「無い」と報告した）とは向きが逆で、**結論が反対に出る**ので気づきにくい。
  原因は規則を知らなかったことではなく、**同じスクリプトの中で書き方が揃っていなかったこと**（影の検査では自分自身を足していたのに、罫線の検査では足し忘れていた）。**「自分は知っている」では防げないので、スクリプト内で統一されているかを確かめる。**
- **`findAll(述語)` を現在のページ以外に使うと、instance の中の層を取りこぼす。** 同じページで `page.findAll(n => n.type === 'TEXT' && n.name === 'Link')` が **0 件**、`page.findAll(() => true).filter(...)` が **122 件**になった実例がある。**述語を渡さずに全件取ってから絞る**
- **検査結果には必ずノード数（母数）を添える。** 0 件が本当に 0 件なのか、走査が届いていないのかは、母数を見ないと区別できない。2026-10-01 には、この取り違えで「全ページで参照 0 件」という**根拠の弱い確認のまま `accent/*` を削除**していた。**この確認は成立しておらず、削除後も参照が 28 か所に残って緑が描画され続けていた**（上の C4）。削除は、参照 0 件を**母数つきで**確かめてから行う

**3 本とも 0 になって初めて移行完了。** 2026-10-01 のブランド適用では、部品ページを 0 件にしたあとも **builder のページに kit 変数が 930 件残っていた**（色 412・余白と角丸 518）。ヒーローの見出しが黒で描画される原因になった。

**検査結果を報告するときは、対象にしたページを必ず明示する。** 「色の移行が終わった」が「サイト全体で終わった」と読まれる事故が実際に起きた。

- kit のボタンのラベルは TEXT プロパティにできない（instance の中の層にプロパティを結べない）。中の TEXT を直接書き換える
- **`setProperties()` や `characters` で差し替えると和欧の当て分けが失われる。** 差し替えのたびに **JP の文字スタイルをノード全体に当て直し、Latin を正規表現で探して範囲適用する**（`applyMixed()`）。**既存の範囲をずらすのではなく、新しい文字列に対して範囲を計算し直す**形なので、文字数が変わっても整合する
- **和欧混植を「文字スタイル」で表す方法と「範囲の塗り」で表す方法は、守るべきものが違う。** 文字スタイルなら上の `applyMixed()` で足り、文字数が変わっても計算し直されるので `insertCharacters` は不要。**範囲の塗りを使っている場合は `insertCharacters` のほうが有利**（Figma が挿入位置より後ろの範囲を自動でずらすので、セグメント数が保たれる）。**どちらが正しいかではなく、何で表しているかで選ぶ**
- **同じものを 2 回数える定義がある。** instance の文言は **`componentProperties` の値**と**表示中の TEXT の `characters`** の両方に出るので、**足すと倍になる**（2026-10-01 に「18 行」が実体 9 か所だった）。**報告するときは定義を明記し、0 でないときは足さない**
- **注記は `label` と `labelMarkdown` の両方を見る。** `labelMarkdown` 側はアンダースコアが `\_` にエスケープされて保存される
- **非表示レイヤーは instance に展開されない。** 走査に出なくても値は `componentProperties` に残っている
- **部品を直しても、instance 側に同じプロパティの上書きが残っていると伝わらない。** 2026-10-01 に `IconCard` の下線を部品で直したが、instance には `textDecoration` の上書きが残っていて反映されなかった（塗りや変数バインドは、上書きが無ければ素直に伝わる）。**部品を直したら、instance 側に反映されたかを実測で確かめる。** `resetOverrides()` で外せるが、**意図した文言の上書きも一緒に消える**ので、variant を控えてから使う。

- **見えない場所に古い文言が残る。** 文言を一括で差し替えるときは、次の 4 か所を必ず含める。どれも画面に出ないので検査を通るが、**状態やプロパティを切り替えた瞬間に出る**
  1. **閉じた Accordion の回答**（非表示なので `findAll()` に出ない。State を一時的に Open にして直す）
  2. **`Show xxx=false` で隠れているプロパティの値**（2026-10-01 の差し替えでは 23 instance 分に旧文言が残っていた）
  3. **variant で隠れている行**（`Price rows=1` のときの 2 行目など）
  4. **部品の `componentPropertyDefinitions` の既定値** — **ノードを辿る走査では原理的に到達できない**（instance を 1 つも置かなくても存在する）。2026-10-01 には、21 instance で直したはずの**禁止語「弊社」が `ServiceCard.Note` の既定値に 1 件生き残っていた**。両 builder の「禁止表現 0 件」は嘘ではなく、**検査の対象が「描画されている TEXT」だった**ためにここだけ見ていなかった。**禁止語・単位のスペース・旧 `cta_type`・プレースホルダ文言の検査は、既定値にも当てる**
- kit の Badge の中のテキストも `Label` という名前。名前で探すと質問文をバッジに書き込んでしまう
- **正規表現での一括置換は、置換後の文字列を読み返して確かめる。** 2026-10-01 の「弊社」→「ComeGin」の置換では、**和欧間の半角スペースが落ちて「基本的にComeGin が負担」になった**（21 instance）。その修正で今度は**読点の直後にスペースが入った**（5 instance）。和文と半角英数字が混ざる文では、置換の前後で**両隣の文字**が何になるかを確かめる
- **レイヤー名に文言を埋め込む命名規約は、文言を直すたびに必ず腐る。** 2026-10-01 に、文言は「ソースコードを無料 DL」に直したのに `CTA 副 / ソースコードを無料DL` のようなレイヤー名が **24 件**（builder のページ）＋ **3 件**（部品ページ）旧表記のまま残っていた。**レイヤー名は Dev Mode で実装者が見る情報**なので、文言と食い違うと「どちらが正か」の判断が発生する。**instance のサブレイヤーの名前も変更できる。**

  **効く条件は 2 段構え**: ①**「レイヤー名がコピーらしい（日本語を含む、または 20 文字超）のに本文と一致しない」** ②**空白・改行の畳み込みだけの差を除く**（Figma の自動命名は連続スペースを 1 つに、改行を半角スペースに畳む）。これで `03 Components` は 24 件に絞られ、うち本物 2 件。
- **dev annotation（注記）は画面に出ないので、仕様の変更に追随しているか誰も確かめない。** 2026-10-01 の `cta_type` の改名では、**87 件すべてが旧値のまま**だった。注記は実装する人が読む情報なので、仕様を変えたら注記も走査して直す
- **複製したフレーム「自体」に `findAllWithCriteria` を掛けると 0 件を返す。** ただし**直接の子を添字（`clonedRow.children[c]`）で取り、その中で探せば取れる**ので、**同じ実行の中で複製して書き換えることはできる**（2026-10-01 に両方の書き方を実測して確認）。`createInstance()` でも解決するが、**複製には variant（表の縞の Odd / Even など）を引き継げる利点がある**ので一択ではない
- **表のセルは放っておくと折り返さない。** 新しく作ったセルの文字は `WIDTH_AND_HEIGHT` のままで、長文が列をはみ出す。**instance の中のテキストでも `layoutSizingHorizontal='FILL'` と `textAutoResize='HEIGHT'` は設定できる**（`resize()` は無視されるが、この 2 つは通る）
- **行の高さは `layoutSizingVertical` で決まる。** セルを FILL にすると行が伸びない。**セル＝HUG / 見出しセル＝FILL** にすると行が文字の高さに追従する
- **エラーが出ると、同じ `use_figma` の変更はすべてロールバックされる。** 大きい書き込みは分ける
- **`setProperties()` の直後は、先に `findAllWithCriteria()` で取った instance の参照が無効になることがある**（`The node with id "…" does not exist` で全ロールバックされる）。対象のノード ID を先に配列で確定させ、1 件ずつ `getNodeByIdAsync()` で取り直してから書き換える
- **要素を「消す」手段が無いとき、空文字や半角スペースで回避しない。** 空文字でも**行の高さが残る**ので、数 px〜十数 px のずれになる（2026-10-01 には、手順の 5 段目だけ半角スペースが残っていて **13px のずれ**が出た）。**部品側に「見せない」BOOLEAN を足す**のが正しい対処。追加するときは**既定値を現状と同じ**にして、既存の instance に影響を出さない
- **文字を直す操作は 3 つあり、範囲スタイル（和欧混植・範囲の塗り）への影響が違う。**

  | 操作 | 範囲スタイル | 使いどころ |
  |---|---|---|
  | **`insertCharacters(pos, 文字, 'BEFORE')`**（純粋な挿入） | **保たれる。** Figma が挿入位置より後ろの範囲を自動でずらす（2026-10-01 に 38 か所と 10 か所で**セグメント数が元のまま**） | スペース 1 文字を足すなど |
  | **`deleteCharacters` ＋ `insertCharacters`**（1 文字差し替え） | 保たれる（17→17 / 8→8 / 3→3 で確認）。**ただし `'BEFORE'` は直前の文字の書式を継ぐ** | `blue.500` → `blue.600` のような 1 文字の訂正 |
  | **`characters` への代入** | **範囲スタイルを全部捨てる**。`applyMixed()` で当て直しが必要 | 文章をまるごと差し替えるとき |

  **⚠ 未検証の注意点**: `'BEFORE'` は直前の文字の書式を継ぐため、**セグメントの先頭文字を差し替えると前のセグメントの書式を拾うはず**（「は2行」の `2` のような位置）。その場合は `'AFTER'` が要る。**API の定義から考えた推測で、実測していない。**

  **コンポーネントプロパティにバインドされたテキストには挿入系が使えない。** 直接編集できず `setProperties()` 経由になるため、**Latin の範囲が文字数のぶんずれる**（「ソースコードを無料DL」→「ソースコードを無料 DL」で Latin 範囲が 9-11 → 10-12 に動く）。この場合は**JP のスタイルをノード全体に当て直してから Latin 範囲を再適用する**。
- **`characters` を書き換えると、範囲指定の塗り（`setRangeFills`）が下地の塗りに戻る。** 2026-10-01 に特商法の表のセルで実際に起きた。①範囲ごとに色を当てる → ②そのあと別の修正で `characters` を書き換える → ③**範囲の指定が消え、下地に残っていた kit の `foreground` が復活**。**範囲で色を当てる前に、下地（`node.fills`）もブランドトークンにしておく。** `characters` の書き換えだけでなく、**`editComponentProperty` で既定値を変えたときも範囲指定は落ちる**（2026-10-01 に `IconCard / Link` の下線 2 件がこれで消えた）。**一括で文言を直す前に、対象が範囲指定を持つか `getStyledTextSegments([...]).length > 1` で確かめる。** なお**範囲の塗り自体を避けてはいけない** — 「文の途中にリンクが 1 語ある」（法務・完了画面・Cookie 同意バナー）は範囲の塗りでしか表せず、文を分割すると折り返しが語の途中で固定される。 この復活は `node.boundVariables.fills` 経由なので、**検査では「色」ではなく「寸法」に分類されて出ることがあり**、気づきにくい
- **`setProperties()` で文言を差し替えたあと、テキストの「格納高さ」が再計測されずに残る。** 2026-10-01 に 27 件（10 Top）。**描画は 2 行なのに格納高さは 1 行分（32px）**という状態で、フレームの高さが 819 → 787px と 32px ずれていた。**色・書体・コピーの検査はすべて通り、出るのはレイアウトの高さだけ**。**このずれは目視・スクリーンショット・インクの境界（`absoluteRenderBounds`）のいずれでも検出できない** — Figma が描画時に再フローするので**画面は正しく、格納された箱だけが古い**。2026-10-01 には `absoluteRenderBounds.height` との比較で 1,577 件走査して 0 件（＝見落とし）、作成時のスクリーンショットでも正しく 3 行で描画されていた。**見つける方法は「`textAutoResize` を `NONE` → `HEIGHT` に往復させて再計測を強制し、高さが変わるか」だけ。** 対象を見積もりで絞ると字間（`Caption` は +4%）の分だけ行数を読み違えて取りこぼすので、**`textAutoResize='HEIGHT'` の全件にかける**。文言を差し替えたら必ず走らせ、フレームの高さを前後で実測する（レシピは `02-component-map.md` §8）
- **空文字で `figma.createText()` したテキストに後から `characters` を入れると、幅 0 のまま折り返して高さが爆発する**（1 文字ずつ改行され、カードが 4579px になった）。`layoutSizingHorizontal = 'FILL'` を当て直しても直らず、`FIXED` にして `resize()` で幅を与えてから `textAutoResize = 'HEIGHT'` → `FILL` の順で復旧する。**空のテキストを先に作って後から流し込む書き方は避ける**
- **効果（影）の色に変数をバインドすると、効果側の不透明度が変数の不透明度（1.0）で上書きされる。** 2026-10-01 に判明し、**`shadow/sm` / `md` / `lg` の 3 つとも作成時からずっと不透明なネイビーだった**（16 ノードと `02 Foundations` の見本すべてに出ていた）。**不透明度を含んだ色の変数**（`rgba(10,59,122,.08/.10/.12)`）を作ってバインドする。作成時に値を `return` で確認し見本も置いていたが、**不透明度だけは数値でも見た目でも確かめていなかった**（「濃いめだが、そういうものか」と見過ごした）。**何を測るかを決めた時点で、測らないものが決まる**
- **罫線は `strokesIncludedInLayout: true` だと高さに含まれる。** 外すとフレームが 1px 縮む。高さを保つなら `counterAxisSizingMode` を `FIXED` にする
- **`paint.color` のリテラルについて、事実は 2 つ。混ぜない。**
  1. **変数の値を差し替えると、Figma はバインド済み塗りのリテラルも instance の override 側まで更新する。** 2026-10-01 に `role/surface-brand` を blue.500 → blue.600 にしたあと、**2 人が独立に測って 4,710 件 / 1,209 件とも食い違い 0 件**。**差し替え後の検査はリテラルで測っても正しい。**
  2. **こちらが `setBoundVariableForPaint` に渡したリテラルが変数とずれている場合、Figma はそれを直さない。** ヘッダーが黒く出た 35 件がこれ（バインドはあるのにリテラル側へ黒を書いていた）。
  
  **この 2 つを 1 文にすると**: **Figma がリテラルを更新するのは「変数の値が変わったとき」だけで、「バインド時に渡された値が変数と違うとき」ではない。書く側のミスは検出も修正もされない。**
  したがって **「リテラルは古い値を保持し続ける」という一般化は誤り**。差し替えでは起きない。
  **それでも検査で変数名まで遡る理由は、「リテラルが古いから」ではなく「リテラルが正しい保証がこちら側にないから」。** リテラルは**書く側が自由に間違えられる値**なので、解決値と一致していても**仕様どおりである根拠にはならない**。**コントラストを測るならリテラルで足りる。仕様どおりかを確かめるなら変数名を見る。**
- **`figma.createText()` で作った TEXT は、塗りを明示しない限り未バインドの黒（#000000）になる。** 手で作るときと初期状態が違う。作るたびに `foreground` などの変数をバインドする（この漏れが 83 件出た）
- `03 Components` の部品は publish していないので `importComponentByKeyAsync` は失敗する。`getNodeByIdAsync` で取る
- instance の中の層は `resize()` が黙って無視される。大きさを変えたいときは部品側に枠と BOOLEAN を足す
- 折り返しの auto-layout では `counterAxisAlignItems = 'STRETCH'` が使えない。高さ揃えは子の `layoutSizingVertical = 'FILL'` で行う
- **部品の既定値に「特定のセクションでだけ正しい完成した文」を入れない。** 2026-10-01 に同じ形が **3 回**出た（`SectionHeading.Lead` → `CTABanner.Body` → `SectionHeading.Title` / `CTABanner.Title`）。判定の基準は **「その文字列が、その部品を置くすべての場所で正しいか」**。すべてで正しいなら既定値にしてよい（`© 2026 ComeGin`、フォームの「メールアドレス」、`画像（準備中）`）。1 つのセクションでだけ正しいなら既定値にしてはいけない
  - **差し替え忘れが日本語として成立するので、目視でも検査でも通る。** 既定値は `【要記入】見出し` のように**それ自体が異常だと分かる印**にする（既存の検査の印に乗せる）
  - **部品の既定値は仕様書の管理外なので、コピーを書き直しても追随しない。** `CTABanner` の `Body` と `Title` は 2 つとも**仕様書から消えた旧コピー**のまま残っていた（全文検索で 0 件の文言が、部品の既定値にだけ生き残っていた）
  - **既定値を変えるときは、既定値に依存している instance を先に明示値に置き換える。** 順序が逆だと正しい値が `【要記入】` に化ける。`SectionHeading.Title` では 5 件が**たまたま既定値と同一文字列で、しかもそれが正しい値**という状態だった
  - **instance のプロパティ上書きは、値が既定値と同一文字列だと「登録されたか」を確認できない。** `componentProperties` を読んでも値が同じなので区別できず、`overrides` には component プロパティの上書きが出ない。**確認できるのは既定値を変えた直後だけ**（化ければ登録されていなかった）。既定値と同じ値を明示的に持たせたいときは、**既定値を変える作業と組にして、変更直後に実測する**。「出た結果を測る」が原理的に測れないケースで、**測れる瞬間を作ってから測る**のが対処
  - 突き合わせは**完全一致で行う**。`SectionHeading.Lead` には既定値と**頭から 30 字が同一**で、差が助数詞の密着（「5 つ」→「5つ」）と文の分割だけ、という instance があった。前方一致や目視では「未差し替え」と誤判定し、**正しく直した側を壊す**

### 10.1 2026-10-08 の改訂で踏んだもの

- **和欧混植のテキストに `characters` を代入すると、全体が先頭のセグメントの文字スタイルに潰れる。** 代入した後に `setRangeTextStyleIdAsync` で欧文（`Latin/*`）と和文（`JP/*`）の範囲を当て直す。`getStyledTextSegments(['fontName'])` でフォントが Poppins／Noto Sans JP／JetBrains Mono だけかを確かめる
- **TEXT プロパティ（`setProperties`）で入れた値は、部品の範囲ごとの文字スタイルを受け継がず、値の先頭の文字のスタイルに揃う。** 「7日」「31,250円／回」「ComeGin は…」のように数字や欧文で始まる値は和文まで Poppins になる（17 件＋α を直した）。**部品を直しても instance 側は直らない**ので、プロパティで文字を入れたら必ず当て直す
- **状態フレーム（Cookie バナー表示中・Mobile メニュー表示中）は、ページ全体の複製を内側に持つ（instance ではない）。** 本体だけ直すと複製に旧文言が残る。修正を「ルートを受け取る関数」にして、本体と複製に同じ呼び出しで当て、変えたノード数が一致することを毎回確かめた
- **DROP_SHADOW の spread は、clipsContent のあるフレームか矩形・楕円にしか効かない。** 2026-10-01 に足した Focus 10 variant のフォーカスリングは 1 件も描画されていなかった（エフェクトは付いていたので、プロパティを読むだけでは気づけない）。**描画を撮って確かめる**
- **`clone()` で複製した variant は、TEXT・BOOLEAN のプロパティ参照が外れる。** Label を変えても表示が変わらない。複製したら参照を付け直す
- **`Steps` の段数を切り替えると、隠れていた段の既定値（旧工程の文）が画面に出ない本文として残る。** 見た目の確認では見つからず、非表示まで走査する検査で見つかった。段数の variant の既定値も H-16 の印にする
- **`qa-audit.js` は約 7.5 万字あり `use_figma` の上限 5 万字を超える。** 縮小版（約 4.2 万字）を貼る。`\uXXXX` は送信経路で生の文字に戻されて構文エラーになるので、本体では使わない
