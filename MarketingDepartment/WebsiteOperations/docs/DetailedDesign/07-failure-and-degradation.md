# DD-07 異常系と縮退運転

詳細設計層。ID の採番の正本は層ごとのファイルにあり、索引は [`docs/README.md` の「ID の採番と正本」](../README.md) にある。横断規約は [DD-01](01-flow-specification-rules.md) を参照する。

02 から 06 が各フローの失敗を個別に扱ったのに対し、この文書は**複数のフローに跨る異常**を扱う。

| この文書が扱うもの | なぜ個別のフローに書けないか |
|---|---|
| 公開経路の断（本番は ALB とその後ろ。旧版は ngrok のトンネル断） | **3 本（`I-05` `I-07` `I-08`）が同時に落ちる。** 1 本ずつ見ても原因に到達しない |
| 沈黙（そもそも動かなかった） | **どのフローにも失敗ログが出ない。** 各フローの観測点では検出できない |
| `E-13` を経由しない変更 | 変更そのものは正常に成功する。**正常な操作の中から異常を見つける**問題 |
| 二重送信 | `I-08` と `I-11` と集計の 3 か所に跨る |
| 縮退運転 | 「何が落ちたら何を止めるか」は連携を跨いだ判断 |

## 1. 異常系の 3 分類

| 分類 | 定義 | 気づきやすさ | 主な検出手段 |
|---|---|---|---|
| **失敗** | 呼んだが失敗した | **気づける**（`fetch.outcome` に残る） | DD-01 の 4 節 |
| **沈黙** | そもそも呼ばれなかった | **気づけない** | 3 節（実行そのものの記録） |
| **偽装成功** | 成功したが、値が事実と違う | **最も気づけない** | 2 節（公開経路の断）・5 節（二重送信） |

**下ほど危険である。** 失敗は次のサイクルで再試行すればよいが、偽装成功は**誤った `E-12` が `evidence` になり、存在しない改善に対する提案が生まれる**（AA-04 の暴走条件 #3 と #10）。

**GSC の OAuth の失効も同じ種類の沈黙である**（2026-09-18 に追加）。OpenSEO は動き続け、Lighthouse も PostHog も正常なまま、**GSC の取得だけが `not_connected` を返して止まる**。同意画面を「内部」にした（TA-04 の 8.3）ため 7 日ごとの失効は起きないが、接続した Workspace アカウントの無効化や同意の取り消しで起きる。`fetch.outcome` には `auth_failed` が残るため、日次の `E-12` を見れば気づけるが、**見る人がいなければ SEO の測定だけが黙って止まる**。検出は TA-05 の項目 10。

**沈黙の最も新しい例が `I-21` の購読解除にあたる**（[04 の 8.4](04-server-to-server-flows.md)）。SNS の通知メールに付く解除リンクを誰かが踏むと、**通知が止まったこと自体が誰にも見えない**。検出は「`Confirmed` の購読数を監視する」しかなく、**その監視の結果を通知経路で知らせられない**という循環が残っている（TA-05 の未決定事項）。

## 2. 公開経路の断（暴走条件 #10）

**2026-09-18 に前提が変わった**（AA-05 の ADR-12）。旧版は「オンプレの Umami・Chatwoot・Mautic へ ngrok の常設トンネルで到達する」前提で、**トンネル断**をこの節の対象にしていた。本番ではこの 3 システムを AWS に置き、入口は ALB になった。**同じ形の欠測は、ALB とその後ろ（ECS のタスク・RDS）の障害で起きる。** ADR-12 の時点で ngrok に残ったのは n8n への Webhook だけだった。**同日（2026-09-19）の ADR-16 で n8n も AWS に移り、本番は ngrok を使わなくなった。** Webhook の欠落は、本番では n8n のタスクの停止として 2.5 で扱う。

### 2.1 何が起きるか

ALB、または Umami・Chatwoot・Mautic の ECS サービスや RDS が落ちると、**公開サイトのブラウザから 3 システムに到達できなくなる**（ALB は 1 台に集約しているため、ALB が落ちると 3 本が同時に止まる。TA-06 の 5.1）。

| 連携 | 公開経路の断の影響 | 見え方 |
|---|---|---|
| `I-05` Umami | 止まる | **セッション数が 0 になる** |
| `I-07` Chatwoot | 止まる | ウィジェットが表示されない |
| `I-08` Mautic | 止まる | **CV が 0 になる**（利用者には送信失敗が表示される） |
| **`I-06` PostHog** | **止まらない**（SaaS 直接） | 通常どおり記録される |
| `I-09` | **止まる**（本番の Strapi を ALB 越しに読む。ADR-16。ADR-15 の時点ではオンプレの Strapi を同一ホスト内で読んだため止まらなかった） | **ビルドが失敗する**（[05 の 1.2](05-build-and-delivery-flows.md)）。公開中のサイトは影響を受けず、止まるのは更新 |
| `I-10` | 止まらない（同一ホスト内）。ただし `pnpm lh` はビルドを含むため、`I-09` を配線した後は `I-09` と一緒に止まる | 通常どおり（`I-09` の配線後はビルドの失敗として現れる） |

**サイトは壊れない。データだけが欠ける。** これが最も危険な形の失敗にあたる。

### 2.2 検出

**`agent/ops-watcher` が公開経路の死活を監視対象に含める**（AA-02 の 1.4）。本番では 3 つの変数が ALB のホスト名を指す（DD-02 の 1.1）。

| 検査 | 方法 | 頻度 |
|---|---|---|
| **直接の疎通確認** | `PUBLIC_UMAMI_BASE` / `PUBLIC_CHATWOOT_BASE` / `PUBLIC_MAUTIC_BASE` の 3 つに HTTP で到達できるか | 日次バッチの**冒頭**、および `pnpm lh` の実行時 |
| **間接の徴候** | **Umami のセッション数が 0 かつ PostHog のイベントが非 0** | 日次バッチの観測後 |

**2 つ目が重要である。** 疎通確認は「いま」の状態しか分からない。**落ちていた期間を後から特定するには、Umami と PostHog の乖離を見るしかない**（AA-04 の暴走条件 #10)。

### 2.3 記録

**すべての `E-12` に `tunnel_up` を書く。**

```yaml
tunnel_up: true    # 観測時に公開経路（本番は ALB とその後ろ）が生きていたか
```

- **本番では、`tunnel_up` は「公開経路（ALB とその後ろの 3 システム）に到達できたか」を表す。** 名前は旧版（ngrok のトンネル）のまま残した。名前を変えるかどうかは 8 節に上げる。
- **公開経路を通らない観測（Lighthouse・GSC・PostHog）にも書く。** 値は常に `true` になるが、**書かないと「確認していない」と「生きていた」が区別できない**。
- **`tunnel_up: false` の `E-12` は `evidence` に使わない。** [06 の 1.2](06-proposal-loop-flows.md) の検査 2 に、この条件を含める。

### 2.4 落ちていた期間の `E-12` をどう扱うか

**AA-02 と AA-04 が未決定として残した項目**（欠測として明示的に記録するのか、その日の観測自体を作らないのか）。**この層で決める。**

| 案 | 内容 | 欠点 |
|---|---|---|
| A 観測を作らない | 公開経路が落ちていたら `E-12` を書かない | **「観測が無い日」と「バッチが動かなかった日」が区別できない**（沈黙に化ける。3 節） |
| **B `tunnel_up: false` として記録する** | 値は記録するが `evidence` に使えない印を付ける | ファイル数が増える |

**B を採る。** 理由は、**A は沈黙（最も気づけない異常）を生むため**である。

- 記録することで、「この期間は計測できていなかった」という事実自体が観測になる。
- `fetch.outcome` は `unreachable` になり、`tunnel_up: false` が併記される。**2 つの項目が同じことを言うが、`outcome` は個別の取得の結果、`tunnel_up` は環境の状態を表す**（Lighthouse は `outcome: ok` かつ `tunnel_up: false` になりうる）。

### 2.5 本番の n8n の停止（ADR-16 の前は ngrok のトンネル断）

**経緯。** ADR-12 の時点では、本番で ngrok を通るのは AWS の Mautic・Chatwoot からオンプレの n8n へ届く Webhook（`I-11` `I-12`。TA-01 の経路 5）だけで、この節はその**トンネル断**を扱っていた。**ADR-16 で n8n も AWS に置き、Webhook は VPC の中で完結するようになった**（[04 の 1 節](04-server-to-server-flows.md)）。本番のトンネル断は起きなくなり、ngrok に残るのは Astro dev サーバーの共有（開発環境）だけである。**トンネル断は開発環境の話になり、本番の Webhook には影響しない。**

**本番で同じ形の欠落を生むのは、n8n のタスクの停止である。** n8n は 1 タスクに固定している（TA-06 の 3.1）ため、タスクの入れ替え（デプロイ・障害からの起動し直し）の間は Webhook の受け口が無い。訪問者から見える機能と計測は止まらないが、次が欠ける。

| 欠けるもの | 見え方 |
|---|---|
| `I-11` `I-12` の受領 | n8n の実行履歴が増えない。Mautic・Chatwoot の側に送信の失敗が残るだけ |
| `I-21`（顧客からの要求の通知） | **通知が届かない。** Mautic・Chatwoot には記録されているため、顧客対応そのものは失われない |
| 日次バッチの入力のうち Webhook 由来のもの | 3 節の「部分的な沈黙」と同じ形で現れる |

- **偽装成功ではなく沈黙に分類する**（1 節）。指標の値を歪めるのではなく、処理が走らない。
- **検出は ECS のサービスの状態（稼働中のタスク数）を CloudWatch のアラームで見る**（TA-06 の 4.6。止まったことは SNS で知らせる）。ADR-16 の前はトンネルの疎通確認（`PUBLIC_N8N_WEBHOOK_BASE` に到達できるか）で検出する設計だった。**n8n が止まると通知（`I-21`）の送り手も止まるため、この検出は n8n の外（CloudWatch）で行う必要がある**（TA-05 の「監視対象が通知経路を兼ねてはならない」と同じ理由）。
- **ADR-16 の前より起きにくい。** 開発機の起動状態・回線・ngrok の 3 つに依存していたのが、ECS のタスク 1 つに縮んだ。ただし Mautic・Chatwoot が送信に失敗した Webhook を再送するかは確認していない点は変わらない（[04 の 11 節](04-server-to-server-flows.md)）。

## 3. 沈黙の検出

### 3.1 何が問題か

**日次バッチが動かなかった場合、成果物も失敗ログも生まれない。** どの連携の観測点を見ても何も起きていないため、**気づく手段が無い**（DD-01 の 9.2）。

エージェントが 1 本も走らなければ、`E-12` は 0 件、`E-13` も 0 件になる。**これは「改善すべきことが何も無かった」という正常な状態と見分けがつかない。**

### 3.2 検出

**日次バッチの完了そのものを記録する。**

| 記録するもの | 置き場 | 内容 |
|---|---|---|
| バッチの実行 | `docs/audits/ops/<audit_id>.md` | 実行した日時、走ったエージェントの一覧、それぞれの `fetch.outcome`、`tunnel_up` |
| 起票を止めた事実 | 同上 | [06 の 1.2](06-proposal-loop-flows.md) の検査で止めた場合、**どの検査で止めたか** |

**`agent/ops-watcher` が「今日のバッチの記録が無い」ことを検出する。** 自分自身が走らなければ検出できないという循環があるが、**この循環はこの層では解けない**（外部のスケジューラが必要で、それが `E-15` の正本の問題と同じ根を持つ）。

**ADR-17 で、循環の一部が解けた。** 日次バッチを起動するのはエージェントではなく監視アプリの定期実行になり（TA-07 の 3.5）、監視アプリは起動した事実・見送った事実（前回が終わっていない場合）を 1 回の実行として記録する（TA-07 の 3.3）。**監視アプリはエージェントの外にあるスケジューラであり、ここで求めていた「外部のスケジューラ」にあたる。**

**（2026-09-19）ADR-18 で、その実行記録が `E-15 AgentRun` の正本に決まった**（TA-07 の 3.6）。書くのは監視アプリのサーバー側だけで、エージェントには書かせない。**「実行そのものを記録する仕組み」と「外部のスケジューラ」が同じ監視アプリの中にそろい、沈黙の検出に `E-15` を使えるようになった。**

- **下の表の食い違いを見るのは監視アプリのサーバー側にする**（この層の判断）。`E-15`（起動した）と成果物（`docs/audits/<source>/` の当日のファイル）の有無を比べるだけの決定論的な照合であり、エージェントに `E-15` を読ませる口を作らずに済む（[06 の 2.4](06-proposal-loop-flows.md) の「決定論的な処理をエージェントに任せない」と同じ考え方）。`agent/ops-watcher` の `docs/audits/ops/` の記録は、観測（`E-12`）として残す。
- **`E-15` の `outcome` のうち、監視アプリが自分で確かめられるのは起動・終了・見送り・成果物の有無までである。** 検査で止めた理由などはエージェントの報告に依る（[06 の 1.2](06-proposal-loop-flows.md)）。

| 状況 | 検出できるか | 手段 |
|---|---|---|
| 監視アプリが起動したが、エージェントが成果物を残さなかった | **できる** | **`E-15`**（監視アプリの実行記録。起動した）と成果物・`docs/audits/ops/` の記録（無い）の食い違い |
| 監視アプリが前回の実行の継続中で、今回の起動を見送った | **できる** | **`E-15`**（監視アプリの実行記録。見送った事実） |
| **監視アプリ自身、または開発機が止まっていた**（電源断・スリープ・監視アプリのプロセスの停止） | **監視アプリの中からはできない** | **ハートビート**（8 節の未決定。送り手を監視アプリにすれば直接に分かる。今の送り手の開発環境の n8n では、監視アプリだけが止まった場合に分からない）。**復旧後は、`E-15` に記録の無い期間として後から読める**（止まっていた間は起動も見送りも記録されないため） |
| **開発機を失った**（ディスク障害など） | **最後に写した時点までは S3 の写しでできる**（ADR-18 の追加の決定 5）。それ以後の分はできない | **`E-15` の正本はローカルにしか無い**（ADR-18 の帰結）。ADR-18 の反映の時点では開発機の外に写すかが未決定で、過去の沈黙を後から確かめる根拠がすべて失われるとしていた。**追加の決定 5 で S3 に写すことになり、写しから過去の起動・見送りの記録を読める**（6.2）。写す頻度は未決定（TA-07 の 9 節） |

- **3 行目が残る穴である。** 開発機が止まると定期実行も止まる（ADR-17 の帰結）。ADR-17 はこれを「改善ループが止まっている」ことをハートビートで知る形にした（TA-07 の 8 節）。
- **見送り・失敗を監視アプリの画面に出すだけでは、見る人がいなければ沈黙と同じになる。** 監視アプリの記録を誰にどう知らせるかは 8 節に上げる。

### 3.3 部分的な沈黙

観測系 4 本のうち 1 本だけが走らなかった場合は検出できる（`docs/audits/<source>/` に当日のファイルが無い）。

| 状況 | 検出 | 対処 |
|---|---|---|
| 4 本のうち 1〜3 本が沈黙 | `docs/audits/<source>/` の当日分の有無 | 沈黙した `source` の `evidence` を使わない。**他の source での起票は続ける** |
| 4 本すべてが沈黙 | `docs/audits/ops/` に記録が無い | **`agent/ops-watcher` 自身も沈黙している可能性がある**（3.2 の循環）。**ADR-17 の後は、監視アプリの実行記録（ADR-18 で `E-15` の正本）で「起動されなかった」のか「起動されたが走らなかった」のかを区別する**（3.2 の表） |
| `agent/proposal-writer` だけが沈黙 | 観測はあるのに `E-13` が 0 件 | 検査で止まったのか走らなかったのかを、`docs/audits/ops/` の記録で区別する。**ADR-18 の後は `E-15` の `outcome`（`skipped` と理由。[06 の 1.2](06-proposal-loop-flows.md)）でも区別できる** |

### 3.4 定期実行が止まっていた間の取り戻し（ADR-17）

**開発機が止まっていた間、監視アプリの定期実行は 1 回も起動しない**（ADR-17 の帰結）。TA-07 の 3.5 は「止まっていた間の分を取り戻すかは、処理ごとに決める」とした。この層で処理ごとに振り分ける（**この層の判断**）。

| 定期処理 | 取り戻せるか | 再開後の扱い |
|---|---|---|
| 観測の日次バッチ（Umami・Mautic・GSC） | **取り戻せる**（期間を指定して過去を読める。GSC は 16 か月以内） | 欠けた日ごとに、**その日を基準日にした固定の範囲で**取り直す。`measured_at` は取り直した時刻、`range` は欠けた日の範囲になる（DD-01 の 4.3。2 つを混同しない）。**エージェントに範囲を判断させない**（定期実行の定義の側で基準日を渡す。ADR-05 の理由） |
| 観測の日次バッチ（Lighthouse・Chatwoot の未解決の会話） | **取り戻せない**（Lighthouse は今のビルドしか測れず、Chatwoot は「今」未解決の会話を読む） | 欠けた日は欠測のまま残す。**欠けた日を `docs/audits/ops/` に「定期実行の停止」として記録し、`tunnel_up: false` と同じく「計測していなかった期間」として読めるようにする** |
| `I-13` の起票 | **自然に取り戻せる**（未起票の `E-13` を毎回すべて見る。冪等キーが二重起票を防ぐ） | 再開後の最初の実行でまとめて起票する（[06 の 2 節](06-proposal-loop-flows.md)） |
| 公開された記事の確認 | **自然に取り戻せる**（前回の確認との差分を見る） | 止まっていた間の公開がまとめて見つかり、1 回のビルドと配信にまとまる（[05 の 5 節](05-build-and-delivery-flows.md)） |
| 誤った書き込みの突き合わせ | **取り戻せる**（送信の記録は Chatwoot に残る） | 突き合わせの範囲を「固定の期間」ではなく**「前回の突き合わせが済んだ時点から今まで」**にする。固定の期間にすると、止まっていた間の送信が突き合わせから漏れる |

- **取り戻しの実行も 1 回の実行として監視アプリに記録する**（TA-07 の 3.3。ADR-18 で `E-15` の 1 件になる）。通常の実行と区別できる印を付け、起票前チェック 3（`measured_at` が 14 日以内。[06 の 1.2](06-proposal-loop-flows.md)）で取り直した `E-12` が新しく見えることに注意する（`range` が古くても `measured_at` は新しい）。
- **長く止まっていた場合にすべてを取り戻すかは決めていない**（8 節）。取り直しが多いと上流（Umami・Mautic・GSC）への要求が集中する。

## 4. `E-13` を経由しない変更の検出（暴走条件 #8）

### 4.1 検出の対象

DA-05 の 4.3 と AA-04 の 2.1 が定めた不変条件（**観測から作用に至る経路は `E-13` だけ**）を、実際に検査する手段を決める。

| 検査 | 方法 | 成立するか |
|---|---|---|
| **コードの変更** | `main` のコミットのうち、対応する `proposal_id` を持たないものを列挙する | **成立する**（Git の履歴が正本） |
| **Strapi のコンテンツ変更** | `I-01` の PostHog イベント（`article_updated` / `article_published`）のうち、対応する `E-13` が無いもの。**本番用のプロジェクトのイベントだけを見る**（ADR-16 で開発と本番のプロジェクトを分けた） | **部分的**（4.2） |
| **Mautic の変更** | Mautic の監査ログ | 未確認 |
| **Chatwoot の変更** | **エージェント専用ユーザーの送信の記録（`sender`）と `E-13` を突き合わせる**（ADR-17。TA-07 の 6.2）。**監査ログ（Enterprise の `audit_logs`）には頼らない**。ADR-16 では監査ログを使い、Community 版ならエージェント専用ユーザーのメッセージと会話の属性で代える形だったが、ADR-17 で Community 版でも同じ方式で運用できる形に改めた | **部分的**（拾えるのは**エージェント専用ユーザーの送信だけ**。会話の属性〈担当者・ラベル・状態〉の変更と人間の操作は拾えない）。頻度は未決定 |
| **n8n のワークフロー変更** | n8n のバージョン履歴 | 成立するが Git の外（本番は RDS に残る。ADR-16） |

**ADR-15（2026-09-19）の後、検査の対象は本番の Mautic・Chatwoot と、オンプレの Strapi（正本）・公開サイトだった。同日の ADR-16 で、対象は本番の Strapi・Mautic・Chatwoot・n8n と公開サイトになった**（Strapi の正本が本番に移り、n8n のワークフローもエージェントが `n8n-prod` で本番に置くようになったため）。エージェントは本番の Strapi・Mautic・Chatwoot に MCP で書き込み、公開サイトへの反映は人間が配信を承認し、n8n のワークフローは人間が有効にする（[06 の 1.5](06-proposal-loop-flows.md)）。したがって検出したいのは「`E-13` を持たない、本番への変更」であり、**人間の操作とエージェントの操作の両方が対象になる**（エージェントの操作は専用のアカウントの操作として本番に残る。Chatwoot では送信者〈`sender`〉がエージェント専用ユーザーになる）。**ADR-17 で、本番の Strapi への書き込みは下書きまでになった**（公開・非公開化・削除は `R2` の管理画面の操作。[03 の 4.1](03-operation-path-flows.md)）。エージェントの誤った書き込みが公開サイトに届く前に、人間の公開と配信の 2 段を通ることになる。

- **本番の管理画面での直接の修正は、設計上ありうる**（TA-07 の 1 節「確認と修正」）。これを一律に違反とすると、誤字の修正にも `E-13` が要ることになる。どの変更に `E-13` を求めるかは BA-05 の分類に従う。
- **エージェントの誤った書き込みの検出方式は ADR-16 で決まり、ADR-17 で改めた**（TA-07 の 6.2）。**エージェント専用ユーザーが送ったメッセージ（`sender`）のうち、どの `E-13` にも対応しないもの**を「誤った書き込みの候補」として監視アプリに出す。**突き合わせは監視アプリの定期実行の 1 つとして起動する**（TA-07 の 3.5。範囲は 3.4 のとおり「前回の突き合わせから今まで」）。**方式が決まったのは Chatwoot だけ**で、本番の Strapi・Mautic・n8n でエージェント専用のアカウントの操作を拾う手段は決めていない（8 節）。
- **ADR-18 で、誤った書き込みの候補を実行に結び付けられるようになった。** `E-15`（監視アプリの実行記録）は突き合わせの使い道を持ち（TA-07 の 3.6）、候補の送信の時刻を `E-15` の実行の期間と照らせば、どの起動（相関 ID）の送信かを絞り込める。**どこまで絞れるかは `E-15` に何を残すかで決まる**（ツールの呼び出しまで残せば実行を特定でき、要約と ID だけなら時刻の重なりまで。TA-07 の 9 節。8 節）。**（2026-09-19）ADR-18 の追加の決定 4 で、`E-15` には要約と ID だけを残すと決まった。** ツールの結果は残らないが、**書き込みの対象の ID（会話・コンタクト・記事など）は残る**。したがって絞り込みは次の 2 段になる。
  - **候補の送信の会話 ID が、時刻の重なる実行の `E-15` の対象の ID にあれば、その実行（相関 ID）に特定できる。** 無ければ時刻の重なりまでしか絞れない。**絞り込みの精度は、対象の ID が漏れなく記録されることに依存する**（エージェントの自己申告に頼らず、監視アプリが Claude Agent SDK の経過に見えるツールの呼び出しの引数から ID を取り出して記録する形を推奨する。結果は捨てる。この層の判断。8 節）。
  - **書き込みの中身（何を送ったか）は `E-15` からは分からない。** 対象の ID から本番の Chatwoot・Mautic の管理画面で元のデータを引いて確かめる（TA-07 の 3.6）。これは本番の管理画面の「確認と修正」（TA-07 の 1 節）の範囲に入る。
- **Chatwoot でも拾えるのは送信だけである**（ADR-17）。会話の属性（担当者・ラベル・状態）の変更は送信の記録に残らないため、この方法では見つからない。属性の変更の誤りは、各会話の履歴を人間が見て気づくことになる（TA-07 の 6.2）。**`agent/conversation-triage` の主な書き込みは社内メモ・ラベル・担当者であり（[03 の 2 節](03-operation-path-flows.md)）、そのうち拾えるのは社内メモ（送信の記録に残るメッセージ）だけ**になる。
- **エージェント専用のユーザーが前提になる**（TA-07 の 3.3）。人間の管理者と同じトークンを使うと、操作の主体を区別できない。
- ADR-14 で上げた「開発環境と本番のずれ（`strapi transfer` による上書き）」は、Strapi をオンプレだけに戻したことで生じなくなった（ADR-15）。**ADR-16 で本番に Strapi を置いた後も生じない。** 記事は本番の Strapi にだけ書き、開発環境との間で転送しないためである（TA-07 の 6 節）。

### 4.2 Strapi の検出が部分的にしか成立しない理由

[04 の 2.4](04-server-to-server-flows.md) で見つけた 2 つの穴が、ここに効く。

- **穴 1**: 非公開化が `article_updated` として送られるため、`承認` 分類の操作を通常の更新と区別できない。
- **穴 2**: 公開済み記事の更新も `article_updated` になるため、同じく区別できない。

**したがって「`E-13` を持たない `article_updated` があった」ことまでは分かるが、「それが `承認` を要する操作だったか」が分からない。**

`I-01` にイベントを足す（[04 の 2.4](04-server-to-server-flows.md) の対処案 A）と、この検出が成立する。**これがその改修の優先度が高い理由にあたる。**

### 4.3 禁止遷移の検出

DD-01 の 8.4 で禁止した 3 つの遷移を、Git の差分から検出する。

| 禁止遷移 | 検出 |
|---|---|
| `draft` → `applied`（承認を飛ばす） | `applied_at` があるのに `approval.state` が `approved` を経ていない、または `approval.record_ref`（PR 番号）が空 |
| `applied` → `draft`（再利用） | `applied_at` を持つファイルへの変更が `git log` に現れる |
| `verified` → `applied`（再適用） | 同じ `proposal_id` の履歴に `applied_at` の設定が 2 回現れる |

**3 つとも `git log -p docs/proposals/` で検出できる。** `E-13` を Git に置いた決定（ADR-04）の利点がここで効く。**提案の状態変化そのものが差分として残る**ため、遷移の履歴を別に持つ必要が無い。

### 4.4 この検出が成立しない範囲を隠さない

AA-04 は暴走条件 #8 の歯止めを「不完全」としている。**この層でもその判断は変わらない。**

| 適用先 | `E-13` を経由しない変更を検出できるか |
|---|---|
| コード（Git） | **できる** |
| `E-13` そのもの（Git） | **できる**（4.3） |
| Strapi のコンテンツ | **部分的**（4.2。`I-01` の改修で成立する） |
| Chatwoot | **エージェント専用ユーザーの送信に限って部分的**（ADR-17。会話の属性の変更と人間の操作は拾えない）。ADR-16 では「Enterprise なら監査ログでできる。Community ではエージェント専用ユーザーの操作に限って部分的」、旧版は「できない可能性」だった |
| Mautic | 未確認 |
| n8n のワークフロー | できる（バージョン履歴）が、**Git の外** |
| PostHog の設定 | **できない**（SaaS・外部リージョンで、こちらから状態を完全には把握できない） |

**Git の中にあるものは検出でき、外にあるものは検出できないか不確実である。** これは AA-04 の 3.3.1 が指摘した「記録が守られることと実体が守られることは別」という構造と、まったく同じ形で現れている。

## 5. 二重送信の検出（`I-08`）

### 5.1 検出

[03 の 3.3](03-operation-path-flows.md) の集計仕様で、`E-12` に 3 つの値を記録する。

```yaml
metric: CV-count
value: 42            # 畳んだ件数（CVR の分子）
raw_value: 45        # 生のフォーム送信件数
dedup_dropped: 3     # 畳んで消えた件数
```

| 状況 | 判定 |
|---|---|
| `dedup_dropped` = 0 | 正常 |
| `dedup_dropped` が `raw_value` の **1 割以下** | 許容範囲（同一人物の再送信は自然に起きる） |
| `dedup_dropped` が `raw_value` の **1 割超**（暫定） | **二重送信が常態化している徴候。** `E-12` に記録し、`agent/ops-watcher` が拾う |

### 5.2 1 割を超えたときに疑うもの

| 疑い | 確認方法 |
|---|---|
| ブラウザ側の二重送信防止（第 1 層）が効いていない | フォームの実装を確認する |
| 公開経路（本番は ALB の後ろの Mautic）が不安定で、利用者が何度も送信している | `tunnel_up` の履歴と突き合わせる（2 節） |
| ボットによる送信 | 送信元と時刻の分布を見る |

**3 つ目は `CVR` を直接汚染する。** `CV 数` が水増しされ、「CVR が改善した」という誤った観測が生まれる（暴走条件 #1 の変種）。

### 5.3 CVR を計算しない条件

**分母（Umami）と分子（Mautic）は異なる系から取る。** 片方だけが欠測すると CVR が跳ねる。

| 条件 | 挙動 |
|---|---|
| どちらかの `fetch.outcome` が `ok` / `empty_but_ok` 以外 | **`CVR` を計算しない**（`E-12` に `CVR` を書かない） |
| どちらかの `tunnel_up` が `false` | 同上 |
| 分母が 0（`empty_but_ok`） | **`CVR` を計算しない**（ゼロ除算。`CV 数` だけを記録する） |

**「計算できなかった」と「0 だった」を区別する。** これは DD-01 の 4.2 が `empty_but_ok` を分けた理由と同じ構造にあたる。

### 6.1 止める判断の原則

- **観測は極力止めない。** 観測が止まると、復旧したときに「いつから壊れていたか」が分からなくなる。
- **作用は疑わしければ止める。** 誤った観測に基づく作用は、元に戻す手間が観測の欠損より大きい。
- **通知の失敗でループを止めない。** 通知は正本ではなく、正本（GitHub の PR）から自動的に発生する副次物である（[06 の 3.5](06-proposal-loop-flows.md)）。
- **ビルドだけは 0 件で失敗させる。** 観測における `empty_but_ok` は成功だが、ビルドにおける 0 件は公開してはいけない成果物にあたる（[05 の 1.2](05-build-and-delivery-flows.md)）。

### 6.2 開発機を失ったときに失われるもの（ADR-18）

**ADR-16 は「開発機のバックアップは本番の復旧に関わらない」とした。ADR-18 で `E-15` の正本をローカルに置いたため、開発機を失うことの意味が「止まる」から「失う」に広がった。** **同日の ADR-18 の追加の決定 5 で `E-15` を S3 に写すことになり、「失う」の範囲は最後に写してから開発機を失うまでの分に縮んだ。**

ADR-18 の反映の時点の表（写さない前提）は次のとおりだった。経緯として残す。

- **写しは正本ではない**（ADR-18 の決定 1 のまま）。復旧では写しから監視アプリのローカルの DB を作り直し、作り直した DB が正本になる（この層の見立て。手順は写しの形式と一体で決める。8 節）。
- **写しに本番の個人情報は入らない**（ADR-18 の追加の決定 4。`E-15` に残るのは要約と ID だけ）。ADR-18 の反映の時点では「写した先にも本番の個人情報が残りうる」ことが写す判断を止めていたが、決定 4 で解けた。**要約に個人情報が紛れ込まないことは、エージェント定義の規則と監視アプリの記録前の検査で守る**（検査の方法は未決定。TA-07 の 9 節）。

### 7.1 #7 が解けない理由（ADR-18 で条件付きで解けた）

**ADR-18 の前は、**`E-15 AgentRun` の正本が未確定であるため、**エージェントの実行そのものを追う手段が無かった**（以下は経緯。「ADR-18 で 1 つ目の条件が満たされた」の箇条から後が ADR-18 の後の状態）。

- DD-01 の 3.4 で `agent_run_id` に相関 ID を入れる暫定策を決めたが、**これは `E-13` の必須項目を埋めるためのものであって、実行履歴を残すものではない**。
- 相関 ID を書くのはエージェント自身であるため、**エージェントが偽の値を書けば辿れなくなる**。外部の記録が無い限り、この歯止めは成立しない。
- **ADR-14・ADR-15 で解ける見込みが生まれ、ADR-16 でも変わらない**（監視アプリはローカルに残った）。 エージェントの起動元が監視アプリに一本化されるため、**監視アプリのサーバー側が実行ごとに相関 ID を振って記録すれば、それはエージェントが書き換えられない外部の記録になる**（TA-07 の 3.3）。`E-15` の正本をそこに置くと決まれば、#7 は成立に変わりうる。ただし日次バッチのような定時の実行を誰が起動するか（3.2 の循環）は、監視アプリが「指示で動かす」ものである限り残る。
- **（2026-09-19）ADR-17 で、定時の実行も監視アプリが起動することになり、上の「残る」は解けた**（TA-07 の 3.5。3.2）。残る条件は 2 つある。1 つは `E-15` の正本を監視アプリの実行記録にすると決めること（TA-07 の 9 節）、もう 1 つは**その記録と定期実行の定義をエージェントが書き換えられない場所に置くこと**（監視アプリをエージェントの作業ツリーから動かすと、記録も定義もエージェントの手の届く所に置かれる。[06 の 2.4](06-proposal-loop-flows.md)）。
- **（2026-09-19）ADR-18 で 1 つ目の条件が満たされた。** `E-15` の正本は監視アプリの実行記録で、書くのは監視アプリのサーバー側だけである（TA-07 の 3.6）。相関 ID も監視アプリが発行して先に `E-15` に書く（DD-01 の 3.2）ため、次のずれを検出できる。**上の 2 つ目の箇条（エージェントが偽の値を書けば辿れない）は、この突き合わせで塞がる。**

| 検出するずれ | 突き合わせるもの |
|---|---|
| 成果物の相関 ID が `E-15` に無い | `E-12` の `fetch.correlation_id` ／ `E-13` の `agent_run_id` と `E-15` |
| 相関 ID が別のエージェントの実行を指す | `E-15` の `agent_name` と、成果物を書いたディレクトリ（1 エージェント 1 ディレクトリ。AA-03 の 4.3） |
| `E-15` が `success` なのに成果物が無い／`skipped` なのに `E-13` が増えている | `E-15` の `outcome` と `docs/audits/` `docs/proposals/` の差分 |

- **成立は条件付きである。残る条件は 2 つ。**
  - **記録と定義をエージェントが書き換えられない場所に置くこと**（上の 2 つ目の条件のまま）。上位層は「定期実行の定義の置き場所」を未決定に上げ、「Git で持ち、承認済みの `main` から作った別の場所で監視アプリが読む」を案とした（AA-05 の未決定事項・TA-07 の 9 節）。**`E-15` の DB も作業ツリーの外に置く必要がある**（[06 の 2.4](06-proposal-loop-flows.md)。この層の判断）。**（2026-09-19）ADR-18 の追加の決定 3 で、定義は案のとおり Git に置き、承認済みの `main` のチェックアウトで読み、変更は必ず PR を通すと決まった。** 定義の側はこれで満たされる。残るのは実装の条件で、**監視アプリのコードも同じチェックアウトから動かすこと**と、**`E-15` の DB を作業ツリーの外に置くこと**（どちらもこの層の判断。[06 の 2.4](06-proposal-loop-flows.md)）である。
  - **`E-15` を失わないこと**（6.2）。開発機を失うと、突き合わせの根拠そのものが消える。開発機の外に写すかは未決定（TA-07 の 9 節）。**（2026-09-19）ADR-18 の追加の決定 5 で S3 に写すと決まった。** 写しは追記だけを許し、削除と上書きを許さず、書く資格情報は監視アプリのサーバー側だけにある。**最後に写した時点までは満たされ、写す頻度の間の分だけが残る**（写す頻度は未決定。TA-07 の 9 節）。
- **S3 の写しは #7 の検出そのものも強める**（この層の見立て）。エージェントがローカルの DB を書き換えても、既に写した記録は写しと突き合わせれば食い違いとして見える（写しは上書きできない）。**写す前の記録の書き換えには効かない**ため、DB を作業ツリーの外に置く判断（上）は変えない。写しとの突き合わせを誰がいつ行うかは決めていない（8 節）。
- **監視アプリを通らない実行は検出の外にある**（DD-01 の 3.2。1 周目の最短経路）。`E-15` に記録が無いことは「監視アプリを通らなかった」ことしか意味しない。
- **`E-15` に何を残すかで、検出できる範囲が変わる**（TA-07 の 9 節）。要約と ID だけなら上の表の 3 つまで、ツールの結果まで残せば「どの本番の書き込みをどの実行が行ったか」まで追える。後者は本番の個人情報をローカルに残す（DA-05）。**（2026-09-19）ADR-18 の追加の決定 4 で要約と ID だけに決まった。** 検出できるのは上の表の 3 つに加え、**`E-15` の対象の ID と本番の書き込みの対象を照らして、どの実行の書き込みかを絞ること**までである（4.1）。書き込みの中身は ID から本番の管理画面で引く。

### 7.2 #8 が部分的にしか解けない理由

4.4 のとおり、**適用先が Git の外にあるものを検出する手段が無いか、不確実である**。

- Chatwoot の監査ログは Enterprise 機能である（`backend/chatwoot-mcp/README.md`）。**ADR-16 で監査ログと `E-13` の突き合わせを検出の手段に決めた**が、Community 版ではエージェント専用ユーザーの操作に限った部分的な検出になる（4.1）。**ADR-17 で監査ログに頼らず、エージェント専用ユーザーの送信の記録で突き合わせる形に改めた。** 版に依存しなくなった代わりに、拾えるのは送信だけで、会話の属性の変更と人間の操作は拾えない（4.1）。
- **Webhook は代替にならない**（[04 の 5.2](04-server-to-server-flows.md)。止められる主体が変更を隠せる）。
- PostHog は外部リージョンにあり、こちらから状態を完全には把握できない。

### 7.3 #11 が部分的にしか解けない理由

**セルフホストの OpenSEO は支出を計量しない**（`whoami` の残高が `null`。AA-05 の ADR-10）。支出を知る手段は DataForSEO 側にしか無く、その取得手段が決まっていない（TA-05 の未決定事項）。

- **前払い残高は「使い過ぎ」を止めるが、「使い過ぎていること」は知らせない。** 残高が尽きた時点で調査もランク追跡も同時に止まり、そこで初めて気づくことになる。
- **ランク追跡のスケジュールは、エージェントが 1 度も呼ばなくても支出を生む**（TA-03 の 4 節「静かに続く」失敗）。エージェント側の stderr にも記録が残らない。

**この 3 件（#7・#8・#11）が残っていることを、ループを本格稼働させる前に解く**（AA-04 の 4 節）。**ADR-18 の後、#7 について解くのは 7.1 の 2 条件（記録と定義の置き場所、`E-15` を失わないこと）である。** **ADR-18 の追加の決定の後は、定義の置き場所と写すことは決まり、残るのは `E-15` の DB と監視アプリのコードの置き場所（この層の判断の実装）と、写す頻度である。**

- **保持期間を過ぎた S3 の写しをどう消すか**（6.2。ADR-18 の追加の決定で新たに生じた）。追加の決定 5 は「写しは追記だけを許し、削除と上書きを許さない」とした。一方で保持期間を決めれば、期間を過ぎた写しを消す必要が生じる。**誰にも削除を許さないまま期間で消す手段**（S3 のライフサイクルによる期限切れの削除だけを許すか、Object Lock の保持期間と組み合わせるか）を、保持期間と一緒に決める。写しの形式（1 件 1 オブジェクトか、まとめて写すか）もこれに効く。TA-06 の担当。判断者 `R1`。
- **削除の請求があったときの `E-15` の扱い**（ADR-18 の追加の決定で性質が変わった）。追加の決定 4 で `E-15` に個人情報そのものは入らなくなったが、**コンタクトの ID・会話の ID は、本番の Mautic・Chatwoot と照らせば個人に結び付く**（この層の見立て）。本番側のコンタクトを削除すれば ID は誰も指さなくなるため、`E-15` の側は消さなくてよいと整理できるかを DA-05 で確かめる。消す必要がある場合、S3 の写しの「削除と上書きを許さない」と衝突する。判断者 `R1`。
- **`E-15` の対象の ID を何から取るか**（4.1。ADR-18 の追加の決定で新たに生じた）。誤った書き込みの候補を実行に特定できるかは、対象の ID が漏れなく記録されることに依存する。エージェントの要約（自己申告）に頼ると、書き込んだ ID を書き漏らした実行は候補から外れる。**監視アプリが Claude Agent SDK の経過に見えるツールの呼び出しの引数から ID を取り出し、結果は捨てる**形をこの層は推奨する。取り出せるかは TA-07 の 9 節の「Claude Agent SDK の仕様の確認」と同じ根。判断者 `R1`。
- **S3 の写しとローカルの `E-15` の突き合わせを誰がいつ行うか**（7.1。ADR-18 の追加の決定で新たに生じた）。写しは上書きできないため、写した後のローカルの書き換えを見つける根拠になる。突き合わせを監視アプリの定期実行の 1 つにするか、復旧のときだけに使うかを決めていない（見つけられるのは、写した後にローカルの DB が書き換えられたことだけで、写す前の書き換えは見つけられない。6.2）。判断者 `R1`。
- **（2026-09-19 に ADR-15 で解消）開発環境と本番の Strapi のずれ。** Strapi をオンプレだけに戻した。**ADR-16 で本番に Strapi を置いた後も、記事を開発環境と本番の間で転送しないため生じない**（4.1）。
- **エージェントによる本番への誤った書き込みの検出**（4.1。ADR-15 で上げた）。**ADR-16 で Chatwoot の方式が決まった**（監査ログと `E-13` の突き合わせ。Community 版ならエージェント専用ユーザーの `sender`）。**ADR-17 で監査ログに頼らず、エージェント専用ユーザーの送信の記録と `E-13` で突き合わせる形に改め、突き合わせは監視アプリの定期実行の 1 つになった。** 残るのは次の 3 つ。判断者 `R1`。
  - **突き合わせの頻度**（TA-07 の 9 節）。範囲は「前回の突き合わせから今まで」にする（3.4。この層の判断）ため、頻度は見つかるまでの遅れだけを決める。
  - **（2026-09-19 に ADR-17 で解消）Chatwoot の版**（Enterprise か Community か）。方式が監査ログに依存しなくなったため、版の選択は突き合わせの成立を左右しない。**代わりに、会話の属性（担当者・ラベル・状態）の変更と、受信箱・チーム・自動化ルールの設定の変更は、どちらの版でも拾えない**（4.1）。これらの誤りを拾う手段を別に設けるかは決めていない。

- **開発環境の n8n の停止とオンプレの全滅をハートビートで区別できない**（6 節。ADR-16 で新たに生じた）。ハートビートの送り手が開発環境の n8n であるため、開発環境の n8n を止めただけ（作業のための再起動など）でも全滅と同じ通知が出る。TA-05 の 4 節の「止める前にアラームのアクションを無効にする」手順を開発環境の n8n の再起動にも適用するか、送り手を移すか（TA-07 の 9 節）で決まる。判断者 `R1`。
- **ハートビートの送り手を監視アプリに移すか**（6 節。TA-07 の 8 節・9 節。ADR-17 で論点が変わった）。ADR-17 でハートビートの途絶は「改善ループが止まっている」ことを意味するようになり、知りたいのは開発環境の n8n ではなく**定期実行の起動元である監視アプリの生存**になった。今の送り手のままだと、**監視アプリだけが止まった場合（ループは止まっている）にハートビートは途絶えず、開発環境の n8n だけが止まった場合（ループは動いている）に途絶える**。送り手を監視アプリに移せば上の項目（区別できない）も解けるが、監視アプリに CloudWatch へ書く資格情報（`cloudwatch:PutMetricData`）を持たせることになる。重大度（`comegin-ops-alert` の即時の通知にするか）も合わせて決める。判断者 `R1`。
- **開発機のスリープ・夜間の停止をどう扱うか**（3.4・6 節。ADR-17 で新たに生じた）。開発機はサーバーではないため、夜間や休日に止めるのが自然である。そのたびにハートビートが途絶えて通知が出るなら、通知が常態化して無視されるようになる。定期実行の時刻を開発機が動いている時間帯に寄せるか、止まっている時間帯をハートビートのアラームから外すか、開発機を常時起動にするかを決めていない。判断者 `R1`。
- **本番の Strapi の停止でビルドが止まる間の扱い**（6 節。[05 の 5 節](05-build-and-delivery-flows.md)と同じ項目）。判断者 `R1`。
- **OpenSEO の停止を誰が検知するか**（6 節）。TA-05 の項目 9 で `/api/health` を監視すると決めたが、監視の主体（n8n か、ホストの cron か）が決まっていない。n8n から叩く場合、無認証の OpenSEO に到達するプロセスが 1 つ増える（ヘルスチェックの経路だけなら費用は発生しない）。**ADR-16 で本番の n8n は AWS に移り、ローカルの OpenSEO には届かない**（トンネルを張らない）ため、n8n で監視するなら開発環境の n8n になる（ハートビートと同じ扱い）。監視アプリ（TA-05 の項目 17 と同じ開発機）に持たせる案もある。**ADR-17 で監視アプリが定期実行の起動元になったため、定期実行の 1 つとして OpenSEO の `/api/health` を見る形が最も素直になった**（この層の見立て）。判断者 `R1`。
