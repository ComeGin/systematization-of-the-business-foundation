# 記事の下書きから公開・配信まで（週 2 本の運用。2026-11-19）

本番の公開サイト（Astro）に、**記事を週 2 本**出すための、毎週の作業の手順。
設定（段階 `operate` まで）が済んだ後の**運用**の手順で、設定スクリプトは確かめない。全体の設定の順番は [`00-setup-overview.md`](00-setup-overview.md)。

- 記事を新しく作るのは **キーワードの経路**（以下、経路 B）。観測から始まる改善提案の経路（経路 A。`weekly-lighthouse` → … → `daily-propose` → `daily-i13-file` → 作用のジョブ）は、提案の種類（`change.kind`）が `content_rewrite` のときだけ記事の下書きを作る。種類は proposal-writer が観測から決めるので、記事を作るとは限らない（`accessibility`・`technical_seo` ならコードの差分になる）。週 2 本はこの経路 B で回す
- **エージェントは下書きまで。公開（`publishedAt`）と配信は人が行う**（ADR-17・ADR-31）。本番の Strapi の管理画面は、オンプレの機械のブラウザから `http://127.0.0.1:1338/admin` で開く（`127.0.0.1` だけに開いている）
- 役割: `R2`（SEO ディレクター）がキーワードの採否・企画の承認・記事の公開を決める。`R4`（ライター）は取材の素材を用意する。`R1` は配信のコマンドを実行してよい（`R2` が兼ねてもよい）。役割の正本は `docs/RequirementDefinition/BA/03-roles-and-raci.md`

## 1. 週の流れ

| いつ | 誰が | すること | 週 2 本のために要る量 |
|---|---|---|---|
| 月 02:30 | `weekly-keyword-research` | キーワードの候補（E-01。`adoption_status: candidate`）を本番の Strapi に作る。**OpenSEO の費用が出る** | — |
| 月〜火 | **R2** | キーワードを採否する（2 節） | 週 2 つ以上を `adopted` |
| 水 02:30 | `weekly-content-plan` | 採用済みで企画の無いキーワードから、企画（E-03。`plan_state: drafted`）を起案する。1 回 3 件まで | — |
| 水〜翌月 | **R2**（R4 の企画は **R4** の素材の後） | 企画を承認・差し戻す（3 節） | **火・金の 02:30 の前に、承認済みで記事の無い企画が 1 件以上**（在庫は 2 件以上が目安） |
| **火・金 02:30** | `weekly-content-draft` | 承認済みで記事の無い企画のうち**最も古い 1 件**から、記事の下書き（E-04）を作って企画に結ぶ。1 回 1 本 | 1 本ずつ |
| 火・金 03:00 | `article-cover` | アイキャッチ（cover）の無い下書きに、OpenAI の Images API で画像を作って結ぶ（1 回 3 枚まで）。**OpenAI の費用が出る**。月曜は動かさない | — |
| 火・金の日中 | **R2** | 下書きを読んで直し、公開する（4 節） | 2 本 |
| 公開の翌日 00:00 | `published-article-check` | 公開を見つけ、本番の値でビルドと Lighthouse を行い、周の**配信の項目**（OK 待ち）を作る | — |
| 公開の翌日 | **R1 / R2** | 監視アプリで配信の項目を OK し、出たコマンドで配信して「実行した」を押す（5 節） | **公開から 48 時間以内** |

- 週 2 本の上限は「`weekly-content-draft` が 1 回 1 本 × 火・金」で決まる。1 回止まると、その週は 1 本になる（1 回で 2 本は作らない）。**承認済みの企画の在庫を切らさないこと**が、いちばん効く
- 配信を週 1 回にまとめたいなら、金曜の分を公開した後にまとめて配信してよい（どちらも 48 時間以内に収まるようにする）

## 2. キーワードを採否する（R2。月〜火）

1. 本番の Strapi の管理画面 → Content Manager → **Keyword** で、`adoption_status` が `candidate` のものを見る（検索ボリューム・検索意図はエージェントが書いている）
2. 書く価値があるものを `adopted`、書かないものを `skipped` にして保存する
   - 読み手は介護・障がい福祉を運営している法人・事業所。そこに合わないものは `skipped`
3. 採用が週 2 つより少ない週が続くと、企画の在庫が減る。候補が足りなければ、次の月曜を待つ

## 3. 企画を承認する（R2。水〜翌月）

1. Content Manager → **Content Plan** で、`plan_state` が `drafted` の企画を開く。`outline`（構成案）と `assignee_role` を見る
2. `assignee_role` で分ける

| `assignee_role` | 意味 | 承認のしかた |
|---|---|---|
| `R2` | 一次情報が要らない（公開されている情報で書ける） | 構成案がよければ `plan_state` を `approved` にして保存する |
| `R4` | 取材でしか得られない一次情報（自社の体験・実績、現場の声、具体的な数字、事例）が要る | **先に R4 が素材を書き足し、そろってから `approved` にする**（下の 3.1） |

3. 書かない企画は `sent_back` にする（素材を集める時間が取れない R4 の企画も、承認せずに `sent_back` でよい）

### 3.1 R4 の素材の書き方

content-planner は、取材が要る見出しに「**R4 の素材が必要**」と書いている。その直後に、R4 が**出典と要点**を書き足す。

```markdown
## 導入の効果
- R4 の素材が必要 → 素材:
  - 出典: 2026-10 の A 社への聞き取り（社名は出さない約束）
  - 要点: 紙の台帳から移して、月末の集計が 2 日 → 半日になった
  - 要点: 移行の初月は入力の二重化で負担が増えた
```

- content-writer は、R4 の企画では**書かれた素材だけ**を使って書く。素材の無い箇所を推測で埋めず、体験や実績を作文しない。素材が足りなければ**書かずに止まり**、足りない素材を実行の要約（`SUMMARY:`）に書く
- 個人情報（氏名・メールアドレス・電話番号）と、会話・フォームの本文は書かない。人や会社は伏せるか、許可を得た範囲で書く
- **素材を書く前に承認しない。** 下書きのジョブは「承認済みで最も古い企画」を飛ばさずに選ぶので、素材の無い R4 の企画が先頭にあると、火・金のたびにそこで止まり、後ろの企画も進まない

## 4. 下書きを確かめて公開する（R2。火・金の日中）

1. Content Manager → **Article** で、その朝に作られた下書き（Draft）を開く。下書きは企画（Content Plan の `article`）に結ばれている。アイキャッチ（`cover`）は 03:00 の `article-cover` が付けている
2. 次を確かめ、必要なら直す。**承認画面の確認項目（`ops/approval-checklists.yaml` の `article`）と同じ**

| 確認すること | 見るところ |
|---|---|
| 事実と数字に出典がある | 本文（`blocks`） |
| 引用と著作権に問題が無い（引用は必要な範囲に収まり、出典を表示している） | 本文 |
| 景品表示法に触れる言い切りが無い（「必ず」「No.1」など根拠の無い表現が無い） | 本文・タイトル |
| アイキャッチ画像は AI で作ったもので、人物・他社のロゴや商標が写っていない | `cover` |
| `description` が 80 文字以内で、本文の内容と合っている | `description` |

3. エージェントが設定しない項目を埋める
   - **`category`**: `know-the-issues`・`compare-methods`・`consider-adoption` のどれか（空でも公開はできるが、カテゴリの一覧と関連記事に出ない）
   - **`author`**: 必要なら
   - `slug` が記事の内容に合っているか（URL は `/blog/<slug>/`。公開の後に変えると URL が変わる）
4. 画面右上の **Publish** で公開する
5. `cover` が空のまま公開しない。`article-cover` がまだ動いていない・失敗したときは、監視アプリのジョブの画面で `article-cover` を「今すぐ実行」してから公開する

> 周のジョブ（`cycle-collect`）を有効にしている場合は、この下書きが監視アプリの改善の周の画面に**記事の項目**として出る。確認項目を入れて OK → 出てきた手順（Strapi で公開）→「実行した」で、システムが `publishedAt` を確かめる。公開そのものは同じく Strapi の管理画面で行う。2026-11-19 時点では `cycle-collect` は無効なので、項目は出ない（上の手順で公開する）。

## 5. 配信する（R1 / R2。公開の翌日。48 時間以内）

公開しただけでは公開サイトに出ない（公開サイトは静的なビルドで、S3 と CloudFront から配る）。

1. 公開した翌日の 00:00 に `published-article-check` が、本番の値でビルドと Lighthouse を行い、改善の周の画面に**配信の項目**（OK 待ち）を作る。朝に監視アプリの改善の周の画面を開く
2. 配信の項目の確認項目（`ops/approval-checklists.yaml` の `deploy`）を入れて OK する
   - Lighthouse の SEO が 1.0（未満なら配信の手順は出ない）
   - 含まれる記事と差分が承認済みのものだけ
3. OK の後に出るコマンド（`aws sso login`・`aws s3 sync` を 2 回〈`_astro/*` を先に、削除を最後に〉・`aws cloudfront create-invalidation`。バケット名・ディストリビューション ID・dist のパスは埋めてある）を、**画面に出た順のまま**オンプレの端末で実行する。配信用の主体（`comegin-prod-deploy`）を使う。詳しくは `cloud/README.md` の 4.14
4. 「実行した」を押す。システムが、公開サイトで記事の URL が 200 を返し、ビルドの印が一致することを確かめる
5. **配信の項目は、毎回最後まで閉じる。** OK 済み・実行済み・確かめられなかった（`failed_check`）の配信の項目が残っているあいだ、`published-article-check` は新しい項目を作らない（次の公開がサイトに出なくなる）
   - 確かめられなかったときは理由が出る。直して、同じ項目で「実行した」を押し直す（差し戻さない）
   - 承認前の古い配信の項目は、新しい公開があると置き換えられる（差し戻される）。そのまま新しい項目を OK すればよい
6. 48 時間を過ぎても配信されていない公開済みの記事があると、監視アプリの「設定の状況」が「更新が必要」で知らせる（48 時間以内は ✓ に「配信待ち」と添える）

## 6. 止まったとき

| 症状 | 見るところ | 直し方 |
|---|---|---|
| 火・金に下書きが出ない（`weekly-content-draft` が `skipped`） | 監視アプリの実行の要約 | 「承認済みの企画が無い」なら、3 節で企画を承認する（次の火・金に作られる。急ぐならジョブを「今すぐ実行」） |
| 下書きが出ない（`success` だが「R4 の素材が無い」「書かずに止まった」） | 実行の要約（足りない素材が書いてある） | R4 が素材を書き足す。急がないなら、その企画を `sent_back` にして、後ろの企画を先に進める |
| アイキャッチが付かない | `article-cover` の実行の要約 | `skipped`（OpenAI のキー・Strapi の書き込みトークンが無い）は設定を確かめる（`onprem/README.md` の `next-js-prod:openai`・`strapi-tokens`）。`permission_denied` は Strapi の書き込みトークンの権限（Upload の `upload` と Article の `update`。`setup/manual-steps.md` の 7.8） |
| 公開した翌朝に配信の項目が出ない（`published-article-check` が `skipped`） | 実行の要約 | 古い配信の項目（OK 済み・実行済み・`failed_check`）が残っている。その項目を閉じる（5 節の 5） |
| 配信の項目に手順が出ない | 配信の項目の Lighthouse の値 | SEO が 1.0 未満。記事の `description`・見出しの構造・画像の代替テキストを直して、もう一度公開する（翌日の 00:00 に作り直される） |

## 7. 関係する定義

- 定期実行の定義: `ops/schedules/weekly-keyword-research.yaml`・`weekly-content-plan.yaml`・`weekly-content-draft.yaml`・`article-cover.yaml`・`published-article-check.yaml`（時刻の表は `ops/README.md`）。**定義は承認済みの main のチェックアウトから読まれる**ので、変えたら PR をマージしてチェックアウトを `checkout --detach origin/main` で合わせる
- エージェントの定義: `.claude/agents/keyword-researcher.md`・`content-planner.md`・`content-writer.md`
- 承認画面の確認項目: `ops/approval-checklists.yaml`
- 配信のコマンドと配信用の主体: `cloud/README.md` の 4.5.1・4.14、[`00-setup-overview.md`](00-setup-overview.md) の P12
