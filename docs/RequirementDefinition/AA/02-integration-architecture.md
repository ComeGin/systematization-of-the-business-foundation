# AA-02 連携アーキテクチャ

AA（Application Architecture）層。ID はそれぞれの正本の定義をそのまま使う（索引は [`docs/README.md` の「ID の採番と正本」](../../README.md)）。**連携点 `I-xx` の採番の正本は本ファイルの 1 節である。**

AA-01 で並べたアプリケーションの**間**を扱う。このファイルの目的は 2 つ。

- **いま何が繋がっていて、何が繋がっていないかを 1 枚の表で確定させる**（BA と DA が各所で「未配線」と書いてきた事実を、連携点の単位で棚卸しする）。
- **未配線・未着手の連携それぞれについて、どの手段で繋ぐかを決める**（3 節。これが次フェーズの着手リストになる）。

**状態が `実装済み` の連携は 5 本しかない**（I-01〜I-04 と、OpenSEO の内部で完結する I-23）。他はすべて `未配線` か `未着手` である。

> **（2026-10-06）ADR-21 の反映。本ファイルの本文より、この注記を優先する。**
> - **本番の n8n はオンプレで動く**（`onprem/n8n`。エディター・API・MCP は `127.0.0.1:5679`）。データは AWS の RDS の `n8n` データベース。ADR-16 の「本番の n8n は AWS の ECS」「Webhook は VPC の中で受ける」「ALB の `n8n.` ホスト名」は旧版の記述である。
> - **Webhook の受け口（`I-11` `I-12`）**: クラウドの Mautic・Chatwoot が、WireGuard 越しにオンプレのリバースプロキシ `http://10.99.0.2:5680/webhook/*` へ送る。プロキシは **POST の `/webhook/*` だけ**を n8n に通し、ほかは 404 を返す。受け付ける送信元は **WireGuard の EC2 の `10.99.0.1` だけ**（EC2 が masquerade するため、届く送信元は Mautic・Chatwoot のタスクのアドレスではなく常にこれになる）。署名の検証（`I-11` `I-12`）は n8n のワークフローの中で引き続き必須である。詳細は DD-04 の 4.4。
> - **`I-21`（n8n → Amazon SNS）**: オンプレから AWS へ、インターネット越しの API で発行する（トンネルを通さない）。認証は**タスクロールではなく、IAM ユーザー `comegin-<env>-onprem-n8n-sns` のアクセスキー**（人が発行し、n8n の資格情報にだけ置く）。詳細は DD-04 の 8.7。
> - **状態の語**: `I-11` `I-12` `I-19` `I-21` は、ワークフローを作り、開発の n8n で動作確認した（外部 API を呼ぶノードの一部はピン留め）。**本番の n8n への取り込みと公開（人間・`R1`）はまだ**のため、状態を **`実装済み（未公開）`** と書く（`middleware/n8n/workflows/README.md` の一覧が事実）。`I-18` は何も送信しない骨格だけで、有効化しない。
> - **開発機・回線・WireGuard・プロキシ・n8n のどれかが止まると、クラウドの Mautic・Chatwoot からの Webhook が届かず欠落する**（`I-11` `I-12`。DD-07 の 2.5）。ADR-16 が解いた「本番の Webhook は開発機の死活に依存しない」は成り立たなくなった。訪問者に届くサービスは止まらない。
> - **未設計の点を 5 節に足した**（`I-27` の起動の経路、旧版の「I-17 のラベル付与」の番号の誤り）。

> **（2026-10-06）ADR-24 の反映。本ファイルの Cal.com の記述より、この注記を優先する。**
> - **Cal.com（`I-25`）は SaaS（cal.com。無料）を使い、無料相談の完了画面に埋め込む**（ユーザーの決定。ADR-19 のセルフホストを置き換えた）。ECS の `calcom`・RDS の `calcom`・ALB の `cal.comegin.com`・開発ポート 3105 は作らない。

> - **氏名・メールアドレス・面談の日時が Cal.com, Inc.（米国）にも渡る**（予約の正本〈`E-16`〉そのものが SaaS にある）。国外に出る先は 3 つ（PostHog・Google Calendar・Cal.com。DA-05 の 1.2）。

> **（2026-10-06）ADR-25 の反映。本ファイルの Umami の記述より、この注記を優先する。**
> - **アクセス解析の正本を GA4 にし、Umami をやめた**（ユーザーの決定）。`I-05` の受信先は GA4（SaaS）になり、**ブラウザから直接届く**（`I-06` の PostHog と同じ。ALB を通らない）。`I-17`（Umami MCP）は廃止し、GA4 の集計値は `I-22`（OpenSEO の MCP）で読む。
> - **公開経路（ALB）の到達先は Chatwoot・Mautic・`consent-api` の 3 つになった**（ALB の `stats.comegin.com` は使わない）。運用経路の管理画面からも Umami が外れる。
> - **GA4 も同意の後だけ動く**（Cookie `_ga` を使うため）。同意の対象は PostHog・Chatwoot・GA4 の 3 つ。同意の前に送る計測は無くなった。
> - **ALB の障害で止まるのは `I-07` `I-08` だけになり、`I-05` `I-06` は生き残る**（3.1）（**ただし同意済みの訪問者に限る**。同意の Cookie は ALB の後ろの `consent-api` の応答で書くため、ALB の障害中は新しい訪問者の同意が成立せず、GA4 も PostHog も新しい訪問者の分は止まる。DD-02 の 1.3・8.4）。
> - 閲覧の記録が Google LLC（米国）に渡る。国外に出る先は 4 つ（PostHog・Google Calendar・Cal.com・GA4。DA-05 の 1.2）。

### 1.1 `実装済み` が 5 本しかないことの意味

I-01 から I-04 の 4 本と I-23 以外はすべて未成立である。I-23（OpenSEO → DataForSEO）は OpenSEO の設定だけで成立する外向きの問い合わせであり、この基盤の他の構成要素とは繋がっていない。残る 4 本の内訳は「Strapi から PostHog への一方向の通知 2 本」と「エージェントから 2 つの上流 API への呼び出し 2 本」であり、**訪問者に関わる連携が 1 本も無い**。

つまり現在の基盤は、**エージェントが操作できる道具は揃っているが、操作した結果が誰にも届かず、誰の反応も返ってこない**状態にある。AA-04 の再帰的自己改善ループが 1 周も回っていない直接の原因はここにある（入力となる I-05〜I-08 が 1 本も無い）。

**（2026-10-06 の注記）この節の「5 本」は 2026-09 時点の数え方である。** その後 `I-11` `I-12` `I-19` `I-21` のワークフローを作り、開発の n8n で動作確認したため、状態を `実装済み（未公開）` とした（本番の n8n への取り込みと公開が済むまで、本番では動いていない）。**訪問者に関わる連携が 1 本も無い点は変わらない**（4 本とも上流システムの内側の連携）。`実装済み` と数えるのは、本番で動いているものだけにする。

### 1.2 冪等性を「要設計」とした 4 本

I-08 / I-11 / I-12 / I-18 の 4 本は、再実行で同じ操作が二重に起きる。とくに **I-08（フォーム送信）の二重実行は CVR を直接汚染する**（`E-09` が 2 件できると分子が 2 倍になる）。DA-02 が「CV の判定はクリックではなくフォーム送信完了」と定義した以上、送信完了の数え方が二重化すると KPI 全体が歪む。

対処の方針を 3 本に統一する。

- **email をキーにした統合を Mautic 側の既定にする**（同じ email の送信は既存コンタクトの更新になる。BA-04 の「作成または既存に統合」に対応）。
- **webhook の受け口（n8n）で重複排除する**。キーは `E-09` なら `contact_id` + イベント時刻、`E-10` なら `display_id` + メッセージ ID。
- **提案の起票（I-13）だけは冪等にする**。`proposal_id` が既に存在すれば起票しない（同じ観測から同じ提案が毎日起票され続けるのを防ぐ。AA-04 の暴走条件 2 への歯止め）。

### 1.3 露出経路の 2 分類（本番は ALB、Webhook は VPC の中）

> **（2026-10-06）ADR-21 で、内部経路（Webhook）は「VPC の中」ではなくなった。** 届き先がオンプレの n8n になったため、**クラウドの Mautic・Chatwoot → WireGuard の EC2（`10.99.0.1`）→ オンプレのリバースプロキシ（`10.99.0.2:5680`）→ n8n** になる。経路は WireGuard で暗号化され、インターネットに出ない（ALB も通らない）。見出しと下の本文の「VPC の中」は ADR-16 の記述である。**「到達できるのは Mautic・Chatwoot だけ」は、プロキシの送信元の制限（`10.99.0.1` だけ）・WireGuard の許可する宛先・EC2 のセキュリティグループ〈Mautic・Chatwoot のタスクからしか受けない〉の 3 つで守る。** エディター・API・MCP は WireGuard のアドレスに開かない（`127.0.0.1:5679` だけ）。**この 1 本が、ADR-16 の「AWS からオンプレへ向かう線は作らない」に対する唯一の例外である**（TA-04）。

**訪問者のブラウザが直接触れるシステム（Umami・Chatwoot・Mautic）は、本番では AWS に置く**（**2026-10-06 の注記: Umami は ADR-25 で廃止。後継の GA4 は SaaS で ALB を通らない**。`R1` の 2026-09-18 の決定。AA-05 の ADR-12、TA-06）。当初は「クラウドに展開するのは製品（Astro）のみ」とし、オンプレの 3 システムへ ngrok の常設トンネルで到達させる設計だったが、訪問者から見える機能が開発機 1 台の死活に依存し、しかも静かに止まるという弱点があったため置き換えた。**さらに ADR-16（2026-09-19）で、正本のデータを持つ Strapi と n8n も AWS に置いた。**

- **公開経路の入口は AWS の ALB になる。** ホスト名は `stats.comegin.com`（Umami。**ADR-25 で不要**）・`chat.comegin.com`（Chatwoot）・`mkt.comegin.com`（Mautic）に確定し（2026-09-18）、ALB のリスナールールで**パス単位の許可リスト**を作る（TA-06 の 5 節）。Strapi（`cms.comegin.com`）と n8n（`n8n.comegin.com`。案）には訪問者向けのパスが無い。
- **ngrok に残るのは Astro dev サーバーの共有（TA-01 の経路 6）だけ**である。ADR-12 の時点では、クラウドの Mautic・Chatwoot からオンプレの n8n へ届く Webhook（経路 5）も ngrok を通っていたが、**ADR-16 で n8n が AWS に移り、Webhook は VPC の中で完結するようになった**（**ADR-21 で n8n がオンプレに戻り、Webhook は WireGuard 越しに届く。ngrok は使わない**）。
- **開発環境は今のままローカルで動く。** オンプレのスタックは `127.0.0.1` にバインドされたままで、ブラウザからの連携は開発機の中で完結する。

**エージェント（Claude Code）は MCP で開発環境と本番の Strapi・Mautic・Chatwoot・Umami・n8n を読み書きする**（**2026-10-06 の注記: Umami〈`I-17`〉は ADR-25 で廃止。GA4 は `I-22` で読むだけ**。`R1` の 2026-09-19 の決定。AA-05 の ADR-15 で Mautic・Chatwoot・Umami、ADR-16 で Strapi・n8n を加えた。同日の ADR-14 の「開発環境だけ」を置き換えた）。I-03 I-04 I-16 I-17 は開発環境用と本番用に 2 回登録し（本番は `read_write` まで、専用アカウントのトークン。`strapi-prod` は Admin トークンの権限で下書きまでに絞る。ADR-17）、I-22（OpenSEO）はローカルだけに接続する。n8n の MCP（`n8n-prod`）はワークフローの定義を運び E-ID を運ばないため、カタログには載せない（TA-07 の 3.3）。本番への作用は BA-05 の承認ゲートに従い、**本番の記事の公開は `R2` が本番の管理画面で行い（ADR-17）**、公開サイトへの反映は人間が配信を承認し、n8n のワークフローの本番での有効化も人間が行う（TA-07 の 6・7 節）。したがって**ALB の機械向けの API を通るのは、エージェントの本番用の MCP（I-03 I-04 I-16 I-17 と `n8n-prod`）と、ビルドが本番の Strapi を読む経路（I-09）**になる。**n8n の決定論的な処理は ADR-16 で VPC の中に移り、ALB を通らない。**（**ADR-21 の注記**: Strapi と n8n の本番がオンプレに移ったため、ALB の `cms.`・`n8n.` のホスト名と、上の「Strapi の `/mcp`・`/api/*` と n8n の `/mcp-server/http`」を ALB で開ける話は無くなった。`strapi-prod`・`n8n-prod` の接続先はオンプレの `127.0.0.1:1338`・`127.0.0.1:5679`。**代わりに、オンプレの n8n が Mautic・Chatwoot の API を呼ぶ処理〈`I-19` など〉は ALB の公開ホスト名〈`mkt.`・`chat.`〉を通る**。トンネルを通れるのは RDS の 5432 だけで、認証は製品側〈Chatwoot の `api_access_token`・Mautic の OAuth2 client_credentials〉と WAF のレート制限で守る。）

**ローカルから AWS の API への呼び出しは、中から外への送信になる。** ブラウザでのログインができないため、**ALB では認証をかけずに API のパスだけを通し、製品側の認証（Chatwoot の `api_access_token`、Mautic の OAuth2 client_credentials、Strapi の Admin トークンと読み取り専用の API トークン、n8n の MCP のアクセストークン）と WAF のレート制限で守る**（TA-06 の 5.2）。オンプレの送信元 IP は固定ではないため、IP で許可する方式は採らない（`R1` の 2026-09-18 の判断）。対象は Chatwoot の `/api/v1/accounts/*`・`/api/v2/accounts/*`、Mautic の `/api/*`・`/oauth/v2/token`、**Strapi の `/mcp`・`/api/*`（Content API）と n8n の `/mcp-server/http`**（後者 2 つは ADR-16）だけで、**Mautic の API の Basic 認証（`api_enable_basic_auth`）は無効のまま**にする（有効にするとパスワードでログインする口が管理者の認証の外に出る）。**Umami は `/mcp` だけを開ける**（**ADR-25 で Umami を廃止したため不要**。Umami v3.4.0 以上の MCP エンドポイント。閲覧専用ユーザーで発行した API キーで認証する。`/api/*` と `/api/auth/login` は管理者の認証の内側に残る。TA-06 の 5.4）。

**監視アプリ（Next.js）から Claude Code への指示の経路も連携点カタログに載せない**（ADR-14、TA-07 の 3.3）。この経路が運ぶのは管理者の指示と実行の経過であって E-ID ではなく、E-ID を運ぶのはその先の MCP（I-03 I-04 I-16 I-17 I-22）である。**ADR-17 で、エージェントを使う定期処理（観測の日次バッチ・`I-13` の起票・公開された記事の確認・誤った書き込みの突き合わせ）も監視アプリが起動することになった**（TA-07 の 3.5）が、起動の経路が運ぶものは手動の指示と同じであり、カタログに載せない扱いは変わらない。監視アプリの実行記録を `E-15 AgentRun` の正本にすると決めた場合は、その時点で連携点として追加する、としていた。**ADR-18 で正本にすると決めた**（TA-07 の 3.6）。ただし記録を書くのは監視アプリのサーバー側だけで、書き先も監視アプリ自身のローカルの DB であり、アプリケーションをまたいで `E-15` を運ぶのは「Claude Code（Agent SDK）→ 監視アプリ」の実行の経過だけである。**どの区間を連携点とし、どの I-ID を振るかは未決定**（5 節）。

**管理者の認証の経路（`admin-auth` → Google Workspace）は連携点カタログに載せない。** カタログは E-ID を運ぶ連携を棚卸しするものであり、ログインの経路は ALB や ngrok と同じく**到達の制御**に属する（TA-01 の経路 17、TA-06 の 5.2.1 で扱う）。

**`I-21`（n8n → Amazon SNS）はこの 2 分類のどちらにも属さない。** 2 分類は「外から中への到達」を扱うものであり、`I-21` は**中から外への送信**にあたるため露出ではない（TA-01 の経路 10）。`I-23`（OpenSEO → DataForSEO）と `I-24`（OpenSEO → 公開サイト）も同じく中から外への送信である。

**OpenSEO（`I-22`）はどちらの経路にも載せない。** UI も MCP も無認証（`local_noauth`）であり、ループバックに閉じていることが唯一の防御だからである（ADR-09）。運用経路に載せると「要認証」の前提が OpenSEO だけ崩れる。GSC の OAuth のコールバックも運用者のブラウザから `http://localhost:3001` に戻るだけで完結するため、トンネルを必要としない。

分離する理由は 3 つ。

- **公開経路は当然に攻撃対象になる。** 管理画面が同じホスト名の下にあると、トラッカーの URL から管理画面の所在が推測できる。
- **エージェントの MCP は運用経路側である。** AA-03 の 2.3 で MCP を stdio 前提にしたため、**MCP は本来トンネルに載らない**（プロセス間通信でポートを使わない）。HTTP トランスポートで運用する場合のみ運用経路に現れ、そのときは固定 Bearer（`MCP_AUTH_TOKEN`）が唯一の防御になる。
- **BA-05 の `禁止` 分類（権限の付与・剥奪、アカウント操作）に到達できるのは運用経路だけ**である。公開経路からこの分類に届く導線を作らない。

**カタログの「発信元」列は、この 2 分類と対応している。** 発信元が `ブラウザ` の行（I-05〜I-08 と **I-25**、**I-29**〈利用者のブラウザ → `points-api` のポータル。2026-10-03 に追加〉）は公開経路（**うち I-06 だけが ALB を通らない**）、発信元が `エージェント` の行（I-03 I-04 I-16 I-17）は運用経路。**ただし I-22（エージェント → OpenSEO）だけはどちらにも載せない**（ホスト内で閉じる。上記）。n8n が受ける Webhook（I-11 I-12）は発信元が上流システムで、**本番では VPC の中の内部経路で届く**（ADR-16。**ADR-21 で、WireGuard 越しにオンプレの `10.99.0.2:5680` へ届く経路に変わった**。開発環境ではホスト内から直接叩ける）。ADR-12〜ADR-15 の間は n8n がオンプレにあり、この Webhook は必ず ngrok の公開経路を通っていた。**GitHub のように VPC の外から n8n に Webhook を送る必要が出た場合は、そのパスだけを ALB の許可リストに加える**（TA-06 の 5.3）。I-13（ローカル → GitHub。ADR-17 で n8n から移した）は中から外への送信であり、露出ではない。GSC は Webhook を送らず、OpenSEO が取りに行く。

### 1.4 経路の構成から生じる制約

- **（2026-10-06 の注記）ADR-21 で、この項は成り立たなくなった。** 本番の n8n がオンプレに戻ったため、**本番の Webhook（`I-11` `I-12`）は再び開発機（オンプレのマシン）・回線・WireGuard・プロキシ・n8n の死活に依存する。** 止まるのは ADR-12〜ADR-15 の ngrok のトンネル断と同じ形で、Mautic・Chatwoot の側に送信の失敗が残るだけで静かに欠ける。ただし ngrok の固定ドメインの契約には依存せず、**経路は WireGuard の 1 本**になった。縮退運転は DD-07 の 2.5。以下は ADR-16 の記述である。
- **本番の Webhook は開発機の死活に依存しない**（ADR-16）。ADR-12〜ADR-15 の間は、ngrok のトンネルか開発機が落ちると n8n への Webhook（I-11 I-12）が止まっていた。n8n が AWS に移ったため、止まるのは本番の n8n のタスクが止まったときだけになる。**ただし Webhook の取りこぼしは静かに起きる**（Mautic・Chatwoot の側に送信の失敗が残るだけ）ため、本番の n8n の死活は `agent/ops-watcher` の監視対象に含める（CloudWatch のアラーム。TA-05）。
- **ALB・ECS・RDS の障害では、旧設計のトンネル断と同じ形の欠測が起きうる。** ブラウザからの送信（I-05 I-06 I-07）は失敗しても黙って捨てる設計にしてあるため、**サイトは壊れないがデータだけが欠ける**。この欠測を「改善」と誤認しない歯止めが AA-04 の暴走条件 3 にあたる。
- **ホスト名は固定である**（`comegin.com` のサブドメイン。TA-06 の 5.1）。旧設計では ngrok の固定ドメインが必要だったが、公開経路については ADR-12 で不要になった。**n8n の Webhook の受け口も ADR-16 で ngrok の固定ドメインが要らなくなった。** 代わりに、Mautic・Chatwoot に登録する送信先を VPC の内部の名前にする（ECS Service Connect か Cloud Map。方法は TA-06 の 11 節で未決定）。**（ADR-21 で決着）送信先は WireGuard の固定のアドレス `http://10.99.0.2:5680/webhook/mautic-event`・`/webhook/chatwoot-event` になる。内部の名前の方式は要らない。** 本番の n8n の `N8N_WEBHOOK_URL` は `http://<WG_ADDRESS>:5680/`（`onprem/n8n/compose.yml`。`WG_ADDRESS` は `10.99.0.2`）で、開発環境の値（ngrok のトンネルの URL）とは別である。
- **URL を合わせる対象が複数ある。** `SITE_URL` / `PUBLIC_UMAMI_BASE`（**ADR-25 で廃止。代わりの `PUBLIC_GA4_MEASUREMENT_ID` は URL ではなく、合わせる対象から外れる**） / `PUBLIC_CHATWOOT_BASE` / `PUBLIC_MAUTIC_BASE` / **`PUBLIC_CALCOM_BASE`** / **`PUBLIC_CONSENT_BASE`** / `N8N_WEBHOOK_URL` / `MCP_ALLOWED_HOSTS` / Vite の `allowedHosts`（`.claude/CLAUDE.md`、DD-02 の 1.1）。1 つでもずれると連携が静かに失敗する。**2026-10-01 に 2 つ増えた**（`I-25` と同意の受け口）。揃える対象が増えるほど、1 か所から生成する仕組みの必要性が上がる（5 節）。
- **公開経路の到達先が 3 つから 5 つに増えた**（2026-10-01）。`cal.comegin.com`（`I-25`）と `consent.comegin.com`（同意の受け口）が加わり、**ALB の許可リストと WAF のレート制限の対象も増える**（TA-06 の 5.3・5.5）。許可リスト方式は、パスを足し忘れるとその機能が止まる側に倒れる（管理画面が開く側には倒れない）ため、デプロイごとの確認（TA-06 の 8 節）の対象に加える。
- **PostHog だけは AWS を通らない**（SaaS のためブラウザから直接到達する）。したがって **PostHog への送信だけは AWS 側の障害に影響されない**。Umami と PostHog の数字が乖離する原因の 1 つになりうるので、乖離を調べるときは真っ先に ALB と Umami の稼働状況を確認する。**（2026-10-06 の注記）ADR-25 で Umami を GA4 に置き換えたため、GA4 も PostHog も AWS を通らない。** 両者の乖離は ALB では説明できず、片方だけが 0 なら、そのタグ（または同意の実装）の欠測を疑う（AA-04 の暴走条件 #10）。

## 2. 上流 API の落とし穴

エージェントが触る API の制約を、連携設計に効く形でまとめる。詳細は各 MCP の `README.md`（`backend/chatwoot-mcp/README.md`、`backend/mautic-mcp/README.md`）にある。

### 2.1 Chatwoot

| 落とし穴 | 連携設計への影響 |
|---|---|
| `Rack::Timeout` により 15 秒でリクエストを打ち切る | 期間の広いレポート・全文検索を 1 回で要求しない。観測の契約は月次より長い期間を 1 回で取らない（DA-02 の 5.2） |
| 起動直後の 1 回目が 500 になることがある | 3 秒待って 1 度だけ再試行する。再試行しても失敗したら `E-15 AgentRun` に `failure` として残し、その日の観測をスキップする |
| **ページ件数がサーバ側で固定**（会話 25 / コンタクト 15 / メッセージ 20 / 監査ログ 25） | クライアントから件数を増やせない。観測の契約には件数ではなく**ページ数の上限**を書く |
| 会話 ID は画面表示の `display_id`（内部 ID とは別） | 他システムに会話 ID を保存するときは必ず `display_id` を使う（後から人間が画面で照合できるようにするため） |
| チームを変更すると、そのチームに属さない担当者が自動的に外れる | `chatwoot_update_conversation` はチーム → 担当者の順に適用する。反映されなかった場合は警告が返るので、エージェントは警告を無視しない |
| 401 が「トークン不正」と「権限不足」の両方を意味する | 401 を一律に「認証の失敗」と解釈して再認証を試みない。権限不足の場合は再試行しても通らないため、その項目をスキップする設計にする |
| `api_access_token` が**ユーザーに紐づく** | 自動処理には専用のエージェントユーザーを作る。権限も操作履歴もそのユーザーのものになる（AA-03 の 2 節） |
| コンタクト一覧（検索なし）は email / 電話 / identifier のいずれかを持つものだけを返す | 「全コンタクト数」を一覧の件数から数えない |
| 会話一覧で `q`（本文検索）を指定すると `status` の絞り込みが無視される | 未解決の会話を本文検索で絞る、という組み合わせは成立しない |

### 2.2 Mautic

| 落とし穴 | 連携設計への影響 |
|---|---|
| **`PUT` は存在しない ID で新規作成してしまう** | **更新は `PATCH` 相当のみ。`mautic-mcp` は `PUT` を使うツールを 1 つも公開していない**（この制約に触れる経路をエージェントに与えない、という形で実装されている） |
| **`GET /api/smses/{id}/contact/{cid}/send` は GET でも SMS を送信する** | **`mautic-mcp` の対象外にしてある。** 参照系のつもりで呼んだ GET が外部に SMS を送るため、`sanitize()` でも `ACCESS_LEVEL` でも防げない（`read_only` でも参照系として登録されてしまえば呼べる）。**除外したこと自体が唯一の防御**であり、3 つ目の MCP サーバを作る場合も「GET だが副作用を持つ API」を同じ理由で除外する |
| 500 の主因は不正な `order_by` | 並び替えの指定はエージェントに自由入力させず、ツール側で許可値を限定する |
| 0 件のとき `[]` を返す（`null` ではない） | 空配列を「取得失敗」と誤認しない（失敗はエラーとして返る）。AA-04 の暴走条件 3 と対応する |
| OAuth2 client_credentials にはユーザーが紐づかない | 権限は Mautic 側のロールで決まる。参照専用のロールを割り当てる（DA-05 の 4.1） |
| メール送信・セグメント追加・キャンペーン追加などの操作系 API が対象外 | BA-05 が `承認` 分類にしているメール送信は、そもそも MCP ツールとして存在しない。**承認ゲート以前に手段が無い**状態になっている（AA-03 の 3 節で `agent/lead-ops` の権限を設計するときの前提） |

### 2.3 エージェントに触らせてはいけない API

上の 2 表のうち、**承認ゲートでは守れない 2 つ**を明示する。

- **Mautic の `PUT`。** 存在しない ID を渡すと更新のつもりで新規作成される。エージェントが ID を取り違えた場合、「更新が失敗した」ではなく「意図しないレコードが増えた」という形で失敗するため、失敗に気づけない。承認者が「このコンタクトを更新する」という提案を承認しても、実際に起きるのは別のことになりうる。**承認の対象と実行の結果が一致しない操作は、承認では守れない。**
- **Mautic の SMS 送信 API（GET）。** GET は参照であるという前提が破られており、`read_only` の `ACCESS_LEVEL` でも（ツールとして登録されていれば）呼べてしまう。BA-05 は「外部に露出する操作はすべて `承認`」としているが、この API は参照系の見た目をしているため分類の網から漏れる。

どちらも **MCP のツール一覧に載せない**ことで対処している。これは AA-03 の権限設計の原則（`ACCESS_LEVEL` は許可されないツールを登録しないことで実装する）と同じ形であり、**「危険な操作は分類するのではなく、到達できなくする」**という一貫した方針になっている。

## 3. 未配線・未着手の連携の実装方針

これが次フェーズの着手リストにあたる。手段は 5 択（Astro のインテグレーション / MCP ツールの直接呼び出し / n8n のワークフロー / Strapi のプラグイン・ライフサイクル / 手作業の設定）。

### 3.1 ブラウザ側トラッカー（I-05 I-06 I-07 I-08）

**手段: Astro のインテグレーション（`Layout.astro` へのスクリプト設置）＋ ALB の公開経路。n8n も MCP も使わない。**

**4 本とも、到達先が AWS か SaaS かで経路が分かれる。**（**2026-10-06 の注記: ADR-25 で `I-05` は GA4〈SaaS〉になり、AWS を通るのは `I-07` `I-08` だけになった。ALB が止まっても `I-05` `I-06` は生き残る。ただし同意済みの訪問者に限る〈冒頭の ADR-25 の注記〉**）Umami・Chatwoot・Mautic は本番では AWS にあるため **ALB の固定ホスト名経由で到達する**（1.3、ADR-12）。PostHog だけが SaaS のためブラウザから直接到達する。したがって**ALB やその後ろのシステムが止まると I-05 I-07 I-08 は止まり、I-06 だけが生き残る**。

| 連携 | 到達経路 | 実装方針 | 前提 |
|---|---|---|---|
| **I-05 GA4**（2026-10-06。ADR-25） | **直接（SaaS）** | `Layout.astro` に **gtag.js を直接置く**（`https://www.googletagmanager.com/gtag/js?id=<測定 ID>`。**GTM は使わない**）。**同意（`comegin_consent` の `s=granted`）の前はタグを読み込まない**。同意の後に `gtag('consent','update',{analytics_storage:'granted'})`。`ad_storage` `ad_user_data` `ad_personalization` は常に `denied`（Consent Mode v2 の basic）。測定 ID は `PUBLIC_GA4_MEASUREMENT_ID`（秘密値ではない）で、**未設定ならタグを出さない。開発環境では設定しない**。CSP に Google の配信元を足す（DD-02） | 本番の GA4 のプロパティ（`R1` が作る。`middleware/ga4/README.md`）／同意の実装（DD-02 の 3.3・8 節） |

### 3.2 Astro ← Strapi のデータ取得（I-09）

**手段: Astro のインテグレーション（ビルド時の fetch）。MCP は使わない。**

- **ビルドはオンプレで行い、本番の Strapi の REST API（Content API）を読み取り専用の API トークンで呼ぶ**（ADR-16）。読み先は ADR-14 で本番の Strapi とし、ADR-15 でオンプレの Strapi に変え、ADR-16 で再び本番に戻した（記事の正本が本番の Strapi に移ったため）。配信は人間が承認する（DD-05 の 1 節・3 節）。
- **画像はビルド時に `dist/` へ取り込む**（ADR-11）。本番の Strapi のメディアは S3 にあり、公開ページから Strapi と S3 へのリクエストは出さない。
- Strapi の REST API をビルド時に呼び、`E-04` から記事ページを生成する。**MCP 経由にしない**（MCP はエージェントがモデル経由で使うための層であり、ビルドという決定論的な処理に挟むと `CHARACTER_LIMIT` による件数削減や `sanitize()` の省略が成果物に影響する）。
- `SITE_URL` 未設定のビルドは意図的に例外で停止する（`frontend/verdant-virgo/astro.config.mjs`）。この挙動は**変えない**（未設定だと sitemap と canonical に localhost が焼き込まれ、警告なく公開されるため）。
- Strapi が停止している状態でのビルドは**失敗させる**（記事 0 件のサイトが黙って公開されると、検索エンジンに空のサイトがインデックスされる）。

### 3.3 Webhook の受け口（I-11 I-12 I-18）

**手段: n8n のワークフロー。**

> **（2026-10-06）ADR-21。** 本番の n8n はオンプレにあり、Webhook は **WireGuard 越しにオンプレのリバースプロキシ（`10.99.0.2:5680`）へ届く**。下の「本番では、Webhook は VPC の中で n8n に届く」は ADR-16 の記述である。**プロキシが通すのは `POST /webhook/*` だけ**（エディター・API・MCP・テスト用の Webhook は 404）で、送信元は `10.99.0.1` だけ。本文・署名ヘッダーは書き換えずに通すため、`I-11` `I-12` の署名の検証（Raw Body の HMAC）は n8n のワークフローの中で行い続ける。**ワークフローは作成済み・開発の n8n で動作確認済みで、本番の取り込みと公開（人間・`R1`）が残る**（`middleware/n8n/workflows/README.md`）。公開されていないワークフローの `/webhook/*` は、n8n が 404 を返す。

- Mautic・Chatwoot のどちらも webhook を送れるが、**受け口になるアプリケーションが n8n しか無い**（Astro は静的サイト、Strapi は自前の API を増やす必要がある）。
- **本番では、Webhook は VPC の中で n8n に届く**（ADR-16）。Mautic・Chatwoot・n8n がすべて AWS にあり、送信先を VPC の内部の名前にするため、ngrok も ALB も通らない。ADR-12〜ADR-15 の間は、オンプレの n8n へ ngrok の固定ドメイン経由で届く設計だった（TA-01 の経路 5）。開発環境では Mautic と Chatwoot がホスト内にあるため、n8n を直接叩ける。n8n のエディターは運用経路（ALB の `admin-auth` の内側）であり、**Webhook パスと UI を同じ入口に混ぜない**（1.3）。
- n8n を経由させる理由は AA-05 の ADR-05 に書く。要点は「エージェントが直接ポーリングすると、実行のたびに取得範囲が変わって `E-12` が比較不能になる」こと。**ADR-17 で、エージェントを使う定期処理（観測の日次バッチなど）の起動は監視アプリに移った**が、Webhook の受け口とエージェントを使わない決定論的な処理は n8n のままである。監視アプリから起動する定期処理では、取得の範囲を**スケジュールの定義に固定して書く**ことで、ADR-05 の理由を守る（TA-07 の 3.5）。
- **n8n のワークフロー作成・変更は `承認` 分類**（BA-05）。ワークフロー自体が「承認なしで実行される操作の定義」になりうるため、エージェントが自分でワークフローを作って承認ゲートを迂回することを防ぐ。**本番では、エージェントは `n8n-prod` でワークフローを置くところ（作成と更新）までで、有効化は人間が本番のエディターで行う**（ADR-16。BA-05 の「n8n のワークフローの本番での有効化」、`承認`・`R1`）。
- I-18（Mautic → PostHog の書き戻し）は**越境の可否が決まるまで実装しない**（DA-03 と DA-05 の未決定事項）。ワークフローを作れる状態にはしておくが、有効化しない。

### 3.4 提案の起票（I-13）と通知

**手段: エージェントがファイルを書き、ローカルから GitHub に起票する（ADR-17）。git 操作はエージェントが行わない。**

**（2026-09-19 に ADR-17 で変更）** 当初は「エージェントがファイルを書き、n8n が搬送する」としていた（ADR-05）。ADR-16 で n8n が AWS に移ると、改善提案のファイル（`docs/proposals/`）があるローカルの Git を本番の n8n から読めなくなるため、**起票はローカルで、監視アプリの定期実行から起こす**ことにした（TA-07 の 3.5）。

- エージェントは `docs/proposals/<proposal_id>.md` を**書くところまで**を担当する（AA-03 の 4 節。リポジトリのルールで状態変更系の git コマンドが使えないため）。
- コミットと PR 作成は人間、または明示的な指示を受けた場合に限る。ローカルから GitHub API で起票する経路（I-13）を用意する場合も、**起票するのは提案であって承認ではない**（PR を作ることと PR を承認することは別の権限）。起票に使う GitHub の資格情報には、PR のレビュー承認とマージに届く権限を与えない（AA-03 の 5.4）。
- **起票の主体をエージェントにするか、エージェントを使わないローカルの処理にするかは未決定**（ADR-17 は両方を挙げている。5 節）。エージェントにすると、上の「git 操作はエージェントが行わない」と、AA-03 の 5.3 の安全装置（エージェントは PR を作れない）が崩れる。
- **通知は GitHub の PR の機能に任せる**（**`R1` の 2026-09-17 の決定**。DA-04 が未決定として残していた「通知先を Chatwoot にするか」を解決した）。`E-14 ApprovalRecord` の正本が PR のレビューである以上、**承認を求める通知も正本と同じ場所から出る**のが一貫する。Reviewer に `R2` を指定すれば、起票・レビュー依頼・マージ・クローズのいずれも GitHub の標準通知で届く。**通知のための連携点（旧 `I-14`）は設けない。**
- **Chatwoot を社内通知に使わない。** Chatwoot は「Web 接客 / チャット」であり（リポジトリルートの `README.md`）、顧客対応が用途である。改善提案の通知をここに置くと、`CAP-12` のレポート（未解決件数・応答時間）に内部の会話が混ざり、`E-10 Conversation` の正本も汚れる。加えて **`agent/conversation-triage` の取得範囲（直近の未解決の会話）が承認待ちの提案で埋まり、承認の滞留がそのまま顧客対応の見落としに変換される**（AA-03 の 3 節の取得範囲と衝突する）。
- **ただし `private` を固定する規則は残す。** `agent/conversation-triage` が会話の一次切り分けで書く社内メモ（`I-03`。**これは顧客対応の中の社内メモであり、用途として正しい**）では、**`private` を固定値 `true` とし、エージェントが指定できるパラメータにしない**。**`private=false` は顧客に即時送信される**ため、誤って顧客に送る事故が構造的に起きない形を維持する。
- **（2026-09-19 に ADR-17 で判明・決定）この規則は `chatwoot-mcp` では実装されていなかった。** 今の `chatwoot_send_message` は社内メモと顧客への送信を 1 つのツールで兼ね、`private` の既定値は `false`（顧客に送信）である。ADR-16 で本番の送信を許したため、社内メモのつもりで `private` を付け忘れると顧客に届いて取り消せない。**ADR-17 で、社内メモ専用のツールを `chatwoot-mcp` に足すか、社内メモ用の登録を分けるかのどちらかで、社内メモだけを使うエージェントに `chatwoot_send_message` を見せないことにした**（どちらにするかは未決定。実装はまだ。TA-07 の 3.3・9 節）。

### 3.5 Google Search Console（I-15）

**手段: OpenSEO の OAuth 連携（`R1` の 2026-09-18 の決定。ADR-06・ADR-09）。n8n は使わない。**

当初は「手作業の設定 → その後 n8n のワークフロー」とし、Search Console API の認証情報を n8n の資格情報ストアに置く設計だった。**GSC を OpenSEO に統合したため、取得は OpenSEO が行い、エージェントは OpenSEO の MCP（`I-22`）で読む。**

| 順 | やること | 担当 | 備考 |
|---|---|---|---|
| 1 | Search Console に**ドメインプロパティ**（`sc-domain:comegin.com`）を登録し、Route 53 の TXT レコードで所有権を確認する | **人間（`R1`）** | **公開 URL（apex か `www` か）の確定を待たない。** ドメインプロパティは両方を覆う |
| 2 | Google Cloud で Search Console API を有効にし、OAuth クライアント（Web アプリケーション）を作る。リダイレクト URI は `http://localhost:3001/api/gsc/oauth/callback` | **人間（`R1`）** | **同意画面は「内部」**（`comegin.com` は Google Workspace。TA-04 の 8.3）。「外部・テスト中」だとトークンが 7 日で失効するため使わない |
| 3 | OpenSEO の環境変数に `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` / `BETTER_AUTH_SECRET`（32 文字以上）を置き、コンテナを作り直す | **人間（`R1`）** | 秘密値。エージェントは読めない（`PreToolUse` フック） |
| 4 | OpenSEO の画面で「Connect with Google」を押し、プロパティを OpenSEO のプロジェクトに結び付ける | **人間（`R1`）** | **OAuth の同意はエージェントに行わせない**（BA-05 で `禁止`） |
| 5 | `agent/seo-auditor` が OpenSEO の MCP で実績を取り、`E-12`（`source: gsc`）に正規化する | エージェント | **GSC のデータは 2〜3 日遅れて確定する**。取り込みは「3 日前までの確定データ」を対象にする（DA-04 の 4 節） |

- **GSC の資格情報は n8n に置かない。** OpenSEO の DB に `BETTER_AUTH_SECRET` で暗号化されて置かれる（TA-04 の 2 節）。n8n に同じ資格情報を二重に持たせない。
- **OpenSEO の順位計測（DataForSEO の SERP）は GSC の代わりにならない。** 表示回数・CTR・実際の検索クエリは GSC にしかない。逆に、**まだ表示されていない狙いのキーワードの順位は GSC では測れない**ため、両者は補完関係にある（DA-02 の 4.3）。
- **URL 検査（インデックス登録の状態・Google が選んだ canonical）も同じ経路で取れる。** `SITE_URL` 未設定のビルドが localhost の canonical を焼き込む事故（TA-02 の 7 節）を、**公開後に Google 側から確認する手段**になる。

**SEO が事業の目的でありながら、検索順位を測る手段が 1 つも無い**、という ADR-06 の矛盾は、この経路が通った時点で解ける。

### 3.6 通知（I-21）

**手段: n8n のワークフローから Amazon SNS に発行する。本番は SNS、開発は MailHog。**

**`R1` の 2026-09-17 の決定。** 顧客からの要求（Mautic のフォーム送信・Chatwoot の会話開始）と、監視の検知を、**運用者のメールアドレスへ通知する**。

| 項目 | 値 |
|---|---|
| トピック | **2 本に分ける。** `comegin-lead-alert`（顧客からの要求）／ `comegin-ops-alert`（監視・障害） |
| リージョン | `ap-northeast-1`（東京）。**越境しない** |
| 宛先 | トピックごとの Email サブスクリプション（購読は**受信者の手作業**で確認する） |
| 開発環境 | MailHog（`backend/mautic-system` の 1025 / 8025）。SNS は使わない |
| 載せる範囲 | **種別・会社名・各システムの ID・流入記事・受付時刻のみ**。email・氏名・本文は載せない（DA-05 の 1.3） |
| 料金 | 月 1,000 通まで無料。超過分は $2.00/100,000 通。**CV が月 100 件規模なら $0** |

トピックを 2 本に分ける理由は 3 つ。

- **宛先を分けられる**（購読はトピック単位のため、1 本にまとめると宛先も 1 つになる）。
- **緊急度が違う。** リード通知は営業時間内に見れば足りるが、障害通知は即時性を要する。
- **無料枠の消費が読める。** 監視通知を「状態が変わったときだけ」に絞らないと、リード通知の枠まで食い潰す。

**エージェントは `I-21` を起動しない。** 通知の発行は n8n のワークフローが行い、その起動条件は n8n 側にある（AA-03 の 5.2）。ADR-05 の時点では `I-13` も同じ扱いだったが、ADR-17 で `I-13` はローカルに移った。**通知はエージェントを使わない決定論的な処理であり、ADR-17 の後も本番の n8n に残る。**

> **（2026-10-06）ADR-21。** 本番の n8n はオンプレにあり、ECS のタスクロールが使えない。**認証は IAM ユーザー `comegin-<env>-onprem-n8n-sns` のアクセスキー**（人が発行し、本番の n8n の画面から AWS 型の資格情報として入れる。RDS に暗号化されて保存される。Claude Code の環境変数には引き継がない）。権限は ops・lead の 2 トピックへの `sns:Publish` に限る点は変わらない。**加えて、n8n のスケジュール実行のハートビート用に `cloudwatch:PutMetricData`（名前空間 `ComeGin/OnpremN8n` に限る）を同じユーザーに足す**（`cloud/stacks/iam.yaml`。**ユーザーとポリシーの名前は変えない**）。**与えないもの**: 購読の変更・トピックの設定変更、アラームの変更・無効化、監視アプリの名前空間（`ComeGin/Onprem`）への送信（オンプレの生存を偽れない）。詳細は DD-04 の 8.7。

**n8n に渡す IAM 権限は `sns:Publish` のみとし、対象トピックを限定する。** `sns:Subscribe` や `sns:SetTopicAttributes` を与えると、**n8n が通知先を自分で書き換えられる＝自分への通知を止められる**（AA-03 の「エージェントは自分の実行条件を変更できない」と同じ形の穴になる）。設計は TA-04。

### 3.8 競合・検索市場調査（I-22 I-23 I-24）

**手段: セルフホストの OpenSEO を MCP で呼ぶ（ADR-09・ADR-10）。n8n は使わない。**

| 連携 | 実装方針 | 前提 |
|---|---|---|
| I-22 エージェント → OpenSEO | Claude Code の MCP 設定は `http://127.0.0.1:3001/mcp`（2026-09-18 に付け替え済み）。接続するのは `agent/seo-auditor` / `agent/keyword-researcher` / `agent/knowledge-scout` の 3 本だけで、使ってよいツールをエージェント定義の許可リストで限る（AA-03 の 2.4）。**2026-10-06 に ADR-25 で `agent/analytics-reporter` が加わり 4 本になった**（GA4 の集計値を読む 5 本と `list_projects`・`get_project_context` だけ。費用の出るツールは持たない）。**OpenSEO と GA4 の接続（Google Cloud での Analytics Admin API・Data API の有効化、リダイレクト URI `http://localhost:3001/api/ga4/oauth/callback` の追加、画面の Connect with Google）は人間（`R1`）が行う**（`middleware/open-seo-main/docs/SELF_HOSTING_GOOGLE_ANALYTICS.md`） | `comegin.com`・日本・日本語のプロジェクトの作成（ローカルには米国市場の `Default` しか無い） |
| I-23 OpenSEO → DataForSEO | 設定済み。**費用の上限は DataForSEO の前払い残高**。月次予算は 10 USD（暫定。ADR-10） | 残高のチャージは人間（`R1`） |
| I-24 OpenSEO → 公開サイト | サイト監査は**自サイトのみ**。実行は人間（`R1`）が行い、エージェントは結果の参照だけを許可する | 公開サイト（`I-20`）が存在すること |

- **n8n を挟まない理由。** ADR-05 は「決定論的な処理は n8n、判断を要する処理はエージェント」と境界を引いた。キーワード調査と競合調査は**どのシードで、どの競合を、どこまで深く調べるかという判断そのもの**であり、エージェントの側に属する。取得範囲の固定（ADR-05 の理由 1）は、エージェント定義の許可リストと費用の上限で代える。
- **GSC の実績の取得（`I-15`）だけは決定論的**であり、将来 n8n の日次バッチに寄せる余地があるとしていた。**ADR-16・ADR-17 の後、この余地は無くなった。** 本番の n8n は AWS にあり、ループバックに閉じた OpenSEO（`127.0.0.1:3001`）に届かない。観測の日次バッチは監視アプリの定期実行が起動し、`agent/seo-auditor` が OpenSEO の MCP で読む（5 節で決着とした）。
- **OpenSEO の中の保存済みキーワードとプロジェクトコンテキストは正本にしない**（ADR-09）。採用したキーワードは `agent/keyword-researcher` が Strapi の `E-01` に書く（`I-16`）。

### 3.9 オンライン面談の予約（I-25）

**手段: Cal.com を AWS でセルフホストし、無料相談の完了画面（`/contact/thanks`）に予約の枠を埋め込む**（**2026-10-06 の注記。ADR-24: セルフホストをやめ、SaaS の Cal.com を埋め込む。ECS・`cal.comegin.com`・Google の OAuth クライアントの自前の発行は不要になる見込み。以下は ADR-19 の記述**）（BA-04 の商談プロセスの段 2）。ユーザーが 2026-10-01 に商談の流れ（C5）と、**Cal.com をセルフホストで動かすこと**を確定したことで加わった連携である。

| 連携 | 実装方針 | 前提 |
|---|---|---|
| I-25 ブラウザ → Cal.com | **Cal.com を ECS on Fargate で動かす**（`cal.comegin.com`。他の本番システムと同じ扱い。TA-06 の 3.1）。完了画面に埋め込みのスクリプトを置く。**スクリプトは `Layout.astro` ではなく完了画面にだけ置く**（全ページに外部スクリプトを足さない。`CAP-09` の Lighthouse のしきい値への影響を 1 ページに閉じる） | **Cal.com のセルフホストの構築**（イメージ・RDS のデータベース・ALB のホスト名と許可リスト。TA-06）／**空き枠の提供**（`calcom` → Google Calendar API の連携。OAuth クライアントの発行は人間の作業。`R3`）／`I-08`（フォームの送信が成功して完了画面に到達すること） |

- **なぜセルフホストか**（AA-05 の **ADR-19** の決定 1）。SaaS として使う案は **TA-01 の 8 節の「SaaS に依存してよい 2 種類」のどちらにも当てはまらない**（「自前で持つと観測の一巡が遅くなる機能」でも「自前で持てないデータの取得元」でもなく、Cal.com は自前で立てられる）。**基準を緩める代わりに運用対象を 1 つ増やす側を選んだ**（ユーザーの 2026-10-01 の決定）。BA-02 の「外部サービスの判断基準を内製する」方針とも向きが揃う。
- **予約の正本（`E-16`）は VPC の中に留まるが、Google Calendar へは渡る。** セルフホストにしたことで**予約そのものの正本は `ap-northeast-1`** になったが、**予約の成立時に訪問者を Google Calendar の予定に招待する**と決めたため（ユーザーの 2026-10-01 の決定）、**氏名・メールアドレス・面談の日時は Google LLC（米国）に渡る**（DA-05 の 1.2.2）。したがって**訪問者・顧客の個人データが越境する先は PostHog と Google Calendar の 2 つ**になった（TA-01 の 8 節の SaaS 依存の基準そのものは変えていない）。予約の画面の注記（`01-content-spec.md` の 4.6 の 6'-2）は「外部のサービス（Cal.com）に送る」ではなく、**自前の予約システムに送り、予定は Google カレンダーに入る**という 2 段の表現に合わせる必要がある（5 節）。
- **Google Calendar との連携は中から外への送信**であり、露出ではない（1.3 の `I-21` `I-23` と同じ扱い）。**`calcom` が Google Calendar API を呼ぶ**ため、OAuth クライアントは `admin-auth` と GSC と同じ Google Workspace の中で発行する（TA-04 の 8 節と同じ扱い）。**空き時間だけを見せ、予定の件名や参加者を出さない設定にする**（`01-content-spec.md` の 10.5 の B5。ユーザーの作業）。
- **CV の成立より後に置く。** 段 2 は `I-08` の成功の後にしか現れないため、**Cal.com の障害で CV が失われることはない**。`CVR` の定義（DA-02 の 1.2）に手を入れずに済むのは、この順序のためである。
- **読み込みに失敗したときの代替の案内を必ず置く**（`01-content-spec.md` の 4.6 の 6'-2）。この画面が商談プロセスの段 2 の唯一の入口であり、代替が無いと予約もメールもできない行き止まりになる。`I-07` が「ウィジェットが出ないだけ」で済むのと違い、**`I-25` の失敗は商談の機会をそのまま落とす**（DD-02 の 7.3）。
- **ALB の障害で予約も止まる。** SaaS なら影響しなかったが、セルフホストにしたため `I-05` `I-07` `I-08` と同時に止まる（1.4、DD-02 の 1.3）。**意図した取り引きである。**
- **予約されたことを Mautic・Chatwoot に返す経路は設けていない。** Cal.com の Webhook を本番の n8n で受ける案はあり、**運ぶ型は `E-16`（DA-01 の 4.1）に決まった**。**ただし今の設計に、予約を受けて自動で動かす処理が無い**（`R3` は Google Calendar で予定を見る）。必要になった時点で連携点を立てる（5 節）。
- **同意（Cookie）の対象に含めない**（暫定。5 節）。2026-10-01 の決定で同意の対象は PostHog と Chatwoot の 2 つになった（DD-02 の 3.3・4.4）。**予約の枠は同意していない訪問者にも表示する**（`01-content-spec.md` の 8.2・10.4 の K5。同意を条件にすると商談プロセスの段 2 が同意率に依存するため）。**ただし予約に関する PostHog のイベント（`booking_viewed` / `booking_scheduled`。DA-02 の 4.4）は同意後にだけ送る。** **セルフホストにしても Cookie を置くかどうかは変わらない**（同一サイトの Cookie になるだけである）ため、この論点は残る（DD-02 の 7.4）。

**（2026-10-03 に追加）収益化（`I-26`〜`I-30`）は番号を振らず、「本システムの完成後」に置く。** 着手の可否を決めるのが配線ではなく**承認ゲート G-1〜G-3（弁護士・税理士・AWS の規約。BA-05）**だからである。依存は **0**（`points-api` を AWS に置くため）と、Amazon SNS（`points-api` が直接通知する。`I-21` の n8n は経由しない）。

**手順 0（AWS の 5 システムと ALB。ADR-12 の時点では 3 システム）が、観測系のほぼすべての前提になった。** 本番では、ブラウザ側の連携は 1 本残らず ALB の後ろのシステムに依存する（例外は SaaS の PostHog だけ）。旧版ではこの位置に ngrok の常設トンネルがあった。

**OpenSEO の調査（並行）も 0 に依存しない。** OpenSEO はホスト内で閉じており、外に出るのは DataForSEO への問い合わせだけである。**観測（何が起きたか）より先に、企画の入力（何を狙うか）を用意できる**唯一の経路にあたる。

**8（起票）は ADR-17 で 7（n8n）に依存しなくなった。** ADR-05 の時点では n8n が起票を搬送していたため、起票の自動化は n8n の構築を待つ必要があった。ADR-17 で起票がローカル（監視アプリの定期実行）に移り、代わりに**監視アプリ（TA-07。`未着手`）が定期での起票と観測の日次バッチの前提**になった。手動の起票（人間がコミットして PR を作る）なら監視アプリも要らない（AA-04 の 5.2）。

**`I-25`（Cal.com の予約）は 0 と 4 の両方に依存する。** セルフホストにしたため **AWS の実行環境（手順 0）が前提**になり（SaaS のままなら 0 に依存しなかった）、完了画面に置くため `I-08`（手順 4）が通っていなければ訪問者が到達しない（3.9）。手順の番号を振らないのは、**着手の可否を決めるのが配線ではなく人間の作業（Cal.com のセルフホストの構築と Google Calendar の OAuth クライアントの発行、空き枠の提供）だから**である。

**同意の受け口も 0 に依存する**（ALB の後ろの ECS のサービスとして置く。3.9 の下の表には載せない。DD-02 の 8 節）。**手順 5（`I-06` PostHog）の前提が増えた**: 旧版は「同意取得 UI」だけが前提で `0 には依存しない` としていたが、**同意をサーバに記録すると決めた以上、受け口が無ければ同意の記録が残らない**。PostHog への送信そのものは SaaS 直接のままなので、**受け口が落ちていても Cookie があれば送信は続く**（DD-02 の 8.3・8.4）。手順 5 の「0 に依存しない」は、**同意の記録を諦める場合に限って**成り立つ。

- **OpenSEO のランク追跡のスケジュールが Docker 版で動くか未確認。** OpenSEO はスケジュール実行を Cloudflare の cron（`*/5 * * * *`）で起動する作りであり、Docker 上の `vite preview` でこの cron が発火するかをコードからは確認できなかった。**実機で初めて週次の追跡を設定したときに確認する**（`R1` の 2026-09-18 の判断）。確認の方法は「設定した次の期限を過ぎても順位の履歴が増えないか」を見ることであり、**増えなければ週次のランク追跡は人間の手動実行か、別のスケジューラに依存する**。判断者 `R1`。
