# DD-07 異常系と縮退運転

詳細設計層。ID は EA 共通用語集の定義をそのまま使う。横断規約は [DD-01](01-flow-specification-rules.md) を参照する。

02 から 06 が各フローの失敗を個別に扱ったのに対し、この文書は**複数のフローに跨る異常**を扱う。

| この文書が扱うもの | なぜ個別のフローに書けないか |
|---|---|
| 公開経路の断（本番は ALB とその後ろ。旧版は ngrok のトンネル断） | **3 本（`I-05` `I-07` `I-08`）が同時に落ちる。** 1 本ずつ見ても原因に到達しない |
| 沈黙（そもそも動かなかった） | **どのフローにも失敗ログが出ない。** 各フローの観測点では検出できない |
| `E-13` を経由しない変更 | 変更そのものは正常に成功する。**正常な操作の中から異常を見つける**問題 |
| 二重送信 | `I-08` と `I-11` と集計の 3 か所に跨る |
| 縮退運転 | 「何が落ちたら何を止めるか」は連携を跨いだ判断 |

## 1. 異常系の 3 分類

| 分類 | 定義 | 気づきやすさ | 主な検出手段 |
|---|---|---|---|
| **失敗** | 呼んだが失敗した | **気づける**（`fetch.outcome` に残る） | DD-01 の 4 節 |
| **沈黙** | そもそも呼ばれなかった | **気づけない** | 3 節（実行そのものの記録） |
| **偽装成功** | 成功したが、値が事実と違う | **最も気づけない** | 2 節（公開経路の断）・5 節（二重送信） |

**下ほど危険である。** 失敗は次のサイクルで再試行すればよいが、偽装成功は**誤った `E-12` が `evidence` になり、存在しない改善に対する提案が生まれる**（AA-04 の暴走条件 #3 と #10）。

**GSC の OAuth の失効も同じ種類の沈黙である**（2026-09-18 に追加）。OpenSEO は動き続け、Lighthouse も PostHog も正常なまま、**GSC の取得だけが `not_connected` を返して止まる**。同意画面を「内部」にした（TA-04 の 8.3）ため 7 日ごとの失効は起きないが、接続した Workspace アカウントの無効化や同意の取り消しで起きる。`fetch.outcome` には `auth_failed` が残るため、日次の `E-12` を見れば気づけるが、**見る人がいなければ SEO の測定だけが黙って止まる**。検出は TA-05 の項目 10。

**沈黙の最も新しい例が `I-21` の購読解除にあたる**（[04 の 8.4](04-server-to-server-flows.md)）。SNS の通知メールに付く解除リンクを誰かが踏むと、**通知が止まったこと自体が誰にも見えない**。検出は「`Confirmed` の購読数を監視する」しかなく、**その監視の結果を通知経路で知らせられない**という循環が残っている（TA-05 の未決定事項）。

## 2. 公開経路の断（暴走条件 #10）

**2026-09-18 に前提が変わった**（AA-05 の ADR-12）。旧版は「オンプレの Umami・Chatwoot・Mautic へ ngrok の常設トンネルで到達する」前提で、**トンネル断**をこの節の対象にしていた。本番ではこの 3 システムを AWS に置き、入口は ALB になった。**同じ形の欠測は、ALB とその後ろ（ECS のタスク・RDS）の障害で起きる。** ngrok に残るのは n8n への Webhook だけで、そちらの断は 2.5 で扱う。

### 2.1 何が起きるか

ALB、または Umami・Chatwoot・Mautic の ECS サービスや RDS が落ちると、**公開サイトのブラウザから 3 システムに到達できなくなる**（ALB は 1 台に集約しているため、ALB が落ちると 3 本が同時に止まる。TA-06 の 5.1）。

| 連携 | 公開経路の断の影響 | 見え方 |
|---|---|---|
| `I-05` Umami | 止まる | **セッション数が 0 になる** |
| `I-07` Chatwoot | 止まる | ウィジェットが表示されない |
| `I-08` Mautic | 止まる | **CV が 0 になる**（利用者には送信失敗が表示される） |
| **`I-06` PostHog** | **止まらない**（SaaS 直接） | 通常どおり記録される |
| `I-09` `I-10` | 止まらない（同一ホスト内） | 通常どおり |

**サイトは壊れない。データだけが欠ける。** これが最も危険な形の失敗にあたる。

### 2.2 検出

**`agent/ops-watcher` が公開経路の死活を監視対象に含める**（AA-02 の 1.4）。本番では 3 つの変数が ALB のホスト名を指す（DD-02 の 1.1）。

| 検査 | 方法 | 頻度 |
|---|---|---|
| **直接の疎通確認** | `PUBLIC_UMAMI_BASE` / `PUBLIC_CHATWOOT_BASE` / `PUBLIC_MAUTIC_BASE` の 3 つに HTTP で到達できるか | 日次バッチの**冒頭**、および `pnpm lh` の実行時 |
| **間接の徴候** | **Umami のセッション数が 0 かつ PostHog のイベントが非 0** | 日次バッチの観測後 |

**2 つ目が重要である。** 疎通確認は「いま」の状態しか分からない。**落ちていた期間を後から特定するには、Umami と PostHog の乖離を見るしかない**（AA-04 の暴走条件 #10)。

### 2.3 記録

**すべての `E-12` に `tunnel_up` を書く。**

```yaml
tunnel_up: true    # 観測時に公開経路（本番は ALB とその後ろ）が生きていたか
```

- **本番では、`tunnel_up` は「公開経路（ALB とその後ろの 3 システム）に到達できたか」を表す。** 名前は旧版（ngrok のトンネル）のまま残した。名前を変えるかどうかは 8 節に上げる。
- **公開経路を通らない観測（Lighthouse・GSC・PostHog）にも書く。** 値は常に `true` になるが、**書かないと「確認していない」と「生きていた」が区別できない**。
- **`tunnel_up: false` の `E-12` は `evidence` に使わない。** [06 の 1.2](06-proposal-loop-flows.md) の検査 2 に、この条件を含める。

### 2.4 落ちていた期間の `E-12` をどう扱うか

**AA-02 と AA-04 が未決定として残した項目**（欠測として明示的に記録するのか、その日の観測自体を作らないのか）。**この層で決める。**

| 案 | 内容 | 欠点 |
|---|---|---|
| A 観測を作らない | 公開経路が落ちていたら `E-12` を書かない | **「観測が無い日」と「バッチが動かなかった日」が区別できない**（沈黙に化ける。3 節） |
| **B `tunnel_up: false` として記録する** | 値は記録するが `evidence` に使えない印を付ける | ファイル数が増える |

**B を採る。** 理由は、**A は沈黙（最も気づけない異常）を生むため**である。

- 記録することで、「この期間は計測できていなかった」という事実自体が観測になる。
- `fetch.outcome` は `unreachable` になり、`tunnel_up: false` が併記される。**2 つの項目が同じことを言うが、`outcome` は個別の取得の結果、`tunnel_up` は環境の状態を表す**（Lighthouse は `outcome: ok` かつ `tunnel_up: false` になりうる）。

### 2.5 ngrok のトンネル断（本番では Webhook だけ）

**本番で ngrok を通るのは、AWS の Mautic・Chatwoot からオンプレの n8n へ届く Webhook（`I-11` `I-12`。TA-01 の経路 5）だけである。** トンネルが落ちても訪問者から見える機能と計測は止まらないが、次が欠ける。

| 欠けるもの | 見え方 |
|---|---|
| `I-11` `I-12` の受領 | n8n の実行履歴が増えない。Mautic・Chatwoot の側に送信の失敗が残るだけ |
| `I-21`（顧客からの要求の通知） | **通知が届かない。** Mautic・Chatwoot には記録されているため、顧客対応そのものは失われない |
| 日次バッチの入力のうち Webhook 由来のもの | 3 節の「部分的な沈黙」と同じ形で現れる |

- **偽装成功ではなく沈黙に分類する**（1 節）。指標の値を歪めるのではなく、処理が走らない。
- **検出はトンネルの疎通確認（`PUBLIC_N8N_WEBHOOK_BASE` に到達できるか）で行う。** Mautic・Chatwoot が送信に失敗した Webhook を再送するかは確認していない（[04 の 11 節](04-server-to-server-flows.md)）。

## 3. 沈黙の検出

### 3.1 何が問題か

**日次バッチが動かなかった場合、成果物も失敗ログも生まれない。** どの連携の観測点を見ても何も起きていないため、**気づく手段が無い**（DD-01 の 9.2）。

エージェントが 1 本も走らなければ、`E-12` は 0 件、`E-13` も 0 件になる。**これは「改善すべきことが何も無かった」という正常な状態と見分けがつかない。**

### 3.2 検出

**日次バッチの完了そのものを記録する。**

| 記録するもの | 置き場 | 内容 |
|---|---|---|
| バッチの実行 | `docs/audits/ops/<audit_id>.md` | 実行した日時、走ったエージェントの一覧、それぞれの `fetch.outcome`、`tunnel_up` |
| 起票を止めた事実 | 同上 | [06 の 1.2](06-proposal-loop-flows.md) の検査で止めた場合、**どの検査で止めたか** |

**`agent/ops-watcher` が「今日のバッチの記録が無い」ことを検出する。** 自分自身が走らなければ検出できないという循環があるが、**この循環はこの層では解けない**（外部のスケジューラが必要で、それが `E-15` の正本の問題と同じ根を持つ）。

### 3.3 部分的な沈黙

観測系 4 本のうち 1 本だけが走らなかった場合は検出できる（`docs/audits/<source>/` に当日のファイルが無い）。

| 状況 | 検出 | 対処 |
|---|---|---|
| 4 本のうち 1〜3 本が沈黙 | `docs/audits/<source>/` の当日分の有無 | 沈黙した `source` の `evidence` を使わない。**他の source での起票は続ける** |
| 4 本すべてが沈黙 | `docs/audits/ops/` に記録が無い | **`agent/ops-watcher` 自身も沈黙している可能性がある**（3.2 の循環） |
| `agent/proposal-writer` だけが沈黙 | 観測はあるのに `E-13` が 0 件 | 検査で止まったのか走らなかったのかを、`docs/audits/ops/` の記録で区別する |

## 4. `E-13` を経由しない変更の検出（暴走条件 #8）

### 4.1 検出の対象

DA-05 の 4.3 と AA-04 の 2.1 が定めた不変条件（**観測から作用に至る経路は `E-13` だけ**）を、実際に検査する手段を決める。

| 検査 | 方法 | 成立するか |
|---|---|---|
| **コードの変更** | `main` のコミットのうち、対応する `proposal_id` を持たないものを列挙する | **成立する**（Git の履歴が正本） |
| **Strapi のコンテンツ変更** | `I-01` の PostHog イベント（`article_updated` / `article_published`）のうち、対応する `E-13` が無いもの | **部分的**（4.2） |
| **Mautic の変更** | Mautic の監査ログ | 未確認 |
| **Chatwoot の変更** | Chatwoot の監査ログ | **Enterprise 機能のため使えない可能性**（DA-05 の未決定事項） |
| **n8n のワークフロー変更** | n8n のバージョン履歴 | 成立するが Git の外 |

### 4.2 Strapi の検出が部分的にしか成立しない理由

[04 の 2.4](04-server-to-server-flows.md) で見つけた 2 つの穴が、ここに効く。

- **穴 1**: 非公開化が `article_updated` として送られるため、`承認` 分類の操作を通常の更新と区別できない。
- **穴 2**: 公開済み記事の更新も `article_updated` になるため、同じく区別できない。

**したがって「`E-13` を持たない `article_updated` があった」ことまでは分かるが、「それが `承認` を要する操作だったか」が分からない。**

`I-01` にイベントを足す（[04 の 2.4](04-server-to-server-flows.md) の対処案 A）と、この検出が成立する。**これがその改修の優先度が高い理由にあたる。**

### 4.3 禁止遷移の検出

DD-01 の 8.4 で禁止した 3 つの遷移を、Git の差分から検出する。

| 禁止遷移 | 検出 |
|---|---|
| `draft` → `applied`（承認を飛ばす） | `applied_at` があるのに `approval.state` が `approved` を経ていない、または `approval.record_ref`（PR 番号）が空 |
| `applied` → `draft`（再利用） | `applied_at` を持つファイルへの変更が `git log` に現れる |
| `verified` → `applied`（再適用） | 同じ `proposal_id` の履歴に `applied_at` の設定が 2 回現れる |

**3 つとも `git log -p docs/proposals/` で検出できる。** `E-13` を Git に置いた決定（ADR-04）の利点がここで効く。**提案の状態変化そのものが差分として残る**ため、遷移の履歴を別に持つ必要が無い。

### 4.4 この検出が成立しない範囲を隠さない

AA-04 は暴走条件 #8 の歯止めを「不完全」としている。**この層でもその判断は変わらない。**

| 適用先 | `E-13` を経由しない変更を検出できるか |
|---|---|
| コード（Git） | **できる** |
| `E-13` そのもの（Git） | **できる**（4.3） |
| Strapi のコンテンツ | **部分的**（4.2。`I-01` の改修で成立する） |
| Chatwoot | **できない可能性**（Enterprise 機能） |
| Mautic | 未確認 |
| n8n のワークフロー | できる（バージョン履歴）が、**Git の外** |
| PostHog の設定 | **できない**（SaaS・外部リージョンで、こちらから状態を完全には把握できない） |

**Git の中にあるものは検出でき、外にあるものは検出できないか不確実である。** これは AA-04 の 3.3.1 が指摘した「記録が守られることと実体が守られることは別」という構造と、まったく同じ形で現れている。

## 5. 二重送信の検出（`I-08`）

### 5.1 検出

[03 の 3.3](03-operation-path-flows.md) の集計仕様で、`E-12` に 3 つの値を記録する。

```yaml
metric: CV-count
value: 42            # 畳んだ件数（CVR の分子）
raw_value: 45        # 生のフォーム送信件数
dedup_dropped: 3     # 畳んで消えた件数
```

| 状況 | 判定 |
|---|---|
| `dedup_dropped` = 0 | 正常 |
| `dedup_dropped` が `raw_value` の **1 割以下** | 許容範囲（同一人物の再送信は自然に起きる） |
| `dedup_dropped` が `raw_value` の **1 割超**（暫定） | **二重送信が常態化している徴候。** `E-12` に記録し、`agent/ops-watcher` が拾う |

### 5.2 1 割を超えたときに疑うもの

| 疑い | 確認方法 |
|---|---|
| ブラウザ側の二重送信防止（第 1 層）が効いていない | フォームの実装を確認する |
| 公開経路（本番は ALB の後ろの Mautic）が不安定で、利用者が何度も送信している | `tunnel_up` の履歴と突き合わせる（2 節） |
| ボットによる送信 | 送信元と時刻の分布を見る |

**3 つ目は `CVR` を直接汚染する。** `CV 数` が水増しされ、「CVR が改善した」という誤った観測が生まれる（暴走条件 #1 の変種）。

### 5.3 CVR を計算しない条件

**分母（Umami）と分子（Mautic）は異なる系から取る。** 片方だけが欠測すると CVR が跳ねる。

| 条件 | 挙動 |
|---|---|
| どちらかの `fetch.outcome` が `ok` / `empty_but_ok` 以外 | **`CVR` を計算しない**（`E-12` に `CVR` を書かない） |
| どちらかの `tunnel_up` が `false` | 同上 |
| 分母が 0（`empty_but_ok`） | **`CVR` を計算しない**（ゼロ除算。`CV 数` だけを記録する） |

**「計算できなかった」と「0 だった」を区別する。** これは DD-01 の 4.2 が `empty_but_ok` を分けた理由と同じ構造にあたる。

## 6. 縮退運転の規則

**何が落ちたら何を止め、何を続けるか。**

| 落ちたもの | 止めるもの | 続けるもの | 根拠 |
|---|---|---|---|
| **公開経路**（本番の ALB・ECS・RDS） | `I-05` `I-07` `I-08`。**CVR 系の `evidence` の使用** | **ループの作用は止めない。** Lighthouse は同一ホスト内で完結する | AA-04 の 5.2（最短経路は公開経路に依存しない） |
| **ngrok のトンネル**（本番では Webhook 用だけ） | `I-11` `I-12` とその先の `I-21`（顧客からの要求の通知） | 訪問者から見える機能と計測（ALB の後ろで動き続ける）。ループ全体 | 2.5 |
| **Strapi** | `I-09`（**ビルドを失敗させる**）／ `I-16` | 観測系 4 本のうち Lighthouse 以外 | [05 の 1.2](05-build-and-delivery-flows.md) |
| **Mautic** | `CV 数` の観測。`CVR` の計算 | 他の観測。**`SESSION-count` は測れる** | 5.3 |
| **Chatwoot** | `I-03`（会話の一次切り分け） | **ループ全体。** 通知は GitHub 側にあるため影響を受けない | [06 の 3.1](06-proposal-loop-flows.md) |
| **PostHog** | `I-01` `I-02`（**黙って捨てられる**）／ `I-06` の観測 | 他のすべて | [04 の 11 節](04-server-to-server-flows.md) |
| **n8n** | `I-11` `I-12` `I-13` | **エージェントの実行と `E-12` の生成は続く。** 起票までは走り、GitHub への搬送だけが止まる | [06 の 2.4](06-proposal-loop-flows.md) |
| **GitHub** | `I-13`。承認（`E-14`）も**提案の通知**も止まる | 観測と起票（ファイルを書くところまで） | AA-02 の I-13（翌日再試行）／[06 の 3.5](06-proposal-loop-flows.md) |
| **Amazon SNS** | `I-21`。**顧客からの要求の通知と監視通知が止まる** | 顧客対応そのもの（Mautic / Chatwoot には記録されている）。ループ全体 | [04 の 8 節](04-server-to-server-flows.md) |
| **OpenSEO** | `I-15` `I-22`（GSC の実績・順位・サイト監査・市場データの取得） | **Lighthouse による SEO の観測と、ループ全体**。GSC 側にデータは溜まり続けるため、復旧後に 16 か月以内なら取り直せる | [03 の 6 節](03-operation-path-flows.md) |
| **GSC の接続切れ**（OAuth の失効） | `I-15`。**`平均検索順位` の測定** | OpenSEO の他の機能（順位計測・市場データ）とループ全体 | [06 の 4 節](06-proposal-loop-flows.md) |
| **DataForSEO の残高枯渇** | `I-23`。**キーワード調査・競合調査・ランク追跡が同時に止まる** | GSC の取得（DataForSEO を使わない）とループ全体。**補充は人間（`R1`）が判断する**（エージェントに補充させない） | [04 の 9 節](04-server-to-server-flows.md) |
| **オンプレが全滅** | 制作（Strapi）・自動化（n8n）・エージェント（MCP）・調査（OpenSEO）。ループ全体 | **訪問者から見える機能と計測（AWS の Umami・Chatwoot・Mautic。ADR-12）は動き続ける**。`E-07` `E-09` `E-10` は AWS 側に溜まり続けるため、復旧後に取り直せる。**`comegin-ops-alert` の通知は届く**（SNS が AWS にあるため。ADR-08）。**オンプレの全滅そのものは、n8n のハートビートが 15 分途絶えたことを CloudWatch のアラームが検知し、SNS に直接発行して知らせる**（TA-05 の項目 16。`R1` の 2026-09-18 の決定）。検知から通知までの経路にオンプレの構成要素は入らない | ADR-08・ADR-12 |
| **`LH-seo` が 1.0 未満** | **ループの作用を全面停止。** SEO を戻す提案だけを起票する | 観測（`E-12` の生成は続ける） | AA-04 の 3.2 |

### 6.1 止める判断の原則

- **観測は極力止めない。** 観測が止まると、復旧したときに「いつから壊れていたか」が分からなくなる。
- **作用は疑わしければ止める。** 誤った観測に基づく作用は、元に戻す手間が観測の欠損より大きい。
- **通知の失敗でループを止めない。** 通知は正本ではなく、正本（GitHub の PR）から自動的に発生する副次物である（[06 の 3.5](06-proposal-loop-flows.md)）。
- **ビルドだけは 0 件で失敗させる。** 観測における `empty_but_ok` は成功だが、ビルドにおける 0 件は公開してはいけない成果物にあたる（[05 の 1.2](05-build-and-delivery-flows.md)）。

| 1 | 偶然の改善を効果と判定し続ける | `verification.state` に `no_change` を正直に記録し、`improved` と同じ重みで次の `evidence` に使う（[06 の 1.4](06-proposal-loop-flows.md)）／ 起票前チェック 6・7（件数上限） | **成立** |

**11 件中 8 件は検出手段が決まった。** 残る 3 件のうち #7 と #8 は AA-04 が既に「不完全」としたものであり、**この層でも解けなかった**。#11 は止める仕組み（前払い残高）はあるが、**止まる前に気づく仕組み**が決まっていない。

### 7.1 #7 が解けない理由

`E-15 AgentRun` の正本が未確定であるため、**エージェントの実行そのものを追う手段が無い**。

- DD-01 の 3.4 で `agent_run_id` に相関 ID を入れる暫定策を決めたが、**これは `E-13` の必須項目を埋めるためのものであって、実行履歴を残すものではない**。
- 相関 ID を書くのはエージェント自身であるため、**エージェントが偽の値を書けば辿れなくなる**。外部の記録が無い限り、この歯止めは成立しない。

### 7.2 #8 が部分的にしか解けない理由

4.4 のとおり、**適用先が Git の外にあるものを検出する手段が無いか、不確実である**。

- Chatwoot の監査ログは Enterprise 機能の可能性がある。
- **Webhook は代替にならない**（[04 の 5.2](04-server-to-server-flows.md)。止められる主体が変更を隠せる）。
- PostHog は外部リージョンにあり、こちらから状態を完全には把握できない。

### 7.3 #11 が部分的にしか解けない理由

**セルフホストの OpenSEO は支出を計量しない**（`whoami` の残高が `null`。AA-05 の ADR-10）。支出を知る手段は DataForSEO 側にしか無く、その取得手段が決まっていない（TA-05 の未決定事項）。

- **前払い残高は「使い過ぎ」を止めるが、「使い過ぎていること」は知らせない。** 残高が尽きた時点で調査もランク追跡も同時に止まり、そこで初めて気づくことになる。
- **ランク追跡のスケジュールは、エージェントが 1 度も呼ばなくても支出を生む**（TA-03 の 4 節「静かに続く」失敗）。エージェント側の stderr にも記録が残らない。

**この 3 件（#7・#8・#11）が残っていることを、ループを本格稼働させる前に解く**（AA-04 の 4 節）。

## 8. 未決定事項

- **`dedup_dropped` のしきい値 1 割に根拠が無い**（5.1）。実データが無い。
- **沈黙の検出の循環**（3.2）。`agent/ops-watcher` が「バッチが動かなかった」ことを検出するには、`agent/ops-watcher` 自身が動く必要がある。**外部のスケジューラか、実行そのものを記録する仕組みが要る**（`E-15` の正本の問題と同じ根）。判断者 `R1`。
- **Mautic の監査ログの有無が未確認**（4.1）。Chatwoot については DA-05 が Enterprise 機能の問題を挙げているが、Mautic については誰も確認していない。確認すれば #8 の成立範囲が広がる可能性がある。判断者 `R1`。
- **公開経路の疎通確認を `pnpm lh` の実行時にも行うとしたが、実装の置き場が無い**（2.2）。`lighthouserc.cjs` に前処理を足すか、`pnpm lh` を包むスクリプトを作るか。**`.claude/rules/build-deploy.md` によりビルドコマンドを勝手に変えられない**ため、`R1` の判断が要る。
- **`tunnel_up` の名前を変えるかどうか**（2.3）。ADR-12 の後、本番では「公開経路（ALB とその後ろ）に到達できたか」を表すため、名前（トンネル）と意味がずれた。`public_path_up` などに改めると、DA-01 の `E-12` の型と既存の記述を同時に直す必要がある。下の「必須項目にするか」と一緒に DA に提起する（判断者 `R3`）。
- **`tunnel_up` を `E-12` の必須項目にするかどうか。** 2.3 で「すべての `E-12` に書く」と決めたが、`E-12 AuditResult` の型定義は DA-01 にあり、**この層で必須項目を増やすのは型の変更にあたる**。DA に提起する（判断者 `R3`）。
- **縮退運転の判断を誰が行うか**（6 節）。表は「何を止めるか」を定めたが、**止める操作を誰が実行するか**が決まっていない。エージェントに止めさせると、止める基準ごと緩められる余地が生まれる（AA-04 の 3.2 が「検知するエージェントと止めるエージェントを同じにしない」と定めたのと同じ問題）。判断者 `R1`。
- **OpenSEO の停止を誰が検知するか**（6 節）。TA-05 の項目 9 で `/api/health` を監視すると決めたが、監視の主体（n8n か、ホストの cron か）が決まっていない。n8n から叩く場合、無認証の OpenSEO に到達するプロセスが 1 つ増える（ヘルスチェックの経路だけなら費用は発生しない）。判断者 `R1`。
